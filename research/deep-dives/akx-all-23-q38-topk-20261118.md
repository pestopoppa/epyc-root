# AKX-ALL-23: does Q38FN's QSA top-k bound CPU decode cost? (2026-11-18)

Scope: offline code reading at champion C14 `eee3da838` (`/mnt/raid0/llm/llama.cpp-experimental`, read with `git show`),
plus existing serving numbers. Nothing was compiled or run. Box: `handoffs/active/autokernel-akx-program.md` AKX-ALL-23.

Model facts: Q38FN (`qwen4exp`) has 48 layers. 12 of them are QSA attention layers (24 Q heads, 2 KV heads, head_dim 256,
f16 KV). The indexer has 4 heads, key length 128, `top_k=2048` and `compress_ratios=[0,0,0,4]x12`, so r = 4
(`cpu-decode-roofline-program.md` L4216). Serving uses MTP D=4, so one verify step has n_tps = 5 query rows.

## 1. How the QSA path runs on CPU

`build_qsa_top_k` (`src/models/qwen4exp.cpp` L675-814) and `build_attn_qsa` (L818-890) emit these ops per QSA layer and
verify step. n_kv is the context length; n_blocks = n_kv/4.

| Op | Shape at 32k | Scales with | Notes |
|---|---|---|---|
| `cpy_k` indexer key | 5 x 128 | O(1) | |
| `get_rows` block members | 32768 x 128 | **O(n_kv)** | all cached indexer keys are gathered again every step |
| 4x `cont` + `add`, `scale` (block mean) | 8192 x 128 | **O(n_kv)** | recomputed every step, although completed blocks never change |
| `rms_norm` + `rope_multi` on pooled keys | 8192 x 128 | **O(n_kv)** | recomputed every step |
| `mul_mat` score, `relu`, `permute`/`cont`, `sum_rows` | 8192 x 20 | O(n_kv) | small |
| `add` block bias | 8192 x 5 | O(n_kv/4) | |
| `get_rows` expand block to cell, `cont`, `add` mask | 32768 x 5 | **O(n_kv)** | |
| `top_k` (width 2051) | 5 rows x 32768 | **O(n_kv)** | `std::partial_sort` per row (`ggml-cpu/ops.cpp` L9259-9296). It parallelizes over rows only, so **5 of 96 threads work** |
| `fill(-inf)`, `set_rows(0)`, `add` (mask) | 32768 x 5 | O(n_kv) | |
| `FLASH_ATTN_EXT` | 120 rows | mask scan O(n_kv), **K/V reads O(top_k)** | see below |

**Attention after selection reads only the selected cells.** n_tps = 5 is below the tile Q size, so FA takes
`_one_chunk` (`ops.cpp` L10572-10594). Its per-cell loop skips aligned all-`-INF` 64-cell runs with a wide integer compare,
and any other `-INF` cell with one compare, **before** the K dot product and V accumulation (L9581-9594). The tiled path
skips all-`-INF` tiles in the same way (L10062-10088). The QSA mask is `-INF` everywhere except the 2051 selected cells, so
per row the walk is an O(n_kv) scan of the f16 mask plus an O(2051) K/V read. The box's premise ("dense FA over all n_kv
cells") is **refuted for the K/V traffic on CPU**: the sparsity is masked, but the masked cells are skipped, not computed.
The mask scan is cheap. 512 selected blocks spread over 8192 leave about 36% of 64-cell runs fully masked. The rest cost
one fp16 compare per cell, which is about 47 M compares per step at 32k, or about 0.3 ms over 96 threads.

What still grows with n_kv is the indexer side: block pooling, norm and rope recomputed every step, the cell expansion,
the mask construction, and the top-k sort.

## 2. Share of decode at 32k / 64k / 128k

**No op-level CPU profile of Q38FN at depth exists.** The only AK census (0.99% FA) ran at about 300 tokens
(`/mnt/raid0/llm/tmp/ak-longctx-audit-20261004/REPORT.md`). No q38fn/longctx/headroom profile row under `/mnt/raid0/llm/tmp`
has a per-op breakdown. The figures below are a bytes/ops model, not measurements.

Step time from `:8074` serving: 41.1 tok/s under 8k and 16.7-18.4 tok/s at 32k-131k, at about 2.5 tokens per step, gives
about 60 ms/step under 8k and about 140 ms/step at 32k.

| Component per verify step (12 layers) | 32k | 64k | 128k |
|---|---|---|---|
| FA K/V reads (120 rows x 2051 cells x 1 KiB) | ~2.9 GiB, ~7-10 ms, **flat** | same | same |
| FA mask scan | ~0.3 ms | ~0.6 | ~1.2 |
| top-k partial_sort (5 active threads, ~0.3 ms/row at 32k) | ~3.6 ms | ~7 | ~14 |
| block pooling + norm + rope recompute (~70 MB/layer traffic at 32k) | ~4 ms | ~8 | ~16 |
| expand + mask fill/set_rows/add | ~1.5 ms | ~3 | ~6 |
| **O(n_kv) indexer residue total** | **~9 ms (~6-7%)** | ~18 ms | ~37 ms |

Estimated shares of decode: attention K/V about 6% (flat), top-k about 2.5%, the whole O(n_kv) residue about 6-7% at 32k.
The residue rises to roughly 10-20% at 128k, where the step is about 150 ms or more.

**Consequence for AKX-ALL-24.** The observed context term is about 80 ms/step between 8k and 32k. The O(n_kv) residue
(~9 ms) does not explain it, and neither does QSA attention, whose K/V read is bounded. The AKX-ALL-24 deep dive's bytes
model (`akx-all-24-cpu-fa-parallelism-20261118.md` §1-2: "120 rows x 32 MiB x 12 layers = 45 GiB") assumes every row walks
all n_kv cells. For Q38FN's QSA layers that **overstates K/V traffic about 16x at 32k** (2051 of 32768 cells are read), so
its "FA traffic is the plausible owner of the context term" does not hold for Q38FN. Split-KV can still help, but only with
the ~7-10 ms bounded FA cost and the 2-walk critical path. Its gain estimate for Q38FN (15-45%) should be treated as
unsupported until the c15 speed row reports. Where the remaining context term comes from is open. Candidates are MTP
acceptance falling with depth or task mix (the 8k and 32k request populations differ), prefill folded into the serving
rates, and the indexer residue being underestimated here. An op profile at depth settles it.

## 3. Levers and decision

| Lever | Est. gain at 32k | Exact? | Cost |
|---|---|---|---|
| Parallel top-k (split each row across ~19 threads, local heaps, merge) | ~2-2.5% (saves ~3 of 3.6 ms) | set-identical except boundary ties (blocks of 4 share a score, so ties at the cut are inherent; current tie order is `partial_sort`-defined) | small, CPU op only |
| Block-level top-k (select on 8192 block scores, then expand) | ~2.5% plus removes the expand | **not exact**: width 2051 = 512 blocks + 3 cells, so the cell-level sort takes 3 arbitrary cells of the 513th block | graph change |
| Cached pooled/normed/roped indexer block keys (compute once when a block completes) | ~3% (saves ~4 ms), growing to ~10% at 128k | bitwise if the same ops run per block | memory-cache change in `llama-memory-hybrid-idx` plus graph; multi-file |
| Gather top-k K/V before FA (the box's lever) | ~0 | - | **not needed**: CPU FA already skips masked cells |

**Decision: NO implementation, no row.** No single lever clears the 3% bar at 32k with confidence. The best,
cached block keys, is at about 3% on an unmeasured model and needs a cache-layer change. The box's structural gather lever
is unnecessary on CPU. The O(n_kv) residue grows to a meaningful share at 64k-128k. If a depth profile shows the indexer
block (`indexer_k_pooled`/`indexer_top_k` nodes) at 5% or more of a 32k step, the cached-block-key lever, with parallel
top-k as a cheap companion, becomes the candidate. Done-when for the box (an at-depth profile) is unchanged. The
measurement that settles both this box and the AKX-ALL-24 attribution is one per-op CPU profile of a Q38FN verify step at
32k and 64k.
