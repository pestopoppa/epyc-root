## 1. Stage-1 fields

- **Title**: Contexture: Runtime Context Eviction for High-Throughput Agent Serving
- **Authors**: Colin Hong, Bryan Shan, Wei Siong Pang, Chengzhi Lu, Xu Guo (NTU Singapore); Nitin Shivaraman, Tao Luo (A*STAR IAIC); Esha Choukse (Microsoft); Kisson Lin (SuperMem Pte. Ltd.); Dmitrii Ustiugov (NTU).
- **Version/date**: arXiv:2611.26980v1 [cs.DC], 20 Nov 2026. Not peer reviewed (preprint). No code link in page.txt (NOT-FOUND-IN-SOURCE); the paper says the prototype is ~7K lines of Python in vLLM 0.26 plus a <100-line engine-core probe.
- **Categories**: context_management, kv_cache, agent_architecture, inference_serving.
- **Novelty**: medium. The ingredients exist (observation masking, file-aware dedup in Cline/SWE-agent, Continuum KV TTL). New is the coupling: supersession picks WHAT, a residency probe + pool pressure decide WHEN, with an explicit "cold commit" (free when the cache past the cut is already gone) and a bounded re-prefill cap.
- **Relevance**: medium-high. Our orchestrator already has masking-style compaction (default-off) and an open compaction A/B (TOC-CMP-4) that has no supersession arm; our llama-server serves hybrid GDN models where a mid-history cut forces recompute from the last checkpoint (exactly the failure mode the paper measures on vLLM).
- **credibility_score**: 2. Arithmetic: preprint (peer-reviewed +0); <=12 months +1; known contributor (Microsoft Research author) +1; commercial bias 0 (one startup affiliation, no product claim); independent corroboration 0 (no replication; baselines are the authors' own ports/runs). Authors state they used Claude for experiment code and plotting.
- **Verdict**: adopt_patterns. Cite for the supersession rule, the cost = "cached tokens after the earliest cut" accounting, and the cold-commit idea. Do not cite for our throughput expectations (see sections 3-5).

## 2. Key claims

0. **Supersession rule (operator asked for the exact rule)**: CONFIRMED, with detail. The tracker records each tool call's type, target and outcome from the structured request (tool name + arguments identify the operation; file tools name paths; shell command lines are parsed with `shlex` to find programs and the files they read or write). A later read or edit of a file supersedes earlier observations of it; re-running a normalized shell command supersedes its prior output; a later run/build supersedes earlier run/build outputs whose target files overlap; a failed output is not superseded by unrelated operations; a test result is superseded only when a rerun of the same test passes. Once ALL tool outputs of an assistant round are superseded, that round's tool calls and reasoning also become candidates. Unmapped tools: superseded only by a repeat of the same call. System prompt and task description are always kept. Candidates mature after a 2-round grace window. Detection is therefore name+args identity plus file-path overlap, not content similarity. Prototype covers sandbox and file tools only; MCP/external services are out of scope (section 5.6).
   - Anchor: "A later read or edit of a file supersedes earlier observations of it." and "a test result is superseded only when a rerun of the same test passes." (section 5.2).
1. **64% definition**: CONFIRMED as stated but NARROWED in meaning. 64.3% is the share of tokens in the *recorded final histories* (Fig 6a) that supersession rules mark as removal *candidates*, including tool results plus associated reasoning and tool-call history; the rules classify 84% (Hermes) and 83% (OpenClaw) of tool-output tokens. It is an upper bound before the grace window, the pressure gate and the cap. What is actually removed at High load is much smaller: cold commits remove 21% of prompt tokens, and adding the pressure gate raises that to 25% (section 6.3.2). The "estimated 30% of the KV pool" figure (Fig 6b) is for in-flight requests when occupancy >=95%.
   - Anchors: "supersession rules mark 64.3 percent of final-context tokens"; "it increases the share of prompt tokens removed from 21% to 25%".
2. **Eviction/KV interaction and cost model**: CONFIRMED. Removing a span invalidates every cached block after the cut (each prefix block depends on all preceding tokens), so the re-prefill is the suffix after the earliest removal point. Batch gain = prompt tokens removed; batch cost = cached tokens after the earliest removal point (zero if the cached prefix ends at/before the cut). Commit rules: cost 0 (cold commit) commits at any pressure; otherwise commit only when pool pressure (fraction of KV blocks held by running requests) exceeds 80% AND cost <= 6 x gain. A read-only residency probe hashes the session prompt block-by-block against the GPU prefix cache. Hybrid (linear-attention) models resume from the last saved recurrent state before the cut, so their real re-prefill exceeds the suffix: removing 2K tokens from the middle of a 64K cached context caused ~41K tokens (not 1.5K) of re-prefill, taking 3.4 s and dropping 32-session aggregate decode from ~1360 to ~53 tok/s on one H100 (Fig 7a). The harness keeps full history; only the model's prompt is filtered; prompt filtering removes tool-output content but keeps template markers.
   - Anchors: "it commits only when pool pressure exceeds the threshold and the cost is at most the gain times a configurable re-prefill cap"; "removing 2K tokens from the middle of a 64K cached context causes the next round to re-prefill approximately 41K tokens instead of 1.5K"; "The re-prefill exceeds the 32K-token suffix because the hybrid model resumes from the last saved recurrent state before the cut."
3. **Headline throughput (20-73% vs best of four; 7-63% vs masking in 5 of 8)**: CONFIRMED as source-stated, with caveats on what the numbers mean. "Throughput under SLO" = sessions completed per minute at the point where p90 slowdown vs the unloaded no-eviction run reaches 10x. Eight configs = {Qwen3.8-27B dense on H200, Qwen3.6-35B-A3B MoE on H100} x {Hermes, OpenClaw} x {Terminal-Bench 2.1, SWE-Atlas-QnA}; FP8 weights, vLLM 0.26, KV pools of 6-7 full 262K contexts, TRACE REPLAY (fixed trajectories; live runs for accuracy). Baselines: no eviction, default/tuned compaction, AgentDiet, Continuum (authors' published code), observation masking (implemented in vLLM's request path). In the three configs where masking wins (all Qwen MoE) it is 6-25% faster but loses 9-28 accuracy points. The Fig 10 caption lists peak throughputs, not SLO throughputs; e.g. MoE/OpenClaw/TB2.1 peaks are 1.21 vs 1.12 (+8%), so the 20% floor cannot be reproduced from caption numbers alone and rests on SLO crossings read off curves (not tabulated). Live fully-live check (one config): replay overstates throughput by 9-13% for Contexture and 2-5% for no eviction; Contexture keeps a 13% SLO advantage.
   - Anchors: "Contexture improves throughput under SLO by 20–73% over the best of no eviction, harness compaction, AgentDiet, and Continuum"; "observation masking achieves 6–25% higher throughput at the cost of 9–28 percentage points lower task accuracy"; "The experiments use a dense model, Qwen3.8-27B ( Qwen Team, 2026c ) , on an H200 GPU and an MoE model, Qwen3.6-35B-A3B ( Qwen Team, 2026b ) , on an H100 GPU."
4. **"+23% vs LMCache on H100"**: PARTIAL. Source: LMCache v0.5.7 with a 100 GB host tier added to both arms on an H100 (Qwen3.6-35B-A3B, Hermes, TB2.1): no-eviction+LMCache 1.89 vs Contexture+LMCache 2.33 sessions/min = +23% (22% on H200 with the dense model). But the same paragraph reports that LMCache offload alone raises no-eviction throughput by 29% and Contexture WITHOUT offload reaches only 2% more than that: on the H100 the two mechanisms are nearly equivalent individually and compose. Contexture's gain also shrinks with more HBM (+32% on H100 with a 1.75M-token pool, +14% on H200 with 4.44M).
   - Anchors: "Offloading raises no eviction’s throughput under SLO by 29%(Fig. 15 (b)); Contexture alone reaches 2% more."; "With offloading, Contexture still gains 23%".
5. **"Up to 11% less GPU energy per session"**: PARTIAL. 11% is the largest of six cells (2/8/11% Qwen dense, 10/10/8% MoE) and is vs the lowest-energy baseline at that load; measured only for Hermes on TB2.1 at three loads, via NVML on H200/H100. Mean GPU power differs by <=2% (dense) across policies, so energy tracks throughput and adds no independent information. Contexture performs the least prefill per completed session despite re-prefill (half of no-eviction's at High with the dense model, one quarter with MoE).
   - Anchor: "Contexture reduces energy per completed session by 2%, 8%, and 11% with Qwen".

Not-in-source (operator steering items): NOT-FOUND-IN-SOURCE for any NPS4/NUMA, CPU, MI210 or non-NVIDIA result; the paper never discusses host-memory placement of KV (its host-side state is the per-session tracker, "well under 1%" of GPU KV bytes per token).

## 3. Reported results (as stated)

- Hardware/software: H200 (dense Qwen3.8-27B) and H100 (Qwen3.6-35B-A3B MoE), FP8, vLLM 0.26, 2 h warm-up, Poisson arrivals, trace replay.
- Throughput at 10x p90 slowdown: +20-73% over best baseline among {no eviction, compaction, AgentDiet, Continuum} in each of 8 configs; +7-63% over masking in 5 configs; masking +6-25% in the other 3 (MoE) at -9 to -28 accuracy points. Continuum is within 6% of no eviction everywhere; AgentDiet is 21-28% below no eviction on three dense workloads.
- Peak throughput examples (sessions/min, Fig 10 caption): dense/Hermes/TB2.1 AgentDiet 0.46, tuned compaction 0.56, no eviction 0.59, Contexture 0.73; MoE/Hermes/SWE-Atlas no eviction 1.61, Contexture 2.41.
- p90 slowdown at the best non-masking baseline's SLO throughput: 30-78% lower.
- Ablation (dense, Hermes, TB2.1): selection alone +20% SLO throughput, energy -18%; cold commits cut prefill/completed session by a further 37% and p90 TTFT to 2.1 s; pressure gate adds +4%; total +24% over no eviction (0.59 -> 0.73). Prefill per completed session 594K -> 288K tokens; p90 TPOT 118 -> 62 ms.
- Parameter sensitivity: grace window 2 rounds best (88% accuracy vs 86% no eviction; 0 rounds -2 to -4 points; 3-5 rounds -6 to -7); threshold 80% beats 70/90 by 5-6%; cap 6 beats cap 0 by 10% (cap 0 loses 5 accuracy points).
- Accuracy (live probes): Contexture mean +1.4 points vs unloaded no eviction, worst -3.7.
- Overhead: median +30 ms before engine execution (0.2% of request time).

## 5. In-house state

- **llama-server checkpoint machinery (C19 a6a32c1)**: `n_ctx_checkpoints = 32` per slot (common/common.h:668), `checkpoint_min_step = 1024` (:669, comment PFXC-A1 "8192 -> 1024 for agentic tool loops"), `checkpoint_after_gen = true` (:670). Checkpoints are created only for models that cannot do partial sequence removal, or that use SWA (server-context.cpp:5266-5275 region). On a new request the server finds the latest checkpoint whose `pos_max <= pos_next` and `pos_min < pos_min_thold` (server-context.cpp:5126-5140), restores it and sets `n_past` there (:5163); if none qualifies it forces full re-processing (:5167). `n_cache_reuse` chunk shifting is gated on `llama_memory_can_shift` (:5000-5010) and is false for recurrent/hybrid memory. Champion eee3da8 not separately checked for these lines (C19 is a descendant).
- **What a mid-history eviction costs here (derived from the code above)**: with cut position c, shortened prompt length T', and nearest usable checkpoint position p* <= c: tokens re-prefilled = T' - p*. For attention-only models without checkpoints (not our served hybrids) the server's common-prefix logic gives p* = c (plus optional approximate `--cache-reuse` shifting of later chunks, which Contexture explicitly avoids because it is not exact). For GDN hybrids the extra (c - p*) is bounded by checkpoint spacing (>=1024 tokens apart, plus one at the end of each generation), and if no checkpoint survives at or before c (32-per-slot cap, LRU) the cost is a full T'. Example at the paper's own size (41K re-prefill): ~48 s on MI210 (41,000 / ~850 tok/s, derived) and ~84 s to ~15 min on CPU (41,000 / 490 down to / 45 tok/s, derived; the rate depends on depth, so it is a range, not a point).
- **When supersession pays on our stack (derived)**: gain accrues to future rounds only through (a) attention-read/KV memory savings, or (b) avoided recompute when a cache would be lost anyway. With a warm prefix, evicting G tokens costs C = T' - p* once and saves G tokens of future prefill only if the cache is later lost. So it pays (i) as a *cold commit* (checkpoint/slot already gone or the request is a cold start: zero marginal cost), (ii) at forced context-overflow (orchestrator already compacts on `ContextOverflowError`, `src/graph/compaction.py:179-215` @ 1a10541b7), and (iii) under real pool pressure (plausible on MI210 with slots+27B; implausible on 1.1 TB CPU). A pressure-gated mid-history cut with the paper's cap of 6 is not justified on CPU at 45-490 tok/s without a device-specific cap.
- **Orchestrator code (read-only, `git -C /mnt/raid0/llm/epyc-orchestrator rev-parse HEAD` = 1a10541b7466f2d5aef240ac547ff6dce2cd43cd)**:

No supersession logic: it clears by age, not by "a later call replaced this". A per-turn sliding window of this kind is exactly what the paper says "moves its window and breaks the cached prefix" (up to 1.24x p90 slowdown at light load) when the cleared block sits inside a cached prefix; whether it does in our REPL prompt depends on where `## Last Output` sits in the assembled prompt, which I did not trace.
  - `src/context_compression.py:253-370` `ContextCompressor.compress`: protects first 3 / last N messages and stubs old `tool` messages by type once >=8 tool calls exist (`TOOL_OUTPUT_AGE_THRESHOLD = 8`, `:54`; summarisation `:346-358`); again age-based.
  - `src/graph/compaction.py:179` `_maybe_compact_context` dispatches to `src/graph/context_arm_ab.py` when `context_arm_ab` is on; its `ARMS = {summary_only, summary_pointer, pointer_only, prune_pointer, full_history}` (context_arm_ab.py:16) and it requires `tool_result_clearing` OFF (:34-36). No supersession arm exists.
  - `src/backends/prompt_layout.py:47` already logs per-block `tool_output` kind, start offset and length (RTE-LOG-1), which is the data a supersession-candidate-share replay needs.

## 8. Contradiction / adversarial pass

- Authors' own limitations/caveats in text: replay excludes behavioural changes induced by eviction (live runs read 9-13% lower for Contexture); prototype rules cover only sandbox and file tools; hybrid-model re-prefill cost in the commit rule is a *lower bound*; masking beats Contexture in three MoE configs (at a heavy accuracy cost).
- Reading of the numbers: all baselines ran on the authors' ports (AgentDiet ported from Trae Agent; masking implemented in vLLM's request path); no independent replication. Throughput gains shrink with more HBM (+14% H200) and nearly vanish against LMCache alone on H100 (+2% for Contexture alone vs LMCache alone). No energy metric was recorded for configs other than Hermes/TB2.1.
- Scope fit: all evidence is shared-GPU, many-session, H100/H200 FP8 serving where KV capacity is THE bottleneck. Our served paths are few-slot, speculative-decoding, MI210/CPU; the capacity-driven part of the gain (fewer preemptions, 70% p90 TTFT drop) has no direct analogue until KV occupancy is shown to bind. The cold-commit logic and the supersession rule transfer; the throughput magnitudes do not.
- Restatements: none found (no blog relays checked).
