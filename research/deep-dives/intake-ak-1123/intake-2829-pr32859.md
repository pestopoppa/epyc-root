1. **Mechanism (what heap allocation is removed)**: CONFIRMED against the diff. Before: every `add_new_bigram` built two `std::string` temporaries from `symbols[].text/.n` for the rank lookup AND a third `left+right` string stored in `llm_bigram_bpe::text`; the stale-bigram check in the merge loop rebuilt two more strings and a concatenation to compare with `bigram.text`. After: the `text` field is removed; staleness is `left.n + right.n != bigram.size` (the SPM check); `find_bpe_rank` takes `std::string_view` and the map key becomes `pair<string_view,string_view>` pointing into a `std::deque<std::string> bpe_rank_strs` filled at load time (deque keeps references stable on end-insert). So per-rank-lookup allocations go to zero. Not removed by the diff: the two `GGML_ASSERT(... .find(' ') == npos)` scans in every `find_bpe_rank`, the unchanged weak pair hash (`hash(a) ^ (hash(b) << 1)`), and, outside the diff, the per-final-symbol `std::string str` plus `vocab.text_to_token(str)` in our tree (llama-vocab.cpp:698-699 @ a6a32c1) which allocates once per output token. That is consistent with the smaller win on deepseek-llm (-17%), where other costs dominate (cause not stated in source).
   - Anchors (diff): "bigram.size = symbols[left].n + symbols[right].n;"; "std::deque<std::string> bpe_rank_strs; // stable backing storage for bpe_ranks keys"; "GGML_ASSERT(token_left.find(' ') == std::string_view::npos);".
2. **"Token ids identical" and how it was tested**: PARTIAL. The author asserts identical id sequences on all five vocabs before/after; the method (which inputs, how compared) is not described.    - Anchors: "Token id sequences are identical before and after on all vocabs."; "tests/test-tokenizer-0 covers llama-bpe, gemma and command-r style vocabs and runs in CI".
3. **Correctness risk of the length-based stale check**: CONFIRMED sound by independent argument, not by tests. A queued bigram (L,R) can only be stale if L absorbed R (R.n becomes 0: skipped by the `n == 0` test), or R absorbed its right neighbour (R.n grows, so L.n+R.n > size: skipped), because symbol `text` pointers are fixed and `n` only grows or becomes 0; equality therefore implies neither symbol changed. This is the same invariant the SPM tokenizer has used (diff context), and the bot reviewer reached the same conclusion. Residual risks flagged by the bot (nits): `impl` becomes unsafe to copy because the map keys are views into the deque (suggest deleting the copy constructor); index arithmetic `size()-2` can use `emplace_back`'s returned reference. Load-time behaviour for malformed merges (no space -> key ("","")) and duplicate merges (first rank wins) is claimed unchanged.
   - Anchor (diff): "left_symbol.n + right_symbol.n != bigram.size".
4. **Present in C19 `a6a32c1`?**: NOT PRESENT. a6a32c1 still has `std::string text;` in `llm_bigram_bpe` (src/llama-vocab.cpp:274), the full-string stale check (:657), `add_new_bigram` allocating strings (:726-747), `bpe_ranks` keyed by `pair<std::string,std::string>` (:1833), two merge-load sites (:2002 and :2093, the first inside a branch that skips Kimi-K2 merges at :1985), and `find_bpe_rank(const std::string&, const std::string&)` (:4018; llama-vocab.h:157). ## 4. Performance-principles table

| Principle | MI210 (gfx90a) | Zen 5 EPYC (NPS4) |
|---|---|---|
| Remove per-lookup heap allocation (string_view keys, stable deque backing store) | NO. Tokenization is host-side; the MI210 never runs it. | YES. Pure host code on the serving thread; applies to every BPE model we serve. |
| Replace content comparison of a concatenation by a length-sum staleness test | NO (host). | YES. O(1) vs O(len) copy and compare per popped bigram. |
| Hash/map layout (node-based unordered_map, string_view into separate heap strings) | NO. | PARTIAL. Lookup still chases a view into a deque element; strings <=15 B sit inline in the deque element (SSO, uncited); cache behaviour and NPS4 remote-node latency of the vocab map (first-touched by the loading thread) are unmeasured. The weak `hash(a) ^ (hash(b) << 1)` is untouched and is a candidate follow-up. |
| Remaining allocations (per-final-symbol `std::string` + `text_to_token`, double `find(' ')` assert scans) | NO. | YES, port cost is small; not covered by this PR; would extend the same idea. |
| Threading | n/a | Single-threaded per request; no SIMD or parallel structure to exploit; AVX-512 irrelevant to the merge loop. |

- Upstream change absent from C19 (section 2, claim 4). Served path: llama-server tokenizes every incoming prompt through `llm_tokenizer_bpe_session` for BPE vocabs (the whole prompt each request, independent of prefix-cache hits), so a served model with a BPE vocab does reach this code.

Gemma-class is retired from production (kv-cache-program.md:119). The PR benchmarked qwen2, gemma-4, command-r, llama-bpe, deepseek-llm, NOT qwen35; the merge loop is shared, so a similar effect is expected but unmeasured.
- **Tokenization vs prefill (derived only from sourced numbers)**: qwen2 master 35.4 ms per 145.8 KB = ~0.243 us/byte; PR 18.2 ms = ~0.125 us/byte (saves ~17 ms per 145.8 KB). Prefill rates in the lane: MI210 Qwen3.8-27B Q8_0 788-919 tok/s at pp512-pp8192 (kv-cache-program.md:540 @ d785b6d); CPU 35B 490 tok/s at 3k falling to ~45 tok/s at 97k (long-context-program.md:288 @ d785b6d). Bytes per token is not sourced; take 4 B/token as an uncited assumption (and 1 B/token as an absurd upper bound on token count). A 100k-token prompt is then ~400 KB: tokenization ~97 ms on master, ~50 ms after (linear extrapolation, uncited), versus a COLD prefill of ~118 s on MI210 (100,000/850) or ~37 min on CPU at ~45 tok/s; the tokenizer is ~0.08% of the former and ~0.004% of the latter. For a prefix-cached agentic turn that prefills ~2k new tokens (~2.4 s on MI210, ~4 s on CPU at 490 tok/s) the full-prompt re-tokenization (~97 ms) is ~2-4% of the turn and the PR would save about half of it (~47 ms, ~1-2% of the turn). Even at 1 B/token the cold-prefill share stays below 1%. So this is a small hygiene win for long prompts, not a TTFT lever.
