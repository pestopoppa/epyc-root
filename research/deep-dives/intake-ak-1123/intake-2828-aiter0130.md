## 2. Key claims

1. **"Wheels GPU_ARCHS=gfx942;gfx950 (ROCm 7.2/7.14/10.0/10.1); does not run on gfx90a"** — PARTIAL. CONFIRMED for the prebuilt wheels: the release text says "Prebuilt manylinux_2_28 wheels, GPU_ARCHS=gfx942;gfx950" (anchor 0), with ROCm 7.2, 7.14, 10.0 and 10.1 rows for cp310 and cp312 (page.txt). NARROWED: the notes say nothing about source builds or JIT targets, and zero of the 339 PR titles mention gfx90a, gfx908 or MI210; "does not run" is therefore an inference from the wheel arch list, not a statement in the source. Our own port path already runs AITER-derived gfx942 assembly on the MI210 after retargeting (program.md:775 and the `AK-ASM-H11` topksoftmax route, topk-moe-asm-gfx90a.cu:1-30 @ a6a32c1). All wheels need ROCm >= 7.2; the MI210 stack is ROCm 6.2 (task brief).
2. **"Changes mostly gfx950/gfx1250 (FlyDSL MoE, Conv3d)"** — CONFIRMED at title level. Of 339 PR lines in the body, 62 name gfx1250, 53 name gfx950, 15 name gfx942, 0 name gfx90a/gfx908/MI210; 78 name FlyDSL and 63 Triton/Gluon; Conv3d appears once ("[HIP] [FlyDSL] Conv3d gfx1250 Optimization", anchor 1). Counts are over titles only (bodies not read except the ones below).
3. **"RFC #7240 kernel provider interface: configuration, priority, provenance, observability"** — CONFIRMED with extra reading. The release lists it as PR #7465 (anchor 2). Fields (from RFC #7240 body rev 0.3 and PR #7465 body; extra reading):
   - configuration: `aiter.plugin.configure(*, source, enable=())`, the only way to enable a provider; `source` is mandatory and recorded in every decision. The environment has one control, `AITER_PLUGINS=0`, which denies everything and outranks `configure()`; installing a provider enables nothing. Later (#8081): `configure(exclude=("provider:op",))`, malformed entries raise.
   - priority: the order of the enable list is the preference order, first-accept-wins; there is no provider-declared priority (the PR calls that "quality arbitration by the back door"). Selection by reported measurement was later added (claim 5).
   - provenance: provider name, kernel/candidate id, artifact digest (`sha256:`), op-contract version, provider-reported qualification (opaque), plus `config_source` naming which configuration layer produced the route; immutable and known before execution.
   - observability: one frozen Decision record read four ways: `last_decision()`, `status()`, `explain(op, *args)` (dry run, executes nothing), `decision_counts()` / `on_decision(cb)`, plus a route-change log; the RFC requires that observing which implementation served a call must not need a GPU profiler. Counts are decisions, not launches (graph replay runs no Python).
   - failure boundary: native fallback only before the candidate's `run()` begins; after that an exception propagates, labelled with provider, kernel id, digest and config_source (#8081).
   - contract check: a candidate whose kernel cannot take the op contract's call is refused with `reason="contract-mismatch"` (the pilot caught a 7-argument call about to be handed to a 6-argument kernel).
   - hot path: measured 2.42 us per provider-served call on a Xeon Platinum 8480C (design target 1 us not met; stated openly).
4. **"Tuner rejects zero timing measurements"** — CONFIRMED (anchor 3; rule read from the merged PR #6941 diff, extra reading). The exact rule: (a) in `mp_tuner.worker`, if the measured `us == 0` after the retry loop (the test asserts 4 `run_perftest` calls) the measurement is set to `us = -1` with `max_err_ratio = 1.0` and returned as failed; (b) in `base_tuner.post_process`, candidates are kept only if `max_err_ratio <= tol` AND `math.isfinite(us)` AND `us > 0`, and the filter runs BEFORE sorting because a NaN makes every comparison false and leaves the list out of order; (c) if every candidate fails, a fallback row with `INVALID_TIME` and error ratio 1.0 is emitted; (d) in `result_to_csv`, rows with non-finite or non-positive `us` go to `self.failed` and are never written, so a zero measurement cannot overwrite an existing tuned config (regression test: existing 12.5 us row survives a 0.0 us candidate); (e) `calculate` (tflops/bw) returns (0, 0) for `time <= 0` or non-finite. Merged 2026-11-09T14:17:01Z.
5. **"Measurement does not influence provider routing" (RFC text) -> reversed within the release window** — CONFIRMED with extra reading, and NOT in the operator steering. #7654 (merged 2026-11-11) adds one optional `latency_us` on `KernelCandidate`, recorded and handed back unchanged, refused at construction if 0, negative, inf or nan, and explicitly "No influence on routing". #8081 (merged 2026-11-17, listed in this release, anchor 5) lets a complete report select among already-enabled providers: `baseline_us`, `baseline_path`, `measured_under`, `measurement_ref` must ALL accompany `latency_us` or none; a candidate that loses to its own baseline drops out; an incomplete report is not an error and not slower, it just does not compete; eligibility stays with people (`configure(enable=...)`), selection may follow measurement.
6. **"MoE sorting changes only if not MX/FP8-dependent"** — PARTIAL. Of the three sorting PRs in the notes: #7640 `moe_sorting` pad ids (extra reading) is NOT MX/FP8-dependent: the opus sorter wrote pad ids as `(topk << 24) | num_local_tokens`, so pad slots read as live routes, serialising atomics (fused_moe 112 -> 341 us at M=64 with 62 live rows on MI355X); the fix writes the tensor height. #7540 is gfx1250-specific and #7653 is MXFP4-scale-specific (titles only; bodies not read). #7640's lesson that bears on us: a relative-tolerance compare on packed ids near 2^27 hid a 94% difference.

## 5. In-house state

- **Provider/lineage registry**: there is no runtime provider registry, by design (one champion). The nearest in-house parts: immutable candidate identity (loop/candidate_manifest.py:1-6, schemas at :20-27), prospective content-addressed source capture (loop/lineage_capture.py:1-14, default-off, "not imported by the live loop"), prospective lineage belief receipts (loop/lineage_beliefs.py:1-6), a kernel-feature presence gate (loop/kernel_coverage.py:1-14), the kernel store with `VERSION.txt`, `SHA256SUMS`, `PROVENANCE.md` (program.md:1085) and sha256-pinned `.co` dependencies (program.md:754-759). `provider_breaker.py` is about the LLM actor provider, not kernels; no `priority` notion exists for kernels.
- **Kill switch + reject-reason logging**: the in-tree fast path has the same shape as AITER's `AITER_PLUGINS=0` and decision log: `GGML_HIP_TOPK_ASM=0` (topk-moe-asm-gfx90a.cu:18, :91 @ a6a32c1), `GGML_HIP_TOPK_ASM_LOG=1` (:19, :96), per-reject-reason log lines (:146-162) and the sha256 symbols of the code objects (:39, :65). There is no uniform registry across knobs.
- **Zero/implausible-timing gate**: the ranked throughput sample path rejects non-finite and non-positive samples: `parse_llama_bench_json` raises on NaN/inf and on `value <= 0.0` ("a zero-throughput repetition means the run did not measure"), execution/microbench.py:1887-1897; the hardened-receipt check rejects non-positive unsynchronized durations (microbench.py:2075); `compare()` refuses an anchor median <= 0 (loop/bench.py:518-519). So the zero rule is already present and stricter than AITER's (AITER retries then marks failed; we raise). Three residual gaps found by reading: (a) `run_once` returns `float(row.avg_ts)` (loop/bench.py:424) while `avg_ts` is validated finite only, not positive (microbench.py:1735-1747, :1915), and its docstring says reductions never use `avg_ts` (microbench.py:1625-1628); (b) trend/drift/spread helpers silently drop `value <= 0` samples instead of failing (loop/bench.py:642, :664, :683, :694); (c) `graph_profile_reader.py:45` accepts `value >= 0`. None is shown to be reachable with a zero today.
- **Intake already recorded**: intake-2696 (v0.1.29) holds the wheel-arch claim (`GPU_ARCHS=gfx942;gfx950`) and fused_reduce_add_rmsnorm / MegaMoE / window-aware split-KV (research/intake_index.yaml:390686-390800 @ d785b6d). This dive does not duplicate those; the arch-list restatement here is a restatement, not corroboration.
