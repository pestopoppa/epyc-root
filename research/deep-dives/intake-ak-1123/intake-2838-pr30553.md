## 2. Key claims

0. **The change: grid = min(nsm, nwork), nwork = ntiles * ceil(K / K_vram). CONFIRMED.** The NVIDIA >= 90% tile-efficiency shortcut (grid = ntiles) is preserved; every other case, including all AMD, gets `std::min(nsm, nwork)` instead of `nsm`. The final form is the maintainer's suggested formula, rounding partial K iterations up.
   - Anchors (diff): `const int nwork = ntiles_dst * ((args.ncols_x + config.K_vram - 1) / config.K_vram); // Maximum number of CUDA blocks that can do useful work.`; `std::min(nsm, nwork)`. Anchor (page): `The existing NVIDIA >=90% tile-efficiency heuristic is preserved.`
1. **Motivation and measured effect: empty blocks cost launch overhead and lengthen the fixup kernel's backward scan; measured +4.2% to +4.5% on RTX 5090 token generation. CONFIRMED with a narrowing: NVIDIA only, no AMD data.** The page reports twelve paired runs per row with a 99.75% CI: RTX 5090 prefill (P1) +0.15% [+0.06, +0.25]; TG at P6 215.21 -> 224.79 tok/s (+4.47% [+2.10, +6.85]); TG at P8 268.39 -> 279.57 (+4.17% [+2.20, +6.15]); DGX Spark: "no significant improvement". Model: Qwen3.8-27B Q4_K_M via `llama-batched-bench`. A separate earlier study, which the author describes only in a sentence (second cap on a Q4_0 model), is +8.1% for `llama-bench pp16` and +5.3% for batched P16 decode.
   - Anchors (page): `Stream-K can launch more CUDA blocks than there are useful K work units. The empty blocks add launch overhead and lengthen the fixup kernel's backward scan.`; `Dell RTX 5090 6 TG 215.21 224.79 +4.47 [+2.10, +6.85]`; `Dell RTX 5090 8 TG 268.39 279.57 +4.17 [+2.20, +6.15]`; `DGX Spark showed no significant improvement.`
2. **Hardware independence: "no scenario where launching more blocks than useful work is beneficial, regardless of hardware vendor". PARTIAL.** The maintainer says this in answer to a reviewer who asked for AMD and MoE numbers and who suspected that MoE expert routing makes the true useful bound lower than `nwork`. No AMD number was supplied, and the MoE question was not answered with data (the maintainer judged the search for regressions not worth the cost). The principle is sound for the cap's direction: the cap can only remove blocks that have empty K ranges. What is untested is the second-order effect: fewer blocks changes `fixup_needed` (`ntiles % nblocks`) and the stream-k partition boundaries.
   - Anchors (page): `There is no scenario where launching more CUDA blocks than there are chunks of useful work is beneficial, regardless of hardware vendor.`; `Do we want this to be tested on AMD hardware as it alters grid sizing for them?`
3. **Numerics: the cap can change FP32 summation grouping and the maintainers accepted that. CONFIRMED.** The first version kept a divisibility test to preserve K-split boundaries; the author showed a constructed CPU case where rounding up changes a sum from 0.99 to 0. The maintainer replied that stream-k results should be the same up to rounding regardless of block count, that bit identity across GPUs with different SM counts is not expected, and that the acceptance criterion is whether `test-backend-ops` passes (MUL_MAT and MUL_MAT_ID passed on RTX 5090). **For us this matters because AK keep gates and the champion-versus-candidate identity checks compare bits**: any grid change, including this cap and #32837's retune, can move token-level identity without being a bug.
   - Anchors (page): `Partial iterations can change FP32 summation grouping.`; `The criterion by which to go is whether test-backend-ops passes.`
4. **Absent from C19 `a6a32c1` and champion `eee3da8` history. CONFIRMED (in-house, git).** `git merge-base --is-ancestor 4c1004c492 a6a32c1` exits 1; `git grep nwork a6a32c1 -- ggml/src/ggml-cuda/mmq.cuh` finds nothing. Our launcher line is `block_nums_stream_k(GGML_CUDA_CC_IS_NVIDIA(cc) && eff >= 90 ? ntiles_dst : nsm, 1, 1)` (`mmq.cuh:1333 @ a6a32c1`). The edit applies by hand: `args.ncols_x` and `config.K_vram` both exist in our launcher (`mmq.cuh:1291, 1311`); only `<algorithm>`'s `std::min` is needed.
5. **Does the cap alone change our gfx90a launches? Only for matrices with `ntiles * ceil(K/256) < 104`; none of our served MMQ-reachable target shapes. PARTIAL (derived arithmetic, not measured).** Our launcher always runs 104 blocks on MI210 (the premise in the task, `mmq.cuh:1333`). With I = 128, J = 16, K_vram = 256 (`mmq.cuh:9`, CDNA table `mmq-config-cdna.cuh`), my arithmetic:

   | Shape (dense, one z) | ntiles | k-chunks | nwork | grid with cap | changes? |
   |---|---|---|---|---|---|
   | m=17408 k=5120 n=16 (27B FFN) | 136 | 20 | 2720 | 104 | no |
   | m=1024 k=5120 n=8..16 (27B attn K/V) | 8 | 20 | 160 | 104 | no |
   | m=2048 k=512 n=16 | 16 | 2 | 32 | 32 | **yes, 104 -> 32** |
   | m=512 k=2048 n=16 | 4 | 8 | 32 | 32 | **yes** |
   | m=4096 k=256 n=16 (single K chunk) | 32 | 1 | 32 | 32 | **yes, and fixup is skipped** (`ntiles % nblocks == 0`) |

   - For MUL_MAT_ID the grid's z dimension is the expert count (`mmq.cu:279-285`: "ne02 is used instead of ne12 because the number of y channels determines the z dimension"), so `ntiles` is multiplied by the number of experts and `nwork` is large; the cap is a no-op there.
   - Where it can bite: small-K or small-M dense matmuls (small drafters, K/V projections of small models, `ceil(K/256) == 1` shapes).    - When it bites, the benefit is the one the PR names: fewer idle blocks and a shorter fixup scan (fixup grid = `block_nums_stream_k.x`, `mmq.cuh:1345`). The magnitude on gfx90a is unmeasured; NVIDIA reported +4-5% e2e on shapes where it applies.
