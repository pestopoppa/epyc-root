## 2. Key claims

0. **What it is: a ROCm kernel library for LLM inference in which agents write the kernels and every kernel is validated automatically before it serves; an engine calls an AKLR operator, AKLR picks a validated kernel, and if none fits the engine uses its original code; AITER is a speed-test baseline, not a runtime fallback. CONFIRMED.** Components: `aklr/ops` (each operator's API, correctness check, speed baseline and kernel files), `aklr/core` (input checks, kernel loading, per-workload selection, validation), `aklr/plugins` (SGLang works today; vLLM and AITER "are planned"), `harness/` (agent skills and tools), `forge_task` (hands an AKLR problem to KernelForge). So "first external AITER provider" in the bearing dive is accurate only through the pilot adapter described in AITER's RFC; the README says the AITER plugin is still planned.
   - Anchors (page): `AKLR uses AITER as a speed-test baseline for library kernels; it does not ship AITER as a runtime fallback.`; `forge_task sends an AKLR problem to KernelForge.`; `aklr/plugins/ Plugins for other projects. SGLang works today; vLLM and AITER are planned.`
1. **Qualification: serve only workloads with a measured speedup of at least 1.05 over the baseline. CONFIRMED (page for the serving threshold; clone for the rest).** From the clone: the acceptance criteria are (a) at least one workload per kernel file at least 5% faster than the baseline, written into the kernel file by CI ("no_qualifying_workload" otherwise), and (b) for a new plugin route, a 2% end-to-end gain on a named workload, which the author reports in the PR (CI does not run the model). At run time only workloads at or above the threshold use the kernel; others run the original code. The measurement profile (version 19) uses CUDA-graph timing with a 1 GiB read cache flush before every call inside the graph, 10 replays per sample, an in-process kernel tracer, and sequential looks at 16 and 32 rounds with the 0.05 error budget split evenly (0.025 per look); thresholds are 1.05 for entry and 0.99 for retain (1% regress allowance). The accuracy check compares to an independent float32 reference with per-op error bounds.
   - Anchor (page): `AKLR_MIN_SPEEDUP=<x> Serve only kernels with a measured speedup of at least x (default 1.05)`
2. **How kernels are generated: a KernelForge `forge-loop` of agent rounds, plus an alternative GEAK campaign. CONFIRMED (clone).** `forge_task prepare` checks the starting kernel and records AKLR's baseline time per workload; the loop runs 20-70 minute rounds at about $10 an hour on a GEMM, "keeps a round only when it beats the kernel kept so far by more than the measured noise", and stops early when its directions are mined out; a human can steer by a message read from the next round; `forge-ablate` measures what each kept round is worth; `forge-finalize` reviews and squashes to one commit; a `--stress` run executes every workload on streams limited to a few CUs and beside a second call of its own, because the normal validation gives a kernel the GPU alone and would pass one whose workgroups wait for each other (such a kernel returns NaN or hangs on a busy GPU); `publish` writes the file; `aklr validate` runs the audit and bench stages. The run is driven through the Claude Code CLI and one idle GPU per run. A one-run-per-regime rule applies because a run scores the mean over its workloads (small-M decode and large-M prefill need separate runs).
   - Anchor (page): `forge_task sends an AKLR problem to KernelForge.`
3. **Arch scope: every kernel in the repository targets gfx950 (MI355X). CONFIRMED (clone statistics, not anchorable).** All 363 kernel schema files list the target `gfx950 / MI355X`; languages are FlyDSL 305, Triton 44, HIP 11, hsaco 3; 290 files carry kernel sources and 73 are definitions without sources (loaded and audited but never served or benched, per `aklr/ops/README.md`). Author-field strings: 169 name an author (`kyle-256` 76, `KernelForge` 37, `openai` 31, `fanxingran` 12, GEAK-related 8, others 5), and 122 files that carry sources name none. The development images are `lmsysorg/sglang:v0.5.23-rocm10-mi35x` and a vLLM ROCm 10.0 image, both pinned by sha256 digest in `stack.json`, with AITER pinned to a commit. The knowledge base is built from "AMD architecture and CDNA3/CDNA4 ISA documents", with 36 pages on gfx950. The only mention of gfx90a in the clone is the GPU_ARCH choice table of a remote-GPU setup skill (an infrastructure option, not a kernel target).
   - Anchors (page): `Development image SGLang lmsysorg/sglang:v0.5.23-rocm10-mi35x ( stack.json )`; `AMD architecture and CDNA3/CDNA4 ISA documents`
4. **The Rosetta Stone savings claim: same 1.28x GEMM speedup in 5h20m and about $52 with the knowledge base against 14h46m and about $205 without. CONFIRMED as stated; weak as evidence. PARTIAL.** It is one task (a bf16 GEMM N = 16384, K = 2048 at 13 values of M), one MI355X per run, one run per arm, spend "estimated" by the authors, and the final scores are close: 1.300x for about $133 with, 1.289x for about $230 without. A second task (GLM-5.2 MoE layer) gives 1.165x in 7h24m and about $87 versus 14h54m and about $170 (clone docs, not on the page). Both arms use the same agent (Claude Opus 5.5) and the KB "as it was before it was reorganised", so the tested KB is not the current one.
   - Anchor (page): `Same 1.28x speedup: 5h20m and ~$52 with the AKLR knowledge base, against 14h46m and ~$205 without`
5. **Provenance: kernels are content-addressed JSON files that embed their sources. CONFIRMED (clone).** The file name is 16 hex digits of the sha256 of `[name, authored_parts]`; it changes with the kernel, targets, requires or author and never with measured fields. `accuracy`, `speedup` and `microseconds` are written only by CI and an author edit of them is flagged (`PERF_EDITED`); `kernel` records language, targets (arch and hardware), requires (for example `hip >= 7.15`), author and the entry point. Agent rules: the runtime and schema code is protected (a code owner must approve); tests first; harness rule 8 says skills prepare changes and evidence but publication and merging need the invoking workflow or user. A `bad-cases` skill lists mistakes agents made (changing a contract to fit a kernel; hiding a slow fallback inside a kernel).
   - Anchor: none on the page; this claim rests on clone files only (`aklr/ops/README.md`, `docs/acceptance_criteria.md`, `aklr/core/validation/stages/_measure.py`, `harness/rules.md`).
