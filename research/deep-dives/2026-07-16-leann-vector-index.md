# LEANN — storage-efficient vector index (intake-831 deep-dive)

`date: 2026-07-16` · `intake: intake-831` · `source: github.com/StarTrail-org/LEANN` · `paper: arXiv:2506.08276 (MLSys 2026 Oral)` · **refined verdict: NO-GO on this host — no benefit at current scale: LEANN trades away storage (our most abundant resource) to save it, solving a non-problem on a 1.1 TiB-RAM host where all vector indexes total ~3.3 GB; CONDITIONAL-WATCH only on episodic-store growth; kernel/technique-mining is a NON-STARTER**

## TL;DR / Refined recommendation

**No-go — but on narrower grounds than an earlier draft argued, and narrower than turbovec's.** LEANN's mechanism is *recompute-not-store*: it discards the embedding vectors entirely and **re-derives them from source text at query time** (a pruned proximity graph + two-level PQ-gated search + dynamic batching keep the number of exact recomputes small). That buys a ~**50x storage cut** (paper-reported: index < 5% of raw data). But storage is the **abundant** resource on this host — 3.7 TB raid0 (608 GB free) and 1.1 TiB RAM (757 GiB available) — so the storage LEANN saves is a resource we already hold in surplus. All of our vector indexes combined total ~3.3 GB (~0.3% of RAM). **LEANN solves a non-problem here.** That — not a resource inversion — is the load-bearing reason for NO-GO: gates 1 and 3 (scale, RAM/storage pressure) are unmet, so the benefit is simply unneeded at current scale.

**Retraction of the "inversion" framing.** An earlier pass framed this as a storage-for-compute *inversion* — LEANN trading our abundant storage for scarce CPU embedding bandwidth "stolen from token generation," making it "strictly worse than turbovec." **That framing is withdrawn: this host is not GPU-less.** A live **AMD Instinct MI210** (gfx90a/CDNA2, 64 GB HBM2e, ROCm 6.2) — currently a testbed on `:8802` and slated by the operator to join the stack — runs exactly LEANN's recompute workload (small encoder forward passes: BGE-large-335M / GTE-small-34M) on its own HBM. LEANN's torch device auto-detect keys on `torch.cuda.is_available()`, which ROCm-torch reports true, so recompute would auto-place on the MI210; the core recompute path (ZMQ server → `sentence-transformers`) is device-agnostic torch, and only the *optional* flashlib kNN backends are CUDA-only. GPU recompute on the MI210's separate memory subsystem contends **zero** with CPU token-generation bandwidth. So the trade does **not** run "exactly backwards," CPU is not LEANN's forced operating point here, and **turbovec is not unambiguously preferable**. LEANN's published operating point (~90% top-3 recall in <2 s) remains a GPU number (NVIDIA A10G / M1 Ultra), and its GPU design point is reachable on this host via the MI210. (This MI210 placement is a code-path inference from the repo, not something we have run — treat "LEANN-on-MI210 works" as a hypothesis to validate before any adoption.)

**Second, the architecture gap that parked turbovec applies unchanged.** LEANN is a **single-vector** ANN index (one vector per item, scalar inner-product / L2 distance). Our certified KB-RAG is **multi-vector late-interaction MaxSim** (per-token 128-dim GTE-ModernColBERT). LEANN cannot express MaxSim any more than turbovec's single-vector MIPS API could — you would have to collapse each chunk's per-token matrix to one vector and throw away the late-interaction signal that is the entire point. So LEANN can *model* only our two single-vector IndexFlatIP stores (episodic, strategy); it cannot model KB-RAG.

**What changed since the turbovec analysis (2026-06-12):** the **episodic FAISS store grew ~8.9x in ~34 days** — from ~72.8K vecs / 298 MB to **~646K vecs / 2.65 GB** today (measured on-disk 2,646,319,149 B). It is single-vector `IndexFlatIP` (gate 2 MET) and is now only ~1.5x below the 1M-vector scale gate on the RAM axis, versus ~14x below in June. This is the one live trajectory worth instrumenting — but even if the scale gate fires, the remedy is a **stock FAISS HNSW/IVF** index, **not LEANN**, because LEANN's only differentiator over stock ANN is storage reduction we do not need, and its recompute machinery — while GPU-accelerable here via the MI210 — buys us nothing when storage is not the constraint.

**Highest-value next action:** do **not** bench LEANN against repl_memory. Set a single instrumented WATCH on the episodic store (`ntotal > 1M` **AND** host RAM-available materially tightening), and separately flag LEANN's **MCP + personal-data connectors** as an *operator-review* candidate for the operator's own personal data — distinct from the production stack (see Decision gates). The LEANN index engine itself stays **NO-GO** for this host at current scale.

**Explicit gates (all must hold to proceed past WATCH):**

1. **Target single-vector corpus exceeds ~1M vectors** (float32 RAM crosses ~4 GB AND exact flat search crosses ~10 ms). **UNMET, but MOVING — and the latency half may already be crossed.** Episodic = **~646K vecs / 2.65 GB** — only ~1.5x below on the RAM axis (was ~14x below at 72.8K on 2026-06-12); at the observed ~8–17K vecs/day it could cross 1M around **late-August 2026**. On the latency axis, scaling the store's own ~1–3 ms @ 73K docstring linearly puts the current flat scan at an **estimated ~9–27 ms** — already at or over the ~10 ms threshold. Gate 1 therefore remains UNMET **only because the RAM half (2.65 GB < 4 GB) has not yet crossed.** KB-RAG = 6,278 chunks (~160x below; multi-vector anyway). Strategy = ~1,424 vecs (~700x below). This is the one gate on a live path toward MET.
2. **Target uses (or can use) a single-vector inner-product index.** **SPLIT.** UNMET for KB-RAG (multi-vector late-interaction MaxSim — LEANN cannot express it). **MET** for the episodic store *and* the strategy store (both `faiss.IndexFlatIP`, single-vector, dim=1024 BGE-large). The growing episodic store is exactly the corpus that satisfies this gate.
3. **Genuine RAM/storage pressure.** **UNMET, decisively.** Combined single-vector footprint ~2.65 GB (episodic) + 5.8 MB (strategy) + ~0.66 GB KB-RAG ≈ **~3.3 GB = ~0.3% of 1.1 TiB RAM**, 757 GiB free. The raid0 is 83% used, but that is GGUF models (~2.9 TB), **not** vector indexes — LEANN would not relieve it. Even at 1M episodic vecs (~4 GB) the store is ~0.36% of RAM. No pressure exists or is on the horizon.

## What it is

LEANN (**"LEANN: A Low-Storage Vector Index for Personal Devices"**, arXiv:2506.08276) is a graph ANN index that **stores the graph but not the embedding vectors** and recomputes embeddings on the fly at query time. **Venue (verified):** MLSys 2026 **Oral** (mlsys.org/virtual/2026/oral/3786, Tue 19 May 2026; OpenReview forum `iVYBpQWGhq` venue field = "MLSys 2026"); earlier a **poster at the ICML 2025 Workshop on Vector Databases** (not the ICML main track). The task brief's "NeurIPS 2025" appears to be a **mis-attribution** — no NeurIPS 2025 listing was found. Authors: UC Berkeley Sky Computing Lab, CUHK, AWS, UC Davis (incl. Stoica, Zaharia, Gonzalez).

**Algorithm (from the paper — all figures below are paper/README OBSERVATIONS, not measurements we ran):**

- **Graph construction + embedding discard.** Build a standard **HNSW** graph over the corpus using full embeddings (Contriever, 110M params, 768-dim), then **discard every stored embedding**, keeping only the graph (adjacency in CSR form) plus a small **PQ codebook** for cheap approximate distances. Raw text chunks (256 tokens) stay on disk.
- **High-degree-preserving pruning (their Algorithm 3).** Node access is heavily skewed — a few high-degree "hub" nodes are visited constantly. Rank nodes by degree; the **top ~2% are hubs** and keep a high max out-degree `M`; all other nodes are pruned to a low max out-degree `m` (`m < M`). Crucially, **back-edges are asymmetric** — any node may form bidirectional edges to newly inserted nodes up to the *full* `M` (not `m`), so every node keeps a chance to connect to hubs, preserving navigability. Net: the pruned graph uses **~half the edges** of unpruned HNSW at comparable recall. Ablation: beats Random-Prune by up to 1.18x and a uniform Small-M baseline by up to 5.76x. Storage budget `C` is the knob (Eq. 1 minimizes search-time recompute work subject to total-edge-storage < `C`).
- **On-the-fly recomputation.** Whenever a node's *true* distance to the query is needed, LEANN fetches that node's raw text, tokenizes, runs the embedding model **forward pass** to regenerate the vector, and computes the exact distance. This is why the 171 GB of embeddings (60M-chunk RPJ-Wiki) need not be stored.
- **Two-level (two-queue) search (Algorithm 2).** An **Approximate Queue** gets a cheap PQ-based distance for *every* node encountered; an **Exact Queue** holds only the most promising candidates whose embeddings are actually recomputed. Best-first loop: pop closest from EQ → PQ-score its unvisited neighbors into AQ → extract the **top-a%** of AQ not yet in EQ, recompute *those* exactly, push to EQ. This decouples *which nodes to explore* (cheap, done for all) from *which to recompute exactly* (expensive, done only for the top-a%). Two-level alone: **1.40x avg speedup** (up to 1.64x).
- **Dynamic batching.** Strict best-first would recompute only ~degree-many embeddings per hop, starving the accelerator. LEANN relaxes the best-first data dependency and accumulates candidates **across hops** until a target batch is reached, then issues one batched forward pass. The shipped implementation batches **device-adaptively** (`embedding_compute.py`: CPU/other batch 32, cuda 256 (VRAM-capped), mps 128), so the mechanism runs on CPU too — it merely loses the large-batch GPU throughput payoff. Two-level + batching: **1.76x overall** (up to 2.02x).

**Backends.** The paper instantiates LEANN on an **HNSW** backbone; **DiskANN appears only as a baseline** (its 4 KB sector-aligned padding gives it the *largest* on-disk footprint of all methods). The public codebase later exposes both HNSW and DiskANN backends, but that is beyond the paper's experiments.

**Headline reported numbers (OBSERVATIONS):** index < 5% of raw data / up to 50x smaller than stored-embedding indexes; **90% top-3 recall in < 2 s** (A10 GPU); M1 Ultra 2.28–3.01x slower; recompute = **76% of total query latency**; **21.17x–200.60x faster than EdgeRAG**; PQ compressed to LEANN's footprint reaches only ~20% recall; GTE-small (34M) vs Contriever (110M) = 2.3x speedup at <2% downstream-accuracy cost. Per-cell storage/latency/recall values live in the paper's Figures 4–5, not text tables.

**Repo maturity (verified via GitHub API, not README).** `StarTrail-org/LEANN`: **12,689 stars / 1,145 forks**, 44 open issues, created 2025-06-09, last push 2026-07-03, **MIT**, not archived, ~608 commits. Python orchestration + C++ backends that vendor **forks of Faiss (HNSW) and DiskANN** as git submodules, patched to add a **ZMQ recompute callback** (HNSW = msgpack; DiskANN = protobuf) to a Python embedding server that re-embeds candidate passages via `sentence-transformers` (default, device-agnostic torch), OpenAI/Gemini/DashScope, Ollama, or MLX. **CPU-only is first-class** (`docker/Dockerfile.cpu` on the CPU torch wheel; device auto-detect with a real CPU tuning branch; Linux CPU-only threading defaults for issue #208), with GPU used opportunistically if present (on this host, that would include the MI210 under ROCm-torch). Ships a hand-rolled stdio **JSON-RPC MCP server** (`leann_mcp`, 4 tools that shell out to the `leann` CLI) plus connectors for codebase, files/PDF, email, browser history, iMessage, WeChat, Slack, Twitter, and LLM chat-export archives. Real test + benchmark harness (financebench, enron, laion, faiss-vs-leann, diskann-vs-hnsw) and cibuildwheel CI. Mature, popular, CPU-path-tested OSS.

## Fit to EPYC

**Our single-vector call sites (verified in code).** `orchestration/repl_memory/faiss_store.py` → `FAISSEmbeddingStore` uses **`faiss.IndexFlatIP(dim)`** (exact, uncompressed brute-force inner product) over **1024-dim BGE-large-en-v1.5** vectors, `normalize_L2` for cosine. Consumers: the **episodic store** (`sessions/embeddings.faiss`) and the **strategy store** (`strategies/strategy_embeddings.faiss`, the dense half reciprocal-rank-fused with BM25). The certified **KB-RAG** (`epyc-orchestrator/src/retrieval/`) is a different animal: **multi-vector late-interaction**, per-token 128-dim GTE-ModernColBERT scored by MaxSim = Σ over query tokens of max over doc tokens of ⟨q_i, d_j⟩.

**Corpus sizes (measured on-disk 2026-07-16; `IndexFlatIP` ⇒ ntotal ≈ bytes / (dim·4)):**

| Store | file | bytes | ntotal | float32 RAM | vector shape | LEANN-expressible? |
|---|---|---|---|---|---|---|
| episodic | `sessions/embeddings.faiss` | 2,646,319,149 | ~646,074 | ~2.65 GB | single-vec, dim=1024, IP | **yes** (gate 2 MET) |
| strategy | `strategies/strategy_embeddings.faiss` | 5,832,749 | ~1,424 | ~5.8 MB | single-vec, dim=1024, IP (RRF dense half) | **yes** (gate 2 MET) |
| KB-RAG (live) | `data/kb_rag/index` (.npz + catalog.sqlite) | ~666 MB | 6,278 chunks / 204 files | ~0.66 GB | **multi-vector** 128-dim/token MaxSim | **no** (MaxSim) |
| KB-RAG (certified K7) | snapshot | 1,227.6 MiB | 18,010 chunks / 577 files | ~1.2 GB | multi-vector | no |

**Host (verified live):** EPYC 9655, 96c/192t, 4 NUMA nodes, AVX-512 (Zen 5), **1.1 TiB RAM (757 GiB available)**, 3.7 TB raid0 (608 GB free, 83% used — that 83% is GGUF models, not vectors). **CPU inference, BW-bound decode;** a live **AMD Instinct MI210** (gfx90a, 64 GB HBM2e, ROCm 6.2) sits on `:8802` as a testbed (slated to join the stack) and is available for encoder forward passes. Combined single-vector vector footprint ~2.65 GB = **~0.24% of RAM**; with KB-RAG, ~3.3 GB = **~0.3%**.

**The architecture gap (identical to turbovec's gate 2).** LEANN's single-vector graph cannot express a sum-of-token-maxes. Collapsing each KB-RAG chunk's per-token matrix to one vector to fit LEANN discards the late-interaction signal that is the whole reason KB-RAG uses ColBERT. So LEANN is architecturally applicable only to episodic + strategy — the two single-vector IP stores.

**The storage-for-compute trade (CPU-cost figures below are ESTIMATES/HYPOTHESES, not measurements).** LEANN saves **storage** by not persisting embeddings and pays **query-time embedding compute** instead. The relevant facts on this host:

- **What we have today:** the episodic `IndexFlatIP` lookup is a **bandwidth-bound scan** of 2.65 GB. The store's own docstring cites ~1–3 ms at 73K vecs; scaling that linearly puts a 646K-vec / 2.65 GB brute-force scan at an **estimated ~9–27 ms/query** (implying ~100–300 GB/s effective BW — not the ideal ~400 GB/s STREAM, which would give the earlier ~6–7 ms figure). Either way it is cheap DRAM streaming, no model forward.
- **What LEANN replaces it with:** BGE-large-335M **forward passes** over only the **top-a% subset of visited nodes that two-level search selects for exact recompute** — tens to low-hundreds, growing polylogarithmically with corpus size, **not** every visited node (the pruning + two-level search exist precisely to shrink this set). LEANN batches these forward passes device-adaptively (`embedding_compute.py`: CPU/other batch 32 vs cuda 256, mps 128), so the batching path runs on CPU but its throughput payoff is a GPU property (large-batch kernel-launch amortization) that largely evaporates when embedding is CPU/BW-bound. The authors' config-guide micro-bench shows HNSW-with-recompute at **0.818 s vs 0.012 s without** (a ~68x penalty) on just 5,000 texts. **Estimate if recompute ran on our CPU:** of order hundreds of ms to seconds per query — roughly **~100–1000x** the stored-lookup latency (basis: the recomputed top-a% subset and the ~68x config-guide penalty, **not** the full visited set). **But** with the MI210 available, LEANN's device auto-detect would place that recompute on GPU HBM, where it contends **zero** with CPU token generation — so the CPU-cost estimate is an upper bound for a code path that, in practice, would not run on CPU here.

So the storage LEANN buys back is a resource we already hold in surplus, and its compute cost — while real on CPU — is largely deflectable to the MI210 rather than "stolen from token generation." The honest verdict is therefore **no benefit at current scale**, not "strictly worse than turbovec": turbovec still avoids a query-time model forward entirely, but LEANN's recompute is no longer an inversion of our scarcest resource once GPU recompute is on the table.

**Why it fails the gates today:** gate 1 UNMET (largest single-vector corpus ~646K, ~1.5x below 1M on the RAM axis — latency axis may already be crossed); gate 2 MET only for episodic/strategy (KB-RAG is MaxSim); gate 3 UNMET decisively (~0.3% of RAM, no pressure). And even a gate-1 firing would not flip the verdict at current understanding: stock FAISS HNSW/IVF (which keeps stored vectors, no recompute backend on the hot path) is the simpler first answer — though **LEANN-on-MI210 becomes a genuinely viable option** if scale AND real RAM/storage pressure ever coincide (see Decision gates).

## Comparison to turbovec (intake-686)

Same three scale gates, **opposite compression mechanism**, same host verdict.

| | turbovec (intake-686) | LEANN (intake-831) |
|---|---|---|
| Mechanism | **Compress-and-store**: keeps vectors, quantizes codes ~8x (4-bit TurboQuant), searches compressed codes with no decompression, no recompute | **Recompute-not-store**: discards vectors, re-derives them at query time from a pruned graph (~50x storage cut) |
| Trades | recall ↓ for **RAM** ↓ | **query-time compute** ↑ for **storage** ↓ |
| Query-time model forward? | **No** — compressed stored lookup | **Yes** — embedding forward pass per exact-scored (recomputed) node; **GPU-accelerable via MI210** |
| x86 story | +12–20% is ARM/NEON-only; on our AVX-512 it is PQ-parity | recompute is GPU-accelerable here via the MI210 (device auto-detect under ROCm); CPU recompute is expensive but largely deflectable to GPU HBM |
| Applies to | episodic/strategy only (single-vec); not KB-RAG MaxSim | same — episodic/strategy only; not KB-RAG MaxSim |
| Gates 1 & 3 today | fail | fail |

**Which wins if a gate ever fires on THIS host:** on current understanding, a **stock FAISS HNSW/IVF** index (still storing vectors, no recompute backend on the hot path) is the correct first remedy before either exotic option. Between the two exotics, turbovec preserves a cheap compressed stored lookup with no query-time model forward, whereas LEANN reintroduces BGE-large recompute — but that recompute is GPU-accelerable on the MI210 (contending zero with CPU token generation), so LEANN is **not** the unambiguously worse fit it would be on a genuinely GPU-less host. The honest bottom line: **neither is warranted today**, because the storage/RAM saving is unneeded (~3.3 GB total, ~0.3% of RAM).

**Novelty vs other low-storage indices (independently checked).** "Recompute-not-store" is genuinely different from the **DiskANN / SPANN / Starling** family (all of which *store* embeddings on SSD and minimize I/O), but it is **not novel relative to EdgeRAG** (arXiv:2412.21023, Dec 2024), which already does IVF-based on-demand embedding recomputation for edge devices ~6 months earlier. LEANN's *real, defensible* contribution is applying recompute to a **proximity graph** (vs EdgeRAG's IVF) plus hub-preserving pruning and two-level selective recompute — yielding polylog recompute count per query vs EdgeRAG's √N growth, hence the claimed 21.17x–200.60x speedup over EdgeRAG. That is a solid **optimization of an existing paradigm, not a new paradigm** — "recompute-not-store is novel" would be an over-claim without the EdgeRAG qualifier. LEANN does not directly benchmark SPANN or Starling.

## Technique / kernel mining

**Nothing worth porting.** All four LEANN ideas are coupled to the recompute-instead-of-store paradigm, whose payoff (storage) is a resource we hold in surplus. Same verdict and same gates as the turbovec precedent.

| Idea | Would target | Verdict | Why |
|---|---|---|---|
| **High-degree-preserving graph pruning** (keep hub nodes so recall survives edge pruning) | episodic/strategy (would need a graph index first); KB-RAG has no graph | **not-transferable** | Both FAISS stores are flat `IndexFlatIP` (exact brute-force, no graph to prune); KB-RAG is multi-vector MaxSim over flat `.npz` (also no graph). The payoff — visiting fewer high-value nodes so *fewer embeddings get recomputed* — is coupled to the recompute paradigm; with embeddings stored (as ours are), stock hnswlib/FAISS-HNSW pruning already suffices. Even at a future >1M gate, plain HNSW/IVF is the answer, not LEANN's recompute-tuned pruning. |
| **Two-level search** (cheap PQ distances gate which nodes get exact recompute) | episodic/strategy | **not-transferable** | The two-level structure exists solely to decide which nodes warrant an expensive *recomputed* exact distance. Our flat scan is already exact and cheap (BW-bound, est. ~9–27 ms at 646K vecs) — there is no costly exact-distance stage to gate. Generic coarse-then-fine (IVF) is just standard ANN, already covered/parked by the turbovec analysis. |
| **On-the-fly recompute** (drop persisted embeddings, re-encode from source at query time) | strategy (~1.4K vecs), KB-RAG | **not-transferable** | The strategy store is the maximal counterexample: its embeddings cost 5.8 MB, so re-running BGE-large at query time to save 5.8 MB of stored vectors is pointless regardless of where the forward passes run (CPU or MI210). It also breaks `index.reconstruct()` (relied on by verifier/distiller paths) and the BM25+dense RRF fusion. For KB-RAG, recomputing per-token ColBERT embeddings per query (~180 ms/encode CPU probe) adds latency to save ~1.2 GiB we are not pressured on. |
| **Dynamic recompute batching** (batch forward passes across graph hops) | episodic indexer / KB-RAG | **not-transferable** | Device-adaptive, not GPU-only — it amortizes batch-forward throughput across traversal hops (`embedding_compute.py` batches 32 on CPU, 256 on cuda, 128 on mps); the code path runs on CPU but the throughput payoff is a GPU property (large-batch kernel-launch amortization) that largely evaporates when embedding is BW-bound. We recompute nothing at query time in our current stores, so there is nothing to batch. The one legitimate batching for us is *build-time* batch encoding, which the KB-RAG indexer already does — standard practice, not a portable LEANN insight. |

If anyone ever wants graph-ANN pruning technique, study **FAISS/hnswlib upstream** directly; LEANN's variant is tuned for the recompute regime we do not need.

## Risks & contradicting evidence

- **Measurement status (MEASUREMENT.md):** we have run **no** benchmarks of LEANN on our host. Every LEANN number here — <5% storage, <2 s to 90% recall, 76% recompute, 21–200x vs EdgeRAG, 68x recompute penalty, 2.3x GTE-small — is a **paper/README-reported OBSERVATION**, usable for hypotheses only, never to gate a keep/deploy/promote decision. Every "cost on our CPU" figure (est. ~9–27 ms flat scan, ~100–1000x recompute) is an **estimate/hypothesis**, not a measurement.
- **MI210 recompute placement is inferred, not measured:** ROCm-torch reporting as CUDA and LEANN auto-placing recompute on gfx90a is a code-path inference from the repo, not something we have run. Treat "LEANN-on-MI210 works" as a hypothesis to validate before any adoption.
- **Recompute is the dominant cost, by the authors' own admission:** embedding recomputation = **76% of total latency**. The whole design trades storage for query-time compute — which on this host is deflectable to the MI210 but is still a cost that stored-vector indexes avoid entirely.
- **The authors' own config guide quantifies the recompute tax:** on 5,000 texts, HNSW with recompute = **0.818 s vs 0.012 s** without (~68x); DiskANN = 0.041 s vs 0.013 s (~3x). This is the true cost of the mechanism, largely absent from the paper's headline framing.
- **CPU-only viability is worked-around, not solved (for genuinely GPU-less users).** For no-GPU users the config guide advises: (a) use **OpenAI cloud embeddings** — which *breaks* the "100% private / on-device" selling point; (b) build the index on a **remote cloud GPU (SkyPilot)** — breaks on-device; or (c) **disable recompute** — disables the very mechanism the paper is about. **On our host the MI210 sidesteps this** — recompute auto-places on GPU HBM — so these worked-arounds apply to genuinely GPU-less users, not us; the privacy/on-device tension is real for the paper's target audience but not the binding constraint here.
- **The evaluation hardware is not a weak personal device.** Experiments use an **NVIDIA A10G (24 GB)** on AWS g5.48xlarge and an **Apple M1 Ultra** (high-end UMA workstation); the A10 is 2.28–3.01x faster than the M1. No genuinely low-end CPU-only laptop is measured, despite "personal devices" being the framing — the sub-2-second numbers are GPU/M1-Ultra numbers.
- **High peak storage during construction:** building embeds *every* chunk once up front (then discards), so **build-time peak storage is high** even though search-time storage is low — undercutting the low-storage story at build time. No CPU build-time is published for the 60M-chunk index; independent write-ups note CPU embedding is "painfully slow."
- **Novelty over-claim risk:** recompute-not-store is **EdgeRAG** prior art (Dec 2024); LEANN's contribution is graph-based recompute + pruning + two-level selection, an incremental (if solid) systems improvement, not a new paradigm.
- **Accuracy caveats:** little benefit on GPQA (Wikipedia poorly supports graduate-level questions); the GTE-small 2.3x speedup costs ~2% downstream accuracy — the "no accuracy loss" banner is conditional.
- **No independent adversarial benchmark exists** (as of Jul 2026). Third-party coverage (neovintage ~2.5 s vs ~0.03 s traditional-ANN, rushis, MarkTechPost, Medium, an author's DEV.to post) is thin, enthusiastic, and mostly promotional — not a replication. Integration interest exists (AnythingLLM #4265, USearch #662) but with no numbers.
- **Correctness regression (as with turbovec):** dropping stored embeddings breaks `index.reconstruct()` and the strategy store's BM25+dense RRF fusion — a functional break, not just a recall trade.
- **Contradicting (in favor):** OpenReview forum is gated (Cloudflare challenge), so reviewer weakness lists could not be retrieved; the paper is an **Oral** (top-tier acceptance), so surviving concerns were presumably minor — its storage win against *store-on-disk* indices is real and large (201 GB → 6 GB on 60M chunks). None of that changes the host-fit verdict, because on this host storage is the resource we already have in surplus.
