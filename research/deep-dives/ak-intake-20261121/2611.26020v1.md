## What is logged, what is replayed, how boundaries are predicted
- **Logged:** "the inputs of every recurrent layer for positions [s, t_m) ... per-token projections, gate inputs, and any required page-end convolution state", in 16-token request-private log pages. The window is ≤1024 tokens past the chunk start; anything wider becomes a proactive cut. 27B log = 957 KiB/token ≈ 19.9 KiB per GDN layer per token. Our inference (not stated in the paper): this is consistent with BF16 logging of the 10240-wide pre-conv projection plus gates. PR31669 by contrast logs post-conv F32 k/v/g/beta at 32.4 KiB/layer/token.
- Precision-rounding bitmasks record where the forward rounded the state to storage precision (chunk and decode-step boundaries), and replay rounds at the same positions.
- **Replayed:** state transitions only (Eq. 2; no outputs o_t, no attention/MLP/norm/proj) from a *leased* resident checkpoint at the chunk start s. It is one cross-layer kernel using device pointer tables, on the same stream, with no host sync. It costs 1.2-3.1 ms per checkpoint in serving, and restores take ~0.2 ms.
- **Boundaries:**
  - Template stable end: render the chat template on two probe conversations at startup; the position before the trailing template suffix becomes a target.
  - End of a finished turn: the last 16-token boundary of prompt+output. This is free, because decode passes through every page.
  - Branch junction: a radix node with ≥2 children, no checkpoint, depth ≥256.
  - Chunk ends: natural, low priority.
- **Retention tiers:** dead −1 < superseded 0 < speculative 1-2 < proven 3 < running 4. Dead checkpoint slots are lent to the KV pool through CUDA VMM.

**Same principle as PR31669?** Yes in the core identity: log recurrent-layer inputs, then recompute state-only from a base state instead of storing per-position state copies. Both descend from ReplaySSM (arXiv 2610.13778, cited by FR as [35]). They differ in scope and placement:

| | PR31669 | FrontierReplay |
|---|---|---|
| Purpose | Within-request spec rollback | Across-request prefix checkpoints |
| Window | ≤ n_rs_seq+1 tokens | ≤1024 tokens |
| Where replay runs | Inside the GDN op at the start of the next ubatch, state in registers | A separate post-forward kernel in the same step |
| Output | The committed live state | A pool checkpoint |

## Mapping onto llama.cpp server and the orchestrator
- **llama.cpp hybrid prefix cache today:**
  - The server creates context checkpoints only during prompt processing: at user-message starts, at 4+n_ubatch, and 4 tokens before the prompt end. It creates none during generation (UFH14-A7, harness-program.md:2991 @ ac1347f).
  - A mid-prompt checkpoint ends a batch at that position. That is FR's "cut": one extra short ubatch, which on a bandwidth-bound host costs about one extra weight pass (order of a decode step, tens of ms on the 27B GPU or A3B CPU).
  - Checkpoints are host-RAM copies (`--ctx-checkpoints`, default 32; `--cache-ram`), not GPU KV-pool pages.
- **What carries:**
  - (a) **Split-free checkpoints.** Run the prompt uncut, keep the GDN inputs for the window before the target, and replay into a checkpoint buffer. PR31669's op extension already provides the replay-only path (CUDA `GDN_LAUNCH_N(..., n_tokens=0, rep_only)`), so the building block exists once A1 of the PR31669 dive lands. Cost on MI210 (27B): log 1.55 MiB/token F32 across 48 layers (~0.8 GB for a 512-token window). Replay ≈ L × ~0.025 ms recurrent, or ~2 ms through the chunked WY kernel. That compares with one extra ubatch per cut. The gain per request is small unless cuts are frequent; measure first (FR-A2).
  - (b) **End-of-finished-turn and template-stable-end anchors.** UFH14-A7 measured 41/230 turns (17.8%) re-prefilling the previous output + 4 tokens, which is 14.8% of prefill time. If the divergence lies *inside* the previous output, a generation-end checkpoint at the template-stable end recovers it. Such a checkpoint is free in FR terms, since decode passes every position, so on llama.cpp it costs only a state copy (27B 149.6 MiB, A3B 62.8 MiB, Q38FN 112.6 MiB). If the divergence is at the output start (reasoning stripped), the existing 4-before-end checkpoint already captures it.
  - (c) **Frontier retention** matters only under pool pressure. KPF-64 (kv-cache-program.md:1654) found checkpointing is the whole effect and `--cache-ram` adds nothing at 4 sessions / 4 slots. The arms that would create pressure (E sessions > slots, F bursts) never ran.
- **Orchestrator multi-turn reuse:** `PrefixRouter` slot pinning and the PREFIX-CACHE-LAYOUT flags (harness-program.md:557-558) already target stable prefixes. RTE-PFX-1 already does FR's "where does reuse end" analysis statically. The junction-checkpoint arm (harness-program.md:511) is FR's branch-junction idea, applied by request flag.
- **MI210 / Zen 5:**
  - Replay leverage should be higher than on the A800 for the full-forward ratio. Per token, the 27B full forward is ≈54 GFLOP vs ≈189 MFLOP for GDN-only replay (48 layers × 48 heads × ~5·128²), a FLOP ratio of ≈285×. A800's measured 20.7× reflects kernel overheads.
  - On Zen 5, the per-head state of 64 KiB is L2-resident, so replay is cheap. The cost is the log footprint and copying, not FLOPs.
  - CUDA VMM pool lending has no equivalent need: llama.cpp checkpoints are in host RAM.

## Adversarial pass
- Search found no independent replication or criticism of FrontierReplay; it is 2 days old and searches surface only SuffixReplay, Tail-Replay and Marconi.
- FlashStates (FutureMLS-Lab; secondary write-up only) is the concurrent in-kernel export alternative. FR's own comparison: export wins by 1.5-2.5% on fine-chunk GDN (C_tile=64) and loses on coarse-tile Mamba-2.
- Internal limits FR states itself: the 34B LongBench goodput loss (static TP sub-pools); 4B ToT 0.99×; Falcon placement floor of 1568 tokens because BF16 Mamba-2 states are rounding-sensitive; 7.2% fallback to cuts at 16-24 GiB on Falcon SWE-agent.
- The headline 4.26× sits at an overload knee (vLLM p99 TPOT ∞).
