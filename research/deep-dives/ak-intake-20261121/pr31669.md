## Mechanism (from the diff)
- **What is logged:** the gated-delta-net op's own inputs for the tokens of the last ubatch: post-conv/post-norm `k [S_k,H_k,n_pend]`, `v [S_v,H_v,n_pend]`, and `gb [g0,H_v,2·n_pend]` (gates, then betas). All are F32, held in per-layer cache rows `cache_spk/spv/spgb_l%d` with one row per cell. n_pend = n_rs_seq+1.
- **Conv window:** the conv state row becomes a channels-first history `[channels, d_conv−1+n_pend]` (window, then pending columns of the raw conv input). Conv "replay" is no recompute, only a column gather: `rs_rep_cols[s][c] = n_rep + c` picks the window after the kept tokens.
- **Where replay runs:** inside the gated-delta-net op, at the start of the same kernel, before the new tokens. CUDA: `gated_delta_net_cuda<..., replay=true>` loops over `n_rep[seq]` pending tokens with the state in registers (`s_shard`). It is the same update as the main loop, without the attention output (`// same update as below, without the attention output`). There is no separate kernel and **no shared memory**. One CTA covers (head, seq, column-block). The upstream base kernel gives 4 columns per warp, `lanes_per_col = warp/4` (16 on wave64), `rows_per_lane = S_v/lanes_per_col`, and `warp_reduce_sum<lanes_per_col>`. The pending rows read are ≤ n_pend = n_rs_seq+1 (8 at n_max 7).
- **Keep/accept signalling:** `keep` is op param 2, fixed at graph build: `2 ≤ n_seq_tokens ≤ n_rs_seq+1`, the same rule as find_slot, so the graph topology never changes. With keep, the kernel writes the **state after the replay** (the committed state) and skips the final state; the new tokens' inputs become pending. Accept arrives through `seq_rm(rollback)`, which does `cell.rs_pend -= rollback`. Next ubatch, find_slot sets `rs_rep = rs_pend` and `set_input` fills the I32 `rs_rep_n[n_seqs]`. Non-keep ubatches (n=1 decode, long prefill) replay and then write the final state.
- **Pending-row stores:** in-graph these are 4 `ggml_cpy` per layer. CUDA's `ggml_cuda_try_gdn_cache_fusion` pattern-matches the 4 cpys and has the kernel write them (`rep.st[4]`). Reviewers want to remove that fusion in favour of fewer pending cpys.
- **Chunked prefill:** CUDA runs a replay-only launch (n_tokens=0, keep) into state_out, then the chunked (mma) kernel in place. 0cc4m: Vulkan's chunked shaders lacked this dual run (follow-up #32721).
- **Numerics:** the KDA main loop was changed to compute `expf(g)` into registers like the replay loop, so a replayed state matches snapshots bit for bit on sm_89 (commit f7e2441).

## Snapshot floor vs replay: cost model (27B, MI210 and Zen 5)
In-house fact (program.md:700 @ 3ab8362e5): "Per-row state snapshots are ~3.1 MB/layer/row on the 27B, an unavoidable ~0.12 ms/row". 3.1 MB matches 48·128²·4 B = 3.15 MB per GDN layer. 48 layers × 3.15 MB / 0.12 ms ≈ 1.26 TB/s, a plausible MI210 store rate.

**Replay removes that floor.** Per verify step of T = n_max+1 rows (8 at n_max 7), per sequence:

| Term | Snapshots | Replay |
|---|---|---|
| State writes | T × 151 MB = 1.21 GB → ~0.96 ms | 1 × 151 MB → ~0.12 ms |
| Input log writes | 0 | T × 48 × 32.4 KiB ≈ 12.4 MiB (~0.01 ms) |
| Conv history | T conv snapshots × 48 × 120 KiB ≈ 46 MB | one row 10240·(3+8)·4 B × 48 ≈ 21.6 MB (~0.015 ms) |
| Extra compute | 0 | n_rep = accepted+1 sequential token steps in registers, ≈5/7 of a main-loop step (no attention output, no state traffic) |

- Replay compute estimate (our inference, flagged): DTREE-0-GDN-ROWS measured the GDN verify slope at ~0.155 ms/row (speculative-decoding.md:939 @ ac1347f). If the 0.12 ms/row snapshot floor sits inside that slope, the in-register compute per row is ≈0.035 ms. At the linear-chain mean accept length 4.65 (DTREE r4 L arm, speculative-decoding.md:1968), n_rep ≈ 5.6, so replay ≈ 5.6 × 0.035 × 5/7 ≈ 0.14 ms.
- **Net, MI210, np1:** ≈ 0.96 − (0.12 + 0.03 + 0.14) ≈ **−0.67 ms per step per sequence**. That is ≈1.3% of the 51.6 ms 27B DFlash2 round (DTREE-ROUND profile L arm). It scales about linearly with sequences in a batched verify, while weight traffic is shared. This is the same shape as the PR's +0.5% at 1 seq and +8.6/+17.8% at 4/8 seqs. It is also ~5% of the 2.39 ms marginal verify-row cost (DF2-VERIFY-SLOPE, speculative-decoding.md:1840): small for chains, compounding for trees.
- **HBM freed (MI210):** np4 at n_rs_seq 7, 4.79 GB → 0.71 GB. Tree mode at n_rs_seq 15 np4, 9.58 GB → 0.82 GB.
- **What remains unavoidable:** one state read plus one state write per layer per step (the K=1 decode traffic).
- **Zen 5 CPU, Q38FN MTP d4 (T=5):** state per copy 36 × 3 MiB ≈ 108 MiB.
  - Snapshots: the CPU op writes 5 snapshots into its dst, then an unfused `ggml_cpy` moves them into the cache. That is ~3 transfers × 5 × 108 MiB ≈ 1.6 GiB moved per round. The working set is (1+n_rs_seq) × 113 MB ≈ 565 MB, over the 384 MiB L3.
  - SYNC-3 (cpu-decode-roofline-program.md:3010 @ ac1347f) showed the 113 MB K=1 state is **L3-resident** (CPY ~1.2 TB/s aggregate).
  - Replay keeps the working set at ≈113 MB + 5.7 MiB pending, so L3-resident.
  - Saving: ~0.5 ms per round if snapshots stay in L3, up to ~5 ms if they spill to DRAM at ~300 GB/s, against a ~55-80 ms round, so **~1-8%, unmeasured**.
  - Replay FLOPs: 36 layers × 48 heads × 5 × 128² ≈ 142 MFLOP per replayed token, ~0.7 GFLOP per round. That is negligible on 96 cores; the per-head state of 64 KiB is L2-resident.
  - Q38P-1(a) (cpu-decode-roofline-program.md:316) already counts "the K+1 GDN state writes". That is where this belongs.
- **A3B CPU frontdoor (np4, MTP n-max 4):** state 30 × 2 MiB = 60 MiB per seq, so a 4×5×60 MiB snapshot set ≈ 1.2 GB per step. It does not fit one NPS4 quarter's share of L3. The relative gain is likely larger than on Q38FN, but it is unmeasured.

## Grounding vs current EPYC state
- Snapshots: our fork uses K = n_rs_seq+1 snapshot slots (chain) and K = W (tree record mode, `ggml_gated_delta_net_tree`, speculative-decoding.md:1908). There is CUDA cache fusion for K>1 (fused tree scatter `5916360ea`) and none on CPU (SYNC-3: "CPU decode runs K == 1, where it is fused on no backend").
- No replay path exists in v10 `ffc1bac82` or C17 `ed5d94969`. Searched: grep of `ggml/src/ggml-cuda/gated_delta_net.cu`, `src/llama-memory-recurrent.cpp`, `src/models/delta-net-base.cpp`. Our kernel has `TAG_GDN_STATE_BF16`, one warp per column, and no `gdn_cols_per_warp`/mma chunked file. The PR does not apply cleanly.
- Rollback safety: C17 refuses a rollback after a cell swap (`c7435cc77`). Under replay that rollback would succeed. How often C17 refuses at np4 is unknown and would add a replay benefit beyond bandwidth.
- KPF-RS-1 (kv-cache-program.md:840 @ ac1347f) already asks for tests that "an unwritten slot cannot leak another sequence" at np=4. That is the v10 exposure above.
- Adversarial: ReplaySSM (arXiv 2610.13778, NVIDIA + Dao lab) is the published origin of the idea. Per its NVIDIA blog and paper summaries, it gives 1.85-2.10x spec throughput on 120B-class models and **no speedup at batch size 1**. That independently corroborates the PR's flat np1 numbers and growing batched gains (restatement of a secondary write-up). No failed reproduction was found. Counter-evidence inside the PR: SYCL prefill +4.26% slower with checkpoints; ServeurpersoCom +1.7% prefill slower on 4k; A3B −3.2% at 2 seqs. A web search for `LLAMA_RS_REPLAY` found nothing beyond the PR (the PR is 17 days old).
