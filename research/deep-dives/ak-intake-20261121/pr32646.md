## What the diff actually does (principles)

1. **Repack layout.** `block<1,8>` = 8 x fp16 d + 128 B qs, interleaved in 8 B chunks: row0 bytes 0-7, row1 bytes 0-7, ..., row7 bytes 0-7, then row0 bytes 8-15, and so on. One Q1_0 block (128 weights) covers four Q8_0 sub-blocks of 32. For sub-block b, the kernel loads the 64 B half `(b%4/2)*64`. `_mm256_srl_epi64` by `(b%2)*32` moves the right 4 bytes of each row's 8 B chunk to the low half. Each weight byte is therefore loaded twice, once for each of two sub-blocks. That is wasted load and shift work, not wasted DRAM bandwidth.
2. **1-bit to int8 expand.** AVX2: `vpshufb` repeats byte g of each row 8 times, `vpand` with the mask 0x8040201008040201, `vpcmpeqb` against zero, then `vpor` with 1, giving +1/-1. AVX-512: `vpshufb` (zmm) and `vptestmb` produce a k-mask directly, then `vpblendmb(k, -1, +1)`. This is the only Q1_0-specific part of the kernel.
3. **AVX-512 GEMM tile.** 16 activation rows (4 x `block_q8_0x4`) by 16 output columns (2 x `block_q1_0x8`), 16 zmm fp32 accumulators. The weights are re-laid out with `vpermd`/`vpblendd`/`vinserti32x8` into 014589CD and 2367ABEF groups. Two shuffle patterns (`_mm512_shuffle_epi32` 136/221 on weights, 160/245 on activations) pair 4-byte groups for the dot product. That goes through `mul_sum_i8_pairs_acc_int32x16`, which in our fork is `vpabsb` + `vpmovb2m`/masked `vpsubb` (sign transfer) + **`vpdpbusd`** under `__AVX512VNNI__` (`arch/x86/repack.cpp:120-142 @ffc1bac`). Then come mask-blend `0xCCCC` transposes, fp16-to-fp32 scale loads, and `vfmadd`. There is no `vpermb`/VBMI and no `vpdpbssd`.
4. **Redundant multiply.** The weights are +/-1. The kernel builds +/-1 bytes and then runs the abs/sign/`vpdpbusd` sequence on them. That spends three ops to apply a sign that the k-mask already holds: `vpdpbusd` against ones of a masked `vpsubb(y)` would do the same job. Our fork's AVX2 `vec_dot_q1_0_q8_0` already uses the cheaper form (xor/sub to conditionally negate the activations). The PR's GEMM is not an optimal 1-bit kernel. It is a structural clone of the existing Q4_0 template with the nibble lookup swapped for a bit expand.
5. **GEMV.** AVX2 only: one `block_q8_0` per step, 8 columns. The 1-bit expand is the same as in the GEMM, with `vpblendd`/`vpshufd` pairing and `mul_sum_i8_pairs_acc_int32x8` (`vpdpbusd` ymm under AVX512VNNI+VL, else maddubs). The AVX-512 GEMM block is guarded by `__AVX512BW__ && __AVX512DQ__`. The dispatcher returns `q1_0_8x8_q8_0` whenever `ggml_cpu_has_avx2()` holds and `ne[1] % 8 == 0`.
6. **Why tg regresses (inferred, the PR has no profile).** tg128 is M=1, so it takes the GEMV path. That path is AVX2-only even on an AVX-512 host. It re-loads and shifts every weight byte twice and adds blend/shuffle pairing on top of the same expand the base vec_dot does. It reads no fewer bytes. On the 9600X, 989.6 MiB x 35.8 t/s is about 37 GB/s at 6 threads, below what dual-channel DDR5 delivers, so tg here is partly instruction-bound and the extra per-byte work shows up as -1.3 to -1.4%. That is consistent with the code, but unproven.

## Grounding against current EPYC state (lane @ ac1347f)

- **Fork x86 repack @ffc1bac** (`ggml/src/ggml-cpu/repack.cpp:4598-4745`, `arch/x86/repack.cpp`): x86 repack exists for Q4_0, Q4_K, Q2_K (AVX-512), IQ4_NL and MXFP4, all 8x8. Q8_0, Q5_K and Q6_K have NEON/RVV repack only, and Q1_0 has none (`grep q1_0 repack.cpp` = 0 hits). The IQ4_NL GEMM already uses the same AVX-512 16x16 tile; its GEMV is AVX2 ymm (`gemv_q4_b32_8x8_q8_0_lut_avx`, `:522`). **The PR has nothing for IQ4_NL or Q8_0 that our tree lacks.** What it adds is a Q1_0 instance of an existing template.
- **Production routing:** under `GGML_IQK=1`, Q8_0, Q4_0, the K-quants, IQ2/IQ3 and IQ4_XS return nullptr from the repack selector, so iqk handles them (`repack.cpp:4535-4552 @ffc1bac`). IQ4_NL is not on that list, so it does use `iq4_nl_8x8` repack. That is the path that went NaN under the v10 fused decode (`handoffs/active/quantization-and-low-bit.md:691 @ ac1347f`). Consequence: an x86 Q8_0 repack kernel (K27) is bypassed in production unless it beats iqk's Q8_0 and is taken off the iqk list.
- **K27** (`quantization-and-low-bit.md:305 @ ac1347f`): "Q8_0 still lacks a promotable optimized x86 interleave kernel ... any future Q8_0 work must be a real AVX2/AVX512/VNNI implementation". The PR's GEMM is the fork's existing Q4_0 AVX-512 template, which is also the natural starting point for K27 (Q8_0 needs no expand, just a 32 B int8 load per row pair). The PR is evidence for that template, not a new design.
- **NEW-6(f)** (`quantization-and-low-bit.md:291-301 @ ac1347f`): all iqk kernels are ymm. The k-mask bit-expand idiom is a small concrete input for any zmm variant.
- **Bonsai / Q1_0** (`quantization-and-low-bit.md:794-800 @ ac1347f`): STEERING 2026-07-19 deprioritised Bonsai-8B/27B Q1_0 as quality-blocked ("Q1_0 6/8 instruction-format"). It may be reopened only on a specific quality path, so Q1_0 speed work has no consumer.
- **Search scope:** the lane handoffs `quantization-and-low-bit.md` and `autokernel-akx-program.md` (grep K27, IQ4NL, IQ4_NL, "Q8_0 interleave", zmm), plus the fork files named above.
