## Mechanism from the diff
- **How the rows are passed.** `KV_rows_ptr` was already a kernel argument (from #29510; unused by vec until now). It is indexed per sequence as `KV_rows_ptr + sequence*ne11`. The vec case detects the row list as `dst->src[5]` and asserts `Q->ne[1]==1 && softcap==0`. With kv_rows, the K/V base pointers stop advancing per block (`K_step = 0`). Only the mask pointer strides.
- **Row ownership.** Per outer iteration, each lane loads one int: `row_lane = max(KV_rows[k_VKQ_0 + threadIdx.y*WARP_SIZE + threadIdx.x], 0)`. Negative padding rows clamp to 0 and are killed by the -inf mask. So one block (nthreads 128 = 4 logical warps × 32) covers 128 KV columns per iteration and each warp covers 32. The list load is coalesced.
- **Shuffle.** In the KQ loop, `K_i = K + shfl(row_lane, lane_KQ, WARP_SIZE)*nb11`. In the V loop, `V_k = V + shfl(row_lane, lane_V, WARP_SIZE)*nb21`. The shuffle width is WARP_SIZE (32), and there is one shuffle per KQ row step and per V column step. K/V stay quantized in place: no conversion, no gather.
- **Dispatch gate.** NVIDIA with Turing MMA and a mask; a non-F16 pair with a compiled vec instance (the default GGML_CUDA_FA_QUANTS compiles same-type pairs only); one query per slice; no softcap. The new tests cover f16/bf16/q8_0/q4_0, D256 GQA12 and D128 GQA4, at 1/3/8 slices.

## gfx90a assessment (wave64)
- In our tree `WARP_SIZE` is the logical 32 (`ggml/src/ggml-cuda/common.cuh:46`). The physical warp size is 64 on GFX9 (`ggml_cuda_get_physical_warp_size`, common.cuh:365-371). `__shfl_sync` maps to `__shfl(var, lane, width)` (`vendors/hip.h:36`), and with width 32 that is a ds_bpermute inside each half-wave. **The PR's shuffle works unchanged on wave64.** A 64-lane wave holds two logical warps (two `threadIdx.y` rows), so each wave owns 64 rows per iteration as two 32-row groups. A native width-64 version (one shuffle domain of 64 rows) is possible but not needed. Neither a 64-bit `__ballot` nor LDS is involved: the shuffle uses no LDS allocation.
- `ggml_cuda_shfl` does not exist in our tree (only the `__shfl_*_sync` macros), so a port is a one-line substitution. Port cost for the kernel: S.
- **Do we already have kv_rows?**
  - Production v10 (ffc1bac82) has NO kv_rows / `flash_attn_ext_rows`. A grep of ggml/src, ggml/include, src, common and tools finds only unrelated ggml-hexagon locals.
  - v10 serves -kvu with dense masked FA plus the fork's own dead-block skip (GGML_CUDA_FA_MASK_SKIP) and per-sequence vec layout (GGML_CUDA_FA_SEQ_ROWS), both in `fattn-common.cuh` around L1045-1066.
  - Champion C17 (`ed5d94969`) DOES carry kv_rows, as the in-house **UP-FAROWS-HIP gather form** (`ggml/src/ggml-cuda/fattn.cu:860-` @ ed5d94969). The listed rows are copied as raw bytes (any K/V type) into a compact multi-stream K/V and mask, then the unchanged kernel selection runs. GGML_CUDA_FA_ROWS_GATHER is default ON since C15. The list travels through a side-channel registry, not a graph edge.
  - **The PR's penalty (MMA converting the whole cache to F16, scaling with idle slots) has never existed for us.** v10 has no kv_rows path, and the C17 gather never converts the cache: on decode both the dense and gathered calls take VEC (C17 fattn.cu comment: "all 18 matching compares were decode calls where both took VEC").
  - What the PR's principle would still buy us is removing the gather copy: one extra read and one extra write of every listed row, plus the mask copy, per layer per step. That gain has not been measured.
- **Collision.** Upstream marks the row list as FA `src[5]`. In our fork, FA `src[5]/src[6]` already carry the H12/QSA top-k sparse-FA inputs (C17 fattn.cu:1054, "qsa top-k FA (src5/src6)"), and a src[7] graph edge for the list corrupted served output (UP-B12421-FAROWS-HIP-PORT r9/r10). Any port must use the side channel.
- BF16 K/V is excluded from VEC on AMD (`can_use_vector_kernel`, C17 fattn.cu ~L610), so the PR's bf16 win does not carry. q8_0 does.
- **G3 (static read, not an endpoint).** In C17 `ggml_cuda_get_best_fattn_kernel_ex`, hd256 f16/q8_0 with 2..16 query rows goes to GQA_VERIFY (H10) before any VEC branch. Plain n_q=1 decode, and one-row-per-sequence batches (`rows_are_seqs`), go to VEC. For KV types GQA_VERIFY rejects (for example q4_0), ≤2 rows take VEC (d1 verify) and larger verify batches take WMMA or TILE. So on q8_0 the served DFlash2/MTP verify should not land in VEC unless the GQA_VERIFY gates fail. Only the native G3 measurement can settle this.

## Zen 5 CPU
UP-B12421-FAROWS-BOUND already established that the CPU serving shape is non-unified, so row lists are moot there. The CPU FA already skips -inf mask entries (LSA-CPU-SPARSE note). The principle (index-list reads in place instead of convert/gather) carries to a CPU FA as one indirection per KV row, which is prefetchable with AVX-512 gathers or software prefetch. There is no consumer today. Port cost S, no consumer.
