## Code entropy of OUR production weights (dive-time measurement, read-only)

Zeroth-order entropy of the stored integer codes, measured with a numpy histogram over the first 32 MB of each tensor via `gguf-py` (script `scratchpad/code_entropy.py`). No inference was run.

| model / tensor class | type | H(code) | Huffman-ideal saving on block bytes |
|---|---|---|---|
| Q38FN UD-IQ4_XS `ffn_down_exps` (blk 0,1) | IQ4_NL | 3.907-3.911 of 4 bits | **2.0-2.1%** |
| Q38FN `attn_qkv`, `ffn_gate_shexp`, `ssm_out`, `ffn_down_exps`(blk2) | Q8_0 | 7.41-7.68 of 8 | 3.8-6.9% |
| Qwen3.8-27B Q8_0, blk 20 (attn_qkv, attn_gate, ffn_*, ssm_out) | Q8_0 | 7.67-7.69 of 8 | **3.7-3.8%** |
| reference: Qwen3-8B Q4_K_M blk 10 | Q4_K | 3.85-3.87 of 4 | 3.0-3.4% |

LazyWeights adds 1.2-2.1% coding overhead above entropy. The net lossless headroom on our weights is therefore about 0-5%, much smaller than the paper's shaped-code 6.2-20.7%. This matches the paper's own statement that "the saving of the coder is thus decided by the quantizer". IQ4_NL's non-uniform grid already spreads code usage, and Q8_0's per-32 absmax scaling fills the int8 range. IQ3_S and Q6_K were not measured.

## Key question: software interleaved-lane Huffman on spare Zen 5 cores (INF-70 / CPU-NT-WEIGHT-STREAM)

Inputs, all from the lane at ac1347f:
- The served Q38FN UD-IQ4_XS recipe streams 5.84 GB/token (dense 4.15 + routed 1.16 + lm_head 0.52). The dense path runs at 186-207 GB/s against a same-window read-sum of 265 GB/s on the half (`cpu-decode-roofline-program.md:316`).
- Weight streaming measured 160-163 GB/s at 48 threads, 62-63% of the 259.8 GB/s read-sum (`cpu-decode-roofline-program.md:320`; `autokernel-akx-program.md:1321`).
- Post-BIOS C0 read-sum 410.4 GB/s at t48 and 446.8 at t96 (`cpu-decode-roofline-program.md:418`).
- The older C5 token decomposition put 62.9 ms in weight nodes at 43% of read BW and 33.4 ms in non-weight nodes (`:393`, `:766-773`). Weight-path time is not proportional to bytes.

Estimate:
- **Bytes saved:** about 4.5% of the 4.15 GB dense path (mostly Q8_0), about 2% of routed, with lm_head Q6_K unmeasured. That is roughly 0.2-0.25 GB per eval, about 4% of 5.84 GB, or **about 1 ms per eval** at 190-200 GB/s, and only if the saving were free.
- **Decode cost:** the dense path is about 3.9 G Q8_0 symbols per eval. Across 48 cores that is about 81 M symbols per core per eval. Even an optimistic one symbol per cycle at about 4 GHz (multi-stream table decode; no AVX-512 Huffman per-core figure was found in search) is **about 20 ms per eval of added work**, spent to save about 1 ms. Per core, the GEMV already consumes about 3.4 GB/s, which would require decoding about 0.85 symbols per cycle in addition to the GEMV.
- **Spare cores cannot do it.** The Zen 5 L3 is CCD-private (32 MB). A producer on other cores would ship **decoded** (larger) bytes across Infinity Fabric to the GEMV cores, costing more fabric traffic than the DRAM bytes it saved. q3 is also reserved for MI210 host threads (memory: CPU rows off q3). Decode would have to be fused on the consuming core, where it is the 20x loss above.
- **Paper's own evidence agrees:** on the Orin GPU, which has far more ALU per byte than a CPU core, software decode is 2.5-3.2x slower per token.

**Verdict: decline. Software entropy decoding of weights cannot beat raw DRAM bytes on our CPU, by about 20x in cost against benefit.** This closes the lever, and it does not touch CPU-NT-WEIGHT-STREAM, which changes cache policy, not bytes.

**MI210:** MI210 has 1.6 TB/s HBM and about 22.6 TFLOPS FP32 vector, about 14 FLOP/B. The Orin Nano Super GPU has about 2 TFLOPS against 102 GB/s, about 20 FLOP/B. MI210 therefore has *less* ALU per byte than the platform where the paper measured a 2.5-3.2x slowdown from in-GEMV software decode. gfx90a has no fixed-function decompressor in the memory path. On wave64, 32 lanes per tile would map to half a wavefront, with per-lane variable-length state and divergent shifts. **Decline.**

**Entropy-aware GPTQ for IQ4_XS/Q6_K on 27B/A3B (no coder):** no gain. At fixed width the file size is identical, and Table VI shows the shaping (gamma=1) raises dPPL relative to llama.cpp's fit (gamma=0) at a given format. The only part that transfers without an entropy-coded runtime is GPTQ error feedback emitting GGUF, which the quant track already pursues through the IST-DASLab GSQ builds (NEW-11, `quantization-and-low-bit.md:669`). **Decline.** Capacity is not a constraint on the host: 12 x 96 GB DDR5 (`cpu-decode-roofline-program.md:387`).
