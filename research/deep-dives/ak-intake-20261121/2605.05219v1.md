## DP formulation and results
Setup: prefix of length N, checkpoints C={c_1..c_M}, overlap depth t ~ p_t; exact resume recomputes r(t)=t - max{c<=t} tokens. Theorem 1: uniform p or worst case -> balanced spacing, E[r]=N/(2(M+1))+O(1), worst ceil((N+1)/(M+1))-1. Theorem 2: exact DP O(NM) (convex hull trick; slopes -s monotone, query points P_j nondecreasing). Lemma 1 (|E_p - E_q| <= N||p-q||_1), Theorem 3 (plug-in error <= 2N(sqrt(N/n)+sqrt(2 log(1/delta)/n))), Theorem 4 (exponential histogram, gamma=0.99, re-solve every 10 requests). Results: DP-optimal beats balanced/block/sqrt/log at low budgets with concentrated overlap (system prompts: same runtime as block caching with fewer checkpoints); QuALITY has a spike near full document length so the gap to balanced is small. Block size clipped to 128 in theory runs, 64 in timing runs (FLA kernel granularity).

## Relation to llama.cpp server checkpoints (grounded)
- llama.cpp @ ffc1bac82: `n_ctx_checkpoints = 32` per slot (common/common.h:633; arg at common/arg.cpp:1522). Production flags use `--ctx-checkpoints 32 --cache-ram 32768` (harness-program.md:515) and `--cache-ram 65536` on :8083 with a planned raise to 102400 gated on an eviction window (harness-program.md:3070).
- Recurrent rollback is bounded by `n_rs_seq` (harness-program.md:2997 cites `src/llama-memory-recurrent.cpp:191-200`; kv-cache-program.md:733 tests n_rs_seq=0/8), so the 'deepest checkpoint <= t then exact suffix' structure is the server's native behavior; the paper adds only WHERE to place.
- Our trunk-then-private-suffix path already places a checkpoint at the shared boundary: `checkpoint_at=[len(trunk)]` (KPF-18.1, kv-cache-program.md:249; orchestrator sends it in the trunk-first path, :425). Per the paper, a single spike is exactly where one checkpoint is optimal. The open arm is the "dense every U tokens" policy control in KPF-18.2 item 5 (kv-cache-program.md:260).
- Sizes (App A Table 6): Qwen3.6-27B checkpoint 153,944,064 B (~147 MiB), Qwen3.5-4B 51.5 MB; 32 checkpoints on a 27B-class slot is ~4.7 GB, which is why --cache-ram must be sized.
- Marconi-style FLOP-aware eviction is already a dormant row (kv-cache-program.md:4152, trigger: KVU-12.1 unpinned-checkpoint churn). The paper explicitly says its DP is orthogonal to Marconi admission/eviction.
Verdict: a cheap config/policy change IS available (more `checkpoint_at` entries at turn boundaries and shared system-prompt lengths), but only worth doing if the measured overlap histogram is multimodal; the DP itself is a tiny offline planner.
