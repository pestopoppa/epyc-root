## Verdict
**dive-verified, with two corrections to how the bearing dives framed it.**

1. **ReplaySSM is not the origin of input-log replay.** Its own related-work section credits fused cached-input replay to *The Mamba in the Llama* (Wang et al. 2024a, intake-488) and to Snakes and Ladders "Activation Replay". It credits periodic checkpointing with input replay to the Nemotron 3 Ultra report.
2. **PR31669 is not mechanically ReplaySSM.** PR31669 replays the accepted prefix at the start of the next step and writes the committed state every step (1R+1W). That makes it the Mamba-in-the-Llama family minus one write. ReplaySSM makes "checkpoint + input ring" *the state representation*:
   - Non-flush steps read the checkpoint once and **write no state** (1R).
   - Verify computes outputs only, through a chunkwise UT-transform form, without materializing intermediate states.
   - The checkpoint is written once per L = 16 committed tokens.

   PR31669 never cites ReplaySSM (a text search of the PR and its diff finds zero hits).

The headline numbers are confirmed. They are all at serving batch (B = 256/512) on an H100 (4B models) or a power-capped B300 (120B-class NVFP4 models). At **B = 1, ReplaySSM is a slight loss or neutral**:
- e2e standard decode 0.96-0.99×
- SSM kernel 0.41-0.88×
- speculative decoding 0.87-1.17×

ReplaySSM is **not bit-exact**. It is exact only "up to floating-point differences": the released tests use rtol 1e-2 / atol 3e-2 (F32 activations), and even the "FP32" speed runs fold corrections that were stored in an FP16 record.

## What this settles for the bearing dives

- **Batch 1 vs batched verify.** ReplaySSM's gain is bandwidth recovered from state traffic. It appears only once the conventional SSM kernel is memory-bound: from B ≈ 8 to 32 on standard decode, and at B ≥ 32 to 128 on spec. That corroborates the PR31669 flat np1 numbers.
  - On our 27B DFlash2 np1 round (51.6 ms), what ReplaySSM adds beyond PR31669 is the per-step committed-state write. That is 48 × 3 MiB ≈ 151 MB, about 0.12 ms, paid on about 70% of steps (a flush every ~L/a ≈ 16/4.65 ≈ 3.4 steps). It comes to **≈0.08 ms/step/seq, ≈0.16% of the round** (our arithmetic). Most of the np1 value is already in pr31669-A1. The extra matters only at np ≥ 4.
- **Logged inputs in bf16/f16?**
  - *For greedy identity gates, no.* The llama.cpp GDN op inputs (k, v, g, beta) are F32 tensors. A replay from rounded copies uses different operands than the original forward, so the replayed state differs from the snapshot state, and an identity gate will see near-tie flips.
  - Bit-identity needs **F32 raw-input logs replayed in the same per-token order with the same `expf`**: PR31669's design (commit f7e2441, per the pr31669 dive).
  - ReplaySSM itself gives up bit-identity in three ways: FP16 u records, output-only/chunkwise evaluation order, and tensor-core `tl.dot` over the ring (`b_d_scaled_tc` is cast to the element type before the dot).
  - The footprint argument for F16 is also weak in the spec-rollback use. An F32 log is ~12.4 MiB per sequence (27B, n_pend 8) against the 151 MB state.
  - F16/BF16 logging is worth it only for FR-style ≤1024-token cross-request windows (1.55 MiB/token in F32). There, a KLD gate, not greedy identity, would be required.
- **Low-precision state, our `GGML_CUDA_GDN_STATE_BF16`.** Our knob stores the state with `__float2bfloat16` (round-to-nearest, `gated_delta_net.cu:17-20 @ ed5d94969`) and reads it back into the recurrence every step. In ReplaySSM's taxonomy that is a **shared checkpoint at L = 1 with RTN, the worst cell**:
  - On GDN, RTN drives FP8/NVFP4 state non-finite by 64K-128K tokens while SR stays finite.
  - FP16-RTN stays within 2.3× of SR KL on GDN.
  - BF16 (7 mantissa bits vs FP16's 10) is not tested.

  The knob is OFF everywhere. Its speed leg closed neutral (+0.74% decode, −0.77% prompt; rocm-kernel-authoring.md:2739-2743). B3 already requires a ≥20K greedy coherence gate before enabling it (kernel-champion-and-promotion.md:1792). The new information is that **SR, not RTN, is the right rounding for a state that feeds back**, and that the long-generation risk is real on GDN.
- **GPU kernel design.**
  - The released GDN decode kernel uses grid `(cdiv(V, BV), B, HV)` with BV = 64 rows per program. K is tiled (BKT ≥ 16) so that `tl.dot` runs on tensor cores and the program never holds a full [BV, BK] tile. The ring of cached (u, k) records is read per step.
  - The verify path is App. B.3: one T×T unit-triangular solve (the UT transform), then Eq. 11. That is **the same algebra as our C8-6 chunked WY kernel** (`T = (I + A)^-1`, chunk 64, fp32 MFMA; `gated_delta_net.cu:23-42 @ ed5d94969`) with S0 = checkpoint and the chunk = [committed ring ; drafts] (≤ 16 + 8 = 24 ≤ 64).
  - Tiling pads T to a multiple of 4 (T = 6 pays for 8).
  - CUDA graphs are handled by a per-row flush flag as device data plus a device-side commit kernel, so there is no host sync. This matches our "topology independent of accept" principle.
  - **Caution (App. A):** serial recurrences that hold the state tile in registers for T or 2T−1 steps "limit occupancy and leave most of the DRAM bandwidth idle". At B = 256, Mamba-in-the-Llama and STree move 1.6-2.9× fewer bytes than vLLM snapshots yet are not faster. PR31669's in-register replay loop is that shape, so its gate must time kernels, not only count bytes.

## Grounding vs current EPYC state

- The **ReplaySSM name is already in-house.** The fork's tree op is documented as "ReplaySSM 'record mode'" (`ggml.h:2707 @ ed5d94969`; speculative-decoding.md:1908). SGLang's ReplaySSM GDN commit routing is intake-2752's sibling entry ("SGLang PR 35725"), and the K28 probe of `bench_gdn_replayssm_fold.py` on gfx90a is at research/intake_index.yaml:69087. That "record mode" keeps K = n_tokens snapshot slots and selects by slot. **It is the vLLM-snapshot scheme, not ReplaySSM.** Only the name was borrowed.
- No ring / output-only verify path exists in C17. Searched: `ggml/src/ggml-cuda/gated_delta_net.cu`, `ggml/include/ggml.h` (GDN ops) @ `ed5d94969`.
- BF16 state: OFF everywhere; speed neutral; B3 coherence gate prepared but unpublished (kernel-champion-and-promotion.md:1792; rocm-kernel-authoring.md:2739-2743). No SR variant exists (`gdn_store<nv_bfloat16>` = `__float2bfloat16`).
- Bit-identity gates: AK-DTREE-2d r7 failed its oracle gate at 1.59% vs 0.78% (speculative-decoding.md:1916). Any ReplaySSM-style output-only verify would add fp-order differences on top, so it must be gated by KLD / oracle-rate rather than token identity.

## Adversarial pass (2 searches)
- "ReplaySSM … criticism batch size 1": only the NVIDIA dev blog, the tridao.me blog and secondary summaries, which restate the 1.85-2.10× and "up to 1.48×" figures. There is no independent replication, no failed reproduction and no criticism. vLLM docs carry a `replayssm_utils` page, consistent with App. G's adoption claim (restatement).
- Internal caveats the paper itself states:
  - The B = 512 e2e gains are power-cap inflated.
  - The 120B-class KL floors are ~2 orders above the 4B floors, at the same level as the eager-vs-graph FP32 difference.
  - GPQA one-cell SE is 2.5-3 pt.
  - A shared NVFP4 checkpoint loses 13 pt GPQA, mostly through truncation.
  - RULER-128K is unaffected, because quantization applies only to decode.
- Against PR31669: App. A finds fused register-resident replay (Mamba in the Llama) no faster than snapshots at B = 256. PR31669 reports +28-34% at 16-32 seqs on an RTX PRO 6000. The settings differ (batch ≤32, GDN, memory-capped snapshots). It is a reason to time, not to doubt.
