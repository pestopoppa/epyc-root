## 2. Key claims
0. **mul_mat_id aborts once a ubatch has more than smpbo/4 tokens (25344 on GB10 and other ~99 KB GPUs)** — CONFIRMED. Quote below. Arithmetic: 25344 x 4 B = 101376 B = 99 KiB. The source says "GB10" (the steering text omitted the device).
1. **PR adds a pre-pass plus chunked compaction of expert ids** — CONFIRMED. The pre-pass counts columns of lower experts ("nex_prev") first; then tokens are compacted and flushed in chunks of `store_cap = min(n_tokens, smpbo/4)`; the kernel is templated on `chunked`, and the single-pass path "is unchanged".
2. **66000-token test cases** — CONFIRMED: `test_mul_mat_id(Q4_0/F16, F32, 4 experts, n_used in {2,3}, broadcast on/off, 32, 66000, 256)`, 6 cases; n_used 3 uses the generic kernel, broadcast covers the dedup inverse-map path.
3. **CUDA source shared by HIP; gfx90a limit is lower** — PARTIAL. mmid.cu is compiled for HIP, and in-house HIP sets `smpbo = prop.sharedMemPerBlock` (ggml-cuda.cu:360 @ 98ff8a42a, HIP branch; the `sharedMemPerBlockOptin` assignments at :380/:387 are the MUSA and NVIDIA branches). On gfx90a that is the 64 KiB LDS per workgroup, so smpbo/4 = 65536/4 = **16384 tokens** (the 64 KiB figure is the brief's hardware fact, `(uncited)` for the HIP property value). PR is only tested on SM80 (CMP 170HX) and the author's NVIDIA hardware; no HIP evidence in source.
4. **Independent replication** — CONFIRMED but narrow: mercant1982 reports all six 66000-token MUL_MAT_ID cases abort at the expected assert with only mmid.cu reverted and pass 6/6 with the fix, "No model weights or inference/performance claim".
5. **Relation to #32505** — CONFIRMED as distinct: a reviewer asks whether #32505 fixes the same issue; the author answers it is a separate issue. (#32505 is already in the intake index.)

## 4. Performance-principles table
| principle | MI210 gfx90a | Zen 5 EPYC |
|---|---|---|
| Chunked compaction of expert ids (fixed store_cap tokens in shared memory, pre-pass for per-expert offset) instead of one store of n_tokens | YES: LDS is a hard 64 KiB with no opt-in raise, so chunking is the only way to remove the 16384-token ceiling; cost = one extra scan of the ids per expert block plus ceil(n/16384) flush rounds, and the per-expert blocks are one wave64 each (launch uses warp_size threads), so the added scan is the same order as the existing compaction scan | NO need: CPU mul_mat_id has no LDS-like cap |
| Template on `chunked` so the common path compiles to the old code | YES: avoids register/occupancy change on the fast path (matters on gfx90a VGPR budgets; ISA gate would catch a change) | N/A |
| Larger LDS instead of chunking | NO on gfx90a (fixed 64 KiB); only available on parts with opt-in (~99 KB on GB10/consumer NVIDIA) | N/A |
| Test with a size that forces the new path on every GPU (66000 tokens) | YES: 66000 x 4 B = 264 KB exceeds even 99 KB; on gfx90a the chunked path engages from 16385 tokens, so the same test covers it; expect the CPU-reference compare to dominate row time (lane lesson, kernel-champion-and-promotion.md:33) | PARTIAL: CPU path is the oracle only |
| ids stored as packed (token 22 bit, slot 10 bit) uint32 | YES already in-house (mmid.cu:5-20 @ 98ff8a42a) | N/A |

- CPU: `ggml-cpu.c:2083-2087` sizes `matrix_row_counts [n_as]` and `matrix_rows [n_as][ids->ne[0]*ids->ne[1]]` in the work buffer (host RAM); no shared-memory cap, no abort at ubatch 16385+.
