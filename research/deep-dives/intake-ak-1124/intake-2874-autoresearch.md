## 2. Key claims
0. **Folding is best in all six model x benchmark settings, up to +19.2% over recency truncation — CONFIRMED, narrowed.** Table 1: folding is the top row in every column. The 19.2% is a relative gain in KernelBench geometric-mean speedup, gpt-6-luna (1.46 -> 1.74); on MLE-Bench the maximum is +7.9% (gpt-oss-120b, 70.5 -> 76.1); mean +8.6%. Baseline is recency truncation, not "no memory". Anchor 0.
1. **Definition of folding — CONFIRMED.** Every attempt a_i is mapped by a summarizer to a short digest (2-4 sentences: action, outcome, root error or bottleneck, change vs prior context); each iteration the coder sees all digests (catalog) plus a subset U_t the agent chose to unfold (full code, reasoning, score, terminal output), admitted by priority until the history budget B_H is hit. Nothing is deleted; every attempt stays addressable. Compaction (running summary + tail) loses individual attempts. Context budget B = 32,000 tokens for the whole prompt. Measured: folding keeps records of 42.0 past attempts at ~12.1k tokens vs 6.2 attempts at 18.4k for recency truncation (Sec 5.1, Fig 3a); later-stage new-best rate 12.0% vs 10.2% baseline vs 9.7% compaction. Anchors 1, 2.
2. **Deletion beats merging and promotion — PARTIAL.** Average relative gain 4.1% (deletion) vs 3.0% (promotion) vs 2.2% (merging). But per cell the ordering is not stable and margins are tiny: MLE-Bench gpt-6-sol promotion 94.3 > deletion 94.1; gpt-oss-120b 73.8 / 73.7 / 73.6; KernelBench gpt-oss-120b 1.25 vs 1.24 vs 1.22; gpt-6-luna merging 1.47 < promotion 1.48 < deletion 1.54. NO seeds, repeats, standard deviations or confidence intervals are reported anywhere (searched page.txt: no "standard deviation" for results, no "independent run", no "significan*"), so the skill-manager ranking is one realisation per cell. Only the direction "managing a library beats an unmanaged library" (all 18 cells improve) is safe; the winner among managers is not established. Anchor 3.
3. **How "persistently unused" is measured and the deletion rule — CONFIRMED (details).** u_k(t) = number of CONSECUTIVE iterations skill k was not selected by the skill picker (an LLM retrieval step reading title/description/applicability trigger vs current symptoms); tau_d = 5; a skill is removed after five consecutive iterations without selection. Eq. (5) as printed, {k in L_t : u_k(t) < tau_d}, is the KEEP set (a typesetting inversion; the prose is authoritative). Deletion touches only the live catalog, not history or standing rules. Libraries are task-local and reset per task (no cross-task transfer; the authors list this as a limitation). Effect on size: 31 live skills at end of a MLE-Bench gpt-oss-120b run vs 312 unmanaged vs 330 promotion. The relevance signal is the picker's own selection, so deletion also encodes the backbone's retrieval habit: gpt-oss-120b picks 6.4-7.1 skills/prompt, gpt-6-luna 1.2-1.9, gpt-6-sol 0.5-0.6, and gains from management shrink accordingly (5.1% / 1.9% / 2.1% mean over the three mechanisms). Anchors 4, 5.
4. **MLEvolver 72.7% medal rate on MLE-Bench Lite and 94% fast_1 on KernelBench L3 — CONFIRMED numerically, NOT comparable to AK.** 72.7% = 16/22; 94% = 47/50 (gpt-6-sol, 32K window, 100 iterations; AIDE and OpenEvolve under the same budget; relative gain 20.5% over AIDE on fast_1). KernelBench protocol: CUDA kernels for PyTorch programs, speedup vs PyTorch Eager, median latency, NVIDIA GH200 144G HBM3e, CUDA 12.8; 50-problem stratified subset (20 L1, 20 L2, 10 L3; 12 of 250 problems excluded as degenerate/algebraically reducible/no reference timing); fast_1 only requires a correct kernel faster than eager (>1x). AK differs on every axis: edits an existing in-tree HIP/CPU kernel of a frozen llama.cpp champion, baseline is the previous champion not eager PyTorch, gated by e2e identity bands and speculative-decoding serving rows, device MI210 gfx90a/EPYC 9655. A "94% beat eager" number says nothing about beating C21. Anchors 6, 7.
5. **Limitations the authors state — CONFIRMED.** Linear sequential loops only (parallel search unexplored), interactive coding agents not evaluated, task-local libraries only. Anchor 8.

## 3. Reported results (as stated)
- Table 1 (MLE-Bench GNS, 10 competitions, 100 iterations; KernelBench GM speedup over PyTorch Eager, 50 problems, 50 iterations; backbones gpt-oss-120b / gpt-6-luna / gpt-6-sol): Baseline 70.5 / 86.1 / 93.2 and 1.17 / 1.46 / 2.16. Folding 76.1 / 89.7 / 94.7 and 1.29 / 1.74 / 2.34 (avg +8.6%). Compaction avg +0.3%. Deletion 73.8 / 87.6 / 94.1 and 1.25 / 1.54 / 2.26 (avg +4.1%). Merging avg +2.2%. Promotion avg +3.0%.
- Unmanaged skill library vs No-Skill: +2.1% average.
- Fig 5/6: MLEvolver 98.1 GNS at iteration 100 on MLE-Bench Lite (AIDE 1.4% lower, OpenEvolve 2.6% lower); KernelBench L3 GM speedup 2.67x -> 2.99x between iterations 50 and 100 (AIDE 1.85x, OpenEvolve 1.41x final); any-medal 72.7%, gold 10 medals; fast_2 31 of 50.
- Context-window ablation (Appendix D, gpt-6-luna, MLEvolver): 32K -> 128K raises any-medal 59.1 -> 63.6%, KernelBench fast_1 72.0 -> 78.0%.
- Merging failure case (Appendix E.3.1): after merging, a skill lost its FP32 requirement and a specific parenthesis fix; the same syntax error recurred. Promotion failure case: a promoted rule about fusing ReLU+HardSwish stayed in every prompt after the kernel structure changed.

## 4. Performance-principles table (mechanism and cost model)
| Principle | MI210 gfx90a | Zen 5 EPYC 9655 | Reason |
|---|---|---|---|
| Digest catalog + on-demand unfold of full records | YES | YES | Pure harness (planner prompt) change; device-independent. AK already has the directory-as-prompt-index variant (`loop/actor_context.py`, lossless, per-call dir). Cost model: prompt tokens at the planner role (27B-class) drop from inline to index, extra tool calls to unfold. |
| Deletion after N unselected iterations | PARTIAL | PARTIAL | Works for situational prose lessons whose use is an LLM selection event. AK negatives are consumed by a deterministic gate (`controller/do_not_repeat.py`), where a closed mechanism is by construction NOT re-proposed, so "unused" is the success state; deleting on that signal would reopen closed mechanisms. |
| Promotion to standing rules | PARTIAL | PARTIAL | Paper shows rules outliving applicability; AK already scopes by epoch (stale marking) which addresses exactly that failure. |
| Merging | NO (for negatives) | NO | Loses applicability conditions (paper's own case studies); AK negatives carry receipts per mechanism and must stay separable. |
| Offensive/defensive skill split | YES | YES | Cheap classifier (7 fixed title rules, no model, App E.1); maps to AK "negatives" (defensive) vs "hypotheses" (offensive). Paper: stronger models read fewer, more defensive skills. |

## 8. Contradiction / adversarial pass
- No variance/seed information; the manager ranking rests on gaps as small as 0.1 GNS and 0.01x. The word "consistently" in the source covers direction only.
- Deletion's signal is the backbone's own selection; for gpt-6-sol (0.5-0.6 skills/prompt) it fires on nearly everything, yet its gain is only +1.0% / +4.6%. The paper itself ties gain to retrieval habit (Sec 5.3), so a different local planner (Qwen-class) would behave differently; the numbers are for GPT-family closed backbones plus gpt-oss-120b.
- Folding's advantage over compaction is partly a prompt-design confound: folding gets an extra LLM call per attempt (digest) plus an unfold-selection call each iteration; the paper reports context tokens but not total LLM calls or cost.
- Task-local libraries starting empty and seed solutions "deliberately weak" favour memory methods early (65.2% of KernelBench gain in the first half); AK works from a strong frozen champion.
- Restatements: none found (single source).
