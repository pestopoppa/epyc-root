1. **Design: quantizers take src1 type as a template parameter, but MMVF uses a runtime flag.** CONFIRMED. 2. **Dispatch before/after.** CONFIRMED (read from the diff plus the PR-head file). *Before* (PR base): in `ggml_cuda_mul_mat` the precheck `src1->type != GGML_TYPE_F32` sends any BF16 src1 to `ggml_cuda_mul_mat_cublas`, with dequantized weights. `ggml_cuda_mul_mat_id` hits `GGML_ASSERT(src1->type == GGML_TYPE_F32)` and aborts. *After*: the precheck admits F32 or BF16. The order is MMVF (if `ggml_cuda_should_use_mmvf`), then the transposed-vector MMVF (F32 src0 only), then MMF **only if src1 is F32**, then few-row MMQ / MMVQ, then MMQ, then FP8 cuBLASLt, then cuBLAS. So BF16 src1 with quantized weights stays on MMVQ/MMQ (quantized to Q8_1 from BF16). BF16 src1 with F16/BF16 weights past the MMVF cap goes to cuBLAS instead of MMF. In MUL_MAT_ID, the new helper `ggml_cuda_mul_mat_id_use_mmvf_float` sends float experts to MMVF on AMD (as before) and now also on NVIDIA when src1 is BF16, gated on even ne00 and a pair-aligned src0. Past 8 tokens, BF16 src1 with float experts on NVIDIA takes the sorted fallback. That path is host-synced (`ggml_cuda_mul_mat_id_needs_sync` true), so CUDA graphs are off for the graph. The reviewer flags this as a future cost, not a regression today. No route selects BLAS for BF16 src1 with quantized weights. Anchors: page "On master a BF16 src1 goes to cuBLAS with dequantized weights, and MUL_MAT_ID aborts.", "BF16 src1 + float experts (F16/BF16) on NVIDIA past 8 tokens goes to the sorted fallback.", "Plain MUL_MAT with F16 weights past MMVF goes to cuBLAS instead of MMF."; diff "// MMVF, MMVQ and MMQ also read a BF16 src1, MMF only an F32 src1".
3. **The bundled int32 overflow fix.** CONFIRMED, and PARTIAL as a fix. In `mul_mat_vec_f` (MMVF) the expert/channel offset `channel_x*stride_channel_x` was `int*int`. Both are `int` kernel parameters, so for a large expert tensor (more than 2^31 elements across experts) the product overflows before it is added to the `int64_t` sample offset. That makes a wrong src0 pointer on the existing F32-src1 path. The PR widens it to `int64_t(channel_x)*stride_channel_x` for `x` and for `gate_x`. The reviewer says this should land separately. The reviewer also notes the y offset (`channel_y*stride_channel_y`) and the dst offset (`channel_dst*stride_channel_dst`) are still `int*int`, and the diff confirms it. The y offset moved into `int64_t offset_y` with the product still `int*int`. Anchors: page "int64_t(channel_x)*stride_channel_x in MMVF fixes an existing int32 overflow on the F32 path for large expert tensors", "offset_y still does channel_y*stride_channel_y as int*int"; diff "int64_t offset_y = int64_t(sample_y)*stride_sample_y + channel_y*stride_channel_y;".
4. **HIP coverage on gfx90a.** PARTIAL: by code reading it compiles, but it is unverified. The PR claims "CPU, CUDA" and posts no AMD numbers or HIP CI evidence. It adds **no new `#ifdef GGML_USE_HIP`**. The only HIP-guarded file it touches, `fp8.cu`, is already excluded on HIP (`#if !defined(GGML_USE_HIP) && !defined(GGML_USE_MUSA) ...`), so the FP8 BF16 part never reaches gfx90a, and MI210 has no FP8 anyway. The rest uses `nv_bfloat16`/`nv_bfloat162`, which our HIP vendor header aliases to `__hip_bfloat16`/`__hip_bfloat162` (`vendors/hip.h:253-254 @ 98ff8a4`). It also uses `ggml_cuda_cast<float2>(nv_bfloat162)`, which already has a HIP branch built from `__low2bfloat16`/`__high2bfloat16` + `__bfloat162float` (`convert.cuh:44-47 @ 98ff8a4`). BF16→F32 widening is a 16-bit shift, so **no native BF16 ALU or bf16 dot is needed**; gfx90a lacking a native BF16 dot outside MFMA does not matter. The MUL_MAT_ID MMVF helper is AMD-inclusive. My judgement: the MMQ/MMVQ/MMVF BF16-src1 paths would compile and run on gfx90a, but they are untested there. 5. **CPU converts a BF16 src1 to vec_dot_type.** CONFIRMED. A new `ggml_cpu_bf16_to_vec_dot_type` widens directly when vec_dot_type is F32. Otherwise it converts BF16 to F32 in a 1024-float stack buffer (block-aligned chunks) and then calls the type's `from_float` (e.g., to Q8_0/Q8_K). `ggml_compute_forward_mul_mat` and `ggml_compute_forward_mul_mat_id` both gain the BF16 case (MUL_MAT_ID used to assert F32), and `supports_op` admits BF16 src1 for both ops. Side effect (reviewer point 6): with the Hadamard hint, a BF16 src1 is now rejected for every src0 type. Anchors: page "CPU converts a BF16 src1 to vec_dot_type."; diff "// converts n BF16 values (whole blocks of vec_dot_type) to vec_dot_type: widened directly to F32, otherwise via F32 in chunks", "GGML_ASSERT(src1->type == GGML_TYPE_F32 || src1->type == GGML_TYPE_BF16);".

It can change unrolling and register allocation, which the PR itself worries about for the quantizer ("a copy changes the register allocation"). The mechanism transfers (a shift, then `amax`, then int8). At served verify widths (ne11 2-16) the src1 bytes are tiny next to the weights. The in-house cost is launch count, not bytes (AK-BW-27B-ACTQUANT-FUSE: ~460 launches/verify at the ~4.5 us floor). Fusing the quantize into the producing rms_norm/add epilogue (already proposed there) is the bigger lever. | YES as the PR does it. It costs O(K·N) per matmul against O(M·K) weight bytes, so it is negligible at decode. |

## 5. In-house state (C21 `98ff8a4`)

- **The PR is absent and does not apply as-is.** C21 has no `ggml/src/ggml-cuda/mmq-few.cu`, no `quantize_launch_typed` / `y_bf16`, no `ggml_prec_get_src` (the #32135/#32387 stack), and no CPU BF16 "widen" path. C21's `ggml_compute_forward_mul_mat` casts src1 to `const float *` whenever `src1->type != vec_dot_type` (`ggml-cpu.c:1569-1610`), and CPU `supports_op` MUL_MAT admits only F32 or vec_dot_type src1 (`ggml-cpu.cpp:530-531`). The function signatures differ too (C21 `ggml_cuda_should_use_mmvf(type, cc, ne, nb, ne11)` vs PR `(src0, cc, warp_size, ne11)`).
- **HIP `ggml_cuda_mul_mat` with BF16 src1 at C21** (`ggml-cuda.cu:2041-2160`): the in-house Q8_MF_INPLACE/MMQ_Q8_INPLACE routes require F32 src1 (`mmq-q8-mf.cu:1270`). Then `CUBLAS_PRECHECK` (`ggml-cuda.cu:2075-2079`) sends any non-F32 src1 to hipBLAS, the same as upstream master before this PR. `ggml_cuda_mul_mat_id` asserts F32 src1 (`:2166`). Nothing served reaches either case, because no served graph feeds a BF16 activation into MUL_MAT.
- **DF2-11: the PR does not help.** The DF2-11 BF16 drafter is **BF16 WEIGHTS (src0) × F32 activations (src1)**, not a BF16 src1. Proof: the route-log `type=` field is `ggml_type_name(src0->type)` (`ggml-cuda.cu:2014-2038`), so `CUBLAS|bf16|8` / `MMVF|bf16|8` in `speculative-decoding.md:1994-2033 @ f74b175` (DF2-11-BF16-TRACE-PROF / DF2-11-BF16-FIX) name the weight type. At C21 a BF16 weight with F32 src1 on gfx90a routes like this:
  - ne11 ≤ 8: MMVF. `ggml_cuda_should_use_mmvf` BF16/AMD/`bf16_mma_hardware_available` returns `ne11 <= ggml_cuda_mmvf_cdna_max_ne11()`, and the C19 default is 8 (`mmvf.cu:789-798, :875`). So the DF2-11-BF16-FIX env arm is now the default on C21.
  - ne11 9-16: MMF refuses F16/BF16 on CDNA2 (`mmf.cu:171`). Q8_MF/WVSK/SKINNY/MMVQ/MMQ are quantized-only, so the call falls to hipBLAS/Tensile (the 144 GB/s path; only `CUBLAS|bf16|11`, 0.28 calls/tok, remained there in the fix row).
  - PR #32533 changes neither route for F32 src1. Its only effect on BF16-weight MMVF would be the per-load `y_bf16` branch (a cost risk, not a gain). For BF16 weights the PR does not touch MMF either ("MMF stays F32-only for now").
  - The DF2-11 levers stay as the handoff lists them: MMF for BF16 on CDNA2, or a BF16 small-M MFMA kernel. Both are unfiled because Q8_0 is the served drafter.
- **Bug present in C21**: MMVF int32 stride products at `mmvf.cu:47-49` and `:84 @ 98ff8a4` (identical to the PR's "before"). C21's AMD MMVF_MMID branch (`ggml-cuda.cu:2196-2201`) also lacks the even-ne00 / pair-alignment guard that the PR base and the PR's helper enforce ("MMVF reads src0 in pairs of values"). Both are latent on served shapes: our expert tensors are quantized and every dimension is even.
- Orchestrator: no relevant path (BF16 activations are a kernel-graph property; nothing to read in `/workspace/repos/epyc-orchestrator`).

## 8. Contradiction / adversarial pass

- **No master-vs-PR control for F32 src1.** The reviewer explicitly asks for MMVF F32-src1 numbers, master vs PR, at 1-8 tokens with F16/BF16 weights. The posted table cannot show whether the runtime `y_bf16` branch slows the default F32 path. The steering's framing of the -8.4%/-4.8%/-12.8% numbers as "gains" is narrowed: they are BF16-vs-F32 src1 on the same branch, an op microbenchmark on RTX 5090, and they exclude the cost of producing BF16 activations.
- **Performance cliffs it creates.** BF16 src1 with F16/BF16 experts past 8 tokens on NVIDIA lands on the host-synced sorted fallback with CUDA graphs off. Plain MUL_MAT with F16 weights past MMVF goes to cuBLAS instead of MMF. The reviewer calls this not a regression today, but whatever starts emitting BF16 activations would need the MMF follow-up first.
- **Bundled, unrelated behaviour changes.** These are the int32 overflow fix; `tiled.cpp` `return true` → `break`, which makes a previously dead src1 type check reachable and changes F16-src1 behaviour; the MUSA QY2 Q2_K MUL_MAT_ID rejection no longer requiring F32 b; and the CPU Hadamard-hint rejection of BF16 src1 for every src0 type. The reviewer asks for these to be split out.
- **The overflow fix is incomplete.** The y and dst channel products are still int*int (diff confirms: `offset_y` keeps `channel_y*stride_channel_y`).
- **Test coverage gap.** Every new BF16 test uses a contiguous src1. The new `nb1x/nb10` stride arithmetic (FP8 used to hardcode `sizeof(float)`) has no permuted or row-strided case.
- No failed reproductions, no corroborating independent benchmarks, and no blog restatements were found.
