# MGMem: mention-graph retrieval for long-term dialogue memory question answering

[Primary source](https://github.com/junhong-h/MGMem) · intake-3024 · 2026-11-27

The release provides a LoCoMo single-conversation fresh-index CLI with en_core_web_trf and progressive mentions, topic segmentation (utterance units, window 3, threshold 1.10 times mean, min peak distance 3, min segment units 2), all-MiniLM-L6-v2 for embedding, 8 workers default, and lexical backfill. The CLI does not create a generative client for default spaCy indexing. Its evaluation reconstructs extraction flags from artifact metadata and disables speaker injection on the query side, with top-5 bridge nodes, up to 3 ego candidates, 0.45 similarity floor, square-root IDF and turn-max dense tie-break by default. Significant public release drift: the parser takes the first ranked extracted mention as subject, whereas paper §3.4 states nsubj/nsubjpass or known speaker aliases. The release also bridges exact hits on short queries by default (two mentions or fewer), while paper §3.4 says Stage 2 visits unresolved mentions. NumPy builds and normalizes a full graph embedding matrix per query and computes all-pool similarities before applying subject-local priority, so ego conditioning is a ranking mechanism here, without an all-pool compute shortcut. The public evaluator invokes LoCoMo loading at entrypoint and shares a client between reader and judge with qwen3-4b default; the paper uses distinct GPT-4o-mini and Qwen2.5-32B. LongMemEval loaders/batch helpers are present, without a tracked matched CLI/experiment bundle. Release trials are packaging checks and explicitly did not rerun benchmark evaluation. Paper Appendix A attributes reported index phase times (16.30s init, 37.67s segmentation, 85.66s extraction, 55.57s normalization/backfill/graph/embedding, 2.40s serialization) and 3.332 ± 0.186 GiB RSS to separate trials, absent from tracked release. Public CLI calls segmentation before prebuilding extraction and again inside build_index, and has no wall-time clock for that CLI. spaCy extraction reports None latency then query parser maps it to 0.0, so stage parse JSONL cannot attest parser wall time. Release persists separate fresh index artifacts with no default overwrite, raw turns and IDs inside episodes, occurrences linked to episode plus surface and source class. No explicit turn ID or byte span is carried in serialized MentionOccurrence, even though extractor has turn ID and text. Reverse backfill is a full pool × episode scan and sorts equal-length strings sourced from a set by length only, so cross-process byte determinism should be tested separately from stable ranking.

Read full README, build and evaluation entrypoints, both packaging-trial manifests and outcomes, parser, selected resolver/extraction/configuration, builder, benchmark stage, and serializer paths. Remaining modules and tests were not exhaustively read. Static assessment only. Remote HEAD and fetched raw text match the October 19 release commit.

## Scope and local transfer

The tracked release can demonstrate the architecture and data contract. It does not reproduce the paper’s exact parser/resolver and published matched metrics out of the box. Derived source provenance in the release is episode-level. An exact cited turn/span must be located in the raw episode or recorded separately. Instrument component/full wall time explicitly. A stored 0.0 parse latency represents a missing measurement for spaCy, and release elapsed_seconds=5.17 measures packaging checks.

Decision-changing local test: compare shipped BM25+EmbeddingGemma RRF against the same fixed episode window and reader token cap, with matched BM25+MiniLM or shared embeddings as attribution control only if needed. Baseline → exact-mention graph → paper-style dependency/alias-gated ego bridge; track first-mention heuristic as a labeled implementation control if it changes recall on a named slice. Held-out source episodes and chronological/all-gold exact evidence are required for multi-session/temporal. Start retrieval-only to avoid model-judge confounds. Capture stage wall, RSS, query p50/p95, exact provenance, sizes and refreshed append/rebuild cost with raw IDs and parser/weights hashes. 9655 run retrieval/index first, compare to hybrid available in lane, consume a common CPU thread budget and two input sizes if scaling answers a real decision. MI210 optionally batch only parser/embeddings if their measured CPU component dominates or use it for the identical frozen reader in a follow-up after retrieval survives, with device/precision/queue competition measured. Avoid importing code until reuse/license terms and behavior are verified; project can implement the narrow comparison using its own primitives.

Current externalization and BEAM reader controls permit adding a raw-episode retriever without changing live memory writes. Add a CPU parser and incidence-postings arm returning original episode IDs and text at the same answer budget. Compare with lexical, raw/full-context and incumbent retrieval; include episode provenance, temporal errors and missed evidence.
