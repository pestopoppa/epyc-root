## intake-1119#record — Concurrency without Model Changes: Future-based Asynchronous Function Calling for LLMs (AsyncFC)

- **URL**: https://arxiv.org/abs/2605.15077

### Claims (as verified)

0. Execution-layer-only asynchronous function calling with no fine-tuning and no inference-server change
   - *narrowed*: PARTIAL. No fine-tuning and no inference-server change are TRUE, and function implementations are unmodified. But the tool schemas are rewritten and an await_future tool is injected (see claim_anchors), so the tool surface DOES change.
   - anchor `Section 3.1 — the schema rewrite that makes "no protocol change" overstated` @ arXiv:2605.15077v1: "automatically transforms function inputs in the schema to accept either concrete values or future identifiers"
1. LLMs have a NATIVE capability to thread symbolic future identifiers through subsequent call arguments
   - *overturned*: OVERTURNED AS STATED. The model does not reason over an unresolved future value; it emits an explicit await_future join whenever decoding depends on the result. The evidence offered for a native capability is an accuracy observation plus an explicit hypothesis that the behaviour arises from priors learned from software artifacts. No premature-dereference rate is measured.
   - anchor `Section 3.2 — the model BLOCKS rather than reasoning over the value` @ arXiv:2605.15077v1: "When further model decoding strictly depends on unintegrated function execution results, the model has no option but to emit an await_future call."
2. 1.26x speedup on BFCL v4 Web Search and 1.44x on SWE-bench Lite end-to-end
   - *narrowed*: CONFIRMED but baseline-sensitive and partly delay-manufactured. Against native parallel function calling the gain is 1.12x-1.17x, not 1.26x-1.44x, and several arms inject 5s or 10s per-function delays into functions the authors describe as having negligible latency.
3. Accuracy preserved, with all reported p_acc above 0.05
   - *narrowed*: The accuracy defence is a FAILURE TO REJECT at n=300, not a demonstration of equivalence. SWE-bench Lite drops 47.6 to 44.3, a 3.3pp fall.
4. Dependency safety is moved from the model to a dependency-aware scheduler over read and write sets
   - *unaffected*: CONFIRMED. The scheduler carries dependency safety, with a conservative no-annotation mode available.

### Dive corrections

- 2026-08-13 STAGE-2b COMBINED INGEST+DIVE (primary source read: arXiv:2605.15077v1, submitted 2026-05-14, the only version). THE CRUX QUESTION WAS ANSWERED AND IT DEFLATES THE HEADLINE: the model does NOT reason over an unresolved future value — when decoding strictly depends on an unintegrated result it emits an explicit await_future join and blocks (see claim_anchors). What it genuinely does is thread an opaque handle through subsequent call arguments, which is dataflow plumbing. The papers evidence for a native capability is an accuracy observation plus a stated hypothesis about priors learned from software corpora, and THE PREMATURE-DEREFERENCE AND HALLUCINATED-VALUE RATES ARE NEVER REPORTED — there is no error taxonomy and no limitations section. "NO PROTOCOL CHANGE" IS OVERSTATED: tool schemas are rewritten to accept future identifiers and a new await_future tool is injected into the tool list, so an adopter must build a schema-transform layer, an async executor, a dependency-aware scheduler with read/write-set annotations, and a turn-boundary integrator. GAINS ARE BASELINE-SENSITIVE: against native parallel function calling the speedup falls to 1.12x-1.17x, and several arms inject 5s or 10s per-function delays into functions the authors themselves describe as having negligible latency. ZERO OPEN-WEIGHT MODELS ARE TESTED, so the strongest and most EPYC-relevant version of the claim — that this works on models lacking native parallel function calling — is untested. No code, no licence, no availability statement.

DO NOT cite the speedups as transferable: several are produced by injected tool delays, and against native parallel function calling the gain is roughly 1.1x. DO NOT describe it as requiring no protocol change. DO NOT assume it works on open weights: none were tested.
