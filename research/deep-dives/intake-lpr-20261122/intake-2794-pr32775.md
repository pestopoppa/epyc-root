## 2. Key claims
1. "AVX-512F/BW/VL path using intrinsics; falls back to AVX2" — **CONFIRMED.** Guard `#if defined(__AVX512F__) && defined(__AVX512BW__) && defined(__AVX512VL__) && defined(__AVX2__)` ahead of the old `#elif`-style AVX2 branch. Anchors: page `Adds an AVX-512F/BW/VL path to iq2_s x q8_K vec_dot using intrinsics.`; diff `#if defined(__AVX512F__) && defined(__AVX512BW__) && defined(__AVX512VL__) && defined(__AVX2__)` (hunk `@@ -3167,7 +3167,68 @@ ggml_vec_dot_iq2_s_q8_K`).
2. How it works (what the PR actually changes) — the grid lookup is NOT a gather: eight scalar `iq2s_grid[qs[k] | ((qh[..] << s) & 0x300)]` loads feed `_mm512_set_epi64` (64 grid bytes = two 32-value groups per iteration, so the loop steps ib32 by 2). Signs: the 64-bit sign words are broadcast with `_mm512_shuffle_epi8` + AND with a bit mask, compared to a mask register, and q8 is conditionally negated with `_mm512_mask_sub_epi8` (xor -1, minus -1). Dot: `_mm512_maddubs_epi16(q2, q8s)` then `_mm512_madd_epi16(dot, sc16)` (no VNNI), scales via the existing `get_scale_shuffle_k4` pair inserted into a ZMM. Anchor: diff `const __m512i dot = _mm512_maddubs_epi16(q2, q8s);` and `sumi = _mm512_add_epi32(sumi, _mm512_madd_epi16(dot, sc16));`; lookups `iq2s_grid[qs[7] | ((qh[ib32+1] << 2) & 0x300)],`.
3. "255 -> 222 ns (1.15x), Xeon Platinum 8573C" — **PARTIAL.** Numbers match the PR body. Unit is ns per single vec_dot call over n=2816 (11 blocks), best of 5 x 200k iterations, cache-hot: 23.2 -> 20.2 ns/block. Gain is 33 ns per 11 blocks, a small compute-side win; no model-level or bandwidth-bound measurement. Anchors: page `master AVX2: 255 ns patched AVX-512: 222 ns speedup: 1.15x`; `test-quantize-fns passes on both builds.` is also in the page body.
4. "Should work on Zen 5" — **CONFIRMED as ISA, PERFORMANCE UNVERIFIED.** Needs only F/BW/VL (Zen 4 and 5 have them). Because this uses no gather, the gather-latency worry from the sibling PR does not apply; the cost is 8 scalar loads + 8 vector inserts per 64 grid bytes, which is exactly what the YMM iqk path also pays.

Intel Xeon Platinum 8573C, -march=native, n=2816 (11 blocks), best of 5 x 200k iterations: master AVX2 255 ns, patched AVX-512 222 ns, 1.15x. test-quantize-fns passes on both builds. AI usage disclosed (exploration, feedback, mechanical checks). Nothing else.

## 4. Performance principles
| Principle | MI210 gfx90a | Zen 5 |
|---|---|---|
| 512-bit width over 256-bit for the same dequant (2 groups per iteration) | NO as written: wave64 already gives 64 lanes; the analogue is per-lane work granularity, already tuned in HIP mmvq. | YES in principle: Zen 5 has the full 512-bit datapath (stated in the brief), so there is no double-pumping penalty. But decode is DRAM-bound; wider ALU does not move a bandwidth-bound row. |
| Scalar grid lookups into set_epi64 (avoid gather) | PARTIAL. GPU lane-local table loads are the native form; no gather concept. | YES, avoids vpgather microcode cost (the Zen gather latency claim is UNVERIFIED in source; the design simply sidesteps it). Same as iqk's IQ2_S path. |
| Sign apply via mask register + masked sub on q8 | PARTIAL. gfx90a has no mask registers; sign flip is done with xor/sub or `__vnegss4`-style per-lane ops. | YES, same as the ZMM sign step in our IQ3_S gather kernel (`_mm512_mask_sub_epi8`). |
| maddubs+madd instead of VNNI dpbusd | n/a | NO benefit: Zen 5 has VNNI, so the better form is vpdpbusd (iqk already uses it where HAVE_FANCY_SIMD). Using maddubs+madd costs extra uops. |
| Unified scale shuffle via inserted 256-bit halves | NO | PARTIAL. Reuses an existing helper; trivial. |
