## 2. Key claims
1. **Mechanism: madvise(MADV_HUGEPAGE), NOT MAP_HUGETLB** — CONFIRMED. `map_hugepage()` does `mmap(PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_ANONYMOUS)`, then `madvise(..., MADV_HUGEPAGE)` on the PMD-aligned subrange; no MAP_HUGETLB (no hugetlbfs reservation needed), so it relies on THP being "madvise" or "always" on the host. Page size read from `/sys/kernel/mm/transparent_hugepage/hpage_pmd_size`; if unreadable/0, or size < one huge page, fall back to the normal vector. Alignment: buffers shorter than two huge pages get one extra huge page of padding and are offset to a 2 MiB boundary; larger ones advise the aligned interior. madvise failure unmaps and returns null -> regular allocation. Anchor diff, locator `common/common.cpp map_hugepage`, quote `madvise(base + aligned_offset, advised_size, MADV_HUGEPAGE) != 0`. Anchor 2 (README): `Buffers between one and two huge pages reserve one extra huge page of virtual address space for alignment.`
2. **Env opt-in** — CONFIRMED: `LLAMA_SERVER_CACHE_HUGEPAGE=1` only (exact string "1"), default off, Linux only. Anchor diff, locator `tools/server/server-context.cpp`, quote `common_get_env("LLAMA_SERVER_CACHE_HUGEPAGE") == "1"`.
3. **H100 results** — CONFIRMED as reported (not verified independently); see §3. Anchor page, locator "GPU benchmark", quote `Mean server minor faults/request 256,074 3,488`.
4. **Causal story (fault reduction -> save latency -> TTFT tail)** — PARTIAL. Fault reduction is plausible (256,074 -> 3,488 minor faults/request, ~73x fewer) but the source does not show THP settings of the test host, does not separate the effect of THP from the effect of the other code in the PR (no-init allocator, `resize_for_overwrite`, mapping reuse), and states `TTFT P50 moved in opposite directions across the two pairs`. 5. **Bundled behaviour change (not THP): restore keeps buffers until BOTH target and draft are restored** — CONFIRMED in diff: `server_prompt_cache::load` no longer clears/shrinks the target buffer after restoring it, and a restore regression test is added. ## 4. Performance principles

## 5. In-house state
- **Host THP (read-only, measured today):** `/sys/kernel/mm/transparent_hugepage/enabled` = `[always] madvise never` (always selected); `defrag` = `[always] defer defer+madvise madvise never` shows `always` selected; `khugepaged/defrag` = 1; `hpage_pmd_size` = 2097152; `/proc/meminfo` AnonHugePages ~10.5 GB now. So `madvise(MADV_HUGEPAGE)` adds nothing to policy on this host: large anonymous `std::vector` allocations already get THP wherever a 2 MiB aligned range is touched, and direct compaction on fault (defrag=always) is enabled. With mode `madvise` or `never` the opt-in would matter (madvise: needed; never: no effect). Whether our 8-slot checkpoint buffers already show THP: UNVERIFIED (no /proc/PID/smaps read of a live server).
- **Champion eee3da8 save buffers:** `common_prompt_checkpoint::data_tgt/data_dft/data_spec` are plain `std::vector<uint8_t>` (`common/common.h:L1131-1136`; `common.cpp:L2189,L2207` `.resize(ckpt_size)`) and prompt-cache entries use `std::vector<uint8_t> state_data_tgt/dft` with `.resize(...)` (`tools/server/server-task.cpp` `server_prompt_cache::alloc`, ~L1687-1750). `resize()` value-initialises (zero-fills), so every byte is touched twice (zero then overwrite). Champion lacks `common_state_data`/`common_no_init_allocator` and `LLAMA_SERVER_CACHE_HUGEPAGE`: upstream change ABSENT.
- **Restore bug present in champion:** `server_prompt_cache::load` clears and shrinks the target buffer right after `llama_state_seq_set_data_ext` succeeds (`server-task.cpp` ~L1827-1850 @ eee3da8) before the draft restore at ~L1856; a draft failure then returns false with the target buffer already freed. The PR's change fixes this.
- **Interaction with INF-70 NOHUGEPAGE:** champion defaults `GGML_NOHUGEPAGE=1`, applying `MADV_NOHUGEPAGE` inside `ggml_aligned_malloc` (`ggml/src/ggml.c:L375-405`, rationale `ggml.c`/`common.cpp:L64` comment: THP coarsens `numactl --interleave` from 4 KiB to 2 MiB, one controller serves small weight tensors; measured 53 vs 362 GB/s; +35.21% served, `handoffs/active/cpu-decode-roofline-program.md:L2882 @ 860023c` CHAMP-2). That applies only to ggml-allocated buffers; `std::vector` save buffers are outside it, and they are not on the weight-streaming path. NUMA: save buffers are first-touched by the server thread that copies the state; under `numactl --interleave` THP would coarsen interleave granularity for them, harmless because they are copied, not streamed in decode. khugepaged could later collapse them in the background (khugepaged defrag=1); no placement guarantee. Not measured here.
- **Does our server use the features?** Yes. `--ctx-checkpoints` default 32 (`common/common.h:L643`, `arg.cpp:L1537`) and `--cache-ram` default 8192 MiB (`common.h:L649`, `arg.cpp:L1628`). Orchestrator registry `orchestration/model_registry.yaml` declares per-role `cache_ram` 32768 MiB (frontdoor :8070 L1854, architect_general :8074 L2094), 65536 MiB (architect_critic :8083 L2022, 27B + DFlash2 drafter), `ctx_checkpoints: 32`, and a role with `cache_ram: 0` (L2771). The "1.13 TB" figure is the host RAM total, NOT a prompt cache; the largest declared prompt cache is 64 GiB per server. Measured 27B entries: ~150 MiB fixed + 38,960 B/token, checkpoints 150-152 MiB (`tests/unit/test_prefix_cache_policy.py:L1-5` in epyc-orchestrator), i.e. each save is >100 MiB, in the PR's target size class.
