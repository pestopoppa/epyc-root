### Settled items
- Sub-group size on Arc: 16 (GGML_SYCL_WARP_SIZE=16, CMakeLists.txt:166 @ eee3da8). At wave64 this maps to warp_size=64 and rows_per_lane = S_v/64 (2 at S_v=128, 1 at S_v=64, and S_v=16/32 collapse to warp_size=S_v with one row per lane).
- S_v / head-dim layout: state stored transposed, M[col][i] = S[i][col]; one warp owns C contiguous columns (each S_v floats); lane l holds rows l, l+warp, ...; grid (H, n_seqs, S_v/(C*2)) with 2 warps per block; `static_assert(S_v % (C*gdn_warps) == 0)` so C=4 needs S_v multiple of 8 (all of 16..128 qualify). q/k are shared across heads through `iq1 = h % neqk1`; v-heads are repeated for GQA-style layouts.
- Threshold analogue (derived by me, NOT in source; needs a sweep): the 1024 rule counts warps after 4x blocking, i.e. H*n_seqs*S_v >= 4096. MI210 has 104 CUs x 4 SIMDs = 416 SIMD slots. Wave count to cover 2 or 4 resident waves per SIMD is 832-1664 post-blocking waves, so H*n_seqs*S_v of roughly 3.3k-6.7k (S_v=128: H*n_seqs about 26-52). The B70's 1024 cannot be scaled by the compute-unit count, since the B70 core count is NOT-FOUND-IN-SOURCE. If we port, make the threshold an env knob and sweep it.
- Does this reach our served shapes? The new test lines use `16, 128, n, 1, 3` and call it "qwen35 prefill layout"; I read this as 16 q/k heads x 3 v-repeat = 48 v-heads, S_v=128 (inference from the test text, not a config read). That gives H*n_seqs*S_v = 6144 at np1 and 24576 at np4, which is above the SYCL threshold, so wide would be selected. On MI210 np1 sits at the 3.3k-6.7k boundary and np4 clearly above.

## 5. In-house state
- HIP/CUDA recurrent kernel: `gated_delta_net_cuda<S_v, KDA, keep_rs_t, state_t>` at ggml/src/ggml-cuda/gated_delta_net.cu:560-723 @ eee3da8. It is NOT column-blocked: each warp owns exactly one column (`col = blockIdx.z*blockDim.y + threadIdx.y`, :591), so a column's `q_reg`/`k_reg` are loaded by every one of the S_v warps of a (head, seq) (:631-638), recomputed per column. Launch geometry :737-740: grid (H, n_seqs, ceil(S_v/4)), block (min(warp, S_v), 4); with wave64 and S_v=128 that is 32 blocks of 256 threads per (head, seq). Two dependent reductions per token (:649, :663), q/k loaded per token with no prefetch, state in `s_shard[rows_per_lane]` (:609), bf16-state option (`GGML_CUDA_GDN_STATE_BF16`, +21.5% at B32 per rocm-kernel-authoring.md:2697) and PDL sync (:612). Upstream's own CUDA kernel was not read here; whether upstream CUDA is column-blocked: NOT-FOUND-IN-SOURCE.
- Prefill reaches a different kernel: `gdn_chunked_try` (:514) routes n_tokens >= 64 (`GGML_CUDA_GDN_CHUNKED_MIN_TOKENS` default 64, :56), non-KDA S_v in {64,128}, CDNA only, to the chunked MFMA WY kernel (gdn_ch_prep/gdn_ch_scan, :113, :228). The PR's headline pp gain therefore does not map to our HIP prefill; only n_tokens < 64 and KDA/S_v outside {64,128} use the recurrent kernel. Compare with the PR's rows: its largest gains are at n_seq_tokens 64-1024.
- CPU: `ggml_compute_forward_gated_delta_net_one_chunk` (ops.cpp:12206-12391 @ eee3da8). Parallel over (head x seq) rows `nr = V->ne[1]*V->ne[3]` (:12399), 4x chunks per thread, disabled for NUMA (:12402-12414). Per token: scale whole state (or per-row for KDA, :12313-12324), then 4-column AVX-512 dot against k (:12329-12335; 4 columns x 4 accumulators, the k vector `shared` loaded once per 4 columns, :12150-12181), then mad with an AVX-512 dual store for snapshots (:12353-12363), then 4-column dot against q (:12368-12374). There is no thread-per-column concept; one thread owns a whole head. So the "q/k once per 4 columns" idea is already present on CPU.
- Our tree carries the sycl file (ggml/src/ggml-sycl/gated_delta_net.cpp:196-198 still shows the old `num_warps = 4` launch at eee3da8), but SYCL is not a served path; the PR is absent at eee3da8.
- Served models with GDN: Qwen3.8-27B (DFlash2 drafter; Qwen3.6-27B noted in intake index as 48 GDN + 16 attention layers of 64), Qwen3.6-35B-A3B (MTP), Qwen3.5-122B-A10B (75% delta-net per speculative-decoding.md:70), Qwen3.8-Flash-Next / Q38FN (CPU MTP). RS-REPLAY ships for qwen35/qwen35moe (speculative-decoding.md:1104).
- GDN share, measured in our lane: prefill only. K28 direct rocprof: GDN summed-kernel 15.397% / 14.649% / 12.180% at p2048 / p8192 / p32768 (rocm-kernel-authoring.md:249-252; the 4x-op ceiling 11.5%/11.0%/9.1% leads to G10 CLOSED_NO_GO, autokernel-loop.md:3435). Qwen3.6-35B-A3B Q8: 15.45% at p2048 and 14.64% at p8192 (rocm-kernel-authoring.md:2765-2766). One production profile showed `gated_delta_net_cuda` at 13.55% (autokernel-loop.md:6569); its workload is not stated there. Decode and verify GDN share: NOT-FOUND in the four handoffs (grep for GDN with a % in decode/verify context returned only the +1.3% fused-decode result, autokernel-loop.md:4184). The only verify-path evidence is the RS-REPLAY kernel number: at np4, 8 rows, snapshot 425.6 -> replay 146.5 us/layer (speculative-decoding.md:1113), and np4 ON/OFF m = 0.931 (R4) / saving 10.9 ms/round against a 13.3 ms kernel prediction (speculative-decoding.md:1119).
- What this means for the served path: at verify (2-16 rows) per-token work per head is one 64 KB (S_v=128 F32) state pass plus snapshot stores; the q/k loads the PR amortizes are 1 KB per token per head. Replay (`LLAMA_RS_REPLAY=1`, np>1 only) already removes the dominant snapshot-write floor for np4. The PR's column blocking would therefore reduce neither the state read nor the replay log. Its reduction restructure could shorten the critical chain per token; value unknown without the op-level measure.
