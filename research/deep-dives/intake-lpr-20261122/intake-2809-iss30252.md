## 5. In-house state (eee3da8)
- Save path: tools/server/server-context.cpp:3529-3563 @ eee3da8 loops over all non-processing slots and calls slot.prompt_save (:514-570) then prompt_cache->update() and, if kv_unified, slot.prompt_clear(), all inline on the server thread at task launch. cache_idle_slots default true: common/common.h:642; disabled only if --cache-ram 0 (server-context.cpp:1849-1852). Same structure as the upstream default-on loop of #20993. So the "all requests wait for all idle saves" part is present.
- Transfer granularity: llama_kv_cache::state_write_data (src/llama-kv-cache.cpp:2832-2942) issues ONE io.write_tensor per contiguous cell range per layer for K (:2872-2876) and for V (:2899-2903); with v_trans it is per range PER embedding row j (:2931-2938), i.e. n_embd_v_gqa * n_ranges calls per layer. The buffer writer (llama-context.cpp:3095-3105) queues winfos and executes ggml_backend_tensor_get at destruction. So a contiguous (non-interleaved) sequence = 1 range = few calls; interleaved -kvu with many busy slots = many ranges = the #30252 blow-up. Our champion has none of #31391 (git log grep for 31391/30881/30137: no hits). Per-cell path src/llama-kv-cache.cpp:2478-2497 is the chunk-KV/other helper, not the save path.
- Whether it bites us: only when (a) kv_unified (-kvu) AND (b) KV on a device (GPU) with several concurrently active slots so cells interleave, AND (c) device tensor_get. Our CPU servers keep KV in host memory (tensor_get = memcpy, no sync) so the stall would be a memcpy count, not seconds. GPU-resident-KV servers (MI210, --cache-ram large) with -np>1 and -kvu are exposed; whether our deployed launchers use -kvu is NOT checked here. A LAMP/LB7 probe already exists in the tree (LLAMA_LB7_PROBES: "kv_write ... n_ranges=" at llama-kv-cache.cpp:2841-2852 and "pst ... idle_save_us" at server-context.cpp:3564-3575), so n_ranges and idle_save_us are measurable without new code.
