## 2. Key claims
1. Checkpoints/prompt cache entries are written to freshly allocated host memory; every first write page-faults at 4 KB. CONFIRMED as description. Anchor: page.txt "llama-server writes context checkpoints and prompt cache entries into freshly allocated host memory".
2. Measured: Qwen 3.8 27B Q4_K_M, ~150 MB per checkpoint, 3 tool calls per request: 124K page faults per request on L4 (similar on H100), faults on the main server thread so GPU waits. PARTIAL (numbers stated; method only in external link github.com/Tensward/tensward docs/research/huge-pages.md, not read). Anchors: "we saw 124K page faults per request on L4"; "each checkpoint was about 150MB".
3. GLIBC_TUNABLES=glibc.malloc.hugetlb=1 cut faults to about 1.8K and improved throughput and TTFT. PARTIAL: no throughput/TTFT numbers on the page. Anchor: "glibc.malloc.hugetlb=1".
4. Proposed: madvise(MADV_HUGEPAGE) on those buffers or 2 MB aligned allocation. Anchor: "Either call madvise(MADV_HUGEPAGE) on the checkpoint and prompt cache buffers".

## 3. Reported results
Faults 124K -> ~1.8K per request (about 98.5% fewer) on NVIDIA L4 and H100 hosts; throughput/TTFT gains claimed without figures on the page. Related issue "#30252" named, content NOT-FOUND-IN-SOURCE. Host kernel THP setting, NUMA, hugetlbfs: not stated.

## 5. In-house state
Champion save buffers are std::vector with zero-fill (per task context; not re-verified here, not read). Zero-fill touches every page on allocation so faults still happen once, on the server thread, in the vector constructor — but also under THP=always the fault count would be low. Nothing in source applies to NUMA (NPS4) placement.
