## 2. Key claims
1. **Exact change** — CONFIRMED (from diff.raw.patch). When `num_rows_per_vec_dot == 2`, the two rows fed to one `vec_dot` call are no longer adjacent (`ir0`, `ir0+1`); they are `ir0` and `ir0 + nr0_split` where `nr0_split = (ir0_end-ir0_start)/2`, so row A walks the first half of the chunk and row B the second half. The outer block loop runs over the first half only (`iir0 < ir0_end_split`, step `blck_0_split = blck_0/2`), the `vec_dot` row stride becomes `nb01 * nr0_split`, and a new helper `ggml_deinterleave_f32` scatters the interleaved `tmp[]` into dst row halves (`dst0` and `dst0 + nr0_split`). nrc==1 reduces to the old code (memcpy). ## 4. Performance principles
| Principle | MI210 gfx90a | Zen 5 |
|---|---|---|
| Split one tile's two weight rows into two far-apart address streams so a stream prefetcher sees two sequential streams | NO: no CPU code path; GPU gets coalescing via wave64 loads, not stream prefetch | PARTIAL: Zen 5 has an L1/L2 stream prefetcher, but its stream-count/page-boundary behaviour is UNVERIFIED (no source cited). Our Q8_0 rows are ~2.7-8 KB apart (nb01), i.e. already different 4 KB pages, so the baseline is probably already two streams; the claimed benefit is uncertain |
| Gain only below bandwidth saturation | n/a | YES, direction transfers: source shows gain collapses at 64 threads (+2.6%); EPYC decode is bandwidth-bound, expect gains only at low threads-per-node or compute/latency-bound verify tiles |
| Deinterleave scatter of tmp to two dst halves | n/a | YES, cost is negligible vs weight streaming |
| Only on nrc==2 (mmla / 2x2 tile) path | n/a | PARTIAL: x86 nrc==2 exists only for Q8_0 (champion `ggml-cpu.c:L308-312`) |
