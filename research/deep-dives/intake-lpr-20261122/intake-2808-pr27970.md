## 2. Key claims

**C0. The op contract is a hint, not an index tensor.**
Verdict: CONFIRMED.
- `ggml_flash_attn_ext_set_n_kv_max(a, n)` stores `n` in op_params slot 4. Zero disables the hint.
- Semantics: the finite entries of each mask row are the sparse K/V set, and `n_kv_max` must bound the number of finite entries per row.
- No new source tensors are added. The backend scans the f16 mask and compacts it into an int32 index list per mask row, padded with -1.
- `build_attn_mha` gained an `n_kv_max` argument. DSV4's CSA/LID path passes `min(raw_mask->ne[0], n_swa) + top_k->ne[0]`, and the GLM DSA path passes `top_k->ne[0]`. Every other call site passes 0.
- Anchors:
  - claim 0, page, Overview: `it is the same idea but instead just relies on a hint from the API about the max number of live kv-entries per token`
  - claim 0, diff, ggml.h: `n_kv_max must bound the number of finite entries in every mask row.`
  - claim 0, diff, ggml.c: `ggml_set_op_params_i32(a, 4, n_kv_max);`
  - claim 0, diff, deepseek4.cpp: `const int64_t n_kv_max = std::min<int64_t>(raw_mask->ne[0], hparams.n_swa) + top_k->ne[0];`

**C1. Kernels and hardware: CUDA only, NVIDIA only, MMA kernel only.**
Verdict: CONFIRMED.
- The compaction kernel and `shall_use_sparse` are compiled out under `GGML_USE_HIP` and `GGML_USE_MUSA`. The HIP build aborts if the host function is ever called.
- The gate requires NVIDIA with Turing MMA, a mask present, `n_kv_max > 0`, no ALiBi, no softcap, and a mask of one head.
- The activation floor is `K->ne[1] >= max(4096, 2*n_kv_max)`.
- Only the MMA kernel gets the sparse gather: (512,512, ncols1=1, ncols2=8) and (576,512, 1, 16). The tile and vec files change only to pass the extra flag.
- The multi-stage cp.async load path is not sparse-capable, so the sparse variant is forced to 1 stage.
- Anchors:

  - claim 1, diff, fattn.cu: `return GGML_CUDA_CC_IS_NVIDIA(cc) && turing_mma_available(cc) &&`

## 4. Performance principles

| Principle | gfx90a / MI210 | Zen 5 |
|---|---|---|
| Mask scan, then index-list compaction before FA (ballot/popc and prefix sum). | PARTIAL. Wave64 widens the ballot to 64 bits and the later HIP port does this (section 7). For our served path the scan is pure overhead, because the top-k indices already exist before the mask is built. | NO. A CPU version would use VPCOMPRESSD or a per-row index list. |
| Gather K/V rows inside the FA tile loader by index (padded slots read row 0 and rely on the -inf mask). | YES as a pattern. Our H12 already gathers by index. The pad-with-safe-row trick is worth copying for any padded top-k list. | PARTIAL. Gather by row is cheap on Zen 5 only for large rows, and rows of 256 f16 are 512 bytes, so it is a prefetch-friendly gather. |
| ncols1 = 1 per mask row, one index list per query. | NO as a design for verify batches. 2 to 16 verify rows each scan the mask and each get a separate list. The unmodified-FA tile then reads K/V once per row, which loses the GQA/verify sharing that our H10/H12 kernels have. Upstream later moved to a union list per group of ncols1 rows. | N/A |
| Activation gate: K at least max(4096, 2*n_kv_max). | PARTIAL. It plays the role of our `MIN_KV_RATIO` (default 8, chosen post hoc). The upstream ratio 2 is a break-even guess from NVIDIA. | N/A |
| Sparse variant pinned to 1 pipeline stage (no cp.async multi-stage). | YES. gfx90a has no cp.async, so this costs us nothing. | N/A |
| LDS: warp offsets plus one row counter, tiny. | YES. Wave64 means 4 warp counters for 256 threads, so LDS is not a constraint. | N/A |

- **Exact collision if we fold upstream past it.**
  1. **FA op_params slot 4.** Ours is `n_seq` (`ggml/src/ggml.c:5686-5699 @ eee3da8`, set at `src/llama-graph.cpp:2836`). Upstream is `n_kv_max`. Readers of slot 4 in our tree: the H10 GQA-verify path (`fattn-gqa-verify.cu:682`, `:739`), the vec-skip logic (`fattn-common.cuh:1079`), and the CPU iqk FA path (`ggml-cpu/ops.cpp:10428`, whose comment says slot 4 is our n_seq hint). All go through the `get_n_seq` accessor except the CPU comment, so moving the slot is a small edit. Other forks already hit and resolved the same collision by moving their own field to slot 5.
  2. **FA sources.** Ours: top_k at `src[5]` and the base mask at `src[6]` (`qsa-sparse.cu:482-488`). The 8e93a9773 diff adds no src. Master later uses `src[5]` for `kv_rows` and refuses the sparse path when it is set (`fattn.cu:155`), so a later fold would collide there too.
  3. **launch_fattn signature.** It gains a `use_sparse` parameter, and the MMA load-tile functions gain an `indices` argument. Any in-house edit to `fattn-mma-f16.cuh` conflicts.
  4. **`build_attn_mha` signature.** Our tree has the function at `llama-graph.h:1161`. Adding `n_kv_max` touches all callers, including our qwen4exp H12 hook.
- **Does our served path reach #27970?** No. For Q38FN, AK-ASM-H12 (`qsa-sparse.cu:454-600 @ eee3da8`) fuses the mask chain before FA kernel selection. On gfx90a the upstream path would also be unreachable, since #27970 is NVIDIA-only and #31259 compiles only the 576/ncols2=16 variant for CDNA.
- **Recommended fold approach.** Move our `n_seq` to slot 5 and adopt upstream's slot 4 for `n_kv_max` (the semantic is then compatible and our H12 can ignore it). Keep `src[5]/src[6]` as is, and put a guard in our H12 selector so a node with `n_kv_max > 0` and our top_k edges does not enter the upstream sparse gate.

## 8. Contradiction / adversarial pass

- **PDL ordering.** ServeurpersoCom found the FA kernel could read index entries before the -1 padding landed, because `ggml_cuda_pdl_lc()` was called early. It was fixed in `be029fd`, and the final diff has the fix. This affects NVIDIA PDL only, not gfx90a.
- **Prefill cost below 32k.** Both reporters measured small losses at 4k to 16k (Blackwell pp2048 at d16384 1739.6 to 1627.9). The activation floor does not prevent them.
- **Qwen4 not covered.** The author said qwen4 is slower for prefill, with other mask issues. #28770 later enabled it.
- **JohannesGaessler review.**
  - A conditional in the load tile is not great, so pad with safe values.
  - Skip unused kernel templates by reusing `may_use_sparse`.
  - The index offset `jt` vs `jt*ncols1` is unclear for more than one token per tile.
  - `shall_use_sparse` must be a subset of `may_use_sparse`.
  - The ggml name should be `set_n_kv_max`, not `set_sparse`.
- **Later upstream restructuring.** The per-row index list became a per-group union list with a count array (`n_lists`, `counts`), and the activation margin was changed (`n_gather`). So the shape of the API stayed (slot 4 is `n_kv_max`) while the internal design was reworked.
- **Greedy output is not bit-equal** to dense. PPL parity only.
