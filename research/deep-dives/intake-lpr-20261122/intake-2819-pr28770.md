## 2. Key claims

**C0. Design: mask scan, not top-k direct. One union list per group of ncols1 queries.**
Verdict: CONFIRMED.
- qwen4exp now passes `top_k->ne[0]` as `n_kv_max` into `build_attn_mha`. The backend then works as follows:
  1. It scans the dense f16 `kq_mask_top_k`, which the graph still builds with fill → set_rows → add.
  2. It selects a column if any query of the group sees it.
  3. It compacts the selection into `min(n_kv, ncols1*n_kv_max)` indices per list, padded with -1, and stores the counts after the lists.
- The MMA kernel bounds its K loop by the count and gathers K/V tile rows by index. Per-query exclusion still comes from the mask.
- Anchors:
  - claim_index 0, diff, `fattn.cu @@ flash_attn_mask_to_sparse_indices`: `// one list per group of ncols1 queries: a column is selected if any query of the group can see it`
  - claim_index 0, diff, `fattn-common.cuh @@ launch_fattn`: `n_kv_max = std::min<int64_t>(K->ne[1], int64_t(ncols1)*n_kv_max_query);`
  - claim_index 0, diff, `qwen4exp.cpp @@ build_attn_qsa`: `ggml_tensor * cur = build_attn_mha(q, k, v, nullptr, kq_mask_top_k, nullptr, nullptr, top_k->ne[0], kq_scale, il);`

**C1. Kernel variants for hd256: (256,256,1,8) and (256,256,8,8). The break-even is 2× the gathered volume.**
Verdict: CONFIRMED.
- `n_gather` is `Q->ne[1]*n_kv_max` for ncols1=1 (per-query lists) and `8*n_kv_max` for the union tile. Sparse is used when `K >= max(4096, 2*n_gather)`.
- The PR body says this means activation at 32768 context for Qwen4, which implies `n_kv_max` = 2048. That matches our H12 r4 note that n_kv/width = 4 at 8k context.
- Decode at GQA > 4 is diverted from VEC to the sparse MMA (1,8).
- Anchors:
  - claim_index 1, diff, `fattn-mma-f16.cuh @@ may_use_sparse`: `(DKQ == 256 && DV == 256 && ncols1 == 8 && ncols2 == 8);`
  - claim_index 1, diff, `fattn.cu @@ shall_use_sparse`: `const int64_t n_gather = (ncols1 == 1 ? Q->ne[1] : ncols1) * (int64_t) n_kv_max;`
  - claim_index 1, page, Overview: `ncols1=8 is take all the union of the tokens being used, so at max it will use see ncols1 * n_kv_max tokens, at twice this value we enable the sparse FA. For Qwen4 this value is 32768 ctx.`

## 4. Performance principles

| Principle | MI210 gfx90a | Zen 5 |
|---|---|---|
| **Group-union index list across ncols1 queries** (K/V row read once per group of 8 queries × 8 heads) | **YES, and it is the main transferable idea.** H12 runs one workgroup per (token, kv head). Every verify row re-gathers its own `width` rows: 16 rows × 2048 = 32k row reads, the same as one dense pass at 32k. A union tile reads each distinct row once. Consecutive verify tokens pick largely overlapping blocks (block indexer, `indexer_top_k + r - 1` whole blocks), so the union is likely much smaller than nq×width. The overlap factor is unmeasured. On gfx90a a union tile of 16 tokens × 12 heads = 192 rows × hd256 is MFMA-sized, while H12 today is scalar FP32 FMA. | NO for now. CPU sparse is a separate track (LSA-CPU-SPARSE). |
| Selection by dense-mask scan before FA | NO for our path. H12 deletes the fill → set_rows → add chain and reads top_k directly. A union can be built from the top_k lists themselves: a bitmap of n_kv bits in LDS is 4 KB at 32k and 32 KB at 256k, within the 64 KB LDS. No mask is needed. | N/A |
| Padded -1 entries with a count-bounded K loop | PARTIAL. H12 already skips masked or -1 cells by branching (`j = -1`, no K read). In a union MFMA tile you would instead pad with a safe row and rely on the mask, as JohannesGaessler asked for in #27970. | N/A |
| Batch-aware break-even `K >= 2*n_gather` | PARTIAL, and the NVIDIA constant does not transfer. It is a bytes-only model. Our r4/r5 data contradict it on gfx90a. At n_kv/width = 16, nb=16, H12 gathers 16×width = n_kv rows, the same bytes as dense, yet wins 2.2-4.6x. On gfx90a, dense FA for this shape is not bytes-bound, or gathered rows hit in L2 across tokens. So the rule's direction (scale with nq) is right for a union kernel but wrong as a predictor for H12's per-token design. | N/A |
| ncols2=8 for GQA 12 | NO, as a fit. With GQA 12 it needs 2 z-tiles (8 + 4), so a quarter of the 16 head columns is wasted. H12 handles G=12 exactly. An MFMA union kernel for us should tile 12 heads × ntok tokens, not 8×8. | N/A |
| Only ncols1 ∈ {1, 8} | NO for speculative decoding. Verify batches of 2-7 fall to per-query lists (C3). | N/A |

## 5. In-house state (champion eee3da8)

- **Absent.** There is no `n_kv_max`. Our qwen4exp `build_attn_qsa` calls `build_attn_mha(..., kq_mask_top_k, ..., kq_scale, il)` without it (`src/models/qwen4exp.cpp:887 @ eee3da8`). It attaches top_k and the base mask as FA `src[5]/src[6]` (`:892-900`).
- **The superseding in-house kernel is AK-ASM-H12** (`ggml/src/ggml-cuda/qsa-sparse.cu @ eee3da8`):
  - One workgroup of D=256 threads per (query token, kv head, stream, split). G q-heads share each gathered row (GQA packing).
  - The score phase is thread-per-cell, scalar FP32 dot products (`qsa_score_row`, `:167-219`). There is no MFMA.
  - Decode and verify split the chunk loop across workgroups and merge in a second kernel.
  - Cross-token sharing: none (`token = blockIdx.x`, `:248`).
  - Gate: `n_kv >= MIN_KV_RATIO*width`, default 8 (`:39-45`, `:543-544`). It does not depend on nq.
  - Measured (completed ledger, `handoffs/completed/autokernel-loop-completed-through-2026-11-20.md:1978 @ 860023c`): 3.16x at kv=32k. At kv=8192 it loses (nb=1 f16 0.94x, nb=16 f16 0.78x, q8_0 0.81x). The threshold is post hoc.
- **Comparison in principle at verify 2-16 rows on gfx90a:**
  - H12 strengths: no mask scan (upstream decode scan costs 17-26 us at 49k on NVIDIA even after #29298); exact G=12; gather work scales with nq×width.
  - Upstream strengths: union sharing across 8 tokens, plus tensor-core (MFMA-class) math.
  - The loss cells H12 has (ratio 4, nb=16) are exactly where union sharing pays most, since 16 overlapping lists against an 8k cache collapse toward a small union. An "H12-union" variant (top_k bitmap union per token group → MFMA tile → per-token membership mask) is the upstream idea that could beat H12 there. It could also lower the break-even below ratio 8.
- **Fold cost:**
  - #28770 needs #27970 first. That brings the op_params slot-4 collision with our `n_seq` and the FA signature churn.
  - Its qwen4exp hunk sets slot 4 on the exact FA node H12 pattern-matches. H12 does not read slot 4, but its matcher must survive the change.
  - On gfx90a, upstream would refuse hd256 sparse anyway, so after a fold the H12-refused cells (ratio < 8) stay dense. There is no regression there and no gain.
  - A bigger risk sits downstream of this PR. Upstream master now builds the QSA selection with a fused `ggml_top_k_mask` op (#30640) and a k-pool selection independent of kq_mask (#30965, #31243). H12's matcher expects fill → set_rows → add. Folding those would likely stop H12 from matching. This is unverified: master keeps a non-fused set_rows path under `cparams.fused_top_k_mask`.

## 8. Contradiction / adversarial pass

- **The gains below the activation point** (pp at 10k/20k) are the author's acknowledged Spark variance. Discount 1.08/1.09.
- **Verify-batch coverage** was criticised by JohannesGaessler and deferred. Upstream never added ncols1 2/4 for hd256: master `may_use_sparse` still lists only 1 and 8.

- **JohannesGaessler's compute-bound caveat**: at large depth ncols1=4 may beat 8, because the union grows and wasted compute rises. On gfx90a, where MFMA throughput is lower relative to HBM2e than on NVIDIA, this point weighs more for a union design. Cap the union group size by the measured union fraction.
