## 2. Key claims

**C0. Why "(again)": #28770 switched DSV4/GLM sparse prefill off by accident, and this PR re-enables it.**
Verdict: CONFIRMED.
- #28770 made the ncols1=1 gate use `n_gather = Q->ne[1]*n_kv_max`. For a 2048-token prefill that never activates, so DSV4/GLM, which have no union (ncols1=8) variant at their head sizes, lost sparse prefill.
- This PR clamps the query count at `64/ncols2`, the number of queries the dense kernel handles per K/V pass.
- There was no revert commit. The "removal" was a side effect of the gate change.
- Anchors:
  - claim_index 0, page, Overview: `#28770 switched off sparse-fa for DSV4/GLM because of the batch-dependent gate.`
  - claim_index 0, diff, `fattn.cu @@ shall_use_sparse`: `const int64_t n_gather = (ncols1 == 1 ? std::min<int64_t>(Q->ne[1], 64/ncols2) : ncols1) * (int64_t) n_kv_max;`

**C1. Wide-kernel preference: when a union variant at full tile width exists and nq > 32/ncols2, skip the per-query ncols1=1 sparse path.**
Verdict: CONFIRMED.
- For hd256 (ncols2=8) the effect is that verify batches of more than 4 rows go to the (8,8) union path, gated at `K >= 16*n_kv_max`. Batches of 1-4 rows stay per-query, gated at `K >= max(4096, 2*nq*n_kv_max)`.
- Anchors:
  - claim_index 1, diff, `fattn.cu @@ switch_ncols1`: `if (!(has_wide_sparse && Q->ne[1] > 32/ncols2) && ggml_cuda_flash_attn_ext_mma_f16_shall_use_sparse(cc, dst, 1, ncols2)) {`
  - claim_index 1, page, Overview: `Also adds a preference for the wide kernel (i.e. 8 ncols1) if it exists at large batch sizes.`

**C2. A scan-kernel fix (template on ncols1 and on an OOB flag) undoes #28770's decode regression.**
