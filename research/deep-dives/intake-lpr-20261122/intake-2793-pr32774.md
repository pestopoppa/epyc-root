## 2. Key claims
1. "AVX-512/VBMI" kernel — **OVERTURNED on the VBMI part.** The asm contains no VBMI instruction (zero matches for vpermb / vpermi2b / vpmultishiftqb in the diff). Instructions used: vpgatherdd (AVX512F), vpmovzxbw/vpshufb/vpsllvw/vpand/vpor, vpmovm2b and kmovq (BW/DQ), vpmaddubsw + vpmaddwd (BW), vcvtph2ps. The guard in the C wrapper tests only AVX512F and AVX512BW. VBMI appears only in the title and a header comment. Anchor: file diff, locator `asm_iq3_s.S` macro GATHER, quote `vpmovzxwd zmm30, ymm3 + kxnorw k1, k1, k1 + vpgatherdd \z{k1}, DWORD PTR [r9 + zmm30*4]`. Also quote `IQ3_S x Q8_K dot product, AVX-512/VBMI, System V AMD64.`
2. "grid gather lookups" — **CONFIRMED, and it is `vpgatherdd zmm` (16 dword lanes, scale 4) against an embedded 512-entry copy of the grid (`.Lgrid` in .rodata; the asm does not reference `iq3s_grid`).** Index build: 16 qs bytes zero-extended to words, the 9th bit from qh via vpshufb+vpand+vpsllvw+vpand+vpor, then zero-extended to dwords, mask register set all-ones each time (kxnorw). One gather = 16 grid entries = 64 B of unsigned weights. Per 256-block: 4 gathers (+4 DOT groups). Same index math as our in-tree ZMM gather16 lambda (`qs` cvtepu8 + masked add 256 from qh bits), except ours takes qh as a ready mask register. Anchor: diff, `GATHER 110, 3, zmm23 + DOT 0, 0, 0, zmm16, zmm0` (shows gather group feeding the DOT group).
3. "two blocks in flight" — **CONFIRMED (software pairing, not out-of-order depth).** `.Lpair` loop issues 8 gathers (blocks i and i+1, 4 each, into zmm16-23) before any DOT, then 8 DOTs, then two FINDB epilogues; loop advances by 220 B (2 x 110 B block_iq3_s) and 584 B (2 x 292 B block_q8_K). Odd tail handled by a single-block copy. Anchor: diff, `add r10, 220 + add r11, 584 + dec r8 + jnz`.
4. "word-sized scale tables" — **CONFIRMED.** 256-entry table (`.Lscaletab`, 256 `.word` rows of 32 words = 64 B per row), indexed by the raw scale byte (`movzx edx, BYTE PTR [...+106+g]; shl rdx,6`). The first 16 words hold (lo-nibble*2+1) and the next 16 hold the hi-nibble value (rows seen: 1,3,5,...). It replaces the shift/mask/cvt scale build with one 64-byte load per 64 values; table is 16 KB in L1/L2 competition with the data. Anchor: diff, `shl rdx, 6 + vmovdqu64 zmm28, ZMMWORD PTR [rax + rdx] + vpmaddwd zmm29`.
5. "395 -> 221 ns (1.79x), Xeon Platinum 8573C, test-quantize-fns passes" — **PARTIAL.** Numbers are as stated in the PR body (verbatim). But the unit is **ns per single vec_dot call over n=2816 (11 blocks)**, best of 5 x 200k iterations, i.e. ~35.9 ns/block -> ~20.1 ns/block on a repeated, cache-resident input. No end-to-end tokens/s, no model run, no DRAM-bound case. 1210 B of weights in 221 ns is ~5.5 GB/s per core: compute-bound by construction, the opposite of a DDR5 decode. test-quantize-fns checks quantize/dequantize and dot-product error bounds only. Anchors: page, `master AVX2: 395 ns patched AVX-512 asm: 221 ns speedup: 1.79x` and `Isolated benchmark on Intel Xeon Platinum 8573C, -march=native, n=2816 (11 blocks), best of 5 runs x 200k iterations`.
6. "Should run on Zen 5" (operator) — **PARTIAL.** Instruction-wise yes (AVX512F/BW only, no VBMI needed, so even Zen 4 would run it). Speed on Zen 4/5 is UNVERIFIED: the PR measured only Intel Xeon 8573C (Emerald Rapids). I cannot cite a source for Zen 5 vpgatherdd zmm latency/throughput; my recollection (uncited) is that AMD gathers are slower relative to Intel, so the 1.79x should not be transferred. In-house datum: our own ZMM gather IQ3_S kernel was measured on Zen 5 and moved nothing at node level (section 5).

## 4. Performance principles
| Principle | MI210 gfx90a | Zen 5 |
|---|---|---|
| 16-lane gather from 2 KB grid (vpgatherdd zmm) | PARTIAL. HIP mmvq already does LUT lookups from constant/LDS (`iq3s_grid` in constant memory); wave64 gives 64 lanes of per-lane loads, no gather instruction needed. The idea "one wide load of 4 B per lane from a small table" is native on GPU. A 2 KB grid fits trivially in 64 KB LDS to avoid constant-cache serialisation on divergent indices (idea, untested). | PARTIAL. Works (AVX512F); throughput on Zen 5 UNVERIFIED. In-house Zen 5 measurement: single ZMM gather per 16 qs already in champion, NO_MOVE at node level. |
| Two blocks interleaved (gathers first, then DOTs) | PARTIAL. On GPU latency hiding comes from occupancy, not manual interleave; the principle maps to unrolling 2 blocks per lane to expose ILP when occupancy is low. | PARTIAL. Zen 5 is a wide OoO core; the compiler/OoO window usually overlaps independent blocks anyway. Value only if the gather latency (UNVERIFIED) is long. |
| Scale-byte -> word table (256 x 64 B) | NO. A 16 KB table per CU wastes LDS; GPU does the nibble split in 2 ALU ops, which are free next to memory latency. | PARTIAL. Replaces ~6 ALU ops with 1 load; 16 KB of L1D (Zen 5 L1D is 48 KB, uncited) competes with weights. Only useful when compute-bound, not when DDR5-bound. |
| Unsigned grid x sign-folded q8 with vpmaddubsw + vpmaddwd | PARTIAL. gfx90a has no byte-dot with unsigned operand; our HIP uses `__builtin_amdgcn_sdot4`-style signed dp4a, signs applied on weights. Not portable one-to-one. | YES, same math as existing AVX2 path; Zen 5 also has VNNI (vpdpbusd) which iqk uses instead (fewer uops). The PR avoids VNNI. |
| Hand-written inline `.S` kernel | NO (n/a). | Maintainability negative: SysV-only (Win64 differs in arg registers and callee-saved xmm6-15), Intel syntax, unconditional add to CMake source list, embedded grid duplicate. |
| Isolated microbench of a single dot | n/a | Cannot predict DDR5-bound decode on EPYC 9655 (decode is bandwidth-bound; see CLAUDE.md hardware note). |
