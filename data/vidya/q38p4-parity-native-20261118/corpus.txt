# MEASUREMENT.md — How numbers become claims in this project

**Purpose.** Every optimization decision rests on a measurement. This file defines the *only*
sanctioned ways to produce a performance or quality number and the grammar for citing one. A
number that does not cite a protocol from the registry below is an **observation**, not a claim,
and MUST NOT gate a keep / revert / deploy / promote / buy / close decision.

**The one rule:** *A claim = (metric, protocol-id, n/reps, date, host-attestation ref).*
Everything else exists to make that rule cheap to follow.

**Document layout (v2).** This core file holds the constitution: claim grammar, metric scoping,
protocol index, noise table, governance, and retroactivity. Full normative protocol text lives in
six annexes in `measurement/protocols/`, which carry the SAME trust boundary and amendment rules as this
file — they are the constitution, filed by family or instrument class, not commentary on it. Daily-use guidance for
sessions is the digest at `agents/shared/MEASUREMENT_POLICY.md`; when in doubt, this file and its
annexes win.

## 1. Metric scoping — task_rate vs tokens/s

Two speed metrics coexist; each is authoritative in its own scope and MUST NOT be substituted
for the other:

- **`task_rate` (tasks / eval-wall-hour, higher-better)** is the **autopilot objective axis**
  (`P-SPEED-OBJ`, per findings-05) and the only speed metric for whole-system / cross-device
  decisions where tokens are not commensurable across arms (different models, tokenizers, or
  devices — e.g. `P-SHED-1`). Noise reference CV ≈ 9.1%: all rate claims go through the
  non-inferiority / improvement e-process, never a single trial. `speed_metric_mode` /
  `protocol_id` journaled.
- **tokens/s (prefill or decode, higher-better)** is the **instrument-level metric** for
  individual model / kernel / configuration benchmarks (`P-BENCH-*`, `P-GPU-1`). Within those
  protocols t/s is fully decision-grade. The v1 phrase "t/s retained as host-health telemetry
  only" applies ONLY inside the autopilot objective scope — it does not demote t/s claims
  produced under a bench protocol.

Metric direction MUST be stated wherever ambiguous (`higher-better` / `lower-better`) —
confirmed-direction errors have burned debugging time before (CLAUDE.md §Debugging).

- ✅ `config 9bd1 confirmed +2q on core_v2 [P-QUAL-T1/seq-v1, E=24.3, k=5, 2026-06-20]`
- ✅ `4/5 toolrunner sentinel pass [P-SMOKE-1, 2026-07-11]`

  under P-BENCH-1)
- Comparisons only within a protocol + instrument version. Cross-protocol comparisons are
  analysis, labeled as such.
- **Category (required)**: every reported measurement declares exactly one of
  `category=OPTIMUM` · `category=BASELINE` · `category=CANDIDATE`.
  - `OPTIMUM` — the best configuration AVAILABLE for that model/role. If no
    speculative draft path exists for the model, the unaccelerated run IS its
    OPTIMUM (e.g. Qwen3-Next-80B-A3B `--spec-type none`); such a row is a headline
    row, NOT a baseline.
  - `BASELINE` — an optimization the model HAS, deliberately switched off.
    Diagnostic only. Appears only under *Addendum — baselines*. Never a headline.
  - `CANDIDATE` — measured, not adopted. Must be labelled so it is never mistaken
    for what production runs.
  An unlabelled measurement is not decision-grade.
  ✅ `ingest_long_context decode 10.12 tok/s, category=OPTIMUM (no draft path exists;
  spec none is optimal) [P-BENCH-1, n=5, 2026-07-31, attest …]`
  ❌ `frontdoor decode 24.92 tok/s, spec-dec off` (no category; reads as a headline,
  is a BASELINE)
- **Instrument class (required)**: every reported measurement declares exactly one of
  `instrument_class=serving` · `instrument_class=bench`. An **absolute** number — a headline, a
  rate, an operating-point or a capacity claim — may be quoted only from the `serving` class, the
  instrument running the role's registered production recipe. A `bench` number is admissible for
  build-vs-build A/B **on its own surface** and is **inadmissible as an absolute headline**. A
  comparison whose two sides carry different classes is **REFUSED, not caveated**. Normative text
  and evidence: **INSTRUMENT-CLASS-1** (appendix).
  ❌ `champion single-stream GPU decode 31.0 tok/s` — a `tg128` bench figure quoted as a rate; the
  production recipe measured 79.25 tok/s on the same build the same day (2.5× understatement)
- **Null declarations (required)**: *"no effect"* unqualified is not a permitted claim. A negative
  result states the effect sizes its power excludes AND cites a positive control, asserted in both
  directions, proving the mechanism reached the system under test. Lacking either, the result is
  recorded as `untested` and is not a negative. Normative text: **BOUNDED-NULL-1** (appendix).
- Per-protocol grammar extensions (e.g. `P-PAIRED` verdict rows, `P-SHED-1` f/stress fields)
  are defined in each protocol's annex entry.

## 5. Governance

- **Amendments**: human-only, PR-reviewed, append-or-version — protocols are never silently
  edited. An amendment appends to the owning annex file and adds a one-line entry to the
  CHANGELOG block at the end of this core file. Superseding amendments name what they supersede.
- **Trust boundary**: this file, its agent digest (`agents/shared/MEASUREMENT_POLICY.md`), its
  `protocols/` annexes, the era registry, the eval tower, and scoring contracts are read-only for
  autonomous optimization processes (program.md). The digest is inside the boundary: it restates
  the rules, so amending it amends them, and it changes only by operator-run ratification.
- **Quality denominator (ETR-1)**: in eval-tower quality, a row the agent or its configuration
  failed (`task_failed`) scores 0 and stays in the denominator; only platform-caused rows
  (`infra_failed`, `scoring_failed`) are excluded. A configuration that fails more MUST score
  lower, never shrink its own denominator. Rows self-identify via
  `quality_denominator_policy: task_failed_scores_zero_v1`; era `E17-eval-task-failed-scores-zero-quality`
  marks the boundary, and pre-E17 quality (which dropped those rows) is not comparable across it.
- **Promotion is decided on the production-optimal configuration alone.** A regression in a
  `BASELINE`-category measurement is NOT a promotion blocker and MUST NOT be cited as one;
  a `BASELINE` improvement is NOT a promotion argument. Baselines are recorded to quantify
  what an already-adopted optimization buys, and appear only in an addendum. A gate that
  blocks on a non-production arm is defective and is repaired, not waived. Where an
  instrument cannot exercise the role's registered production recipe (e.g. `llama-bench`
  cannot drive speculative decoding), its cells are RECORDED and reported alongside and
  MUST NOT by themselves block promotion. Supersedes the protocol-scoped statement at
  `measurement/protocols/bench-cpu.md:216-220`, which is generalised by this clause.
- **Deterministic replay before regeneration** *(operator-ratified 2026-07-27; absorbed into the
  constitution by this v2 — previously lived only in the digest)*: if a result can be obtained
  without inference — by deterministically rescoring or transforming previously saved outputs —
  ALWAYS do that instead of regenerating. Scorer/converter/extractor defects get a tail replay
  over banked outputs; regenerate only when the generation path itself was defective. Quality
  scores transfer across kernel eras once parity is proven; rebaseline only the axis that
  changed. Before any full-suite rerun, prefer focused runs on the discordant items. Pre-commit
  a stopping rule before any bench campaign.
- **Consolidated apply-time ratification** *(operator-ratified 2026-07-27; absorbed likewise)*:
  evidence collection and validation never wait on a human signature. The human signs ONCE, at
  apply time, over a consolidated bundle (protocol + evidence hashes + validation results +
  exact state diff). Human-only writes remain exactly: era-registry rows, this constitution and
  its annexes, AutoPilot baseline-state applies, production freezes/cutovers, host reboots. A
  failed validation re-presents the SAME apply token with updated hashes — never a restarted
  chain. Boundary tokens are presented only while compute is saturated; unrelated work never
  gates on a pending token. Operator-presented commands must be pre-validated end-to-end.
- **Evidence must be DURABLE, not merely hashed** *(operator-ratified 2026-08-02)*: a
  ratification bundle records evidence hashes, but a hash over an artifact that no longer
  exists proves nothing — there is nothing left to check it against. Evidence backing any
  ratified or production-affecting claim MUST therefore live inside a repository, under
  `epyc-inference-research/data/<campaign>/`, with a `SHA256SUMS` and a README stating what
  was measured, when, and which claim it backs. Scratch paths (`/mnt/raid0/llm/tmp/...`) are
  valid for work in progress and MUST NOT appear as the evidence citation of a ratified
  claim. Artifacts too large to carry (multi-GiB imatrix files, build trees) are recorded
  hash-and-provenance-only, and the citation says so explicitly rather than pointing at a
  blob that is not there. Enforced by `scripts/validate/check_evidence_durability.py`, which
  fails on any citation resolving outside the repository or to a missing path.
  *Origin: on 2026-08-02 the master registry was found citing 158 unique scratch paths,
  including the MMMU-250 result that gated a live vision model cutover. 152 still existed and
  4.0 MiB carried nearly all of them — full exposure, no loss yet. The gap was constitutional
  rather than clerical: §5 mandated the hash and was silent on where the artifact must live.*
- **Evidence retention and reclamation** *(operator-ratified 2026-10-25, `RATIFY-WS58-RETENTION-LESSONS-20261025`)*: the
  durability clause above says where evidence must live; this clause says what may not be removed
  while it is still the only copy. It grants no reclamation authority to anyone. It bounds the
  removals that other approvals authorise.
  - **Homes.** Evidence behind a ratified or production-affecting claim lives under
    `epyc-inference-research/data/<campaign>/` with a `SHA256SUMS` and a README. Design, decision
    and review documents live in root `docs/` (`docs/design/`, `docs/reviews/`,
    `docs/coordination/`) or in the owning handoff. Evidence for work in progress or a provisional
    result may stay in scratch until the result is ratified, and is carried to its home then.
    **Reproducible data is never carried**: worktrees, build trees, raw logs and downloads stay in
    scratch, and a claim that cites one records it hash-and-provenance-only.
  - **Durability classes.** This aligns the durability clause above with the operator ruling of
    2026-08-03 that raw campaign data stays on local disk, gitignored. There are three classes:
    - *carried-in-git*: tracked and reachable from a pushed ref;
    - *durable-untracked*: the bytes sit under `epyc-inference-research/data/<campaign>/` on this
      host, gitignored, and are covered by a `SHA256SUMS` that is itself carried in git;
    - *hash-and-provenance-only*: the bytes are not kept; the SHA-256, size, collection recipe and
      provenance are.

    The first two satisfy "inside a repository" above. A durable-untracked artifact has no
    off-host copy.
  - **The reclamation predicate binds every reclaimer**: an interactive session, a wrap-up
    cleanup, a trash sweep, an approved volume reclaim and an autonomous loop alike. A path under
    `/mnt/raid0/llm/tmp`, `/mnt/raid0/llm/worktrees`, `/mnt/raid0/llm/.trash` or
    `/mnt/raid0/llm/state` may be removed only when ALL of these hold:
    1. **Not cited.** No record cites it. The citation sources are: root handoffs (active and
       blocked, on `origin/main` and in the working tree); the compute queue (FILLERS, grants and
       launchers); the canonical belief ledger; the research registry; AutoKernel campaign
       inputs; the scratch manifest; the session bus; the observer registry; and crontab. A cited
       path becomes removable only after it is promoted to its home and every citing record is
       re-pointed (`REPOINTED from`), or after it is de-cited. **No removal may take the sole copy
       of a cited artifact.**
    2. **Not KEEP-marked.**
    3. **No size threshold.** Size is a reported column only. No keep-or-remove verdict reads it.
    4. **Fail-closed.** A citation source that cannot be read makes the verdict UNVERIFIABLE, and
       an unverifiable path is kept.
    5. **Re-checked at every step.** The citation check runs at plan time, again at execute time,
       and again on the original path at purge time.
    6. **Trash first, then held.** Removal moves the path to the trash. A trashed entry is purged
       no sooner than 7 days after trashing. A batch approval does not shorten the hold. Only an
       exact-path, per-entry approval with a clean re-check does.
    7. **Explicit target.** Exact paths only: no glob, pattern, `find -delete` or listing-driven
       sweep.
    8. **Tombstone before unlink.** The purge record is written and fsynced before anything is
       unlinked. It carries the original path, a SHA-256 computed immediately before removal, the
       size, and the approval it acts under.
  - **Three states, not two.** A verifier distinguishes three cases for a cited artifact:
    present and hashing correctly is *conforming*; absent with a tombstone is *expected
    absence*; absent without a tombstone is a *defect*. A defect is reported as an incident,
    never left as a silent gap.
  - **Scope and enforcement.** The autonomous-loop expiry grant drafted on 2026-08-03
    (`artifacts/operator/autokernel-policy-draft/evidence-retention.draft.md` §3.2-§3.7) is not
    enacted by this clause. Until it is, loop reclamation is governed by this predicate like any
    other. The enforcers are the guards named in `agents/shared/OPERATING_CONSTRAINTS.md` →
    *Destructive operations* and `epyc-inference-research/scripts/validate/check_evidence_durability.py`.
  *Origin: the 2026-10-25 reconciliation (`docs/reference/tmp-loss-reconcile-2026-10-25.md`) found
  244 real losses among 497 handoff-cited `/mnt/raid0/llm/tmp` paths. The 2026-10-20 volume reclaim
  skipped its citation check for every entry under 0.02 GiB, which covered 72 of the 73 cited paths
  it removed. A follow-on script then purged that batch out of the trash within two minutes. §6
  already pointed here, but the clause had never been written.*
- **Validators**: `scripts/validate/check_claims_grammar.sh` (warn-mode; scans new handoff/index
  diffs for uncited decision-flavored numbers — built 2026-07-30 per ledger L5); journal rows
  carry `protocol_id`; the ATTESTATION artifact (findings-04 §B) is the `attest <id>` referent.
- **Measurement-debt queue**: when a number is demoted-to-prior, a re-measure ticket is created
  at `handoffs/active/measurement-debt/` keyed by corpus type; the master handoff index surfaces
  outstanding items. Closing a debt item requires a new measurement citing the current protocol.

## 6. Retroactivity & reconciliation

**Scope first**: the claim grammar governs **decision-gating claims** only. It does NOT govern
training data (episodic memories, item-difficulty priors) or narrative history (progress logs,
archived handoffs). Mislabeling those as "claims to be purged" is the inverse category error.

**Prime directive**: *never destroy primary records; demote, label, or re-derive
interpretations.* Three verbs:

- **retro-certify** — provably produced by a now-named protocol (command/env/reps recorded) →
  `protocol_id: <P> (retro)`, full claim status, no re-measurement.
- **demote-to-prior** — real data from an unknown/flawed instrument → hypothesis formation and
  item-difficulty priors only; CANNOT gate; a decision resting only on demoted numbers gets a
  re-measure ticket (priority = consumer impact).
- **retire-view** — derived artifacts (frontiers, baselines, dashboards) rebuilt under current
  policy/era; the old view archived read-only, never edited in place.

Known-contaminated data keeps its supersession tag (`bug_corrupted_by`) — tagged history, not
deletion.

## AGGREGATION-SPEEDUP-1 — speedup aggregation (RATIFIED 2026-08-03)

**Rule.** Aggregate per-item speedups as `harmonic_mean({s_i : i correct})`, reported **beside**
`correctness_rate`, never instead of it.

**Forbidden:** a harmonic mean over any set containing failure-clamped sentinel values. Failures are
counted in `correctness_rate`; they are never encoded as a speedup and folded into the aggregate. A
published headline in this literature moved **2.8× on byte-identical outcomes** purely from the choice
of clamp constant — a single number whose value is set by a convention rather than by the data.

**Why harmonic and not geometric.** Harmonic mean punishes slowdowns heavily and nearly ignores large
speedups, which is the asymmetry we want: large wins on minor items should not offset a regression.
Geometric mean is the documented attack surface — `[0.1, 1000]` across two items yields a geometric
mean of 10 while one item regresses, and agents have been shown to perform exactly that optimization.

**SCOPE — this governs speedup and ratio aggregation ONLY.** It does **not** reach the
completion-probability geometric mean used for confidence calibration in the autopilot RLVR path, which
is a different quantity with a different justification. An audit on 2026-08-03 found **zero** sites
applying a geometric mean to speedups, so this rule is **prospective**: it prevents a future choice
rather than correcting a present one. Do not let a future sweep "retire geomean" by grepping the token.


## PAIRED-CI-1 — paired confidence intervals (RATIFIED 2026-08-03)

**Rule.** Paired comparisons report a closed-form paired confidence interval, computed **with the
small-K correction**.

**The small-K correction is mandatory, not advisory.** Without it, relative error is roughly **70% even
at N=2000**, because a `1/(K−1)` per-question bias does not average away as N grows. At the K=3–5 reps
this project typically runs, omitting it makes the interval worthless — worse than reporting none,
because it looks like rigour.

**Do not add bootstrapping.** The empirical-variance z statistic, the bootstrap and the sign test are
proven equivalent for this estimator; resampling machinery would add cost and no information.

**What this closes.** Before this rule, paired comparisons reported point estimates with no interval.
`llm_primitives/stat_tests.py` provides `wilson_interval` (a binomial proportion CI) and **no paired
CI** — so this is a genuine gap, not a restatement.

**SCOPE LIMIT, binding.** The estimator models two noise sources: data and prediction. **This
project’s dominant hazard is a third — environment/machine drift — which pairing does NOT remove**
unless both arms are interleaved within one environment window. The affine drift correction that
handles that third source **is not implemented anywhere in this project as of 2026-08-03**. Therefore:
a paired CI computed under this rule is valid for arms interleaved in one window, and **may not be used
to rank close variants across windows** until the drift correction exists. Adopting this alone is half
the instrument, and the half that is missing is the one that bites hardest here.


## CENSORING-1 — right-censoring and robust aggregation of repeats (RATIFIED 2026-08-03)

**Rule 1 — right-censoring.** For any benchmark with a wall-clock cap, a run that reaches the cap
scores **0**. The censored magnitude is **never imputed, extrapolated, or replaced by the cap value**.
The principle generalises: *make the score’s dependence on the measurement vanish at exactly the point
the measurement stops being informative.*

**Rule 2 — robust aggregation of repeats.** Aggregate R repeated timings with the **Hodges–Lehmann**
estimator (median of pairwise means) rather than the arithmetic mean. Drop-in, no other implication.

**Explicitly NOT adopted: `eff@k` as a scoring function.** It saturates — a caveat derivable from its
own defining equation and not stated in its source: on the hardest level the ceiling is
`α/(α−1) = 2` at `α = 2`, so **a 2× and a 1000× score identically**. It is unusable wherever magnitude
matters, which for kernel and serving work it does.

**BLOCKING PRECONDITION on any harness adopted to implement Rule 1.** The reference implementation in
the literature executes untrusted generated code in bare subprocesses with a documented inability to
kill `try`/`except` infinite loops. On a host shared with live inference servers that is not runnable
as delivered. **Adopt the rule; run it under our own isolation.**


## CONFORMANCE-VECTORS-1 — cross-backend numerical conformance vectors (RATIFIED 2026-08-03)

**Decision.** Cross-backend numerical conformance vectors are adopted as a **first-class instrument**.
Instruments touch the measurement trust boundary, which is why this is a ratified decision rather than
a task.

**What the instrument is.** Committed, edge-weighted test vectors that pin a decoder **bit-exactly**
rather than to a tolerance: each case carries the decoded value **and** its exact bit pattern, weighted
to boundaries and to the step either side of them.

**Two design requirements, both load-bearing.**

1. **Dual contracts per format.** Where a spec behaviour and our implementation behaviour legitimately
   differ, they are recorded as **two separate contracts**, so a backend cannot satisfy one by breaking
   the other. This is what lets a compatibility path be recorded as *documented-divergent* rather than
   as a bug.
2. **VERIFIED vs ASSERTED, per row.** Every row names the test that consumes it, or is marked
   `not yet checked`. A backend is conformant only if a test actually consumes the vectors; anything
   else is an observation from reading source and is marked as such.

**What motivated it.** An audit on 2026-08-03 found **three different answers for the same
quantization edge case across seven backend sites** in our own tree — CPU finite, HIP/Metal/SYCL/Vulkan
/OpenCL +Inf, CUDA ≥12.8 NaN. Nothing had compared them **because nothing ran**.

**Known limitation, recorded at adoption.** Hand-written vectors drift — that is the same failure mode
they exist to document. The `VERIFIED`/`ASSERTED` column is what makes the drift visible rather than
silent.


## INSTRUMENT-CLASS-1 — a bench-surface number is never a serving number (RATIFIED 2026-09-08)

**Rule.** Every measurement declares exactly one `instrument_class`:

- **`serving`** — the instrument runs the role's registered production recipe: its drafter, its
  batching, its concurrency, its pinning. **Absolute numbers come from this class and no other** —
  headlines, rates, operating-point choices, capacity claims.
- **`bench`** — a kernel A/B surface (`llama-bench` and its kin). Admissible for build-vs-build
  comparison **on its own surface**, where the absent production machinery cancels between arms.
  **Inadmissible as an absolute headline, as a rate, and in any cross-surface ratio.**

**A comparison whose two sides carry different classes is REFUSED, not caveated.** No footnote
repairs it: the two surfaces are not measuring the same system.

**What it cost, measured 2026-09-08** — champion `ef81196d5`, Qwen3.8-27B-Q8_0, MI210. Asked for the
model's decode rate, this project answered with `llama-bench` `tg128`: **31.0 tok/s**. The
production-recipe answer, same build, same day, is **79.25 tok/s** — a **2.5× understatement of our
own system, stated confidently.** The cause is structural rather than a tuning gap: **`llama-bench`
cannot do speculative decoding at all**, so on a served path with a drafter in it `tg128` was never
measuring the served configuration. Receipts:
`epyc-inference-research/data/ak-champion-maxperf-2026-09-08/` (research main `7020bb94`); design
record `docs/design/champion-max-performance-20260908.md`.

**The A/B is not retracted; its promotion to a rate is.** That same pair (production 29.4 / champion
31.0, **+5.63%**) remains a valid kernel-vs-kernel comparison inside the `bench` class.

**The class gap is not a constant, so it cannot be corrected away.** On the same day the serving gate
fired for the first time, over the same six keeps: the `tg128` proxy read **+5.958%** while the
serving instrument returned *"cannot tell, probably slightly negative"* — **−2.18% at n=10, not
decisive**. An **11-point** proxy-vs-truth gap that disagrees in **sign** as well as magnitude. A
calibration factor between the classes would have to be fitted per keep, which is to say there is
none. Receipt: `epyc-inference-research/data/ak-r2358-shim-serving-2026-09-08/`
(research main `7020bb94`).

**Relation to §5.** §5 already rules that where an instrument cannot exercise the registered
production recipe its cells are RECORDED and MUST NOT by themselves block promotion. This block
supplies the converse and completes that clause: such cells MUST NOT headline either. §5 is
**extended, not superseded** — a bench cell still records, still reports alongside, and still cannot
gate.


## FLOOR-UNIT-1 — a floor carries its unit, and n=10 on a tail statistic cannot gate (RATIFIED 2026-09-08)

**Rule 1 — `unit` is a required field.** Every floor record writes `unit ∈ {arm, session, process}`
alongside harness, n, contention model and host state. **A floor with no unit is inadmissible as a
gate input.** A gate asked to compare an effect against a floor of a different unit **REFUSES** — it
does not warn, and it does not caveat.

**Rule 2 — a floor intended to gate is calibrated at n ≥ 24, and records `n` and an interval, not a
point.** `p95` is an extreme order statistic; at n=10 its own sampling distribution is wide enough
that the point estimate carries no useful precision, and every gate built on it inherits that.

**Why the unit is worth three orders of magnitude.** Measured on one host in one day (INF-70,
2026-09-08):

| scope of variation | sd | consequence |
|---|---|---|
| within-session (**arm**-scoped knob) | **0.501%** | — |
| between-session (**process launch**-scoped knob) | **2.793%** | floor ~**13× coarser** |

A process-scoped knob faces a floor ~13× coarser than an arm-scoped one. Substituting the arm floor
for the launch floor sized a transparent-hugepage A/B at **4 sessions per side**; the correct
session-unit answer is **4,780** — a **1200-fold** error, and one that would have been spent as real
host hours before the design failed to converge. Receipt:
`epyc-inference-research/data/inf70-retest1-2026-09-08/` (research `1780fa7b`).

**Why n=10 is not a tight condition.** The standing serving floor for
`qwen3.8-27b-q8-gpu-dflash2-np4` is recorded as **4.581% at n=10** (it recomputes to **4.494%** from
its own inputs — a second, smaller reason that record is not load-bearing). The same configuration
over **n=24** measures **6.596%**, **1.47× wider**. Bootstrap, 20,000 draws of n=10 from those 24:
median **6.258%**, 5th–95th percentile **4.200%–7.821%**, and only **9.0%** of draws land at or below
the standing value. Receipt: `epyc-inference-research/data/ak-r2358-shim-serving-2026-09-08/`
(research main `7020bb94`).

**Scope limit, binding.** Two conditions differ between those two calibrations (build and window), so
**the 1.47× is NOT a measured degradation of the host** and must never be reported as one. What is
established is the instability of the *estimator*, which is a property of n=10 and holds whichever of
the two conditions moved.

**Grade.** This block adds two required fields and a calibration size. It changes no threshold and
re-verdicts nothing already decided: floors already in force are re-derived under it as measurement
debt, not invalidated retroactively.


## BOUNDED-NULL-1 — a null needs its power and its fired-knob control (RATIFIED 2026-09-08)

**Rule.** *"No effect"* unqualified is not a permitted claim. A negative result states **both**:

1. **Its power** — which effect sizes the design excludes, and at what n. The admissible sentence has
   the shape *"a large effect is excluded; a small one is not."*
2. **A positive control proving the mechanism reached the system under test**, asserted in **BOTH
   directions** — the control must fire where it should and *not* fire where it should not, so that a
   mislabelled arm cannot pass the check.

**A result missing either is recorded as `untested`. It is not a negative result.**

**The worked case (R23-58, 2026-09-08).** 48 launches, 24 per arm, none discarded; both claims
returned null (dispersion ratio OFF/ON **0.713**, p = 0.3159; sd(log) ratio 0.918, p = 0.5854). It is
a *finding* rather than an absence because of two things the design carried:

- **Bound.** At n=24/arm the primary permutation test had **~0.97 power against a 3× dispersion ratio
  and ~0.69 against 2×**. Unqualified "no effect" was forbidden in writing by the pre-registration,
  frozen before the first launch.
- **Control.** All **48** positive-control readbacks fired in both directions: the kernel
  `THP_enabled` flag read back correct **every time**, with AnonHugePages at **~53% of RSS** in the
  control arm and **0.0%** in the treatment arm on every one of 24 launches. **The mechanism
  demonstrably ran and produced nothing.**

Receipt: `epyc-inference-research/data/ak-r2358-shim-serving-2026-09-08/` (research main `7020bb94`) —
pre-registration, `FROZEN-AT-LAUNCH.sha256`, `launches.jsonl`, `thp_proof.txt`.

**The counterexample is from the same campaign.** INF-70's SYNC-18 was untestable as built: its knob
only reached a function that no longer gates execution, so *"no effect"* and *"the knob never fired"*
were indistinguishable in its result table — and they are indistinguishable in **every** result table.
Only the control separates them. Receipt:
`epyc-inference-research/data/inf70-retest1-2026-09-08/` (research `1780fa7b`).

**Choose the statistic from the hypothesis' shape.** R23-58 ran as two interleaved, order-balanced
A/A calibrations rather than a paired A/B, because the available comparator varies the *build* (so a
same-build environment arm is inexpressible) and its median-contrast statistic is exactly what misses
a compressed downside tail — the shape the effect under test would have had. A means-only comparator
can return a null on a real effect, and such a null satisfies neither clause above.

## Reporting Units

- **A count of scheduler records is not a count of work.** Any queue-depth, backlog-size or
  advisory-volume figure must be stated in the form **"N records resolving to M distinct rows, of
  which K were dispatchable at emission."**
- **K is the only one of the three that is a claim about the fleet.** N measures how often a
  producer wrote; M measures how many things it wrote *about*; only K says how much work was
  actually available. Quote a figure without its distinct-row and dispatchable-at-emission
  denominators and you have reported a producer's tick rate as a property of the backlog.
- Applies to queue depth, backlog size, advisory volume, retry counts and anything else derived by
  counting emitted records. If K cannot be computed, say so and quote no headline number — an
  uncomputed K is not a small omission, it is the absence of the claim.

(origin: C50 — the "4,602 pending picks" retraction; Appendix)

## Observation Windows — a sample that misses the phenomenon proves nothing

**A measurement whose window does not overlap the phenomenon is not evidence of its absence.**
The reading is real; it is simply about a different moment than the claim. Same family as
verified-at-one-timestamp / read-at-another. (Claim grammar and protocol rules stay canonical in
`agents/shared/MEASUREMENT_POLICY.md`, which is human-amendment-only; this is the agent-side
sampling discipline that feeds it.)

- **Sample DURING, never after.** A post-exit sample cannot distinguish *never resident* from
  *finished* — the two worlds produce byte-identical readings. If the process the claim is about
  has already exited, you hold a timestamp, not a measurement. Report the sample times and the
  process's lifetime together, or make no claim.
- **An absence claim needs PERSISTENCE, not a sample.** `llama-bench` EXITS between probes, so
  0% utilisation and 0% VRAM are the *normal* reading inside a perfectly healthy sweep. Any
  idle-hardware, not-resident or stalled claim must name the condition **and** the number of
  consecutive samples over which it held; a single sample landing in the gap is sampling error.
- **Two numbers, not one — do not confuse them.** `agents/shared/INVARIANTS.md` invariant 13 sets
  the ACTION floor: **two** persisted samples before any destructive or escalatory action on an
  absence or idleness claim. This rule sets the CLAIM requirement, which is stricter and has no
  fixed floor: a published absence claim must name its own count, whatever it was. Clearing the
  action floor does not license the claim.
- **`fleet_watch` is the instrument that implements the persistence gate** for fleet-level idle
  detection (`logs/fleet_watch.log` receipts); a per-run claim implements it by sampling during the
  run. Neither is satisfied by a single reading.
- **Dispatch corollary: short one-at-a-time benches GUARANTEE the appearance of idle hardware.**
  Queue compute back-to-back for occupancy instead of dispatching probe by probe — saturation
  scheduling (below, *Codex Delegation & Long-Horizon Throughput*) is also what makes the idle
  signal readable. Idle compute stays a reportable condition; this raises the bar for calling it
  idle, it does not license ignoring it.

- **The state file is not the phenomenon.** For a phase that runs for minutes, a controller's
  state file only moves at phase BOUNDARIES — so "state unchanged" is the normal reading in the
  middle of one, and is indistinguishable from a wedge. Prove liveness from ARTIFACT ACTIVITY (new
  writes under the build/output tree) plus a live child process, and only then read the state file
  for *what phase* it is in. A monitor built the other way round reported "no progress" through a
  perfectly healthy 15-minute single-threaded HIP build.
- **A probe reports the absence of what it never looked at.** Three shapes, one failure. (a)
  TRUNCATION: `| head`, `| cut`, `--limit` on a probe's OUTPUT silently shrink its window —
  `ps -eo … | grep … | head` dropped the supervisor, factory and compiler and produced a confident
  "the campaign is DOWN" while all three were alive. (b) WRONG TREE: a git worktree contains only
  TRACKED files, so a probe run there reports gitignored or untracked state as missing even when it
  exists in the real clone — this produced a whole operator decision request against a watermark
  that had existed for two days. (c) VACUOUS MUTATION: a mutation test whose injection did not
  land (the tree lacked the line being mutated) passes while testing nothing. Count before you
  truncate, run the probe in the tree the claim is about, and assert the mutation landed before
  trusting that it fired.

(origin: INC-20260812-post-exit-vram-sample; and the 2026-08-27 AutoKernel
v28–v31 work, which produced all three false readings above within one
investigation; Appendix)

## Inference and Benchmarks

- **Stop measurements when the question is answered.** Before long runs, use the [measurement sufficiency guide](../../docs/guides/agent-workflows/measurement-sufficiency.md) to reuse evidence, predeclare useful interim decisions and preserve partial results. A practical early stop does not change a fixed protocol or turn incomplete coverage into a gate pass.

- Never launch a process that runs inference ITSELF (llama-bench/cli, a self-launched llama-server, run_benchmark.py, an eval suite driving its own server) without a held CPU-region claim covering the cores the run pins — use `region-lock run --cpu-list <list> -- <command>` (epyc-orchestrator/scripts/region-lock); `bench_canonical.sh` acquires it automatically and refuses to run unlocked. Concurrent runs on overlapping regions silently poison both sides — the claim, not a human, is what prevents that.
  - **Traffic sent through the orchestrator API (`:8000`) is not such a run, and an outer `region-lock` must never wrap it.** The orchestrator places and region-claims every call itself; an outer claim over the same regions holds the cores that placement needs, and every call fails `placement timeout … reason=race_lost holders=[]` → 503 `contention_denied`. A quiet window for API traffic is coordinated with the session that owns the measurement, not taken with a lock. (origin: HS-4 P0.4 run 1, 2026-09-26 — an outer lock over q0-q3 around an OpenCode→`/v1` client; `handoffs/active/harness-selection-and-integration.md` P0.4)

- **The llama-server KV mode is an argv fact, not a default.** The server turns on unified KV by itself only when
  `-np` is absent: auto slots means 4 slots plus unified. With an explicit `-np N` it runs split KV, where each
  request is capped at `-c / N`.
  - So a bench launched without `-np` measures a different server than a production launcher that passes `-np`.
  - Every serving recipe and every A/B arm must pass `--kv-unified` or `--no-kv-unified` explicitly and read the
    launch log's `kv_unified =` line back.
  - Unified vs split also **changes outputs at the same seed**, because float summation order changes. Replay,
    determinism and output-comparing A/B tooling must pin the mode, and aggregate t/s across modes confounds answer
    length.
  - Details and measurements: `wiki/kv-cache.md`.

  - An outer hold covers everything inside it. A bench helper must not request gpu-quiet `shared` while its caller

## The Single Champion — one aggregate per production kernel tree, between promotions

**Ratified 2026-08-31 (operator, verbatim requirement).** Inference research owns **ONE SINGLE
CHAMPION PER PRODUCTION KERNEL TREE**, each aggregating **all** improvement work done on that
tree between its production promotions — manual inference research AND AutoKernel keeps, merged
into one branch, always precompiled, always carrying a current measured standing versus that
tree's frozen production state.

The production kernel SET is three frozen trees (`llama.cpp`, `whisper.cpp`, `qwentts.cpp` —
CLAUDE.md § the 2026-08-11 kernel-set freeze), so up to three champions may exist, one each.
Today only the `llama.cpp` champion is active; an STT or TTS champion follows the same contract
if and when that work opens. **The uniqueness constraint is per tree**: two champion lineages
for the same tree is a defect the moment the second one exists.

- **The lifecycle is a cycle, not a tree.** Promotion N → that tree's champion := its production
  state (the aggregate is empty) → every improvement on that tree merges IN → promotion N+1 →
  reset. "Seed the champion from frozen production" is correct in exactly ONE moment: immediately
  after that tree's promotion. Applied mid-cycle it silently discards the accumulated research.
- **The loop anchors on its tree's champion branch tip and commits keeps onto it**; manual
  research admits through the documented admission pipeline onto the same branch. Never fork a
  sibling "champion" from the frozen base.
- **Every champion change updates the aggregate standing**: the measured performance number(s)
  versus the CURRENT frozen production state of that tree — resolved live from the frozen tree,
  never a pinned commit that goes stale at the next promotion — and the artifact-derived feature
  list, refreshed automatically at every advance AND at loop startup. A restart may never present
  a stale headline.
- **A champion exists so that promotion is "take the one precompiled branch"** — never a hunt
  across worktrees. Whatever is not merged into its tree's champion does not exist at promotion
  time.
- **Enforced in code, not memory**: `autokernel.loop.run` refuses to start if its worktree or
  anchor provenance disagrees with the champion branch tip. Do not bypass or weaken that
  refusal; a run that cannot prove its anchor is the champion is run 18/19/20 again.

## New actor seats — wire-test before any live call

**Ratified 2026-09-26 (operator).** A new actor seat must not take a live call until two stub checks have
passed on its EXACT invocation. A new seat is any of these, in AutoKernel or any other autonomous loop:
- a new model or backend kind;
- a new harness or CLI;
- a changed seat config: permissions, prompt transport, or output or context limits.

The two checks:
1. **A fake-model wire test.** Drive the exact invocation against a scripted OpenAI-compatible stub
   server, and check each of these:
   - the full reply survives capture at full length;
   - both exit-code paths are handled;
   - the timeout covers a slow reply;
   - requested limits reach the wire;
   - permissions hold: a read-only seat can never reach an `ask`-class prompt.
2. **One stub end-to-end dry iteration.** It exercises stop, resume, and continuation past a keep.

Until the gate exists in code (INF-78 OAB-29/OAB-30), the session bringing the seat up runs both by hand
and records the result in the owning handoff. Checklist: `docs/guides/agent-workflows/agent-loop-design.md`
→ *Bringing up a new actor model or backend*.

(origin: INC-20260926-local-actor-bringup — 57.5 h passed from the first local-planner launch to the first
measurement. ~11 of ~26 incidents were harness semantics that a fake server finds in seconds.)

## Retry Policy

- Maximum 3 retries for the same failing command.
- After 3 failures, stop retrying and perform root-cause analysis.
- **A terminal raise on a RESUME path becomes an infinite loop the moment restarts are enabled.**
  These are one change, not two. AutoKernel's supervisor was clamped to `max_restarts == 0`, so
  every crash was a permanent exit and the operator was the restart loop. Lifting the clamp was
  correct — the resume path worked, and a crashed campaign kept its accumulated state — but it also
  turned an unreconcilable-in-flight raise from "die once" into a 30-second restart loop heading
  for the 1000-restart cap. Before enabling restarts, every raise reachable on the resume path must
  be demoted to a recorded, advancing disposition: losing one attempt is correct, looping forever
  is not.

## Dangerous Operations

Require explicit user confirmation and rollback planning before:

- Recursive deletes in data or model directories
- Kernel or boot-level configuration changes
- System-wide privileged changes that impact stability
- Sending an unverified control character or key sequence to a live agent pane. If you lack
  direct evidence of what a key does in that specific TUI, do not send it — reproduce the
  situation in a disposable tmux session you create and kill yourself, learn there, then act.
  Prefer the least destructive action already observed to work this session. Never send
  `Ctrl-C` to a Codex pane to clear an input buffer (a second `Ctrl-C` exits the session);
  `Ctrl-U` alone clears the composer. Never nudge via raw `tmux send-keys` — use
  `scripts/coordination/tmux_adapter.py nudge` (chunks long messages; raw sends blob past
  ~800-1000 chars and Codex silently truncates at 1024) and verify submission. A mangled input
  buffer is cosmetic: submit and follow with a correction — escalating to destructive input
  handling to fix a cosmetic problem is the error, independent of which key turns out to be
  fatal. (origin: INC-20260728-ctrlc-destroyed-main)

### Destructive operations — mandatory pre-flight and the trash-first rule

**Never `rm -rf`, `mv` over, or `kill` on an assumption. "Looks like a duplicate" is an
assumption; identity is evidence.** (origin: INC-20260828-glm53-model-deleted — a "duplicate
cleanup" deleted the only copy of a 200 GB model: two paths with identical listings were
treated as two copies when both were aliases of one physical tree.)

1. **Identity check, before any delete/move/kill of a path or process:**
   - `scripts/safety/path_identity.sh <path>...` — prints realpath, inode, device, mount, and
     any ALIAS paths that reach the same inode. Two paths are the same file iff inode+device
     match; `realpath` resolving one path into the other is decisive even when listings look
     identical. For processes: only kill PIDs you captured yourself (see Process Management).
   - Cross-check with `du -sb <parent tree>`: a real second copy adds its size to the parent;
     a symlink/bind alias adds nothing.
   - **Reference check — idle is not unused.** Before removing a worktree, checkout, store or
     model, also search live process environments and argv (`/proc/*/environ`, `cmdline`), recent
     launch and watchdog scripts, crontab and campaign state for its path, honour KEEP markers, and
     hold a live run's watchdog first. Procedure: `docs/guides/agent-workflows/cleanup-reference-check.md`.
     (origin: INC-20261004-cleanup-removed-load-bearing-worktree — an approved cleanup removed a landed, clean, 7-day-idle worktree that
     DS41's launchers export as `EPYC_ROOT_REPO`, and DS41's next relaunches died)
   - **Citation check: cited is not removable.** Before removing anything under
     `/mnt/raid0/llm/{tmp,worktrees,.trash,state}`, check that nothing cites it. The sources are
     handoffs (active and blocked, on `origin/main` and in the working tree), FILLERS rows, grants

## Act, Don't Defer — the admission test for escalating at all

**The default is ACT. Escalation is the exception and must earn itself.**

Before any item is deferred, escalated, or written into a "Deferred / Open / Awaiting operator" list, it
must pass this test:

> **Name the specific decision only the operator can make, or the external event you are waiting on.**
> If you cannot name one in a single sentence, you are not blocked — finish the work.

- **Find a bug → fix it.** Do not report it as an open item.
- **Find a gap → close it.** Do not file it as a recommendation.
- **Find work you were already told to do → do it.** An instruction does not expire, and a decision the
  operator already gave is not re-openable by restating it as a question.
- **Something genuinely needs a choice → present it as a decision package** (below) and *keep going on
  everything that does not depend on the answer*. A pending decision blocks its own item, never the rest.

- **Missing software, platform or license is never a blocker (operator, 2026-10-21; platform/license rule first ruled 2026-10-20).** After a dive declined CacheClip because
  "it needs plumbing we don't have": *"WE CAN BUILD PLUMBING WE DON'T HAVE!"*, *"I've told you amillion
  times. The blocker should NEVER be missing software"*, *"we can always build it ourselves"*. Missing
  software, plumbing, kernels, server features, a platform port, or upstream "not supported" is a **build
  cost to estimate and plan**, never a blocker, decline reason, or reason to downgrade a recommendation.
  Only real technical constraints limit (e.g. recurrent state not splittable by position, which bounds
  the payoff; a measured quality loss) and they call for a workaround design. Anything missing
  from llama.cpp or llama-server (a server option, cache path, kernel, op) is built on a
  `llama.cpp-experimental` branch and folded into the champion, per CLAUDE.md → *Experimental Kernel
  Workflow* (operator, 2026-10-21: "We can always build it and fold it into our champion kernels!");
  it is never a limit. Intake form: `research-intake` Phase 4c.

Mentioning something in passing is fine. Mentioning it **instead of doing it** is the failure.

**Three shapes that look like diligence and are not:**

| Looks like | Actually is |
|---|---|
| "Deferred: X" with no named blocker | a stall wearing a status label |
| "Awaits your call" on something already answered | re-opening a closed decision |
| A well-formed decision package for a choice you could make yourself | the contract below applied where it does not belong |

**The recurrence check, and it is not optional.** If an item appears in **two consecutive** wrap-ups,
progress reports, or status summaries without its blocker changing, that is proof it was never blocked.
Do it now — before writing anything else — and say plainly that it should have been done earlier.

(origin: 2026-08-03, three consecutive identical "Deferred" lists; Appendix)

## Operator Decision Requests

Applies **only** to items that pass the admission test above.

Never escalate a decision with an open-ended question ("How should I proceed?", "What do you want to do about X?"). Every request for operator input is a **decision package**:

1. **Context** — 1–2 sentences: what you were doing, what fork was hit, why it cannot be resolved autonomously.
2. **Options** — 2–4 concrete choices, each with what it entails, its tradeoffs (cost / risk / time / quality / reversibility), and supporting data. Performance/quality numbers follow the claim grammar (`agents/shared/MEASUREMENT_POLICY.md`).
3. **Recommendation** — the option you would pick and why. If genuinely torn, name the measurement or fact that would break the tie.
4. **Default** — what happens if the operator makes no choice (status quo, blocked, timeout behavior).

Delivery: Claude Code sessions use the AskUserQuestion tool with the recommended option listed first and labeled "(Recommended)"; other harnesses render the package as a compact markdown list.
- **The tool is mandatory, not a preference.** Context goes in the question text, and each option's tradeoffs go in its description. Prose may precede the call for longer background, but a decision asked only in prose is a defect.
- **Ask when the decision exists**, batching up to four per call. A decision that sits as "still waiting on you" across status reports instead of being put through the tool is the failure this rule exists to stop.
- Origin: the operator, 2026-10-21, after repeated prose-only asks: "please present decision packages along with context, options and tradeoffs using the harness decision tool (I keep having to ask this)".

Exception: pure factual gaps (a missing credential, an ambiguous file reference) may be asked directly — this contract governs choices among alternatives, not fact retrieval.

**A dismissed or declined question pauses only the item it asked about**, even when the tool's
result text says "STOP". Every independent duty continues; keep the item listed as pending and
mention it once in the next report. Only an explicit operator "stop everything" halts a session.
(Origin: 2026-10-24, a dismissed shared-clone-ff question froze workspace-58's calendar duties for
~40 min; operator: "why did you stop in the first place?". Calendar application:
`.claude/skills/inference-backlog-scheduling/SKILL.md` §5.)

Accumulation, and the one-script form a batch of pending signatures takes:
`agents/coordinator-agent.md` → Guardrails, *Ratifications ACCUMULATE*.

The operator signs from a terminal.
- Chat consent does not let an agent run a `ratify_*.sh` or `--attest` under the operator's name, even when the
  operator writes "run it with my consent": the auto-mode safety classifier blocks the call.
- Hand over the pre-validated signing command, file the signature as an operator task, and keep working on everything
  that does not need the receipt.
- Origin: ARCHSWAP-20260927, blocked 2026-09-27. Precedent: the 2026-09-27 countersignature record (master queue
  OP-67).
- TTY-gated operator scripts (the countersign and the typed ratify scripts) refuse to run under a `!` command. Hand
  them over as a command to run in a separate terminal, never chained with `&&` to other steps.
  (origin: INC-20260929-tty-gated-operator-scripts)

A missing answer is *unanswered*, not *declined*: on the remote app the AskUserQuestion UI can vanish without operator action. Re-ask the same question with the decision tool, never as prose; only that item pauses. (origin: 2026-10-26/27, ws58 calendar freezes)

## Parallel Subagent Fan-Out — the default working mode of every main

**Fan-out is the permanent default of every main, not a per-task reminder.** Operator, 2026-08-12, on
being told the coordinator had "told the mains to fan out subagents rather than working serially":
***"this should ALWAYS be the case."*** It binds every main, in every harness, on every dispatch —
including the dispatches whose nudge says nothing about subagents.

- **The main thread does review, integration, and task boundaries.** Execution — implementation,
  docs, research, analysis, verification harnesses — goes to subagents.
- **3–5 subagents run CONCURRENTLY.** Independent work issued one agent at a time is serial working
  with extra steps; put the independent calls in one block.
- **Match subagent model and effort to the task** (`agents/README.md` → Model Routing (Task-Based);
  Codex-side sizing in the section below).
- **Every subagent brief names its lane checkout and the owning handoff's declared `**Scratch**:`
  root (operator, 2026-10-30).** The subagent writes only in those locations. Any exceptional throwaway
  worktree belongs under that scratch root and is removed through the gate when its task lands.
- **Every subagent brief says how to READ and where to WRITE the repo (2026-10-21).** The `/workspace`
  shared clone can sit hundreds of commits behind `origin/main` (2026-10-21: about 400) and can carry a
  peer's staged change (a hygiene-hook edit was riding its index), so a file read from it describes an old
  tree. Read through `git fetch origin && git show origin/main:<path>` or the lane's private checkout
  refreshed from `origin/main`; never trust a working-tree read in the shared clone for current state.
  **Reuse one checkout per lane; do not create a new checkout per task or smoke.** Any exceptional
  throwaway worktree belongs under the declared scratch root. Write only in the lane's private checkout;
  a subagent that edited the shared clone directly (it happened more than once on
  2026-10-21) is stopped and corrected, its stray hunks reverted by path, and a staged peer change is left
  alone. This is the read-side twin of the pathspec/private-index rules in `agents/commands/wrap-up.md`.
- **Every subagent brief requires a CPU-region claim for local compute.** Builds, self-launched servers and
  test suites run as `/workspace/repos/epyc-orchestrator/scripts/region-lock run --cpu-list 0-95 --role build
  --tag <tag> -- <cmd>`, so they queue behind a held window instead of running inside it. `taskset`, `nice` or
  `ionice` onto "spare" cores is not isolation: CPUs 96-191 are the SMT siblings of 0-95, so 160-183 *is*
  physical cores 64-87, and `region-lock` drops sibling CPUs from a `--cpu-list`, so claim the physical cores.
  (origin: INC-20261004-subagent-unlocked-cpu-in-held-window)
- **Every subagent brief states the close-out sequence (operator, 2026-10-21).** Report first; once
  main approves, the subagent ticks the box, writes its agent_log, appends a progress shard,
  updates the relevant handoffs and cleans its task scratch (index rows stay prepare-only, ruling (b)).
  Retain the lane's one reusable checkout; remove an exceptional throwaway worktree through
  `scripts/system/worktree_gate.py` immediately when its task lands. Resolve DIRTY/UNLANDED tails by
  reviewed landing or documented abandonment with patches/evidence and refs preserved. Migrate live
  dependencies and retire stale references before removal; never bypass the gate.
  Operator: *"subagents should update logs, progress report, and
  relevant handoffs when their tasks are approved as complete. This allows us to not lose
  important work logging in between major/thorough /wrap-up which you should trigger/dispatch at
  major work boundaries"*. The boundary dispatch is in `agents/shared/SESSION_LIFECYCLE.md` →
  *Wrap-up cadence*.
- **Dispose of a finished subagent; never reuse it for a new task (operator, 2026-10-21).** Once a
  subagent's task is approved and closed out, it is done. A new task gets a FRESH subagent so stale
  context does not weigh it down. If the concurrency cap is full, queue the new task until a slot
  frees; never resume a finished agent with an unrelated brief. Resuming the same agent to continue
  ITS OWN task (review fixes, close-out, a wait-then-test step) is fine. Operator: *"subagents
  shoudl be disposed once they've finished their tasks and updated logs, progress report, and
  relevant handoffs. Stale context shoudln't weigh down new tasks that require subagent
  dispatching"*.
- **Every subagent result is PROPOSED work.** Review its evidence and diffs, and run validation,
  before accepting it.
- **A main observed working serially is a defect in these files, not a nudge target.** Fix it here.
  A rule that lives in dispatch nudges is a per-task favour that disappears the moment a nudge
  omits it.
- **Exception, narrowly scoped**: a single read-only command whose output decides a management
  step (`ls`, a status read, `git log -1`) may run on the main thread. Anything multi-step, any
  edit, and anything that runs code still goes to a subagent. See *Token-Efficiency Operating
  Rules* below for the full contract this exception belongs to.

**When NOT to fan out.** Sequential phases of the same work; tightly coupled components; work
requiring shared state; and any decomposition by ROLE rather than by context boundary — the last is
a named anti-pattern, measured as subagents spending more tokens on coordination than on work.
Source: intake-1121 (Anthropic, 2026-01-23, dive-verified via `/research-intake`). Width 3–5 above
is unchanged and vendor-endorsed verbatim; this adds the negative conditions the rule previously
lacked, ratified 2026-08-13. See also the *Doctrine rulings* section below, ruling (c).

Coordinator-side strict form (its main thread spends NO time on execution work):
`agents/coordinator-agent.md` → Guardrails. That form is the **tightest instance of this rule and
never an exemption from it** — no role is excused from fan-out by being the coordinator.

**A fan-out's cost is its discarded work, not its width** (ratified 2026-09-07). Width 3–5 is
unchanged and this clause proposes no change to it; what it adds is where to look when a fan-out
looks expensive. In the only published per-outcome accounting of a large agent swarm, **80% of all
tokens went to runs that produced no merged output and 52% to runs aborted outright**, while in the
follow-up system the entire central coordination tier was **~11% of compute** and 3–5 concurrent
workers beat a single worker on *both* wall-clock and token cost at matched completion. So the
diagnosis order is: first measure the share of subagents whose output was never used, and only then
consider the number of subagents. Narrowing width to control cost is treating the cheap term.
(sources: `intake-1304`, `intake-1305`; our own instance is [the active fleet-fanout measurement handoff](../../handoffs/active/fleet-fanout-measurement.md), FM-5.)

(origins: 2026-08-12, 1,070 open backlog items while five mains worked serially;
INC-20260728-idle-mains for the coordinator-side half. Appendix.)

## Dispatching Backlog Work — the task text is the identity

Binds anyone who dispatches, claims, or cites a backlog row: coordinator, main, or subagent.

- **A line number is a hint; the task TEXT is the identity.** Every dispatch carries the verbatim
  box text as primary and `file.md:LINE` only as a hint. **If they disagree, the text wins** —
  re-resolve with `scripts/coordination/backlog_row_check.py --row "<text>"` (`--ref` takes the
  line form; `backlog_queue_gen.py --generate` emits a text-keyed bench).
- **Anchor rot is structural, not carelessness.** Inserting rows above a pointer is what working
  in a file *does*. Measured queue-wide rot: 27% (2026-07-29) → **34.5%** (2026-08-11) — twelve
  days of ordinary edits, no intervention, and no human refresh cadence can hold line anchors.
- **A screener proves WELL-FORMED, not STILL-NEEDED.** `backlog_row_check.py` validates a row's
  form against the file; it cannot know the world. Screen for form, then **verify the premise
  independently** — read the state the row asserts still holds — before pointing a main at it.
- **This is mechanically enforced, not merely written.** Since AUD-2 (2026-08-12) a `task-assign`
  is a typed row: `task_text` is the identity and `session_bus.py append` REFUSES without it;
  `row_ref` is a declared hint field; `screened_by` records that the screener ran;
  `expected_occupancy` (`est_h`, basis, gating) and `constraints[]` (each naming its `source` line)
  are required; payloads over 4 KB must point at a `brief_path` instead. Schema:
  `coordination/session-bus/session_bus.schema.json`. The rot reached 34.5% while this rule was
  already written down in the role's own queue file — which is why the enforcement is in the
  schema now and not only here.

(origin: INC-20260812-dispatch-by-line-number; Appendix)

## Token-Efficiency Operating Rules (operator, 2026-10-05)

Consolidated token-discipline doctrine. May get amendments later; this section is their canonical
home — amend here, not by re-deriving the rule at the point of use.

### Main thread scope

- Main thread = management and review of completed work only; all execution goes to subagents.
  The one exception is the single-read-only-command carve-out already stated under *Parallel
  Subagent Fan-Out* above — it does not widen into multi-step work, edits, or running code.
- **Canonical home for model tiering is `agents/README.md` → Model Routing (Task-Based)**: the
  per-tier task categories, the escalate-exactly-one-tier rule, the no-`fork`-for-cheap-work rule,
  lock discipline under cheap tiers, and the brief/report contract all live there — this section is
  not complete without it.

### Zero-Token Liveness Watching — no recurring polling prompts

- **No recurring LLM polling for steady-state liveness.** A cron job or loop that re-invokes an
  LLM prompt every N minutes just to check "anything changed?" burns tokens on every negative
  tick. Use a zero-token script watcher (inotify, a poll loop in bash/python with no model call,
  a blocking wait on a lock or file) that exits ONLY on a reportable change and then re-invokes
  the session — mirroring the existing *Observation Windows* and *Saturation scheduling* rules
  against manufacturing false idle/busy reads from a sampling cadence, but for liveness instead of
  compute occupancy.
- **A backgrounded `region-lock run` blocked on lock acquire is a zero-token waiter** and is the
  correct way to wait for lock-gated work to become available. Never sleep-poll for a lock in a
  loop that re-prompts an LLM on each cycle.

### Cross-session handoffs are pushed, never "I'll notice"

- A cross-session handoff is delivered via `SendMessage` plus a flag file touched on both success
  and failure — never left for the other session to discover by polling or by chance re-read.
  This is the push-side of the existing *Bus drain (M1)* practice (`CLAUDE.md` → Agents &
  Automation): drain reads what arrived, this rule is about making sure something arrives.

### Operator status replies stay short

- Replies to the operator are short; long material (reports, diffs, logs, analysis) goes into a
  file and the reply names its path. This is the same instinct as the decision-package contract
  immediately above (*Operator Decision Requests*) applied to ordinary status updates, not only to
  decisions: the operator's terminal is not the place for the material itself.

## Doctrine rulings — 2026-08-16

Three live self-contradictions in this corpus, each closed by one explicit ruling (P1-3 of
`handoffs/active/loop-owned-fleet-implementation.md`). **This section is the canonical home**; the
handoff records the same text because the task required it. A surface that contradicts a ruling
below is stale and must be corrected, not reconciled.

**(a) Wrap-up cadence.** The binding 2026-08-11 operator rule wins: **one task done = one wrap-up,
AS YOU GO** — not manual-trigger-only, not deferred to session end. Exactly two BROAD, DESTRUCTIVE
steps stay at the operator cadence and run ONLY inside an operator-invoked `/wrap-up`: index
**PRUNING** (deleting or archiving rows, and handoff compaction) and the **wiki compilation
sweep**. Everything else — progress report, checkbox sync, handoff updates, `Next action` refresh,
agent log, pathspec commit, lane promotion — runs at every completed task, autonomous and
nightshift sessions included. **Nothing may auto-trigger the full routine**: no `Stop`,
`SessionEnd` or `PreCompact` hook, no cron, no nightshift task — and there must not be one. A
per-task wrap-up is invoked by the session doing the work. Cadence contract:
`agents/shared/SESSION_LIFECYCLE.md` → *Wrap-up cadence*; step-level split:
`agents/commands/wrap-up.md` → CADENCE.

**(b) Subagent index edits.** **A subagent may PREPARE index edits; the owning session APPLIES
them and owns the commit.** Drafting row text, running `scripts/handoffs/index_state.py --check`
and reporting the exact diff is preparation. Adding, deleting or re-pointing an index row is never
a subagent's own write. This reconciles the lifecycle rule that a wrap-up may run via a
coordinator subagent on a session's behalf with the standing CLAUDE.md prohibition: both hold,
because preparation is not modification. Explicit operator approval is required only to widen it —
a subagent writing an index directly. The same rule governs intake entries and handoff stubs.

**(c) Role-based delegation.** **Decomposition by ROLE is a measured anti-pattern and no live
surface may instruct it.** Decompose by CONTEXT BOUNDARY (§ *Parallel Subagent Fan-Out*, *When NOT
to fan out*). Confirmed by sweep on 2026-08-16: the eight persona files are archived under
`agents/archived/`, and `coordination/session-bus/config.yaml` — closed role set
`main` / `coordinator-agent` / `reviewer` / `retired` / `service` — is the sole authority on who
holds which role. `agents/README.md` → Model Routing (Task-Based) is model-tier-vs-task-difficulty
routing, **not** the anti-pattern, and stays.

## Appendix — incident origins

Narrative only. Every rule above is complete without this section; nothing here is a directive.
Full ledgers: `docs/reference/agent-config/INCIDENT_LOG.md`,
`handoffs/active/coordinator-role-failure-modes-and-refactor.md`,
`handoffs/active/session-bus-thin-dispatcher.md`.

**C50 — Reporting Units (the "4,602 pending picks" retraction).** A 4,602 figure was reported as a
backlog. It was a repetition count: a stuck picker re-selecting the same work on consecutive ticks,
resolving to **nine distinct rows, all from one file**, none newly dispatchable. N was 4,602, M was
9, K was approximately 0 — and only N was ever computed. The error survived because 4,602 is a real
number, honestly counted, of the wrong unit; nothing about the figure looked wrong, and no reader

# Compute Fillers

Early-ending compute blocks leave gaps. Registered **fillers** use them, without ever competing with the calendar.

- Registry: `/mnt/raid0/llm/tmp/compute-flags/FILLERS.md` (one row per filler: id, owner, launcher + PID, resources, minimum useful window, max private RAM, STOP file, status). This is a separate file from the calendar; never edit the calendar from it.
- Grants dir: `/mnt/raid0/llm/tmp/compute-flags/grants/`.
- How the calendar owner PACKS the queue onto the host (bins, derived classes, grant-writer invariants,
  the operator STATUS/ETA report, `queue_status.py`): project skill `.claude/skills/inference-backlog-scheduling/`.

Plan long measurements and intermediate decisions using [measurement sufficiency](measurement-sufficiency.md); a grant end is a resource boundary, not a scientific completion criterion.

## Protocol

1. A block that ends before its booked end writes `/mnt/raid0/llm/tmp/compute-flags/<block>_FREED`. The calendar owner (workspace-58) consumes it.
2. The calendar owner grants the gap to a registered filler by writing `grants/<filler-id>.grant`, one line: `regions=<...> start=<UTC> end=<UTC hard>`.
3. The filler launcher polls its own grant file (every 30-60 s, shell `sleep` only, no LLM) and runs only between `start` and `end`, under its own **build-role** region-lock claim. **No grant, no run.** One grant is one run; then it waits for the next.
4. At `end`: stop new items, SIGTERM then SIGKILL the run (kill by captured PID / the process group the launcher itself created, never by name pattern), verify dead, release the claim, delete the grant, write `grants/<filler-id>.ended` (`rc=<n> time=<UTC> reason=<...>`).
5. All work done: write `grants/<filler-id>.complete`, mark the registry row COMPLETE, exit for good.

## Rules for a filler

- Resumable: a slice of any size must be useful (resume-skip on already-written rows).
- Honours a STOP file between items (a started item is finished).
- Build-role claims only; never runs inside a timing block unless the grant says so.
- Respects the host rule of at most ONE DS41-class CPU server (>= 200 GiB) at a time.
- Mutual exclusion: refuses to start while the scheduled runner for the same results file is live (its server port listening, or the per-arm runner lock held) and reports it as `.ended rc=4`.
- Test before arming: `bash -n`, then a dry-run with a fake grant in a temp grants dir (`FILLER_GRANTS_DIR`) and a stub runner (`FILLER_STUB_CMD`) proving poll, start, end, cleanup, `.ended`.

## Queue semantics and launcher rules (2026-10-22)

The operator's ruling: "Being queued implies BEING ready."

- **QUEUED** means status ARMED and `ready=y`, with a live launcher pid that is polling its grant id. Every other row is **BACKLOG**, with a named `blocker=` and an owner. A row that is "ready but nobody armed it" is BACKLOG (`blocker=missing launcher`), not QUEUED. The calendar owner grants only QUEUED rows. `scripts/coordination/validate_fillers.py` enforces this (see *Grant validator* below).
- **ARMED means ready to run, waiting only for a window** (operator, 2026-10-25: "only arm into the calendar inference tasks that are actually ready to go but need a window"). A row blocked on anything else (a code fix, an operator decision, a HOLD, a missing or unproven launcher) is BACKLOG with `blocker=`, even while its poller is alive.
- **A failed or HELD end demotes the row in the read-out step itself.** The step that reads the result and files the fix also sets the row to BACKLOG, `ready=n`, `blocker=<task/fix>` in notes. Writers park items in their own `.done`/`.held` files and never write FILLERS, so only the owner can do this. Re-ARM (`ready=y`, live `pid=`) only after the fix is pinned in what the launcher runs. At every task boundary, run `queue_status.py`: an ARMED-UNBOOKED row that cannot actually run is a defect, fixed that turn. Origin: 10-25, four stale ARMED rows (inf66, akx-lb3-2, hpr-b, nib2-gnx1-reindex-2) nearly starved the KPF-64.3 EB one-shot writer, whose gate waits until no ARMED whole-host row is pending.
- **One live launcher per grant id.** A launcher keeps polling its id after its window ends, so two live launchers on one id race for the next grant. To re-arm, kill the old poller by its captured PID, verify it is dead, then start the new one.
- **A filler's inner claim must match its FILLERS resources.** If the job claims more than the row books, it times out behind other holders. `akx-all-27b-run` asked for `gpu-quiet` excl + q0-q3 while booked for the GPU plus 184-191, hit rc=75, and left the MI210 idle for 40 min.
- **Never grant q3 while a GPU runner holds it.** A GPU job's host threads (184-191) are SMT siblings in q3 and claim that quarter. A CPU grant on q3 during a GPU window only queues behind the GPU job. On 2026-10-22 the calendar owner granted `v11-086-fa-vkq-build` q3 while f8's KPF-18 S1 GPU sweep held it until ~13:02Z, and the build waited. Check the GPU calendar before granting q3.
- **region-lock folds `--cpu-list 184-191` into a q3 claim.** The MI210 sat idle 12:24-12:41Z behind a q3 build that the calendar owner had granted (the second q3 violation on 2026-10-22). The first fix, `region-lock --no-fold-siblings`, does not work: `--cpu-list 184-191 maps to no regions`, rc=1 (12:44Z). The working pattern is `filler_run6.sh`: the GPU job claims **GPU-quiet only** (no CPU region) and tasksets 184-191 itself.
- **No timing-class CPU work on q3 during GPU windows.** Correctness and build work may use q3 only when no GPU runner holds it. An exception is a job that deliberately keeps its folded timing claim (`kpf60` does), which needs q3 empty for its short timing step.
- **No ungranted region-lock claims.** A subagent started `cs8l-asr2` (a CS-8.L second-ASR job) on q2 at 12:50Z with no grant. It was found from the region holder list, its owner was identified, and the owner killed it by its own PIDs (~12:55Z). Every claim needs a `grants/<id>.grant`; re-queue as a filler row if the work is wanted.
- **Use an explicit interpreter under region-lock**, for example `/usr/bin/python3` or the venv path you mean. A bare `python3` inside `region-lock run` resolves to the orchestrator `.venv` 3.11, and f8-day-q0 failed with rc=2 that way.
- **Never wrap a check in `strings <bin> | grep -q` under `set -o pipefail`.** `grep -q` exits on its first match and `strings` dies of SIGPIPE, so the pipeline fails even though the match was found (f8's "wrong build" false alarm). Capture first (`strings <bin> > f; grep -q PAT f`), or use `grep -c` with no early exit.

## Grant gate: `grant_ok.sh` v2 (2026-10-23, CTC-Q-A2 + CTC-Q-C.1)

`/mnt/raid0/llm/tmp/compute-flags/grant_ok.sh <row-id> <need_gib> [ds41]` is the one admission check a grant writer runs immediately before writing `grants/<id>.grant`: `validate_fillers.py --row <id> --for-grant`, then `ram_admit.sh`. v2 (`grant_ok.v2.sh` until the calendar owner swaps it in) keeps that legacy form byte-for-byte and adds optional launcher checks for the two rules writers kept breaking:

```
grant_ok.sh <row-id> <need_gib> [ds41] [--window-s N] [--regions R] [--reserve R] [--pid P]
```

- **The launcher** is `--pid P`, or by default the row's `pid=`. A wrapper pid (`bash -c '... setsid nohup bash launch.sh ...'`) is followed to its nearest live `filler_run*.sh` child with `--id <row-id>`; the `--inner` region-lock child is skipped. Its argv is read from `/proc/<pid>/cmdline` (read-only) and parsed the way `filler_run{,2..8}.sh` parse it: `--min-window --class --claim-cpus --gpu-quiet --no-fold-siblings --self-claim --gpu-threads`.
- **`--window-s N`** (the window the writer is about to write): `N >= --min-window + 300 s`. Exactly-equal windows were refused `rc=3` three times (kpf60 10-22, rtepfx2 10-23, ch28 near-miss). The gate reads the minimum from the launcher's argv, not from the writer's hand-typed copy.
- **`--regions R`** (the grant's `regions=` value) must pass the launcher's own `parse_regions` for its class: `cpu` takes no `mi210_0`, while `gpu` and `cpu+gpu` need `mi210_0`. This was the c2 `rc=2` on 10-22. R must also cover every region the launcher's region-lock claim takes: the `--claim-cpus` list folded onto quarters, plus `gpu-quiet` when it claims the GPU. `mi210_0` in R counts as gpu-quiet. A 0-95 claim therefore needs `0-95` or `q0,q1,q2,q3`.
- **`--reserve R`** names regions the writer's claim-wait keeps free besides the grant. Two cases need it:
  - `gpu-quiet` for `--class cpu --gpu-quiet exclusive --claim-cpus 0-95` (the grant is CPU-only);
  - `0-95` for a GPU job whose claim is the whole host (`--class gpu --gpu-quiet exclusive` with no `--claim-cpus` on `filler_run2/6`).
- **Class report (CTC-Q-C.1).** With any new flag, success prints `class=<derived>` from `validate_fillers.py --print-class`, followed by the launcher's claim. Callers set gpu-quiet from it rather than hand-picking quiet. `warn=quiet-claim-on-<class>-row` flags a whole-host exclusive launcher on a non-quiet row; `warn=quiet-row-launcher-not-whole-host-exclusive` flags the reverse.
- **QUEUED check.** With any new flag, a row that is not `ARMED` with `ready=y` is refused. `--for-grant` alone passes a well-formed BACKLOG or COMPLETE row.

Exit codes:

| Code | Meaning |
|---|---|
| 0 | Admit |
| 10 | Validator refuse (with the new flags, also: row not QUEUED) |
| 11 | RAM refuse |
| 12 | Window short |
| 13 | Class/region mismatch: `parse_regions` refuses, the claim is not covered, a `--no-fold-siblings` claim is SMT-only, or a region token is unknown |
| 14 | Launcher dead: no pid, a zombie, or a wrapper whose engine is gone |
| 15 | Launcher argv unrecognised: no `filler_run*.sh --id <row>` under the pid. With `--window-s` only, the gate falls back to the row's min-window; `--regions` needs a recognised launcher |
| 16 | Internal error |
| 64 | Usage |

Every refusal is one stdout line starting `refuse:`. Tests: `compute-flags/test_grant_ok_v2.sh`, which uses fixture `/proc` trees and compares the legacy form against v1 on the live queue. The writer-side call is in `.claude/skills/inference-backlog-scheduling/references/grant-writer-pattern.md`. Tracked copies: only `scripts/coordination/validate_fillers.py` is tracked, and it is identical to the live copy. A durable `scripts/coordination/grant_ok.sh` + `grant_ok_launcher.py` would be loop plane and is gated by D9, like `ram_admit.sh` (OP-RAMADMIT-D9).

### Grant validator (proposed 2026-10-21, pending workspace-58 agreement)

`scripts/coordination/validate_fillers.py [--file F] [--row ID] [--for-grant]` checks the 18-column QUEUE table in `/mnt/raid0/llm/tmp/compute-flags/FILLERS.md` (column 6 `peak host RAM GiB` (formerly `max private RAM`) must be a number in GiB such as `48` or `48 GiB` -- definition (workspace-58, 2026-10-22): private/anon peak PLUS file-mapped weight bytes, counting mapped weights even with mmap; `ram_admit.sh` compares it with MemAvailable (margin 64 GiB); `class`, `status`, `DS41-class`, `ready`, `substrate` enums; `prior` a path or `none found (<who>, <date>)`; `decision` one line; `min_effect` with a unit or `n/a (build)`; `block-timing-quiet` additionally needs a champion/candidate baseline in `decision` and a floor file cited in `notes` or `prior`).
