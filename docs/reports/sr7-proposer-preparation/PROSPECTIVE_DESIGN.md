The operator retargeted SR-7 from the deprecated 122B to a served composed-recipe model. ## Comparison

Use three independent, separately granted whole-host CPU windows. Preselect at least 15 unique prompts per window, at least five each from code, RAG and real prose, and nonoverlapping prompts and seeds between windows. A prompt is the paired unit, not each request or token. For each prompt compare `ngram-mod,draft-mtp` and the non-context-reading `draft-mtp` control at draft widths 2, 4 and 6. Pin the ngram-specific width separately: `--spec-draft-n-max` does not cap that proposer. Rotate the six arm orders across prompt blocks. Hold template, formatting, seed, sampling settings, output budget and all other effective settings fixed. Use a fresh server per request, a fresh single request per server, `cache_prompt=false`, and no previous generated response in the prompt or server context. Preserve the request, actual rendered prompt and token IDs, request settings, raw response and full trace, including failure and interruption. The server lifecycle and grant controls must make the single-request/fresh-context condition independently auditable; a changed context or failed request invalidates the entire paired unit, not just its failing arm.

Audit each rendered prompt for repeated 5-gram numerator, denominator and fraction. Seal the exact prompt/seed partitions and their source and provenance, check against the known prior exposure inventories and avoid previously exposed or model-generated material; exact-hash checks alone do not establish complete disjointness. Require the actual target model, template, production-store binary and libraries to be pinned and checked before exposure, and retain verified CPU placement and linkage. The source and exact per-proposer trace format of the binary must match the parser; per-request aggregate counters must equal the sum of the per-proposer counters. The production sampler and effective launcher must be resolved and sealed, not inferred from an uncommitted registry file. The result must remain an observation until all measurement-constitution controls are satisfied.

## Draft analysis and rule

For each complete prompt and arm calculate aggregate accepted/generated draft-token ratio. Report composed width-2, width-4 and width-6 acceptance and the two adjacent paired differences (4 minus 2 and 6 minus 4), then report the same control differences. A change in unlike output lengths or in sampled trajectories can change the workload. Preserve token IDs and generated lengths and report them by arm; a prompt with an output-budget, incomplete-response or trace-counter mismatch fails the paired unit. Do not silently drop failures. Record the total planned, attempted, completed and excluded counts and reasons.

Within each window, average the prompt-level acceptance differences equally within each class, then average the three class means equally. Generate 10,000 class-stratified prompt-cluster bootstrap draws, resampling the same prompt's six arms together, with fixed seed 20261102 and windows sorted by ID. For each adjacent composed comparison use the percentile interval at sorted indices `floor((0.05/4)*(10000-1))` and `ceil((1-0.05/4)*(10000-1))`: this is a two-sided Bonferroni adjustment over the two adjacent contrasts. Repeat for the control, but treat control estimates as descriptive, not additional confirmatory tests. Convenience prompts, only five per class and dependencies between windows limit coverage and generality; these intervals are approximate and are not a power guarantee.

For each composed adjacent pair, classify the window as `RISE` only if its lower bound is strictly greater than zero, `NO_RISE_RESOLVED` only if its upper bound is at most zero, otherwise `INCONCLUSIVE`. The prospective cross-window result for a pair is `REPLICATED_RISE` only when every window is `RISE`; `NO_RISE_RESOLVED` only when every window is `NO_RISE_RESOLVED`; all other patterns are `INCONCLUSIVE`. A `REPLICATED_RISE` shows a rise on this tested model, workload and configuration; it does not prove a monotonicity violation is universal. This rule is deliberately conservative with three windows and does not convert failure to detect a rise into evidence of a decrease. There is no adaptive sample extension, post-hoc threshold or changed workload to rescue a result. A missing window, prompt, native response, counter, runtime seal, control or valid lifecycle makes the relevant result `UNKNOWN`.

For each width pair separately compute proposer generated-token shares and acceptance rates, and the exact symmetric mix/rate decomposition of the aggregate acceptance change using `acceptance_decomposition.py`. Preserve its scope: it is a descriptive accounting identity, not causal evidence. If either proposer generated zero tokens in a comparison cell its rate is undefined; show counts and mark that decomposition `UNDEFINED`, not zero and not a dropped proposer. Also show the control's acceptance curve. A mix shift consistent with the hypothesis can motivate a causal follow-up, but cannot alone prove the cause of a change or explain the historical 122B result.
