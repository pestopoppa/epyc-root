# D-f1 / D-f3a live verification readiness (2026-11-02)

D-f1's acceptance is two concurrent `/chat` requests on the same session under the live six-worker API: prove serialized ownership with the later fencing token, preserve both checkpoints, and verify no live lease remains after both return. D-f3a additionally requires live snapshot-volume confirmation in that same exercise. The source retention implementation keeps the newest 100 distinct run IDs and at most 100 snapshot rows per retained run by default, pruning in the fenced write transaction. The handoff does not specify a precise sampling procedure or imply that an empty table proves pruning.

Passive observations, 2026-11-02: `127.0.0.1:8000` is listening with one uvicorn parent and six worker processes (parent PID 2307743, worker PIDs 2307748–2307753; process start 2026-10-30 22:32 UTC). `/health` returned HTTP 200 but reported `degraded`, `models_loaded: 0`, and backend connection errors. `STATE_HISTORY_SNAPSHOTS` was absent from one worker's environment; this alone does not establish the effective feature configuration. A read-only SQL query of the default sessions database found `graph_snapshots` present but empty (0 rows, 0 distinct runs). This is a point-in-time observation of the default path; worker database identity and effective flags were not proven. Empty history cannot demonstrate a live snapshot insert or retention, and the source checkout and process start time alone cannot prove which implementation is resident in running workers. Neither checkbox is satisfied.

For a coordinated inference-owner window, first establish the actual API deployment source/commit and effective snapshot feature flag and database path without restarting another session's service; prove the running deployment includes the retention change. Confirm a usable model/backend, prepare one disposable session and capture baseline counts and relevant run IDs with read-only queries. Launch two correlated requests concurrently under a rowflow-managed grant, record request/response and lease token ordering, both completed checkpoint identities and contents, plus final lease status. With snapshot writing enabled in that controlled window, capture before/after global distinct-run count, maximum rows per run, the new run's rows and limits; distinguish no snapshot produced, preexisting oversize history and actual prune evidence. An ordinary two-request run need not cross either retention threshold and therefore can confirm observed volume/insert but cannot alone prove a live prune at the bounds. Existing deterministic tests support the source bound; do not claim a threshold-crossing live test unless the controlled workload actually crosses it.

A row needs a reviewed, bounded launcher that creates the isolated session and performs the concurrent requests and read-only postchecks, unique result path, explicit timeout/cleanup and decision rule for both checkpoints, token ordering, lease release and snapshot observation, plus write-side belief wiring before decision-bearing capture. Verify identity/configuration and model inputs outside the grant. The live API is shared; no restart, flag change, test request, database write or compute was performed during this review.
