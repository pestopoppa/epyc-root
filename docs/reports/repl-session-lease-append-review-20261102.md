# D-f2 source review — 2026-11-02

Orchestrator source examined at `9e138e3a3e22ecf8c57cd5bf50beed571d107b54`. **Decision: fence these session mutations; independent append transactions avoid row overwrites but do not prevent a stale session owner from inserting obsolete findings/documents or tags after lease loss.** No production service/database was exercised; this is a source review, not a concurrency test. D-f2 remains open until implementation and tests land.

`src/session/sqlite_store.py:1062,1130,1626` insert documents, findings and tags in separate SQLite transactions without `check_fence`; ids are primary keys and tags use `(session_id, tag)` as primary key, so concurrent distinct inserts do not overwrite one another. That limited property does not establish owner freshness or atomic consistency with checkpoint saves. `SessionPersister.sync_findings` (`persister.py:254-287`) emits findings individually after checkpoint save (`:225-230`) and clears the buffer only after the loop, exposing partial sync and duplicate-key retry if a mid-loop failure occurs. Document cache tracking (`document_cache.py:169`) and API finding/tag writes (`api/routes/sessions.py:300,378`) also lack a lease token. `update_document`, `update_finding`, `delete_finding` and `remove_tag` are additional mutations of the same data and need the same lifecycle review; `delete_finding` currently receives only an id and the route does not bind that id to the path session.

The SQLite connection factory (`sqlite_store.py:490-494`) does not enable `PRAGMA foreign_keys=ON`; although schema declares cascades and references (`:246-270,344`), SQLite enforcement is per connection and defaults off. Consequently a deleted session can receive orphan child records unless session existence is checked atomically in the same write transaction; foreign-key enforcement across all connections and existing data migration need separate careful coverage.

Recommended implementation: add optional fencing tokens to store/protocol mutations and propagate the held token through persister/document paths; use `BEGIN IMMEDIATE`, `check_fence(conn, session_id, token)`, session/child ownership verification, then mutation and commit in the same transaction. Define API behavior for external writes during a live lease (e.g. the existing 409 mapping) and preserve unfenced writes only when there is no live lease, consistent with `lease.check_fence`. Bind finding deletes/updates to the actual session in-transaction; treat tag uniqueness separately from other integrity errors. Address partial finding sync with a single atomic batch or demonstrably idempotent retries, including failure behavior and legacy no-lease callers. Validate any global foreign-key activation and orphan cleanup explicitly rather than assuming the declarations work.

Tests: two real processes with a delayed writer and a reclaimed lease for each mutation category; current-token acceptance, stale/missing token refusal without partial writes, no-live-lease compatibility, different-session independence, tag duplicate and unrelated integrity error distinction, session-deletion races/no orphans, route cross-session delete refusal, batch rollback and retry after a mid-sync failure. Verify SQLite settings on every connection and include existing-database migration/compatibility tests if foreign keys are enabled.
