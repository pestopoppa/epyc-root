# Filesystem Containment Guard

The mechanical enforcement of the operator directive **"do not touch anything
outside `/mnt/raid0/llm/`"** — the guard that did not exist when it was needed
(INC-20260823-filesystem-containment-gap, 2026-08-23): an agent ran
`sudo -n mkdir -p /mnt/bigdisk && sudo -n mount /dev/sdb1 /mnt/bigdisk`,
planned writes to `/mnt/bigdisk/epyc-backup/`, and `sudo apt-get install restic`.
Nothing stopped it — the Claude Bash surface had no guard, and the opencode
surface had no permissions and no plugins.

The original fix built the guard in two surfaces (Claude hooks + opencode
plugin/permissions) with **duplicated hand-written rule tables**. On
2026-08-23 the guard was UNIFIED: one scanner is the single source of truth,
every other surface is **derived** from it, and parity tests fail on any
drift.

## The unified model: one truth, everything else derived

```
                 scripts/hooks/filesystem_containment_scan.py   (THE SOURCE)
                 module tables + --dump-rules + --command + --check-path
                                  │
      ┌──────────────┬────────────┼────────────────┬──────────────────┐
      │              │            │                │                  │
  Claude Bash    Claude        opencode plugin  opencode          codex PreToolUse
  PreToolUse     Write|Edit    (project +       permission        hook bridge
  hook           hook          global: bash +   blocks            (codex 0.147:
                              write/edit)      (GENERATED)        wiring verified,
                                                                   firing unproven)
      │              │            │                │                  │
  .claude/settings.json (both matchers → check_filesystem_containment.sh)
  .opencode/plugins/filesystem-containment.ts (+ global copy)
  /workspace/opencode.json + ~/.config/opencode/opencode.jsonc
  ~/.codex/config.toml
```

`scripts/hooks/filesystem_containment_scan.py` is the ONLY place the policy
lives (the repo rule, RTG-52: never a fifth parser). It reuses
`shell_scan.segments()` and exposes three CLI modes, all fed by the same rule
tables:

| CLI mode | Surface | Meaning |
|---|---|---|
| `--command "<cmd>"` | Bash (all harnesses) | scan a command: CLASS A (privileged ops) + CLASS B (writes outside roots). PreToolUse JSON on stdin (`tool_input.command` / `tool_input.file_path`) is also accepted |
| `--check-path <path>` | Write\|Edit / write / edit / codex file_path | one file path against the SAME containment roots + allowlist as CLASS B: `0` inside, `2` outside (fail-closed on an unreadable allowlist) |
| `--dump-rules` | generators + parity tests | the canonical tables as deterministic JSON: class A verbs, package tools/actions, dpkg flags, write verbs by tool, containment roots (realpath'd) |

Exit `0` = allowed; `2` = refused (human message on stderr, JSON verdict on
stdout). Empty input never produces a clean verdict.

## Rule-change procedure (the operator's one-step edit)

Adding a CLASS A verb, a package tool, a write verb, or a containment root is
ONE edit plus regeneration:

```bash
# 1. Edit the table in scripts/hooks/filesystem_containment_scan.py
#    (e.g. add "nix" to _CLASS_A_VERBS, or a root to _RAW_ROOTS).

# 2. Regenerate every derived surface:
python3 scripts/hooks/generate_opencode_permissions.py --write-project --write-global

# 3. Prove parity (exit 0):
uv run --with pytest pytest -q \
  scripts/hooks/tests/test_harness_guard_parity.py \
  scripts/hooks/tests/test_filesystem_containment.py

# 4. Commit the scanner change + the regenerated opencode.json together.
#    (The global ~/.config/opencode/opencode.jsonc and ~/.codex/config.toml
#    live outside the repo — regenerate, never hand-edit.)
```

Nothing else needs to change: the Claude hooks, both opencode plugins, and the
codex bridge read the scanner at call time, and the permission block is
regenerated. **A scanner change without regeneration fails
`--check` and the parity tests** — that is the anti-drift guarantee, and the
mutation tests prove it (delete a CLASS A verb → 4 parity tests fail).

## Policy, in one paragraph each

- **CLASS A — privileged host-level operations, operator-only**: `mount`,
  `umount`, `mkfs*`, `fdisk`, `parted`, `mkswap`, `systemctl`, `modprobe`,
  `shutdown`, `reboot`, `apt`/`apt-get`/`dpkg` install/remove/purge, `dd`
  `of=/dev/*` (except `/dev/null`). Refused with or without `sudo`.
- **CLASS B — writes outside the containment root**: `mkdir`, `touch`, `cp`,
  `mv`, `tee`, `dd of=`, `>`/`>>` redirection, `rsync`, `tar -C`/`--directory`,
  `restic backup|init --repo`, `borg create|init`, `rclone` write verbs,
  `chown`/`chmod`, plus same-class siblings `ln`, `install`, `rm`/`rmdir`,
  `git clone|init|worktree add`. Containment set: `/mnt/raid0/llm/**`,
  `/workspace/**`, `/tmp/opencode/**`, `~/.claude/**`, `~/.codex/**`. Bare
  `/tmp/**` writes are tolerated (ephemeral scratch; CLASS A still applies
  everywhere). Everything else — `/mnt/bigdisk`, `/opt`, `/etc`, `/usr`,
  `/var`, `/media`, `/home/*` outside the config dirs — is refused.
- **Unresolvable targets fail closed**: a quoted or `$VAR`-expanded target
  (other than `~`/`$HOME`) is refused with `unresolvable_target`, never
  guessed at. `cd` is tracked across chained commands, so
  `cd /mnt/bigdisk && mkdir -p x` is caught.

**Semantic note on the Write|Edit unification (2026-08-23)**: the superseded
`check_filesystem_path.sh` allowed `/mnt/raid0/*` broadly; the scanner allows
`/mnt/raid0/llm/**` — equivalent in practice because `/mnt/raid0` contains
only `llm/` (verified at unification time). Its `*/.claude/*` carve-out is
covered by `~/.claude/**` (project `.claude/` lives under the roots anyway),
and its `/workspace` device check is gone — `/workspace/**` is unconditionally
inside the containment set.

## What the opencode permission block is (and is not)

The generated `permission.bash` deny patterns are **defense-in-depth for the
unambiguous literal verbs** (`mount*`, `sudo mount*`, `apt install*`,
`dpkg -i*`, `dd of=/dev/*`, ...). Two properties are inherent and stated:

- opencode patterns are literal-prefix globs: `sudo -n mount ...` slips past
  `sudo mount*` — the plugin scanner catches it (runner-skipping).
- `dd of=/dev/null` is over-denied by `dd of=/dev/*` — the scanner's
  `/dev/null` carve-out is the real decision.
- The containment roots and allowlist are NOT in the permission block: they
  cannot be expressed as deny patterns without hand-copying the rule tables —
  the exact drift this unification kills. The plugins (bash + write/edit) run
  the real check (realpath'd, allowlist-aware, fail-closed).
- opencode's schema accepts path-pattern rules for `edit`, but a static
  external-prefix deny list would be another duplicated table; the plugin is
  the gate for file tools, the permission block stays bash-only.

## Operator overrides — visible in the record, never silent

1. **One-off (both classes, all surfaces)**: set in the environment of the
   tool call / process `EPYC_FS_ACK="operator: <who> <date>: <reason>"`. Read
   from the hook/plugin scanner's process environment ONLY — a command cannot
   self-authorize by writing the ack into its own text.
2. **Permanent (CLASS B paths only)**: an entry in
   `scripts/hooks/filesystem_allowlist.yaml` (schema
   `session_bus.filesystem_allowlist.v1`):

   ```yaml
   entries:
     - path: /mnt/bigdisk/epyc-backup
       reason: operator-approved backup target
       added_by: <operator>
       added_on: 2026-08-23
   ```

   A path entry is a prefix (covers everything beneath it). CLASS A NEVER
   opens via the allowlist. If the allowlist is missing or unparseable the
   guard FAILS CLOSED (`allowlist_unavailable`).

## Codex surface — status and honest gap (2026-08-23)

`codex exec` (the RTG-52 D2 scale-out worker harness) is wired with the
same scanner via `~/.codex/config.toml`:

```toml
[[hooks.PreToolUse]]
command = "python3 /workspace/scripts/hooks/codex_filesystem_containment.py"
timeout_sec = 10
status_message = "filesystem containment"
```

The bridge (`scripts/hooks/codex_filesystem_containment.py`) reads the codex
PreToolUse envelope from stdin (`hook_event_name`, `tool_name`, `tool_input`,
`cwd`) and blocks with exit 2 + stderr reason. The wire format was verified
against the embedded JSON schemas of the locally installed binary (codex
0.147.0: `pre-tool-use.command.input` requires `hook_event_name`,
`tool_name`, `tool_input`, `cwd`, `permission_mode`, `session_id`, `model`,
`tool_use_id`, `transcript_path`, `turn_id`; blocking = exit 2 with a reason
on stderr).

**GAP, stated honestly (2026-08-23): end-to-end firing could NOT be
demonstrated on this host.** The config parses (`codex features list` loads
it), but five separate probes (global `config.toml` with both
`[[hooks.PreToolUse]]` and `[hooks.PreToolUsePermissionRequest]`, project
`.codex/config.toml`, `.codex/hooks.json`) — each a marker-writing command,
with shell tool calls demonstrably executed by the model — did not fire the
hook in `codex exec` mode on 0.147.0. So until the codex hook surface is
observed firing, **codex exec workers are effectively UNCOVERED** by this
guard (codex's own sandbox on this host is `danger-full-access`). The wiring
stays (it is the documented shape; it costs nothing when dormant and lights
up if the surface activates). Re-verify after any codex update:
`codex exec "run the shell command: echo probe"` with the hook writing a
marker file.

## Known scope limits

The guard sees the command/path an agent TYPES through a harness tool.
Daemons, cron, and scripts that internally shell out are invisible to it
(OS-level enforcement is the layer for those); the inner command of
`bash -c '...'` is quoted data and is not scanned. Quoted/`$VAR` targets are
refused rather than silently allowed. codex `apply_patch` payloads are not
shell commands and are not scanned.

## Restart requirement

opencode loads config and plugins at start. After changing the plugin, the
regenerated `opencode.json` / global `opencode.jsonc`, or the codex hook,
**restart opencode** — the running session will not pick the guard up. Claude
Code loads `.claude/settings.json` per session start; codex reads
`~/.codex/config.toml` at process start.
