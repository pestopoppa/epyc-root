# TOC-CMP-3 production-tenant canary protocol

Can an owned production tenant session cross a real compaction boundary, preserve its execution brief and governance through the final model request, and produce a continuation permitted by the semantic gate? The isolated integration and gate screens used private CPU Qwen3-4B and leave this question open. Candidate features default off. Eligibility and controls below apply prospectively. [Isolated integration results](../research/toc-cmp-3-live-results-20261118.md) · [Runtime gate protocol](toc-cmp-3-runtime-protocol-20261118.md)

## Before admitting a row

- Select a native task within the existing operator-authorized scope, with an identified owner, allowed actions, route, time window and permitted raw-capture/evaluator access. Bind its native assignment or claim and applicable access restrictions to the task, principal, tenant, session and trace IDs. Follow the normal entry point with the tenant's actual authenticated principal and record the selected orchestrator, backend and route decisions. Use an existing eligible task with an expected native boundary. Freeze the task and route before observation. Eligibility excludes replay, fixture injection, invented traffic and a boundary forced solely to obtain a result.
- Bind the specific candidate source commit, patch and dependency digests, build or image digest, configuration and scoped feature flags to the applicable deployment authorization. Prepare the concrete candidate and recovery procedure before requesting any deployment decision that existing authorization does not cover. Pin the requested compaction mode and gate position. Record who owns inference and the approved change window. Any live reload belongs to that owner at their inference boundary. Require an approved recovery procedure and name the owner who can execute it.
- Bind the approved manifests to actual serving processes at run time, separately for summary, continuation and evaluator. Record requested and resolved model IDs, immutable weight digests or a previously verified manifest bound to the loaded files, GGUF quantization and shard inventory, exact template bytes and digest, template source and rendering settings. Record kernel source commit, approved build manifest, hashes or build IDs for the actual executable and loaded ggml/backend libraries, and process/listener mapping with request correlation. Use launch/load receipts and runtime linkage evidence to prove which files served the calls, including dynamic backend libraries. Directory names, mtime and generic version strings cannot establish identity.
- Qualify capture and enforcement on the same candidate before tenant admission. Seal the observer and checks, exact expected contract and governance, reviewer controls, action oracle, scheduled observation window, request timeouts and hard row deadline. Confirm that authorized storage can hold exact bytes and that access and retention are enforceable. Resolve transport coverage against the prospective runner README under `scripts/experiments/toc-cmp-3-final-request/`. Admission requires coverage for the actual production transport, with enforcement before dispatch on the bytes bound to the gate. A shadow-only observer can support a diagnostic and leaves enforcement unobserved.

## Evidence for the admitted session

1. Record the source history and observed native fold event, including turn IDs, compaction trigger and settings, retained turns and exact omitted ranges. Require at least one genuinely omitted span. On the summary path capture the full model-backed summary request and response, extract the actual generated summary, and bind its digest to the fold and subsequent request. On the manifest path verify that the configured manifest substituted for a summary. Record call counts and whether generated summary evidence applies. Keep full authorized native event and verbatim history records.
2. Retain exact HTTP request body bytes at the last serialization before model dispatch and complete response bytes, including raw SSE frames, HTTP status, native terminal marker and any tool-call deltas. Capture the requests and responses for summary, evaluator and continuation when called. Seal byte lengths and hashes, request and trace IDs, transport/framing metadata and timestamps, with proof of receiver-side binding and stream completeness. Record the proposed final bytes for a blocked dispatch and verify from native route and dispatch evidence that they never left the gate. If an intermediary can mutate the payload, verify equality at the receiving model boundary or fail closed. Keep credentials out of recording and store sensitive bodies in the approved restricted location.
3. Decode the captured final request with the pinned schema and compare the length-framed originals literally against `verbatim_task`, `current_intent`, `plan`, `completion_requirements`, `artifacts`, `pointers` and `pinned_governance`. Check expected roles, placement and uniqueness. Where a manifest is required, reconcile it with actual omitted code, output and error entries, including empty spans. Validate each source identity, offset, length and SHA-256 directly against the sealed verbatim log. Record each literal result and manifest result separately from semantic verdicts.
4. Have a separately qualified evaluator examine the reference and complete proposed final request, including roles, retained turns and summary or manifest. Freeze evaluator weights, configuration, rubric and importer. Before admission require agreement with independent reference labels on fixed controls for compatible paraphrase, operative contradiction and missing independent support for an external-state assertion. Exercise missing evaluator, timeout, malformed result, fabricated citation and mismatched request digest as block controls. Bind each of the seven judgments and its citations to the same request digest, verify cited ranges against the captured input, and exclude continuation outputs from evaluator input. Structural checks validate evidence custody. Semantic labels remain evaluator judgments. [Semantic evaluator rubric](../../scripts/experiments/toc-cmp-3-semantic/README.md)
5. Allow dispatch only when request binding and required literal and manifest checks pass and all seven validated obligations are entailed. Contradicted, UNKNOWN, unavailable or incomplete evidence blocks. Persist the verdict and allow/block transition before dispatch, and verify the actual route behavior. Record complete stream consumption, native REPL or tool action, any execution error, side effect, terminal state and owner-approved completion check. An SSE terminal marker certifies stream completion only. A verified block is an observed policy outcome with no continuation due. A dispatched action with a verified failure stays a failure even if transport and delivery passed.

## Sample, stop rules and interpretation

Use a fixed denominator of one prospectively selected owned native session and its first eligible boundary. Freeze the observation and deadline before admission. One result moves any session fraction by 100 percentage points. Confirmed capture and policy agreement are higher-is-better. Unexpected dispatch and missing evidence are tracked separately. This sample resolves individual outcomes only and supplies no estimated error rate, effect size, adoption threshold or population inference. Qualifying controls stay outside the tenant denominator.

Stop on answer after the first eligible boundary and its verified gate and terminal outcome. Stop on futility at the first identity, authorization, custody, calibration, transport or protocol failure, unexpected dispatch, owner stop, access revocation or deadline. Record partial evidence with per-stage observed, failed, UNKNOWN or not applicable status. Missing boundary, incomplete response and unverified outcome stay UNKNOWN at the affected stage. Preserve the slot and safely stop according to the approved procedure. No automatic retry, new boundary attempt or replacement task. A later attempt requires a new prospective row.

Before publication, a production-tenant row needs sealed input provenance, a native assignment and route within authorized scope, source and serving-identity checks, qualified evaluator and capture controls, and a bounded launcher. Its run must then capture the observed fold and summary or manifest evidence, finalized request and gate decision, and verified allowed or blocked behavior; these are outputs, not prerequisites that must already exist before publication. Retain attempted rows with missing evidence in the ledger as partial or UNKNOWN. Compare any native outcome with the frozen task completion check and report custody, policy behavior and task result separately.
