# A3B harness revalidation and exploratory task comparison

Question: what useful real-world work can A3B complete independently, what guidance does it need, and does using it save main-model effort when local generated tokens are treated as free? This is exploratory evidence, not a promotion gate or a CPU/GPU benchmark. No numerical material-benefit threshold is imposed.

## Harness prerequisite

Hold real-task comparisons until one frozen OpenCode-derived configuration passes model-free controls and native C22 qualification. Preserve the twelve observed useful direct tools and the matching Code Mode catalog. Prove actual syntax-error feedback followed by corrected execution, questions answered through the supported API, child sessions, skills, public web access, read-only reference custody, effective output caps for every model role, absolute wall enforcement, and reasoning continuity through same-session resume. Preserve raw requests, outputs, tool results, hashes and failure details. A new harness defect requires repair and renewed affected controls before comparing quality.

Use C22 composite `ce6fcbbde1ee58f165283fbfe74910f47bb2efba`, both CPU and GPU servers with four slots and 131072 context tokens per slot. CPU whole-host serving may overlap GPU control cores as authorized. Thinking runs use GPU. Content-based executable/library identity, live mappings and GPU residency must be proved during inference. A qualification output cap of 8192 is a synthetic-control setting, distinct from a proposed quality primary cap of 32768 with context headroom and a separately recorded cumulative generated-token ceiling. Do not inherit the old six-read or thirty-step restriction as a model capability boundary.

## Task and mode comparison

Reuse valid historical inputs, acceptance checks and results; do not repeat completed implementations merely to close a backlog box twice. Confounded closed cases are calibration replays from their original source pins, with fresh sessions and no prior solution or critique supplied initially. Freeze acceptance to the original brief for both arms. Check every oracle against a failing baseline and a positive fixture before use; published later solutions are not interchangeable with original scope.

Run paired thinking-on/off cases on the same GPU kernel and context configuration, counterbalancing order. Official coding-on and off recommendations differ in sampling; record those exact settings and use an additional common-sampling off condition where needed to distinguish the thinking switch from the recommended profile. Treat small-case observations as case evidence rather than an inferred universal win rate. Use CPU nonthinking lanes for independent cases in parallel, without interpreting device differences as a thinking effect.

## Guidance and main-only comparison

For each eligible case, record the initial independent outcome before any additional assistance. The reused owner briefs already contain substantial task guidance (for example, PFXC supplies its p95, arithmetic and proposed budget). Label these results independent execution from a detailed pinned brief, rather than unguided work from raw backlog text. Historical brief-preparation effort is unmeasured and reused in both arms; report that limitation separately. If detailed-brief successes leave the guidance question unresolved, add fresh light-brief arms with task text, source pins and scope but without supplied solution facts, keeping both models matched. Subsequent feedback must be explicit and retained: who identified the defect, what information was provided, how many rounds, paid/main-model tokens, elapsed time and whether main directly repaired or replaced the output. A takeover is distinct from model completion after feedback. Stop on an accepted result or clear diagnostic futility, saving each increment instead of silently restarting.

Use fresh main-only sessions with the actual main profile, `gpt-6.1-sol` at low effort, pinned original inputs and the same acceptance standard. Keep them blind to A3B outputs and prior solutions. Record the fresh-context difference from this long-running manager session. Count main review, guidance, repair and takeover in the assisted arm; report harness preparation/coordination separately from task execution. Compare accepted results, paid input/cache/output/reasoning tokens and wall time. Local A3B tokens cost zero for the economic comparison but remain measured for feasibility and throughput.

## Evidence and stopping

Retain per-task and per-stream latency, actual streaming upstream/delivered TTFT, native prefill/decode timing and rates, aggregate concurrency-aware rates, prompt/cache/generated tokens, MTP proposal/acceptance, sampled resources and exact failure details. Unknown reasoning-token splits remain unknown. Nonstream response arrival is not actual first-token latency. Preserve source/binary/config/template identities and all intermediate guidance.

The initial bounded replay set is intended to answer practical routing and guidance questions; expand only if the observed cases leave a concrete question unresolved. Do not claim the harness fully repaired from unit controls alone, a thinking benefit from device-confounded runs, or economic benefit from excluding main review and repair. Findings extend the existing Taskflow belief-source contract rather than creating a second grading ladder.
