## HIL-2 — objective axes and evaluation plan (design only)

Common report columns for each paired arm: successful task completion/correctness (higher better); invalid/error rate and other failed executions (lower better); latency and model-token cost per successfully solved task (lower better); plus the feature-specific axis below. Keep scored and attempted counts separate. A refusal is an objective only when the case is a labelled unsafe-control and the refusal is correct under that label; an unlabelled refusal is not a quality/reliability objective and remains a separately reported outcome. Declare each feature's primary objective before arm generation; auxiliary axes diagnose trade-offs and cannot be promoted retroactively. Pin inputs, harness/config/prompt digests, suite/split identity, and applicable stack/request conditions for both paired arms.

| HS-4 feature | Primary axis and source-named suite | Paired comparison / protocol boundary |
|---|---|---|
| §3.1 profile memory | BEAM `preference_following` and `instruction_following`; compare profile-on with explicit `x_memory=off`. Also retain M-12 no-memory control and the UTM-V3 write-precision audit as a separate safety outcome. | P-AB-1 is the existing orchestrator A/B protocol for a paired feature effect. Use the existing M-12/BEAM instruments and their pinned arms; write precision remains an explicit labelled audit unless its claim protocol is human-ratified. |
| §3.2 notes | Same BEAM preference/instruction outcomes, but only as a separate on/off leg if §3.1 first shows an effect. | Reuse the same P-AB-1 comparison and the §3.1 frozen suite/split. No extra suite or metric is justified before the conditional leg opens. |
| §3.3 session search | M-12b BEAM `trace` arm and UTM-B4 Tulving `retrieved` arm; retrieval evidence recall and task correctness are reported separately. | Reuse P-AB-1 for a paired surface change; honor each owning M-12/UTM protocol and holdout. Retrieval hit/recall alone is not an answer-quality claim. Do not add an LLM summary arm. |
| §3.4 background review | Labelled-transcript proposal precision/recall; BEAM preference-following with derived-profile vs no-memory; background prefill tokens/session (lower better). | Mechanism tests/SMOKE are not efficacy claims. P-AB-1 can cover paired downstream outcome only if its unit and sampling contract fit; proposal precision/recall is not currently given a named protocol in this source map, so it remains an observation until a human-approved protocol amendment defines labels, denominator, sample unit and noise rule. |
| §3.5 delegation | Delegation task success and child-artifact correctness; routing decision correctness/parity; latency and token cost per solved task. | Use the existing delegation rows in the eval tower and P-AB-1 for paired prompt/parameter effects. Existing live `/chat` vs `/v1` escalation acceptance remains a separate runtime gate; no source-only result substitutes for it. Generalization/promotion requires the existing P-QUAL-PROMO holdout rule, not the tuning set. |
| §3.6 compaction | CF-3c quality monitor with mandatory masking/truncation anchor; Tulving/BEAM long-context folded-vs-full arms; prefill tokens per solved task, prefix-cache hit share, and byte-identical-prefix check. | Reuse P-AB-1 where the paired A/B unit is appropriate; preserve CF-3c and the owning M-12/UTM protocol. Prefix identity and mechanism correctness are gates/diagnostics, not quality evidence. A fold failure must remain visible and counted. |
| §3.7 skills | No HIL objective until the separately named M-11a/M-12 SkillBank A/B gate admits it. | No tuning before P0.4 freeze and the SkillBank gate. Each exported skill remains a reviewed commit. |

Protocol governance: MEASUREMENT.md defines claim grammar and its registry. P-AB-1, P-QUAL-T1, P-QUAL-PROMO and P-SMOKE-1 already exist for their stated scopes. A mechanism smoke or a value lacking a fitting cited protocol is an observation and cannot gate keep/revert/promotion. Any new protocol, metric definition, sample unit, MDE/noise rule, or amendment to existing protocols requires human amendment under MEASUREMENT.md §5; this design does not create one. HS-5b/P0.4 ordering is strict: no tuning or efficacy claims until the OpenCode Harness Card is published and P0.4 acceptance/freeze is complete. HIL design itself can proceed before that point.

## HIL-3 — option-B shared-substrate extraction plan

The source review does not support moving the AutoPilot controller or copying its gate logic. Several named components already exist as importable modules; the brittle boundary is that key journal/gate/PromptForge pieces live under `scripts/autopilot`, where the running controller establishes `sys.path` and frequently imports bare module names. Keep one implementation and expose a narrow package API; do not fork logic into a second loop.

| Component named by HIL | Current source/call shape | Proposed extraction / effort (engineering days, estimate) |
|---|---|---|
| Journal + shards | `scripts/autopilot/experiment_journal.py` (`ExperimentJournal(journal_dir=...)`) and `journal_shards.py`; AutoPilot imports journal from script path. Journal already supports explicit directory and dual package/bare import, but owns append/rotation/repair semantics. | Leave implementation and storage contract in place; define a package-qualified, read/write API used by both callers, make journal-path explicit for the sibling loop, and prohibit it from opening AutoPilot's live journal by default. Preserve append-only, locking, fsync and recovery behavior. **1–2 d.** |
| Safety/promotion gate | `scripts/autopilot/safety_gate.py`; controller builds `SafetyGate`, then runs `SafetyGate.check` and baseline/promotion methods. It consumes tier baseline, archive and regime state. `src/autopilot_core/ap55_promotion_gate.py` is already a pure importable component but is only one part of the gate. | Expose a no-side-effect evaluation entry point taking explicit immutable baseline/infra/suite evidence; leave baseline mutation and AutoPilot state update on the existing controller path. Sibling loop can call a verdict but cannot ratchet the production baseline. **1–2 d.** |
| PromptForge / MHS guards | `scripts/autopilot/species/prompt_forge.py` combines proposal code including `subprocess.Popen` with validation; `_prompt_forge_convention_guardrails` is in `scripts/autopilot/actions.py` beside dispatch/application behavior. | Extract only pure validation/classification guards into an import-safe module and keep old functions as delegates to the same implementation. Sibling must never import/instantiate proposal code just to call a guard; no Claude CLI, apply, commit or worktree path is reachable. **1–2 d.** |
| Infra identity | `src/autopilot_core/infra_fingerprint.py`; controller calls `_infra_fingerprint_for_trial` / baseline capture. `src/autopilot_core/ap55_promotion_gate.py` consumes the resulting fingerprint. | Reuse these source modules directly. Pass captured identity as data; collector remains read-only and PID-bounded. No additional extraction needed (0–0.5 d integration). |
| AP-53 rejected-mutation ledger | `scripts/autopilot/rejected_mutation_ledger.py`; action reject paths append it and planner renders it. `reproposal_rate.py` imports the ledger and journal. | Reuse ledger builder/fold with an explicit separate loop ledger path; package-qualified imports and read-only projection for planning. No backfill/cross-write into AutoPilot's live files. **0.5–1 d.** |
| AP-54 eval fence | `src/repl_environment/knowledge_fence.py`; `/chat` arms the context carrier per request and hooks record/deny touched paths. Existing eval fence is request-scoped; absence means production no-op, false is unarmed control. | Reuse the fence through the existing request field/trace seam; the sibling loop must not create a second fence or change production semantics. Pass explicit `eval_fence` in eval requests; verify both arms through the normal eval path when later authorized. **0.5–1 d.** |

Estimated narrow compatibility extraction: **4–9 engineering days** (rounded up from the per-row rough bounds, whose sum is 4–8.5 engineering days), including parity checks after each seam. This is an unvalidated planning estimate, not a commitment. It excludes the future sibling-loop driver/scheduler/UI and feature-specific objective/evaluation instruments. A conservative sequence is (1) identify side-effect-free exports, (2) add package-qualified aliases without changing call order, (3) make new API consume explicit paths/immutable evidence, (4) route AutoPilot through those aliases with unchanged args/ordering, (5) parity-regression checks and inspect the diff. No runtime default, baseline file, live journal, endpoint, policy or decision gate changes. Existing `program.md` describes evaluation data/scoring and safety gate as a trust boundary; do not import edit authority implied by older broad “can modify” prose. The MHS-3/MHS-4/MHS-5 guards and human-only MEASUREMENT policy remain authoritative.

## Scope gaps / MAIN application notes

1. HIL-1..5 are all design/prospective-preparation deliverables, distinct from the globally deferred act of starting the improvement loop. They do not need P0.4 before preparation; they do need it before tuning.
2. The source map's several §3.1–3.6 implementation descriptions are historical design state. HIL-1 classifies the intended surfaces; it does not assert that every feature currently has a serving caller or is deployed. HIL-2's suite list likewise records planned/source-named instruments, not that they have run or passed.
3. Current SC86 source-table row is `OpenCode-shell runs through /v1 (HS-4 P0.4 acceptance, HS-14 bake-off)` → `measurement` → `scripts/vidya/adapters/opencode_shell_run.py`. At ROOT `df50558f`, `opencode_shell_run_capture.py` writes a closed-schema `opencode_shell_run.beliefs.jsonl` at run finalize; `opencode_shell_run.py` reopens the recorded attempt-file bytes and projects them to the shared ClaimTuple grader. 4. One HIL-4 phrase in the original handoff says the substrate needs refactoring into importable components.
