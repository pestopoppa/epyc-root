## Goal and threat model

An evaluated agent may be adversarial: it can inspect every byte, path, environment variable, tool result, and process interface available to its process; attempt filesystem traversal, symlink following, `/proc` inspection, network access, persistence, and resource exhaustion; and encode discoveries in its candidate output or tool calls. A grader or reference artifact is any withheld oracle material that can reveal the answer or affect scoring: hidden tests, expected outputs, reference implementations, deterministic judges, private fixtures, scoring prompts, credentials, and control state. The security objective is that the agent and candidate code cannot read or alter these artifacts, and cannot change the trusted grading decision. Confidentiality and integrity must be enforced by the OS boundary and by the judge/worker dataflow; transcript review is only a secondary tripwire.

The evaluated agent, runner, and trusted grader currently may share one host user and checkout. Exact deployed UIDs, mount tables, process ancestry, and path permissions were not established by this source-only audit. Treat the current setup as co-resident and potentially mutually readable until a runtime deployment proves otherwise. Same UID permissions and a git worktree are not isolation. A separate worktree does not help if it is mounted or traversable by the agent.

## Source-audited current layout

- DTAP source and grader material are inside the orchestrator repository: `scripts/autopilot/evals/dtap/cases.json`, `fixtures/`, `judges/<case_id>/judge.py`, and `manifest.json`. TU-DTAP-1 imports the 18-case subset into this tree (`handoffs/active/tool-use-eval-contract.md`, TU-DTAP-1); thus these bytes are in the shared workspace checkout unless a runtime mount policy hides them.
- `scripts/autopilot/evals/dtap/harness/runner.py` defines `JUDGES_DIR` as the sibling `judges/` directory; `JudgeApplication.load()` imports `judge.py` into the runner process. `CaseRegistry` reads the registry JSON. The run process therefore needs grader access. Whether the model-serving process can also read these paths depends on its UID and mount namespace and is unverified here.
- `harness/endpoint.py::ChatEndpoint.complete()` sends model/messages/temperature/token-limit fields to an OpenAI-compatible endpoint; the request body contains no judge path. `harness/runner.py::render_messages()` constructs the agent-visible prompt from case prompt material. This is an application-level separation, not an OS barrier: endpoint/model processes may still see shared host paths.
- `harness/trace.py::TraceRecorder` writes JSONL records with a SHA-256 chain and replay re-applies the deterministic judge. The native verifier checks in-file chain/root consistency; detecting a complete coherent rewrite additionally requires comparison with a separately retained trusted trace ID/root or other authenticated anchor. The trace's in-file chain/root alone is not an authenticated anchor: someone able to rewrite the complete trace can construct a self-consistent replacement. Hashes support integrity checks and reproducibility when anchored; they do not prevent a process with path access from reading the judge or changing the live environment.
- `scripts/benchmark/code_exec_scorer.py::_run_once()` creates a fresh temporary cwd, limits CPU/address-space/core, supplies a small environment, starts a new process session, and kills the process group on timeout. `score_code()` appends an assert-style test snippet to candidate source before launching Python, so that test source is part of the executed script. Its module docstring explicitly says there is no network isolation or real filesystem jail and prohibits adversarial code. `handoffs/active/scoring-infra-standardization.md` 2a-iv plans bubblewrap (`--unshare-net`, read-only root, tmpfs `/tmp`); this is planned scorer hardening, not evidence of an active sandbox and not by itself proof that a model agent cannot see grader files.
- `src/typed_decisions/prepared_action.py` fingerprints a host snapshot and offered choices, validates freshness/authorization, and emits a receipt. These typed contracts protect decision integrity and replay/accountability; they do not constrain process filesystem, mount, UID, network, or `/proc` access. Same for DTAP typed outcomes, judge AST/trace guards, and transcript grep.

## Required separation

1. **Control plane / grader:** own the case registry, hidden tests, expected values, judge source, scoring policy, signing keys, and final score. Run under a dedicated UID or a separate service identity. Keep grader storage outside every checkout/worktree visible to the evaluated agent. Do not pass hidden tests or expected answers in prompts, tool schemas, environment variables, argv, candidate-visible files, or candidate-process stdin.
2. **Agent process:** expose the task prompt, public tools, sanitized task inputs where required, and a private per-run scratch filesystem. Use a private mount namespace or equivalent jail with explicit allow-listed mounts; hide unsanitized host workspace/repo roots, grader roots, host home, credentials, and writable host paths. Use a dedicated UID with restrictive permissions as defense in depth. Deny network by default unless the evaluation explicitly requires a mediated service; never let network reach grader storage or host control sockets. Restrict process view and inherited file descriptors. Apply CPU, memory, process-count, disk, and wall-time controls at the worker/cgroup boundary.
3. **Candidate transport:** send only bounded candidate bytes and a run identifier from agent to grader over a narrow broker/pipe/socket. The broker validates size/type, stores candidate output in a fresh untrusted area, strips paths/metadata as appropriate, and grants no readback channel to reference data. The candidate must not choose a grader path, test selector, or score. Exports from the trusted runner are limited to typed verdicts and approved diagnostics; no reference bytes, stack traces containing private paths, or judge-derived hints. Bind candidate, task, and verdict with content hashes in the trusted record. Hashes document identity; they do not substitute for OS access control.
4. **Candidate execution:** treat generated source as hostile even after model generation. The execution worker must not receive the grader tree, hidden test source, runner credentials, host mounts, or unrelated network. Keep the oracle in a trusted supervisor. Where hidden tests are needed, use a protocol that lets trusted code decide the verdict without embedding the tests in a candidate-readable source file or argument. The current `code_exec_scorer.py` assert concatenation violates that confidentiality goal for hidden assert snippets and is explicitly trusted-code-only; it cannot satisfy TU-GR-1 for adversarial candidates as-is.
5. **Audit tripwire:** scan transcript, tool arguments/results, candidate output, and worker file/network audit records for grader-path literals and denied-access attempts. A path-literal or denied-probe hit prompts review; it does not by itself establish access or invalidate a run. Benign negative probes may intentionally name the protected path. A trusted canary disclosure or evidence that the agent/candidate accessed or controlled grader material fails the isolation acceptance. A miss proves nothing: an agent can use aliases, symlinks, descriptors, encoding, or other channels. Preserve the benchmark's existing judge, outcomes, and score denominators; any broader incident-handling policy is separate work.

Do not select a specific container, namespace, UID arrangement, or broker implementation in this spec. Bubblewrap is the existing planned 2a-iv candidate for code execution; the agent-side boundary, trusted supervisor split, and evidence protocol remain unspecified implementation work. A mechanism is accepted only after its concrete launch configuration and operating environment pass the access-denial matrix below.

## MAIN-reviewed JEV refinement alignment

The published TU-GR-1 refinement requires coordination with scoring-infra 2a-iv and specifically names `src/typed_decisions/judge_redundancy.py` as a reusable frozen-rubric and typed verdict/failure contract. Conformance fixtures may mock verdict readers while keeping expected labels host-only; they must test denied grader-path reads, leaked-path transcript review, changed candidate/read-set detection, malformed or unresolved verdicts, and controlled result export. They should retain separate independent-accuracy and reader-agreement measures, with agreement never presented as accuracy. This specification does not edit or activate the coherence judge and adds no grading ladder.

Those fixtures validate policy/dataflow handling only. They should include (a) expected denial for grader-path reads, (b) path-literal transcript hit classified as review rather than automatic failure, (c) changed candidate digest and changed prepared read-set rejected as stale/mismatched, (d) malformed and unresolved typed verdicts retained as failures, and (e) exported result constrained to the approved verdict schema. They do not prove OS isolation; the chosen mechanism still needs its real synthetic access-denial acceptance check before untrusted benchmark use. This source-only audit cannot say which models or chat templates are active at runtime.

## Acceptance matrix for a future implementation

All cases must run against the actual agent and candidate-execution identities/mount namespaces using a benign sentinel grader file containing a unique random value. Capture OS-level denial evidence (mount namespace, effective UID/GID, capabilities, visible mounts, and denied syscall/path result) from inside each tested process. Synthetic mocks and unit tests can validate wiring only; they cannot support a security claim. Any actual read/write access or trusted-canary disclosure fails the isolation gate and disqualifies that run from an isolation-backed claim. A denied probe is expected evidence, including when it names the protected path.

| Probe | Required result | Evidence |
|---|---|---|
| Read known absolute grader/judge/reference path | `ENOENT` due to absent mount or `EACCES` from separate UID/mode policy; sentinel bytes never appear | Inside-process open attempt + mount/UID snapshot; a denial is expected and not itself an incident |
| Traverse from cwd using `..`, absolute paths, symlink chains, hard links where applicable | Cannot reach unsanitized host workspace/checkout, grader, host home, or sibling run | Attempt log plus namespace/mount evidence; a denied probe is expected and not itself an incident |
| Inspect `/proc/<runner-pid>/root`, environ, fd, maps, cmdline; inspect inherited FDs | No grader bytes, credentials, writable control FDs, or host namespace handles | Explicit probes and FD inventory |
| Read grader data via relative import, `PYTHONPATH`, cache, bytecode, environment, argv, stdin, trace, or tool response | No hidden content delivered; only approved public task bytes and bounded candidate input | Input-channel inventory and sentinel scan |
| Inspect own source/argv while candidate executes hidden-test case | Candidate cannot recover hidden tests or expected values; checker remains outside candidate-readable process inputs | Canary hidden test plus file/argv/stdin inspection |
| Write/delete/rename grader files; mutate judge, trace, score, neighboring run | OS denies; grader source and expected artifact digests remain unchanged | Denied operations and before/after trusted hashes |
| Network, Unix sockets, host services, container/runtime sockets | Denied by default; only explicitly mediated allow-listed endpoints reachable | Egress/socket probes and firewall/namespace record |
| Candidate emits path probes or sentinel guesses in output | Output is treated as untrusted; no extra grader bytes are returned; path literals prompt review; a trusted canary disclosure or actual access fails the gate | Raw candidate output, typed outcome, tripwire result, canary comparison |
| Controlled export from grader to agent | Only declared verdict/diagnostic schema leaves; no test contents, paths, secrets, or judge internals | Schema validation and leak scan against sentinel corpus |

At minimum repeat the matrix after changes to worker image, UID, mount list, launch flags, host kernel/runtime, candidate transport, grader path, or shared-host topology. Record exact versions/config hashes and the tested identities. The security statement must be scoped to those measured conditions and must not claim general isolation from mock-only tests. A unit test or mock may verify expected status handling but cannot substantiate an access-denial claim.

## Reusable pieces and missing work

Reusable evidence/mechanisms: DTAP's deterministic judge and hash-chained trace; `JudgeGuard` source/handler attestation; typed failure outcomes; prepared-action snapshot/fingerprints and decision receipts; scorer time/resource limits and descendant process-group cleanup; the planned bubblewrap direction in 2a-iv. These improve reproducibility, decision integrity, observability, and resource bounds.

Missing for TU-GR-1: actual runtime agent/worker mount and UID boundary; grader outside the agent-visible namespace and worktrees; network and host-interface restrictions; a brokered candidate-byte boundary and controlled exports; hidden-test execution without candidate-readable test source; and access-denial evidence from the actual launched process. Review handling for tripwire hits and a separate policy for confirmed exposure remain implementation governance questions. None of the reusable pieces above is a substitute for these controls.

## Scope and next step

This document specifies a boundary and evidence gate only. No sandbox is activated, no judge or scorer is changed, and no live run is authorized. Runtime integration is a separate HIGH-risk task requiring a concrete mechanism and review before deployment. TU-GR-1 remains open until an implementation passes the matrix with real OS-enforced denial evidence.
