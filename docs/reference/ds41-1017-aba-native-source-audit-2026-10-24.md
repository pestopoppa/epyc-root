## What the ABA bytes warrant

The six served result files retain arm, segment, concurrent GPU-job label, load duration, warmup markers, token counts and measured rates. Their recipe files retain exact argv and selected environment values, including the model path, binary path, CPU-only flags, serving parameters, and port. Logs and driver stdout retain model-load details, region-lock role/CPU coverage, segment start/end and process rc. These support a descriptive historical account of what the committed files say was run.

They do not provide a native row that binds those values to result bytes, an emitted timestamp/measurement identity, producer revision, model shard pins, binary/library digests, or source HEAD and dirty state. The raw llama-bench JSONs were not committed; the research `SUMMARY.md` says they remained in `/mnt/raid0/llm/tmp/ds41-w5-20261021/runs-aba/` and records their hashes and summary values. Recomputing a sidecar or ClaimTuple now would assert a write-time warrant that was not captured. Do not do so.

The retained command line suggests the 1017 and Sept model paths and CPU backend. It does not replace the native producer's artifact/binary custody. For a source-authored row with that custody, the existing adapter's safe scope is exact `model_file` and `backend: cpu`, with `quant` omitted. Do not infer a whole-model quant, particularly for Sept Q4, whose full-file digest was never recorded. `loop_beliefs.collect()` prefers this explicit source applicability over legacy `SOURCE_SCOPES`; the matcher uses the model basename and checks declared dimensions, while an absent quant stays undeclared. Applicability rules do not create a native source row where none exists.
