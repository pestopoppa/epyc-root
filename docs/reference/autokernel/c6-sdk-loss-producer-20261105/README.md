# SDK buffer receipt prototype — uncompiled and unqualified

This isolated in-process SDK client creates one lossless 1 MiB buffer with HIP runtime API and kernel-dispatch services. It records every callback's reported drop value and header count, typed API and dispatch data, and a SHA-256 over the exact closed record stream in a receipt bearing its in-process PID, context, buffer, SDK status codes, counters and write-error flag. It stops the context, explicitly flushes, and only then emits a receipt; missing receipt is inconclusive. Raw callback drop values are retained rather than assuming cumulative or incremental semantics. `records.csv` lines begin C (callback sequence, header count, drop count), A (correlation, numeric operation, thread, start, end, PID) or K (correlation, agent, queue, kernel, dispatch, start, end, workgroup xyz, grid xyz). Kernel IDs are not resolved to names. Context and buffer handles are process-local, not physical identity.

Source references are pinned in SOURCE.sha256: the installed 6.2 SDK headers and sample used for signatures and lifecycle. This is a source prototype only: **no compile, load, native execution, GPU, independent SDK ABI review or actual receipt has occurred**. Do not attach to production, publish or claim qualification. Build and runtime must be independently checked against exact source, SDK/ROCm shared library, OpenSSL ABI, and target process; establish correct tool loading order and callback/finalizer semantics and inter-client conflicts. Failure to initialize might leave records with no receipt; no evidence should be inferred. `fini` depends on normal SDK finalization: crashes, signals, `_exit`, callback failure, or failed writes can omit or truncate the receipt. SDK stop/flush success and zero observed callback drop values concern only this tool's buffer; they do not prove hardware/driver delivery, every source event, successful finalization of other buffers or another tool's output. File hashes and in-process PID are self-reported, not authenticated custody; private same-UID files are forgeable. Caller must independently bind PID plus birth/executable and loaded tool identity, KFD agent and device, grant, record file descriptors and output ownership, ensure receipt is complete and digest matches, and account for test selection and trace output size. This tool does not bind or validate rocprofv3 CSV and cannot confer its loss guarantees on it. Correlation is conditional, not an operation attribution or complete-coverage assertion. GPU smoke, negative/drop/flush/fault injection, performance overhead and cleanup remain future work.

## Target-operation boundary is absent

The retained pre-b4 `BASE-SOURCE.json` pins `tests/test-backend-ops.cpp` SHA-256 `1083472c74143af21e6561266cf5136e888999cbfc5b58d68212201adeda9cc7`; the corresponding retained source at `/mnt/raid0/llm/tmp/codex-c6-mmvq-fix-20261102/src/tests/test-backend-ops.cpp` shows warmup and repeated graph/timing around lines 3272–3341. This prototype captures whole-process initialization and warmup as well as the selected operation, without a marker or timestamp boundary to distinguish them. No normalized target dispatch structure or target attribution follows. A future design must implement and validate operation-specific boundaries in the source-bound test harness (or an independently verified equivalent), distinguish warmup from measured intervals, and rebind/requalify the paired images before any target-operation conclusion.
