# Harness Cards — EPYC layer-B disclosure

**Promoted 2026-09-17** out of [`handoffs/active/harness-selection-and-integration.md`](../../../handoffs/active/harness-selection-and-integration.md)
(rows HS-6, HS-6b, HS-6c), which is where they were written and ticked. They are standing
disclosure artifacts, not campaign history, and they have a consumer outside that handoff:
[`agents/shared/HARNESS_RUN_POLICY.md`](../../../agents/shared/HARNESS_RUN_POLICY.md) requires a run
report to name *"the applicable Harness Card"*.

**Two cards, two questions.** The first asks *what can be changed without code*; the second asks
*what configuration produced a score*. They are complements — a run report cites the conformant card
and lists where its run departs from it.

Re-publishing rule (HS-7): a model or freeze change refreshes the conformant card for the realized
configuration before the result is called re-targetable.

### HS-6 Harness Card — current Layer-B disclosure (2026-07-29)

This card is a source audit, not an assertion that every listed surface is live in every
request path. “Editable” means a policy/configuration/prompt or pluggable client surface can
alter the behavior without changing its mechanism; “code-owned” means a code change is needed.
The latter is not a defect — it is where security, correctness, and measurement boundaries belong.

**Selection implication.** A cooperating open harness should control only the editable client
surface (transport, toolset, per-request body overrides, and its own compaction/delegation knobs —
each of those knobs counts as cooperating only if it passes the HS-1g call-verb check).
It must not absorb the code-owned memory, output, observability, or governance mechanisms. This
preserves the Layer-A moat and makes a harness/model swap a client integration rather than a
trust-boundary migration.

### HS-6c Conformant Harness Card — EPYC eval tower (ETCSOVG / arXiv 2605.23950 Appendix A Table 3), 2026-09-16

This card sits beside the editable-vs-code-owned card above and complements it. That card asks *what can be changed without code*. This one asks *what configuration produced a score*. Values are the settings the **eval tower actually uses** (`epyc-orchestrator@92bbeb06`, source-read 2026-09-16, no run). A run report cites this card (HARNESS_RUN_POLICY.md "applicable Harness Card") **and** lists where its run departs from it. Gaps are disclosed as gaps, not filled. `intake-1344#record`.

**Undisclosed or unfixed fields (the card is conformant *because* these are named, not because they are solved):**
1. No substrate isolation for the REPL or the code_execution scorer.
2. No eval-wide network-off switch.
3. Pinning is owned by the launcher, not the tower.
4. No emitted per-role tool manifest.
5. No retryable-class contract.
6. Ordering and cache policy are undeclared.
7. Live memory flags are not written to artifacts.
8. `worker_vision` has conflicting `n_ctx` values.
9. No rollback contract.
10. No per-row trajectory pointer or checkpoints.
11. No self-check or anomaly stage.
12. No test-based patch validation in EvalTower.
13. Approval is auto-approve.

Two consequences follow. First, **any cross-harness comparison run on this tower is locked-harness only**, per the paper's admissibility rule. Second, items 1, 7, 8 and 10 are the cheapest to close. `scripts/autopilot/system_card.md` (`gen_system_card.py`) already records roles and tiers and is the natural generator for this card. Wiring that is a follow-up and is not done here.
