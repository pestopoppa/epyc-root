# FW-3 — prior art for fuzzy workflow authoring

Verified 2026-10-06 from official documentation. This is a design survey for [FW-1](../../../handoffs/active/fuzzy-workflow-authoring-gui.md#fw-1-sketch--worker-failure-routing-as-a-two-layer-workflow-2026-09-17), with no ingestion, installation, model download, execution or GUI implementation. Borrow the authoring affordances below into the existing contract; they confer no runtime, calibration or latency evidence.

| Prior art and verified affordance | Borrow for FW-1 | Refuse in the EPYC authoring contract |
|---|---|---|
| Dify exposes separate failure branches with error type/message; iteration can continue with nulls or omit failed outputs. [Error handling](https://docs.dify.ai/en/cloud/use-dify/build/predefined-error-handling-logic). | A visibly distinct `reject`/`fallback` edge carrying the gate ground and reason to its destination; preserve failed outcomes in the record. | Silent substitution or dropping failed attempts as success. Every exhausted parse/retry path needs an on-canvas destination; a missing destination blocks save. |
| Dify distinguishes stateful loops from independent iteration, offers maximum counts/exit nodes, and separates working drafts from published versions. [Loops](https://docs.dify.ai/en/cloud/use-dify/nodes/loop), [versions](https://docs.dify.ai/en/cloud/use-dify/build/version-control). | Show loopback, persistent state reads, each independent budget, and draft revision identity. Reuse the single referenced failure-routing `subflow`. | A shared loop count that charges parse repair to worker retry/escalation; opaque exits; a Publish control that enables a workflow. Authoring remains proposal-only pending existing execution gates. |
| Langflow uses typed ports and validates incompatible connections; exported JSON carries nodes, edges and metadata, and can include API keys. [Typed components](https://docs.langflow.org/components-custom-components), [flow export](https://docs.langflow.org/concepts-flows-import). | Typed input/output connectors, visible `reads`, and a reviewable versioned document with stable node/edge references. | Provider URLs, credentials or arbitrary component code in imported documents. FW-1 code nodes reference owned functions; fuzzy nodes reference roles/pins or proposed program IDs. Model work stays through `LLMPrimitives`. |
| PAW's official playground is the authoring entry point; docs describe spec/compiler content identity, cached compiled artifacts, and website compilation publishing programs by default. [Playground](https://programasweights.com/playground), [pipeline](https://programasweights.readthedocs.io/en/latest/guide/how-it-works/), [publishing](https://programasweights.readthedocs.io/en/latest/hub/publishing-programs/). | A spec editor with task examples, explicit compiler/program revision, and separate compile-candidate versus invoke affordances. | Compiling/uploading internal specifications as a save side effect, downloading/interpreting bundles automatically, or treating a stable program ID as correctness/calibration evidence. PAW remains an internal research candidate under its owning handoff's gates. |

The existing seam is source-native typed decisions, not a workflow compiler: APP `15e5b52ec8941c8a46211d363cc9b6774813b30b` has [`QuestionKind`/catalogues](https://github.com/pestopoppa/epyc-orchestrator/blob/15e5b52ec8941c8a46211d363cc9b6774813b30b/src/typed_decisions/types.py), [schema builders](https://github.com/pestopoppa/epyc-orchestrator/blob/15e5b52ec8941c8a46211d363cc9b6774813b30b/src/typed_decisions/schema.py), [parser and explicit JSON/native runner modes](https://github.com/pestopoppa/epyc-orchestrator/blob/15e5b52ec8941c8a46211d363cc9b6774813b30b/src/typed_decisions/runner.py), and [native decoding](https://github.com/pestopoppa/epyc-orchestrator/blob/15e5b52ec8941c8a46211d363cc9b6774813b30b/src/typed_decisions/native.py). `noul` is a boolean question kind, not a transport-null or failed-output substitute. The pure [confidence expectation helper](https://github.com/pestopoppa/epyc-orchestrator/blob/15e5b52ec8941c8a46211d363cc9b6774813b30b/src/typed_decisions/confidence_expectation.py) accepts explicitly synthetic exact coverage; it never changes a discrete decision. Native probability provenance remains distinct from calibrated correctness.

A runtime workflow compiler/executor was not located in the surveyed APP `src/` and `orchestration/` source; compiled-function execution and the workflow document remain proposed seams. Keep FW-1's `code/fuzzy/gate/expensive/terminal/subflow` vocabulary and L1–L11: total value edges, recorded probabilities, explicit fallback, independent counters and gate placement before expensive work. Confidence branching still requires an operator-ratified record for the exact model pin/catalogue. Shadow proposals must preserve executed arguments and stay off the foreground critical path; latency is an unmeasured execution gate, not a borrowed UI promise. Existing ClaimTuple/native-receipt grading governs evidence; canvas validation or passing fixture evidence cannot authorize deployment. See [typed-decision plane](../../../handoffs/active/typed-decision-plane.md), [PAW contract](../../../handoffs/active/paw-compiled-specialists.md), and [loop design](../../guides/agent-workflows/agent-loop-design.md).

Placement remains FW-2's contract: subsystem schema/executor in the orchestrator, page/registry/health/freshness on the hub, no second router or shell runtime. This note settles FW-3's survey and informs the existing sketch; it does not close FW-1's mocked-GUI execution acceptance.
