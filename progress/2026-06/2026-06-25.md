**Goal**: graft ik_llama's `iqk_mul_mat` AVX-512 quantized-GEMM kernels into `production-consolidated-v6`

### Result — all 3 stack quant patterns covered, correct, measured uplift (same-build GGML_IQK on/off, llama-bench)

| Model | Path | Quant | Prefill pp512 | Decode tg128 | Correctness |
|-------|------|-------|---------------|--------------|-------------|
| gemma-4-31B | dense | Q4_K_M | 155.9→232.5 **+49%** | 8.66→9.34 **+7.9%** | byte-identical |
| gemma-4-26B-A4B | MoE | Q4_K_M | 577.7→707.5 **+22.5%** | 44.5→48.5 **+8.8%** | byte-identical |
| Qwen3.6-35B-A3B | MoE | Q8_0 | 401.0→500.6 **+24.9%** | 26.3→26.4 ~0 (BW-bound) | correct, FP-cascade |

Q8_0 decode neutral is expected: 8-bit is fully DRAM-BW-bound on EPYC, the kernel can't add headroom
(no regression). Q8_0 chat output is correct (Paris+primes, coherent) but not byte-identical (early
tokens identical → late FP-cascade) because the dequant/repack prefill path is distribution-preserving,
not bit-exact ([[project_q8_8x8_avx512bw_outcome]]) — eval-suite parity is the deploy gate, not bit-compare.

### Two root-cause fixes en route (debugged, not patched)

1. **Dequant crash** (commit `715383cde`): ASAN found a `type_traits[]` global-buffer-overflow READ —
   `is_dequant_better` returns ik-only repacked types (Q8_0_R8=208, Q8_K_R16=397) which were passed to
   v6's `ggml_row_size`, indexing past its 42-entry table. Fix = `iqk_row_size()` shim using ik's
   block-size formulas at the 3 dequant call sites. (Earlier "heap corruption" / "8-vs-16 packing"
   diagnoses were red herrings — ASAN gave the primitive evidence.)
2. **Prefill only +16% vs ik's +62%** (commit `c9bf4dad4`): `GGML_USE_CPU_REPACK` intercepted >85% of
   Q4_K matmuls on v6's generic-C kernel BEFORE the iqk hook. Fix = guard in
   `ggml_repack_get_optimal_repack_type` returning nullptr for iqk-supported types when GGML_IQK=1.
   This also revealed decode was repack-STARVED, not BW-capped — closing the guard restored +7.9–8.8%
   decode on Q4_K (superseding the earlier "decode neutral / BW-bound" read for 4-bit).

## gitnexus analyze — non-TTY progress visibility fix (tooling)

**Problem.** `gitnexus analyze` (run via `scripts/gitnexus-analyze.sh`) logs a start banner, a few
warnings, then goes silent for the entire multi-minute graph-build — can't tell "still working" from
"hung." Reported at ~26 min, ~1 core, 8.3 GB on the epyc-root re-index.

**Root cause (confirmed by reading the package, not guessed).** The CLI *already* computes full
pipeline progress and feeds it to a `cli-progress` SingleBar (`dist/cli/analyze.js:338`, `updateBar`
at `:292`). That bar is a TTY widget: `cli-progress` defaults to `noTTYOutput:false`, so when stdout
is not a terminal — exactly the case under our wrapper / the agent harness (output captured) —
`bar.start/update/stop` render nothing. The progress data was computed and thrown away. Not stuck,
just invisible.

**Decision (operator).** Progress-tracker fix only; multi-core deferred. Parsing is *already* parallel
(worker pool `min(8, os.cpus()-1)`, `workers/worker-pool.js`); the slow tail (cross-file binding
propagation, MRO, Leiden communities, process tracing) is single-threaded and mostly algorithmically
sequential — out of scope for now. Patch must self-heal after `npm update -g gitnexus` wipes `dist/`.

**Changes.**

| File | Repo | Change |
|------|------|--------|
| `scripts/gitnexus-patch.js` (new) | epyc-root | Idempotent, sentinel-guarded, version-stamped patcher. Injects a non-TTY renderer into the installed `dist/cli/analyze.js` that prints `[gitnexus +Ns] NN% \| <phase>` to **stderr** on every phase change and on a **15s heartbeat** (keeps the silent sequential tail observable). Hooks the package's existing `onProgress`/`elapsedTimer`; adds no pipeline logic. Fails safe: anchor-miss → warn + exit 0 without modifying the file. |
| `scripts/gitnexus-analyze.sh` | epyc-root | Runs the patcher (non-fatal `\|\| true`) before `exec gitnexus analyze …`, so the fix re-applies on every invocation and survives gitnexus upgrades. Header conventions + `--skip-agents-md --skip-skills` preserved. |

Target mutated by the patcher (NOT in our repos):
`/usr/local/share/npm-global/lib/node_modules/gitnexus/dist/cli/analyze.js` (gitnexus 1.6.5).

**Results (verified end-to-end on a 40-file scratch repo).**
- Patcher applies once; second run reports already-patched (idempotent); mutated file passes `node --check`.
- Non-TTY run: clean progress through every phase — scan → structure → parse → resolve imports/calls →
  MRO → Leiden communities → process tracing → LadybugDB load → search indexes → `100% Done`, then
  `indexed successfully`.
- TTY path (PTY-allocated): no plain lines leak; original `cli-progress` bar still renders (NON_TTY guard holds).
- Negative path: corrupted anchor → patcher warns, exits 0, file byte-identical (md5 unchanged).
- Scratch repo + temp logs cleaned; throwaway gitnexus registry entry removed.

**Deferred — multi-core.** Parse worker cap is hardcoded `min(8, cpus-1)`; on the 96-core box only 8
cores parse. Lifting it is a one-line env lever, but parse may not dominate wall-clock. The graph-build
tail (cross-file/MRO/Leiden/processes) is genuinely sequential; per-level parallelism of cross-file is
feasible but needs correctness work. Now that progress is visible, a real re-index will show which phase
actually dominates — defer the multi-core decision until it's measurement-driven.

### Deep-dive: recommended actions required correction

Post-intake analysis of the autopilot journal revealed three errors in the initial recommended actions:

1. **"Q3/Q6/Q7" don't exist** — fabricated suite names. Actual suites: `general`, `math`, `coder`, `thinking`, `simpleqa`, `hotpotqa`, `gpqa`, `debugbench`, `livecodebench`, etc.

2. **MR filter inapplicable to autopilot** — the journal has 141/852 trials with `question_results` (trials 789–969), tracking 1382 unique qids. Only 50 qids appear in ≥50 trials (stable core). Of those 50, **only 3/50 are mid-range (30–70%)**; the rest are 15 floor (<30%) and 32 ceiling (>70%) questions. Applying the filter would reduce the stable eval core from 50 to 3 questions. More fundamentally: the MR filter optimizes cross-agent rank ordering; autopilot performs within-system regression detection — opposite sensitivity requirements. Ceiling questions are regression signals; floor questions are breakthrough signals.

3. **Leaderboard submission angle removed** — of no interest.

### Correct applications

- **Autopilot use**: per-qid pass rate data should drive question pool *curation* (rotate saturated/floor qids from `simpleqa`, `general`, `coder` stable core), not subset selection.
- **TB Core external evals**: after building a Harbor adapter for our `/v1/chat/completions` (~1 day: Terminus-compatible wrapper over OpenAI-compatible endpoint), run the 89 fixed TB Core tasks. The MR filter then reduces future TB re-runs to ~37–50 tasks at stable rank fidelity.
