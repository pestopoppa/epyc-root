## CH-19.1 — the fused MoE up+gate path never engaged (fixed, `b51a0047d`)
- Diagnosis confirmed in source: `ggml_can_fuse_ext` requires node i to consume node i-1. The up and gate
  MUL_MAT_IDs are siblings (same src1 and ids; only the GLU consumes them). Graph order is gate, up, SWIGLU,
  because the DFS visits `glu->src[0]` first. So the predicate was always false, and the earlier NMSE of 0 was vacuous.
- New predicate `ggml_cpu_can_fuse_moe_up_gate` (ggml-cpu.c) is `ggml_can_fuse_subgraph` plus these conditions:
  SWIGLU split form, not swapped, src0=gate/src1=up, both nodes adjacent, use count 1, no views, shared src1+ids,
  same shape.
- Second bug fixed in the same commit: if `iqk_moe_fused_up_gate` failed after the per-thread activation
  quantization had written wdata, the fall-through raced the unfused MUL_MAT_ID's use of wdata. All threads now
  pass a barrier before falling back.
- Result: the fused path engages in every cell (one process per cell, marker present) on Q4_K/Q8_0 x nt=1/8.
  Fused-vs-unfused NMSE is exactly 0, which is real: the same iqk GEMMs run on both paths, and iqk `v_silu` is a
  copy of `ggml_v_silu`. test-backend-ops CPU-vs-ref: MUL_MAT_ID 815/815, MUL_MAT_ID_FUSION 13/13, SWIGLU 24/24.
