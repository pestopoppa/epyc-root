## Verdict: not a REG bug; failures 1-4 are pre-existing, 5-12 come from the oracle
- **The oracle.** `test-backend-ops` compares the CPU backend with itself under `use_ref`. Under `use_ref`, `ops.cpp` forces
  the vec `one_chunk` loop, with no tiling and no split-KV. C's default hybrid accumulates F16-V `VKQ` in **FP16**
  (`ggml_vec_mad_f16`), rounding once per cell over the whole KV. REG never runs under `use_ref` (port commit).
- **The error is linear in KV, at one constant on both paths.** ERR/kv is about 2.1e-8 to 2.3e-8 per cell for D=256 REG
  (kv 64k and 128k) and also for D=512 non-REG (kv 32k and 64k). Rounding an N-term FP16 sum gives an NMSE of about u^2·N, which
  is linear in N. The same constant on a path that cannot run REG means the common cause is the oracle. It also predicts a pass at
  kv 8192 (about 1.8e-4), which is what happened.
- **D=512 decides nb=1.** `fa_vacc_f16_select(DV=512)` returns null, so B with REG=1 runs C's code for D=512. The
  harness also shows Bunset byte-identical to C. Those cells fail only at nb=1, where the default takes the split-KV path:
  192 threads (`hardware_concurrency`) each run a short FP16 chain and the partials are reduced in FP32. nb>=2 runs the
  oracle's own loop and passes. **So C fails the 4 nb=1 cells as well.** That is the prediction for the filler below.
- **The 8 cells at D=256, nb>=2.** C runs the oracle's own FP16 loop there, so it passes (prediction). REG accumulates in FP32,
  so it differs from the oracle by the oracle's own FP16 error. Here REG is the more accurate side.
- **The fixed-seed harness dumps already on disk**
  (`fa_h{1,2}_{C,B1,Bauto}`) give an NMSE for REG vs C of 3.3e-5 to 4.4e-5 at 1024 visible cells, 6.7e-5 to 8.4e-5 at 2048, and
  8.9e-5 at 4096: the same linear law. The NMSE is exactly **0** wherever REG is off (DV 512/576, tiled nb>=64, and auto with
  DV<256 and multiple rows). At nb=1 C's split-KV path is close to FP32 itself (7.5e-6).
- **Static review of `8110933ba`** (`accumulate_reg`, `fa_vacc_f16_block<NR>`) found no defect. The block max is taken over
  the scored cells. `ms = exp(M - Mnew)` scales both S and the accumulator, with 0 on the first block into a zeroed `VKQ32`. A
  block that is all -INF is skipped before M changes. The -INF run skip advances exactly `GGML_FA_MASK_RUN` cells and stays inside
  the block bound. The standard 5207-case corpus passes 5207/5207 under REG=1 and auto, including mask, sinks, softcap, ALiBi and
  odd DV.
- **Not decided from logs:** C and B-unset were never run on the long set. The filler below measures that directly.
- **No fix commit.** REG is not at fault, so nothing goes onto `experimental/fa-vkq-reg-on-c-20261022`; the tip stays `8110933ba`.

## Parser fix (`/mnt/raid0/llm/tmp/fillers-3c4ca599/v11drv/fa086v2_integrity.py`, backup `.bak-pre-ansifix`)

before `FAIL`, so `\bFAIL\b` never matched. The parser now strips ANSI first. It records each `[OP] ERR|NMSE = x > thr CASE: test
failed` line (case, err, threshold) and the `Failing tests:` block. It adds `parser_consistent`, which is False when the pass count
is below the total but no case was captured. `--selftest` covers all of this. INTEGRITY.json was regenerated (backup
`.bak-pre-ansifix`). `long_B1` and `long_Bauto` now report `n_failed` 12, 12 captured cases, 12 listed, and consistent; `tbo_fa_100`
is still False. **The same latent bug is in the timing driver** `v11drv/v11_driver_086v2.py::parse_tbo`: it uses `\bFAIL\b`
and `NMSE =`, while this build prints `ERR =`. It fails closed (passed==total is still required), so I left it alone because it
is the running poller's job. Patch for main: reuse `parse_tbo_text` from `fa086v2_integrity.py`.

## Decision package — what the long-context integrity gate should compare against (operator / main; not this agent's call)
The facts behind it: the gate's oracle is about 1.4e-3 NMSE away from the exact result at 64k cells and about 2.8e-3 at 128k.
That is 3 to 6 times the 5e-4 tolerance. So the long set as written rejects any FP32-accurate path, and (predicted) C's own nb=1
decode path too. It cannot separate a correct kernel from a broken one beyond about 24k cells. Production C runs with
`GGML_FA_SPLIT_KV=0` and therefore carries that FP16 error at long context. That is a pre-existing accuracy property of the
champion, not something introduced by V11-086.
- **A. Keep the gate as written → V11-086 is hold.** No rule change. REG is never timed, and the gate would hold any future
  FP32-VKQ candidate the same way.
- **B. FP32 oracle (recommended once `v11-086-longfa` confirms the prediction).** Under `use_ref`, accumulate F16-V VKQ in
  FP32. The patch is one line in `ggml_compute_forward_flash_attn_ext_f16_one_chunk`:
  `vkq_f16_first = v->type == GGML_TYPE_F16 && fa_vkq_mode != FA_VKQ_F32 && !params->use_ref`. The 5e-4 tolerance stays.
  - It needs its own commit on an experimental branch, a rebuild of the test binary for every arm that uses this oracle, and a
    recorded amendment to the predeclared integrity gate. The amendment is post-hoc, so it needs the operator's ratification.
  - Expected result: REG passes the long set. C's FP16 hybrid fails the long nb>=2 cells, which exposes the accuracy property above.
  - Risk: standard-corpus cases near kv 16384 (predicted NMSE about 3.6e-4) may come close to 5e-4 for C. A run is needed before
    adopting it.
- **C. Make the long-set gate relative to C** (B's fail set must be a subset of C's). REG still fails the 8 nb>=2 cells, so
  this does not help on its own.
- **D. Scale the tolerance with KV** (for example 5e-4·kv/8192). Not recommended: it also loosens the gate for real errors.
- Recommendation: run `v11-086-longfa` first, since it costs about 10 minutes and needs no decision. If the predictions hold, take
  **B** and re-run the long set on C, B-unset, B REG=1 and B REG=auto against the FP32 oracle. Until then V11-086 stays **hold**.
