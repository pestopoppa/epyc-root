# Bundle-attached document search candidate

`bundle-search.patch` applies after `document-search.patch`; `repl_document.bundle-candidate.py` is the resulting candidate. It accepts a bundle only when exactly one text section is byte-for-byte equal as a Python string to the complete reconstructed searchable document. It returns section-relative offsets with `bundle_section` and `read: context.get`; a caller opens the hit via `context.get(name, max_chars=end-start, offset=start)`. Search itself consumes no pull; the existing bundle getter enforces byte budgets and accounts for the actual UTF-8 read. Missing or duplicate exact sources fail before search and pull; it never charges document text to an unrelated bundle section. Legacy no-bundle behavior is retained.

Four synthetic controls pass (`PYTHONPATH=/mnt/raid0/llm/epyc-orchestrator /mnt/raid0/llm/epyc-orchestrator/.venv/bin/python -m pytest -q progress/evidence/repl-emb42-document-search/test_bundle_candidate.py`): pointer resolution and accounting, budget refusal, missing source, ambiguous source. These are not model, retrieval-quality, or live API results.

This is not an integrated feature. The current `request-optin.patch` intentionally rejects document_search with context_bundle and must be redesigned before use. In the existing executor, the document branch overwrites the earlier bundle root prompt; review the full request path, prompt, pre-existing document accessors, print caps, and externally supplied document identity before lifting that guard. This exact-full-document convention is restrictive; no fallback to mismatched or text-identical-but-ambiguous sources is allowed. Search accounting is not added to `context_pulls.search`; only the subsequent `context.get` pull is counted. APP has not been edited or reloaded.
