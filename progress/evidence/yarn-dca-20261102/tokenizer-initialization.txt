DCA candidate tokenizer GPU initialization audit — 2026-11-02. No re-execution or GPU access during audit.

Finding: the executable used for candidate segment counts was HIP-linked, not CPU-only. It was run without acquiring the canonical GPU claim. The count command's source and the built machine code show that it enters backend initialization and that the HIP backend registration calls hipGetDeviceCount. The retained evidence does not establish whether that call succeeded, whether a GPU was visible, whether a HIP context or VRAM allocation occurred, or whether the GPU executed work. It was a vocabulary-only tokenizer run, not inference. My prior report's statement that no GPU lock was acquired was correct, but it omitted this GPU-initialization exposure and must not be read as saying the run was CPU-only or had no GPU interaction.

Evidence:

Exact executable SHA-256 53767a9aa1140c2a08a6183c9906affc4547691471f8eb328402b7ccb93fe9f0 matches candidate-counts.json and the current executable. The successful four outputs and counts were recorded in the session; receipt records their hashes/counts. The initial invalid-option attempt exited before normal backend initialization; the corrected command succeeded four times.
- readelf reports tokenizer dependencies on libllama-common.so.0 and libllama.so.0; candidate libggml.so.0.16.0 directly needs libggml-hip.so.0. Candidate build configuration has GGML_BACKEND_DL=OFF, GGML_HIP=ON and its ggml CXX_DEFINES include GGML_USE_CUDA and GGML_USE_HIP. HIP library needs libamdhip64.so.6. Binary inspection shows the tokenizer calls llama_backend_init, candidate libggml calls ggml_backend_cuda_reg, and candidate HIP library calls hipGetDeviceCount. Candidate source tools/tokenize/tokenize.cpp:142 invokes llama_backend_init before loading model with vocab_only=true; src/llama.cpp:89 initializes backend registry; ggml/src/ggml-backend-reg.cpp registry invokes ggml_backend_cuda_reg; ggml/src/ggml-cuda/ggml-cuda.cu:217 calls cudaGetDeviceCount, mapped to hipGetDeviceCount by ggml/src/ggml-cuda/vendors/hip.h:76. Successful output requires reaching tokenization after this call path.
- Each subprocess used stderr=PIPE, but candidate_counts.py neither saves nor prints stderr; only token IDs and counts/digests were retained. There is no contemporaneous per-process KFD/VRAM trace or loader map, no retained device-enumeration log, and no preserved environment snapshot for device visibility. Accordingly, whether initialization reached a visible device and any effects on another workload cannot be reconstructed. Static dynamic-link evidence plus source/build configuration identifies the expected path, not an observed successful GPU residency.

Qualification: candidate-counts.json supports the stated count result within its recorded source/model caveats; it does not establish GPU residency, absence of GPU use, server tokenizer equivalence, or scientific inference behavior. No inference, publication, or resource-lock acquisition occurred in count preparation. Future tokenizer captures must use an independently verified CPU-only build or normal canonical GPU ownership, retain stderr and process/loader provenance, and avoid relying on vocabulary-only as proof of no GPU initialization.
