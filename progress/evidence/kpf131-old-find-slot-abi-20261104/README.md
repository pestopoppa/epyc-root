# KPF-13.1 old-image find_slot entry inspection

The existing historical `libllama.so.0.0.10348` at `kernels/builds/gpu-20261020-a1f0c8cf9/bin/` matches SHA-256 `33bf73eaedfee5a52aa07312d0d12431133e23c54d411744e7bd51bccf375f64`. The standalone inspector checks 14 exact instruction signatures in executable ELF segments at fixed virtual addresses, accepting that image only. It reports 14 matches. Its six model-free tests include a mutation at each signature, mismatched digest, malformed/truncated ELF, wrong architecture, a nonexecutable segment, and ambiguous overlapping mappings.

The actual image's demangled `find_slot(llama_ubatch const&, bool) const` begins at `0x15a280`. Its entry saves incoming RDI, RSI, RDX and ECX, dereferences RSI and RDX, and its return path writes the result through the saved incoming RDI and returns that pointer in RAX. Thus an observer that blindly treats entry RDI as the cache object would inspect the result buffer instead. In this build the code's use of a hidden return pointer and source signature implies RSI is the cache `this`, RDX the ubatch reference and ECX the boolean; these remain a source-and-machine-code interpretation pending live native validation.

On the debug-enabled path, instructions read `this+0xc8`, `this+0xc0`, `this+0x90` and `ubatch+0x10`, `ubatch+0x40`; the stream index multiplies by `0x3098`. Source at experimental commit `a1f0c8cf9`, `src/llama-kv-cache.cpp`, suggests the corresponding seq-to-stream, cells, heads and unique-sequence access, but these offsets alone do not prove data structure field layout or that particular snapshot values are valid. `this+0x70` gates this path; the source calls it `debug`. Exact instructions and control flow may differ in any other image.

No model, historical cell, GPU or debugger was run; no physical cache position, allocator head, batch row, request association or current/historical DSO custody was established. This is a static, incomplete candidate for the later native fixture and is not an approved capture adapter.
