## D5 — the correctness gate never ran, and blamed the patch every time

`gates.op_correctness` invoked `test-backend-ops ... --suite-seed <n>`. That flag does not
exist in this llama.cpp tree, so the binary printed its usage text and exited 1, and the
gate reported `MUL_MAT failed on ROCm0`. For every candidate. In every run.

Proven against the anchor, which passes 1139/1139:

```
test-backend-ops test -o MUL_MAT -b ROCm0 -j 1 --suite-seed 2026081301   → exit 1
test-backend-ops test -o MUL_MAT -b ROCm0 -j 1                           → exit 0
```

**Retracted as a result:** the published run-9 analysis said 7 of 10 iterations died
because the patch broke MUL_MAT correctness, and concluded the Q4_K dequant path is
numerically load-bearing and unpatchable by the planner. Those seven patches were never
tested. The conclusion had no evidence and is withdrawn.

Fixed so the shape cannot recur: a non-zero exit is not sufficient evidence a test failed
— it is equally consistent with the tool refusing to run — so the verdict is decided on
**positive proof the suite executed** (its own `backends passed` summary), and an oracle
that could not run returns a distinct `oracle_unavailable` verdict that must never read as
evidence about the patch. A silent exit 0 does not pass either. (research `d40e9b8e`)

**Memory was poisoned and is retracted.** 16 of 28 rows carried the fabricated verdict, and
the critic was already citing them — run-9 rejections quote *"Already measured and
rejected: … MUL_MAT failed on ROCm0"* — so a harness fault was steering new hypotheses away
from correct work. Annulled in place by `scripts/benchmark/autokernel_retract_false_oracle.py`
(backs up first, refuses if any row is left unannulled, regenerates `experiments.md`).
Retracted rather than deleted: the attempt happened and is worth keeping, only the reason
was false, and deleting would make a future planner re-derive it blind.

For two of the four the veto was **decision-changing**: `akm-q4k-wave-row-ownership` (+1.664%) and

### Root cause: DVFS, observed directly rather than inferred

A passive trace — read-only `pp_dpm_sclk` + `gpu_busy_percent` sampling, adding no load of its own,
**2,554 samples over 21.7 min** — shows the card occupying exactly **two** clock states and nothing
in between:

| sclk | samples | share | mean busy |
|---|---|---|---|
| 800 MHz | 2,316 | 90.7% | 0.05% |
| 1700 MHz | 238 | 9.3% | 72.4% |

The GPU idles at 800 MHz and jumps to 1700 MHz under load — a **2.125× clock transition at the
start of every benchmark window**. Each `llama-bench` invocation is a separate process, so the card
dropped back to 800 between invocations and paid the ramp again on the next one. That is the
mechanism by which a fixed anchor binary drifts, and it is a direct observation, not a hypothesis
fitted to the drift numbers.

Two independent instruments agree on the same quantity: 238/2554 = **9.3% of wall time under
load**, against the loop's own separately computed **91.8% idle-while-claimed**. Trace:
`/mnt/raid0/llm/epyc-root/tmp/ak-loop-deploy/dvfs-trace-BEFORE-pin.tsv`.

### Resolution

The operator pinned `power_dpm_force_performance_level` to `high` (root-owned; this session runs as
uid 1000). Verified after the change: perf level `high`, `pp_dpm_sclk` pinned at **1700 MHz** on
every DPM level, idle temperature 33 °C.

**Run 11 was launched identical to run 10 in every respect except the pin** — same surface, same 9
pairs, same 1.175% floor, same store, same anchor commit — so the two runs are a clean comparison
of clock policy and nothing else.

Independently of the pin, the loop now records `sclk_min_mhz`, `sclk_max_mhz` and `clock_stable` in
**every** residency proof (research `44da8b2e`). A result taken across a clock change now says so
in its own record, instead of needing a separate trace to discover it after the fact. The pin is
host policy that another session or a reboot can undo; the record is ours.

## D7 — the drift GATE was a coin flip, and the clock check could not fail

`drift_pct` is a median-of-halves contrast. On 9 samples that is a 4-vs-5 split consuming two
order statistics and discarding the other seven; its **null SD is about 1.10% against a 1.175%
bar**. Measured on this harness it **vetoed 7 of 9 comparisons**. The flagship case,
`akm-fattn-single-partition-direct`, was vetoed at +1.599% median-of-halves while its rank
trend was rho = +0.100, p = 0.81 — no trend at all.

Replaced with a **Spearman rank-trend test against position** (critical values tabulated by n;
0.700 at n = 9, two-tailed alpha 0.05). Distribution-free, uses every sample and all the
ordering information, imports no calibration from another statistic. A gross median-of-halves
backstop survives for arms shorter than 8, where no rank test has power. `drift_pct` stays
*reported* as a size diagnostic; it no longer decides.

Replayed over all 9 recorded comparisons, **vetoes fall 7 → 2** — exactly the two arms with
real trends (rho = +0.800). Four results resolve, all above the floor: +1.664%, +2.621%,
**+4.284%** and its own rerun +3.385%.

**The clock check was vacuous too.** `sclk_mhz` read `pp_dpm_sclk` and took the starred DPM
level; under performance level `high` that file stars *both* levels, so it returned 1700
unconditionally, `min == max` by construction, and `clock_stable` was True on every run
forever. A check that cannot fail is not a check. It now reads the achieved clock from hwmon
`freq1_input`. (research `a1fcc89e`)

## D8 — the noise floor was built from subsets of one fixed sample

`MEASURED_FLOOR_PCT` was p95 of |median effect| over exhaustive subsets of **one fixed 20-pair
sample**. Subsets of a fixed sample cannot exceed that sample's own observed tail, so the
construction was bounded below the true p95 *by construction*: it measured how much one sample
varies internally, not how much a fresh measurement varies.

Recalibrated by bootstrap over an **A/A campaign** — three conditions (settled, preheated,
post-build), 20 fresh pairs each, true effect zero by construction, so every non-zero number
it produces is estimator error:

| pairs | enforced (decode) | bootstrap (decode) |
|---|---|---|
| 5 | 1.502% | **2.422%** |
| 9 | 1.175% | **2.021%** |
| 20 | 0.067% | **1.188%** |

**The 9-pair bar we had been keeping and rejecting against was low by 0.846 pp.** Only the
`tg128` row is rewritten; the campaign measured only that surface and `pp512` remains
uncalibrated. Every run from 13 onward uses 20 pairs at the **1.188%** floor.

Re-adjudicating every recorded measurement, two verdicts change — and one of them is a banked
champion commit, `akm-fattn-two-partition-collapse-stabilized` (+2.018%), which now misses by
0.003 pp. **It nevertheless stands**, on the pooling argument above: six measurements of one
patch, median +3.834%, all six positive, sign test p = 0.031 — significance from the sign
alone, assuming nothing and needing no floor. Its recorded +2.018% understates the mechanism by
about 1.8 pp.

The design gap this exposes is filed rather than fixed: **the loop keeps on a single comparison
and has no notion of pooling repeated measurements of the same mechanism**, even though its own
planner reached for exactly that. (research `bbdbf0c5`, `011c4d74`; A/A log
`aa-campaign/aa-campaign.json` in the store)

## D9 — the anchor never advanced, so every effect was cumulative

Run 13 (`tg128`, 20 pairs, floor 1.188%, sequential) ran **10 iterations in 118.6 min and kept
four patches**. Only one of the four improved anything.

The anchor was a **fixed binary** while the candidate worktree accumulated every kept patch, so
each reported effect was cumulative against original v9 rather than the marginal value of the
patch under test. A patch that made the champion *worse* still cleared the floor, because the
accumulated total did. Decomposed across the whole champion history to that point:

| commit | mechanism | cumulative | **marginal** | |
|---|---|---|---|---|
| `61d00786` | `akm-q8-1-contiguous-1d-index` | +3.898% | **+3.898%** | WIN |
| `5582ebcc` | `akm-fattn-two-partition-collapse` | +2.018% | −1.809% | noise |
| `042cb2e4` | `akm-q4k-branchless-scale-unpack` | +5.574% | **+3.486%** | WIN |
| `bbbce33c` | `akm-q8-1-float2-halfwave` | +5.353% | −0.209% | noise |
| `2a52f805` | `akm-q8-1-float4-eighthwave` | +4.849% | −0.478% | noise |
| `b04fad24` | `akm-q8-1-fourlane-dual-fragment` | +1.846% | **−2.864%** | **REGRESSION** |

Two real wins, three nulls, and **a regression committed as a keep**. The champion ended at
+1.846% over v9 having been +5.574% one commit earlier.

*"Screen against the champion so gains compound"* was the requirement from the start. A static
anchor asks *does the accumulated tree beat v9*. The question that decides a keep is *does THIS
patch improve on the best we have*, and only an advancing anchor asks it.

The fix is cheap because the kept candidate build **is** the new champion, already compiled:
promotion is a directory *move* (never a copy — an anchor sharing a path with the next candidate
is an anchor that measures against itself), and it happens only after the commit succeeds. The
champion was **reset to its demonstrated best, `042cb2e4`**; the three demoted commits are
tagged `ak/pre-anchor-fix-full-history` and their patches remain in the store. (research
`cf3de5fd`)

## D10 and D11 — run 14 found two defects, and one of them was in a test I had just written

**`shutil` was never imported.** `promote_anchor` calls `shutil.move` and `run.py` did not
import it, so anchor promotion raised `NameError`. Run 14 kept a real **+6.723%** patch,
advanced the champion to `01893a36`, then crashed in promotion — the keep was recorded as a

**The drift veto over-vetoed.** A trend test says an arm *moved*; it says nothing about whether

at least a third of the effect. Either alone is wrong: magnitude alone was the coin-flip gate
D7 replaced, trend alone discards a strong effect over a small wobble. The force-MMQ case still
vetoes correctly — there the drift *was* the result. Re-adjudicated over every recorded
measurement, **8 vetoes lift, 7 of them to KEEP**. (research `0a34801f`)

## Runs 15–16 — continuous operation, and the loop noticing its own repetition

Two capabilities landed between the runs:

- **Superseded is a queue entry, not a loss** (research `f003d9bd`). A candidate formed against
  champion N and overtaken before it could be measured is *not refuted*. It is banked and
  re-proposable against the new champion, with a disposition that says so in those words.
- **The loop must notice its own repetition** (research `ac08e41b`). Run 11 measured one
  mechanism seven times and run 15 measured `akm-q4k-reuse-q8-sum` five times. A mechanism
  measured 3+ times is marked **characterised** and the planner is told, rather than waiting for
  a human to spot the pattern in a log.
- **Continuous operation** (research `1c3c5c98`, `4d17196b`, `e434df4b`): unbounded iteration
  with a STOP sentinel, re-profiling on every champion advance (the hotspot table is stale the
  moment the champion moves), and anchor pruning so generations do not accumulate on disk.

1. **The git order was wrong.** `reset_to_champion` ran `checkout --detach` *before*

2. **The containment gap.** `reset_to_champion` sat **outside** the lane's `try` block, so a

   published status, kept advancing the champion, and reported nothing wrong — **it just ran at
   43% capacity**. A degraded run that looks healthy is worse than one that stops, because
   nobody goes looking.

Everything an iteration does is now inside the `try`, recorded as `lane_error` with the raising
frame; mutation-tested, one of the two tests checking the lane **recovers** rather than merely
survives. Worth stating plainly: the `lane_error` handler was added earlier the same day
*specifically* so a lane could not die silently, and the first statement of the loop body was
left outside it. **A guard that covers most of the thing it guards reads exactly like one that
covers all of it.** (research `9b31c648` — its title says four lanes because it was written

## D13 — the STOP sentinel was accepted and dropped

`drive()` took a `should_stop` parameter and **never forwarded it to `run_pool`**. The sentinel
sat in the store for **three hours of run 16** doing nothing: the file existed, the predicate
was correct, the parameter was in the signature, and none of it was connected. Accepted and

The test meant to cover this asserted that `pool.stop_requested()` returns True for a file on
disk. It does. **It never checked that anything asks.** Now forwarded, with two tests: one
pinning the forwarding at the call site, one end-to-end proving an unbounded pool actually

`champion_tree` to the **live** champion tree and the first version reached for the running
