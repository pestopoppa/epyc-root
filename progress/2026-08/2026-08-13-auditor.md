## D4 — HIP bf16 LIGHTNING_INDEXER numerical failure (root-caused to bf16 load path)

Operator-directed GPU task on the idle MI210. Reproduced the `GGML_OP_LIGHTNING_INDEXER` `type_K=bf16`
backend-op failure on frozen `production-consolidated-v9` and narrowed it decisively.

- **Repro** (v9 `build-hip` `10125`, HIP residency proven via `verify_ggml_linkage.sh` PASS + device log
  `AMD Instinct MI210`): `test-backend-ops -o LIGHTNING_INDEXER -p type_K=bf16` → `6/12` fail, all `nb=1`
  (`ERR≈1.0`); `-p type_K=f16` → `12/12` pass. Deterministic, identical to the recorded v7/v8 result.
- **"Flaky" is refuted**: the isolated 5-rep run in the v8 audit re-tested the *passing* `nb=512` shape, so
  "v7 fails 5/5, candidate 0/5" was both builds passing the same non-failing config. The real discriminator is
  `type_K=bf16`, not build or chance.
- **Root cause narrowed to the bf16 K-load path of `lightning_indexer_kernel_vec`** (`lightning-indexer.cu` →
  `get_dequantize_V<GGML_TYPE_BF16,…>` → `dequantize_V_bf16` in `fattn-common.cuh`). Ruled out: WMMA kernel
  (`#if !defined(GGML_USE_HIP)`, never runs on gfx90a — the handoff's "WMMA-era" suspicion is wrong), tensor
  indexing (q/k/w/m all cross-checked vs CPU reference), warp reduction (shared with f16, which passes),
  bf16 type sizes (2B/4B confirmed via HIP headers), and the HIP `ggml_cuda_cast<float2>` low/high extraction.
- **Standalone ggml dump** (`/tmp/opencode/dump_{li,li2,f16,rand}.cpp`, linked against `build-hip/bin`) shows
  bf16 output is a constant garbage value (`3.3e7` for all-ones; `~-3.5e5` for random) for *all* batch sizes in
  the direct non-graph path, while f16 is byte-exact — so the bf16 K load itself is defective, not the batch
  geometry. (`ERR≈1.0` in the test is NMSE with garbage-dominated output, not a "half" — corrected my own
  earlier read.)
- **Impact**: latent correctness bug only — no production role uses a bf16 indexer K-cache. DSA indexer bf16
  path is numerically untrustworthy on gfx90a.
- **Remaining for upstream**: pin the exact line via `hipPrintf`/patched build comparing `dequantize_V_bf16`
  against the known-good `vec_dot_fattn_vec_KQ_bf16` (fattn-common.cuh:117), then file against `ggml-cuda`
  (introducing commit `3b5321936` / PR #25545).

Evidence: `epyc-inference-research/data/kernel-v8-candidate/lightning-indexer-v7-v8-{baseline,isolated}/`
(v7/v8) + this session's v9 `test-backend-ops` runs. Handoff `llama-cpp-dsa-contribution.md` D4 checkbox
