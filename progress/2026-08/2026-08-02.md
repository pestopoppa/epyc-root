### P-GPU-1 circularity — scoped, not deferred

Follow-up question resolved: the GPU protocol carries two clauses that bite at different times
(new §3.0). The **consumption** clause blocks every GPU T1 round from the first campaign and is what
`P-AK-SEARCH-1` exists to lift; the **decision-grade** circularity blocks only a freeze that needs new
GPU evidence. It is *not* confined to "GPU freezes", because CPU and GPU share `llama.cpp` and one
frozen branch — a CPU-only champion still produces a new binary on both paths whenever it touches
shared ggml core.

Added the **binary-identity escape** (AK-D18): the release plan compiler compares candidate and
incumbent binary plus linkage hashes per backend; byte-identical means the incumbent's evidence
transfers by identity and that backend's cells drop from the matrix with an explicit receipt. Wired
into §10.2 phase 1 and the AK5 compiler task.

Sequencing decided: **draft the amendment early, ratify it last.** Its bindings reference the
evaluator bundle hash, derived scope manifest, and evidence hash tree — artifacts AK1 and AK3 produce.
Protocols are append-or-version and never silently edited (`MEASUREMENT.md:116-118`), so a binding
written against a schema sketch is expensive to walk back.

**Correction to the first formulation of the escape.** Naive binary byte-identity was wrong and would
never have fired: llama.cpp/ROCm builds embed build IDs, timestamps, and absolute paths, so a fresh
build is essentially never byte-identical to one made months earlier elsewhere. Replaced with a
two-stage test — build-system-derived source-closure diff as the gate (deterministic, cheap,
independent of build reproducibility), then normalized section comparison against an anchor rebuild in
the candidate's own environment as confirmation. A disagreement between stages is a hard finding
against the build-identity machinery, never a silent preference for the cheaper answer. Transfer also
requires the incumbent's evidence to still be in scope (same models/recipes, same topology hash, no
era boundary crossed).

### AutoPilot scar sweep — twelve gaps folded in

Swept the incident log, 21 autopilot/evidence-plane/eval-tower audits, the autopilot package's own
"why this exists" comments, and the progress record, for what AutoPilot cost this project to learn.
Most transferred learnings AutoKernel already encoded. Twelve did not; all are now folded in, with the
scar recorded beside each in the new §2.5 table.

Two were structural rather than hardening:

- **The planner regenerates false beliefs from its own prose.** AutoPilot's worst contamination lived
  in planner-authored free text *inside the primary journal*: the loop re-read its own narrative each
  round, regenerated a refuted story, and re-distilled it into new strategies — one instance ran 81
  further trials on the same false story after the code fix landed. An append-only journal makes this
  strictly worse, so AutoKernel was more exposed than AutoPilot, not less. Fixed by separating machine
  record from `narrative`, excluding narrative from retrieval by default, and adding
  `RETRIEVAL_SUPERSEDED` so a belief can leave retrieval without leaving the record (invariant 20,
  §5.5, AK-D26).
- **Nothing tested the gate's ability to accept.** Controls and the v8 dry-run all test rejection, so a
  gate that had quietly stopped promoting would be indistinguishable from an exhausted surface —
  AutoPilot ran 1,055 trials of which 8 were even of a promotable type while every surface read
  "active, blockers: []". Added a fifth control: a historical-win replay (iqk port) that MUST promote,
  and a failure to promote is a gate defect, not a research finding (§15.2, AK-D27).

The other ten: operator controls now acknowledged, latched, and fault-injected (invariant 19,
`OPERATOR_STOP_REQUESTED`); `PLANNER_DEGRADED` split from `PLATEAU_STOP` and filtered proposals

### Kernel source authoring — the gap the AutoPilot comparison exposed

Operator question: AutoPilot's edits are minimal and config-shaped; AutoKernel's planners must perform
real code interventions in the kernel. Is the setup suited?

**Partially — and the precedent is worse than it first looked.** AutoPilot's *one* venture into
autonomous source mutation destroyed `src/escalation.py` (454 lines → 3) and caused 11+ hours of API
downtime, and the mutation was **syntactically valid** (`progress/2026-04/2026-04-04.md:5`). So
AutoKernel's core activity is precisely the thing that failed for AutoPilot, at greater scale.

The project's answer then was four layers — syntax, >60% shrinkage reject, public-name preservation,
live `importlib` round-trip. **None transfer directly**: those defend interpreted Python, and there is
no import round-trip for compiled C++/HIP. "It compiles" is a far weaker claim than "it imports". A
kernel edit that drops a template specialization, deletes a dispatch case, or removes an op
registration compiles cleanly and silently changes behaviour for every shape nobody tested.

T0 as written gated *behaviour* — compile, ops, determinism, sanitizers — and nothing gated **source
integrity**. Added §8.5.1, which runs before any behavioural check:

1. **Symbol and registration preservation** — diff exported symbols, op-registration tables, and
   dispatch predicates between anchor and candidate binaries; an undeclared removal or arity change is
   a hard failure. This is the C++ analogue of public-name preservation and the check that catches the
   `escalation.py` class of edit.
2. **Clean build from the recorded snapshot**, never the actor's incremental tree — otherwise stale
   objects hide errors and the actor's build state becomes part of the artifact.
3. **Semantic diff conformance** — the diff touches only the declared surface, no unrelated deletions.
   Invariant 13 said one conceptual mutation; this enforces it rather than trusting it.
4. **Repair from a clean parent**, capped per proposal, with cap exhaustion raising `PLANNER_DEGRADED`
   — AutoPilot's scar was a loop compounding edits onto an already-corrupted file.

Two further findings from the same question:

- **`core_header` is now its own change class and risk tier** (AK-D30). A small textual diff to shared
  ggml core reaches every op in both CPU and GPU builds, so it forces full-tree surface, per-backend
  binary comparison, and human review regardless of diff size.
- **The candidate binary is the real privilege boundary, not the actor's shell.** The loop compiles
  code it authored and executes it with GPU access on a shared host; path allowlists on the agent's
  tools do not constrain that binary's syscalls. Candidate execution now runs under the evaluator's
  sandbox and owned-cgroup regime, and AK2 carries the task to verify it on the real host before any
  unattended operation.

`change_class` gained `core_header`; the proposal schema gained `declared_symbol_deltas`; §12 gained
four rows; AK3 gained an implementation task plus a red-team task that must fail four specific
mutations (deleted specialization, dropped dispatch case, removed op registration, snapshot that does
not build) before any behavioural check runs.
