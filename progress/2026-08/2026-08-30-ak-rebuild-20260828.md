### `ac785d2d` — 43 of 43 CI runs red, and what that hid

The autokernel-guards workflow had failed **every run since its first commit** — 43 for 43 — and

|---|---|---|

### `7ee090a5` — the suite-floor guard

Installing pytest closed the hole. It did not close the **shape** of the hole: a suite that runs
*fewer* assertions than it used to reports exactly the same green.

- pytest exits **5** on zero collected — verified, so total collapse is caught.
- A **partial** collapse exits **0**. Nothing catches it.

So both suites now declare a floor — **101** and **196** — asserted with `>=`, never `==`, so the
guard does not become a second thing to update on every added test.

The guard found two defects **in itself** on its first run:

1. It laundered a collection error into a plausible `93 collected`, because pytest prints the
   count on the same line as `, 1 error`. A parse that reads a number off a line it did not
   validate will happily read the wrong number.
2. Its own test module had a cwd-dependent import.

CI is now green on research `main` **with real counts in the log** — the point being that the log
shows the numbers, so a future collapse is visible rather than inferred.

## 5. Two corrections to my own earlier claims, both material

### GPU idle-while-claimed is not ~35%. It is ~12%.

I reported 35–40% repeatedly, and wrote it into INF-66 as *"the next efficiency target"*. Roughly
two thirds of that is **GPU work the metric does not count**: `gpu_reading()` defines busy as
summed `device_seconds`, which excludes warmup pairs, `test-backend-ops` and rocprofv3 profiles —
all of which are the device under load. The device is closer to **~88% busy**.

The **13.5% serialized-tail** figure is retired with it. It was a single-lane number taken from
run 13. Run 18's tail cycle was **265.8 s median, IQR 263.3–270.6** — that is a saturated tail, not
a 13.5% one.

> An efficiency target derived from a metric that under-counts the numerator is a target for the
> metric, not for the machine. I published a work item off it.

### iqk: I said it was absent from the build. It is in every build, including production's.

`GGML_IQK` **is not a cmake option at all.** `GGML_USE_IQK_MULMAT` is set *unconditionally* for the
CPU backend, and `GGML_IQK=1` is a **runtime env gate** read at `iqk_dispatch.cpp:49`. Verified
directly: **23 iqk symbols present in `libggml-cpu.so` in both arms.**

So "iqk is missing from the candidate build" was never a real divergence, and any reasoning that
rested on it is void.
