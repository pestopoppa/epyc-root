## epyc-inference-research — the guard that had never guarded anything

### `ac785d2d` — 43 of 43 CI runs red, and what that hid

The autokernel-guards workflow had failed **every run since its first commit** — 43 for 43 — and
every one died on `No module named pytest` **before collecting a single assertion**.
`actions/setup-python` ships a bare interpreter; nothing ever installed the test runner.

The cost is not the red X. It is that a check which looks *identically red whatever the code does*
carries no signal at all, so it hid two real regressions for two days:

| Regression | What it asserted | Why it was wrong |
|---|---|---|
| `test_check_regrowth_guards` | `LOOP_LOC_BUDGET == 3000` | the budget was deliberately raised to 3400 |
| `test_experiments` | the same refusal at two different times **deduplicates** | the exact opposite of the identity fix in `5090931d`, which put `recorded_at` into the hashed material *precisely because* identity had collapsed and repeated refusals were being silently dropped |

**A permanently-red check is indistinguishable from an absent one.** It is worse than absent,
because it occupies the slot where a working check would go.

### `7ee090a5` — the suite-floor guard

Installing pytest closed the hole. It did not close the **shape** of the hole: a suite that runs
*fewer* assertions than it used to reports exactly the same green.

- pytest exits **5** on zero collected — verified, so total collapse is caught.
- A **partial** collapse exits **0**. Nothing catches it.

So both suites now declare a floor — **101** and **196** — asserted with `>=`, never `==`, so the
guard does not become a second thing to update on every added test.

The guard found two defects **in itself** on its first run:

1. It laundered a collection error into a plausible `93 collected`, because pytest prints the
   count on the same line as `, 1 error`. A parse that reads a number off a line it did not
   validate will happily read the wrong number.
2. Its own test module had a cwd-dependent import.

CI is now green on research `main` **with real counts in the log** — the point being that the log
shows the numbers, so a future collapse is visible rather than inferred.

## An operational fact I had wrong all session

The hub supervisor gained `sync_dashboard_from_origin` + `check_hub_stale_source` on 2026-08-28.
It fetches `origin/main` every **300 s**, syncs changed `dashboard/` files, and **restarts the hub
itself**.

I twice asked the operator to `kill -TERM` the hub by hand when the supervisor would have done it
unattended. The reason: I read *"Never restarts a healthy hub"* in the usage text and never opened
the log that showed deploy-sync running.

> **The correct deploy path is: push to `origin/main` and stop.** Hand-patching `/workspace` is
> both unnecessary and fragile — the sync has a provenance test that trusts only a blob which has
> existed on `origin/main`.

Generalises to: a usage string describes intent; the log describes behaviour. When they disagree,
the log wins, and it costs one `tail` to find out.
