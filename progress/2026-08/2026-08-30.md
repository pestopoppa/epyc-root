## D14 — pruning silently froze the anchor after the first keep

The 30 champion commits against 7 recorded keeps is the visible symptom. The other 23 are
`lane_error` rows reading `Destination path '.../anchor-gen-002/lane0' already exists`.

`promote_anchor` numbered generations as **COUNT(existing) + 1**. Pruning to `keep=1` pins that
count at 1, so **every promotion after the first targeted `anchor-gen-002`**. The first move
created it; the next moved *into* it (`shutil.move` into an existing directory nests rather
than replaces); the third collided outright.

The errors are the lesser harm. **The real damage is that `anchor_build` never advanced past
the first keep**, so every later measurement in run 17 was cumulative against a stale champion —
precisely the defect D9's advancing anchor was built to prevent, reintroduced by the pruning
that was meant to save disk. Two changes, each correct on its own, wrong in combination.

Numbering is now **MAX + 1**, which cannot collide with a population held steady by pruning,
and `promote_anchor` refuses outright if the destination exists: a nested anchor leaves the old
binary in place, so every later comparison measures a champion that has already been
superseded, and nobody is told. Mutation-tested by restoring count-based numbering, which fails
the promote-and-prune cycle test. (research `9c88039f` — its body says 457 iterations because
it was written at 08:34Z while run 17 was still going; the finished run recorded 464)

## The pattern worth stating plainly

Across the two days, several of these defects survived a green suite because **the test verified
that a component EXISTED rather than that it was WIRED IN**. Three are exact instances of the
same shape:

- A test asserting the **string** `shutil.move` appears in `run.py` passed while `shutil` was
  unimported and every promotion raised `NameError` (D11).
- A test asserting `pool.stop_requested()` returns True for a file on disk passed while
  **nothing ever called it**, and the STOP sentinel sat inert for three hours (D13).
- The drift and clock tests used **synthetic values** rather than real sample vectors or real
  sysfs, so neither ever exercised the path that was wrong — and `clock_stable` was True on
  every run, forever, from a check that could not fail (D7).

D12 is the structural cousin: the `lane_error` handler was correct and its **scope** was wrong,
so a guard covering most of what it guards read exactly like one covering all of it. The
remedy that actually works, applied to every fix from D7 onward, is **mutation testing** —
reintroduce the defect and confirm the suite goes red. Every fix commit from `a1fcc89e` onward
names the mutation it was tested with.

**Two of the errors were the operator's, not the loop's**, and they are the same class:

- Stopping run 12 reached the **`timeout` wrapper** rather than the workload underneath it, and
  what eventually died was `llama-bench` mid-measurement (`rc=-9`), taking the run with it.
- The STOP sentinel in run 16 was **reported as proven working** on the strength of a shared
  status file that had gone stale — a second-hand reading of a producer that was no longer
  writing, which is the same "verify the consumer, not a consumer" failure in human form.
