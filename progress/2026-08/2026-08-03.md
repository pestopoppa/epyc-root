```bash
"…/hermes_drift_precommit.sh" "$@"
```

A bash script exits with the status of its **last** command, so a failing

### Addendum — the denominator got measured, and two of my own defects got caught

**Measured achievable MI210 bandwidth: 1433.3 GB/s = 87.5% of the 1638 GB/s datasheet peak.** Run by the
inference-owning session (research `328b768d`), minimum tier, three servers resident and idle with
autopilot paused. Correction factor **1.143×**, so fp16 62.6%-of-spec → 71.5%-of-achievable.

**My estimate was low.** I predicted ~1.3–1.4 TB/s and a 17–26% rise; the card attains more of its
datasheet than the HBM2e folklore figure suggests. Worth recording the direction of the error.

**The correction that matters more than the number.** Converting *our* figures to an achievable basis
while a competitor's stay on a spec basis makes the AMD-vs-NVIDIA gap look smaller without it being
smaller. **This measurement does not narrow that gap at all** — the comparison must stay spec-to-spec
until somebody measures GB10's achievable bandwidth. Same failure mode as the vendor-KB defect this batch
already caught (per-OAM TFLOPS ÷ per-GCD bandwidth → ridge off by 2×), now recorded as a usage rule
alongside both denominators.

The ridge point inherits the same problem and is labelled for it: 110.5 FLOP/byte on the spec basis,
126.3 on the achievable basis — and the second is **mixed-basis** (spec FLOPS ÷ measured bandwidth),
because nobody has measured the matrix units. Both fall inside the measured bf16 knee of B≈96–128, so the
observation does **not** discriminate between them; claiming the new one fits better would be reading
precision the data does not have.

**Two defects in the probe I wrote, both mine, one serious.** The parallel session found them because it
was the first to actually compile the thing:

1. `TIME(idx, (hipLaunchKernelGGL(...)))` — `hipLaunchKernelGGL` expands to a `do{...}while(0)` statement,

2. **`hipcc ... 2>&1 | tail -20` takes the pipeline's exit status from `tail`, so a failed build exited 0

   same trap for piped pytest. Fixed with `PIPESTATUS` + explicit `exit 5`.

The screen that would have caught it is already written down — *"does the thing that runs this check
propagate its answer?"* — and I did not apply it to my own script. Worth running over the rest of the
probe family.

### Executed autonomously: the last two open measurements

**Peak FLOPS measured — 172.2 TFLOPS**, 95.1% of the 181.0 derived. The shortfall is **clock, not
architecture**: implied sustained 1.617 GHz against the 1.7 GHz boost the derivation assumed, so the
`104 CU × 1024 FLOP/clk` arithmetic is confirmed. **This retires the mixed-basis ridge** — with both terms
measured, the clean ridge is **120.1 FLOP/byte**; 126.3 (spec FLOPS ÷ measured BW) is superseded and 110.5
remains correct on its own spec basis. `B*` measured: Q4_K 34 · Q8_0 64 · bf16 120.

Measurement quality mattered here more than usual, because **a peak-FLOPS loop that gets optimized away
reports infinite throughput**. Three guards: operands register-resident so no memory traffic enters the
timed region; the emitted ISA carries exactly `UNROLL=8` `v_mfma` instructions; and the occupancy sweep is
**flat from 104 blocks to 3328** (172.13–172.32), so the plateau is issue-limited rather than a grid
artifact. Rep spread 0.02%.

It still does not sharpen the bf16 knee. Measured knee is B≈96–128 and the measured-basis `B*` is 120 —
inside it, as were both earlier candidates. Measuring peak FLOPS removed the *basis* ambiguity, not the
*knee* ambiguity; the observation interval is simply wider than the spread between candidates.

**NUMA bidirectional asymmetry — re-run at n=10, interleaved, and it is real.** Node 0 45.32 ± 3.98 vs
node 1 33.96 ± 0.26, node 2 34.06 ± 0.49, node 3 36.85 ± 2.05. Node 0 vs the rest: **+10.36 GB/s, z = 8.0**
— an effect invisible at the n=2–3 of the first pass. Round-robin rather than blocked, because a blocked
design aliases thermal drift onto the arm, which `P-AK-SEARCH-1` forbids.

**The variance structure is the actual clue and it was not visible before:** the fast nodes are *noisy*
(node 0 sd 3.98, node 3 sd 2.05) while the slow ones are *tight* (node 1 sd 0.26). That is the signature
of an intermittently-available fast path, not a fixed per-node cost — a stable topological difference
would show as tight distributions at different means. Still bidirectional-only, still not device locality
(the MI210 is on node 1, which is in the slow group), and still **not** a placement input until the
mechanism is explained.

### Real-mode inference was 503-ing for EVERY role

`/chat` with `real_mode=true` returned `503: Failed to initialize real mode backends:
'_MISSING_TYPE' object has no attribute 'split'`. AutoPilot's seeder calls
`localhost:8000/chat`, so **all 17 seeding calls INFRA_SKIP'd** against a stack whose servers were
all healthy.

**Root cause.** The Pydantic→dataclass bridge read
`getattr(settings.server_urls, name, f.default)`. `f.default` is `dataclasses.MISSING` for any
field declared with `default_factory` — which is all of them. So a field on the dataclass but NOT
on the Pydantic model was passed `MISSING` **explicitly**, defeating its own factory.
`architect_critic` was added to the dataclass in W1 (2026-08-01) and never to the settings model.
Backend init calls `.split(",")` on every URL, so init raised for *every* role, not just that one.

Fixed at both ends: the bridge omits absent keys so the dataclass's own factory applies (kills the
class), and the settings model gains the field. Verified: `200`, `mock_mode: False`, answer `'ok'`.

**The 9 long-standing `ServerURLsConfig` test failures were this bug's alarm.** They were dismissed
as "pre-existing" three times without anyone asking what they were failing ABOUT.

### Backend conformance: harnesses executed, and a safety claim retracted

**Three backend rows moved ASSERTED → VERIFIED** by running the real decoders rather than reading them.
`e8m0_cpu_harness.c` includes the frozen `ggml-impl.h` and calls the real CPU decoders;
`e8m0_hip_harness.hip` includes `common.cuh` and runs the real device decoder **on gfx90a**. 27 executed
values, all matching the pinned vectors. Read-only on the frozen tree throughout.

The HIP row is the one that justifies the effort: which branch of `#if CUDART_VERSION >= 12080` is taken
was previously **inferred from source** and is now **observed on the card** (`cudart_version_defined:
false`). That is the entire difference between ASSERTED and VERIFIED.

**And the instrument immediately falsified its own first classification.** I had written that the E8M0
divergence was "documented-divergent, not a defect", justified by `validate_e_e8m0` rejecting `0xFF` at
load. **Wrong on two counts:**

1. That gate runs only under `check_tensors`, which **defaults to `false`** (`common/common.h:585`) and
   is passed by **none of our launchers**. The loader does not protect us.
2. It is not dead code disagreeing with live code — **both paths are live.** CPU MXFP4 uses fused
   `GGML_E8M0_TO_FP32_HALF`; GPU MXFP4 uses `ggml_cuda_e8m0_to_fp32(e) * 0.5f` at 5+ call sites. They
   agree everywhere except `0xFF`, where `+Inf × 0.5` is still `+Inf` while the fused half yields a
   finite 2^127.

What actually bounds the risk is much weaker than a loader rejection: **we serve no MXFP4 model.** That
is a property of the current fleet, not of the code.

**So the claim is now checked rather than asserted.** Five reachability sentinels; the load-bearing one
fails the moment an MXFP4 model enters the registry or lands on disk, with the remediation options in
the failure message. The others watch the dead CPU decoder gaining a caller, either live path changing
composition, and `check_tensors` flipping default.

The generalisable bit: **"unreachable in practice" is a claim about the world, not about the code, and an
unchecked claim about the world decays silently.** The first version of this instrument documented a risk
and then relied on someone remembering it. A sentinel that fires at the moment of danger is what turns
that into engineering.

### Acquisition-time tensor validation, and three defects found only by running it

Operator decision: validate at **acquisition**, not at serve. `--check-tensors` reads every tensor
linearly, so on an mmap'd model it forces **first-touch of every page** — adding a full read to every
server start *and* perturbing NUMA placement, a hazard already documented here. Validating once when a
model lands gets the same detection with the serving path untouched. It is also a corrupt-download
detector for every quant we serve: a corrupted fp16 scale in a 38 GB download produces garbage output,
not an error. Upstream report stays deferred until we adopt MXFP4; both decisions are wired into the
sentinel's failure message. Research `91ff1d65`.

**Three defects, all found by executing the tool rather than reading it, all the same shape — a verdict
produced by something other than the thing being measured:**

1. **`llama-cli --check-tensors` is unusable here.** With a non-TTY stdin it enters an interactive loop
   and emits `> ` forever: **312 million lines, 895 MB of log**, with `-no-cnv` set *and* stdin from
   `/dev/null`. Replaced by a harness calling `llama_model_load_from_file(check_tensors=true)`, which
   returns NULL on rejection and does nothing else. *When a CLI will not yield a boolean, the API
   underneath it usually will.*
2. **Binary selection took the first `llama-cli` found**, and reported its linkage error as *"this model
   is invalid"*.
3. **Two result states instead of three.** A tool that cannot run has not found a bad model; `FAIL`
   would send someone to re-download a good 38 GB file. Now `PASS` / `FAIL` / `ERROR`.

### The properties that were verified rather than accepted

Each was probed directly in the main thread, because a builder reporting its own module clean is not
evidence:

- **A verdict cannot be stamped.** `Verdict.__init__` refuses without a module-private mint token, and
  stealing the token does not help — `__post_init__` re-derives status, effect resolution and
  speed-rank admissibility from the gate results on the same object and raises `VerdictTampering` on
  disagreement. `dataclasses.replace(v, status=...)` raises. There is no reachable analogue of
  `kernel_eval.sh`'s unconditional `"status":"OK"`.
- **Correctness precedence is unobtainable, not penalised.** `rank_key()` *raises*; there is no
  sentinel a ranking loop could sort by mistake.
- **Nothing consults `StopRequest.origin`.** Authorship never influences disposition — AK-D38 made
  structural rather than documented.
- **The control latch cannot be cached.** `ControlLatchStore.__slots__` is `('path',)` with no
  write-back method and a disk read per call, so AutoPilot's failure — pause a silent no-op for months
  because cached state was written back over the operator's change — has no object here that could
  hold the state to write back.
- **Thresholds are derived.** `alpha_sel` derives from the controls, `alpha_conf` chains from it,
  e-thresholds compute as `1/alpha`. The only literal `alpha=0.05` is in a docstring describing a
  20,000-null-window validation.

### What the red-team passes actually caught

The AK4 pass found **11 live defects**, two on the worst axis — a path where model output could decide
a transition — and three on "does it deliver its guarantee or only appear to". The builder's report
had claimed the module clean.

The anchor work surfaced a subtler one: **nothing rejected a fabricated digest, in v2 either.**
`_need_sha256` accepted 64 zeros, so "never fabricate an anchor" was a docstring rather than a rule
and the new v3 exemption would have been bypassable by writing zeros. Two live fixtures were *already*
fabricated anchors feeding dispatch. Closed with `is_placeholder_digest` at validation and emission.

And a mutation-testing lesson worth keeping: two mutations initially killed one case each, because in
the full `evaluate_t0` path the determinism gate's own refusal fires first and **masks** the
reconciliation under test. Direct tests were added so the record-to-record binding is asserted
independently. Without that the mutation score would have looked fine while the specific defect went
untested — the difference between mutation testing as ceremony and as instrument.
