## Dashboard hub serving a frozen checkout — fixed (:8100)

**Symptom (operator):** handoff dashboard "not updating anymore".

**Root cause:** the :8100 hub process was launched 2026-08-21 13:15 from the
scratch worktree `/mnt/raid0/llm/tmp/dashboard-v26-telemetry-integrity-20260821`
(`hub_supervisor.sh loop` started with EPYC_ROOT pointed at the worktree).
`dashboard/server.py` resolves `REPO = Path(__file__).resolve().parents[1]`,
so `HANDOFF_DIR` became that worktree's frozen copy of `handoffs/` (last write
2026-08-21 13:06). The board's freshness badge read **fresh** the whole time —
the board panel is a live scan of its own checkout, so a frozen checkout
certifies itself. The supervisor's stale-source watchdog could not catch it
either: it validates the hub against `${EPYC_ROOT}/dashboard`, which was the
same frozen checkout. Counts (175 vs 170 active), `activity_today` (0 vs 2),
and the per-day window (max date 2026-08-21) all pinned the freeze.

**Fix:**
1. Stopped the worktree-launched supervisor (PID 1450109) and hub (1450142) —
   both captured by me.
2. Relaunched the canonical supervisor from the real repo:
   `nohup setsid -f /mnt/raid0/llm/epyc-root/scripts/dashboard/hub_supervisor.sh > /mnt/raid0/llm/epyc-root/logs/hub_supervisor.out 2>&1 &`
   (EPYC_ROOT default = the live repo; same .git inode as /workspace).
3. Verified: board `generated_at` live, counts match the repo
   (170 active / 6 blocked / 181 completed / 103 archived), today's commits
   visible, supervisor quiet across poll cycles.

**Failed hardening attempt (reverted):** added a wrong-cwd guard to
`hub_supervisor.sh` comparing `readlink -f /proc/<pid>/cwd` against EPYC_ROOT.
It false-positive in this containerized environment (`/proc/<pid>/cwd` of a
legitimately launched hub resolved to a different inode than the path —
namespace artifact), producing a ~15s restart loop. Reverted to the original
script (verified `git diff` clean). Lesson: /proc cwd comparison is not a
reliable watchdog here; do not reintroduce without a different probe.

**Note:** the hub had been launched from the v26 worktree by a session that
ended; the worktree's code == live repo code (HEAD was an ancestor of main),
so nothing was lost in the restart.

**Boundary note:** no writes were made outside `/mnt/raid0/llm/`; the
filesystem-containment plugin/scanner (INC-20260823) is present and wired
(`.opencode/plugins/filesystem-containment.ts` + generated `permission.bash`
block in `opencode.json`). Scanner allows read-only system probing by design;
per operator directive, such probing is off-limits regardless.
