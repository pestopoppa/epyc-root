## Findings

**1. The gates-before-relaunch ordering caught a defect that would have poisoned the campaign.**
My champion HIP build had `GGML_HIP_ROCWMMA_FATTN=OFF`. That flag **defaults to OFF**
(`ggml/CMakeLists.txt:219`), and on gfx90a with `-fa on` the non-rocWMMA flash-attention path
produces non-finite values at longer sequence lengths. Every one of the 12 pinned olympiadbench
prompts failed on task 0 (`rejecting DFlash batch after 3020800/3020800 non-finite target
features`) while a 25-character prompt succeeded on the same binary — **prompt length is the
discriminator**, which is exactly why my own short smoke test passed and hid it.

Attribution was verified rather than assumed. My first hypothesis — that merging MoE-Spec into
DFlash2 broke it — was wrong: the standalone DFlash2 build `2046c64e9` ran the identical prompts
and flags at 46.1 / 69.4 / 58.9 t/s with zero errors, and `git diff 2046c64e9 5c278648a --
src/ common/` is **+67 insertions, 0 deletions**, so DFlash's source is byte-identical between
them. Rebuilt with the flag ON: all prompts pass. Had v32 kept running, AutoKernel would have
screened against a broken reference for days.

**2. AutoKernel's own GPU builder omits the flag** (`discovery_deployment_factory.py:2052` passes
only `GGML_HIP=ON`, `AMDGPU_TARGETS=gfx90a`, `GGML_NATIVE=OFF`). Every AutoKernel GPU candidate is
therefore built with a different flash-attention kernel than production runs, which undercuts
transferability of any GPU result it produces. Filed as **CH-8**; flagged for an operator decision
rather than silently changed, because adding the flag changes the sealed build identity and breaks
comparability with every prior GPU screen.

**3. CH-6 is not the task it was described as.**
- `ubatch 512→1024 (+46.9%)` is a **null arm**. llama.cpp clamps `n_ubatch = min(n_batch,
  n_ubatch)` (`src/llama-context.cpp:265`), so the screen's `-b 512 -ub 1024` ran **both arms at an
  effective ubatch of 512 on one identical binary**. The +46.9% is a bimodal sample
  (`25409, 18083, 25372, 16175, 25381`) whose median landed on the fast mode, against an anchor
  bank ~30% below the independently measured steady state (AK-BH-2, n=30). Its `batch_up` sibling,
  equally null, reported +0.59% by landing on the other mode. Guard added at the producer; it
  refuses the class, not the instance.
- `MMQ_MFMA ON→OFF (+26.6%)` **is real** for `Qwen2.5-Coder-0.5B-Q4_K_M @ pp512, np=1, gfx90a`
  (independently reproduced at n=30, +26.81%), but it is a **build-time** config flag and cannot be
  a champion member — `champion.py` requires source evidence for every member. The open question is
  whether it survives a real model at `-np > 1`, where the champion's own state file records MMQ
  forcing *inverting* on MoE workloads (B2 −30%, B4 −21%, B8 −10.5%).

**4. A claim of mine was wrong and is corrected.** I had reported filing the champion program as
handoff INF-65. No such file existed — the program had been running untracked. Created this
session; the index gate caught it as an orphan, which is the gate working.
