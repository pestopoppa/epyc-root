## The eval scorer was discarding 1,452 questions every run

### Problem

The operator ruled that prior instrument eras are irrelevant and that the scorer itself was the
problem. The logs bore that out: every eval run dropped **1,452 rows** as unscoreable, and
`instrument_eras.yaml:known_dead_instrument_items` already recorded *"ALL T1 quality numbers have
effective n ≈ 35 of 43 and ceiling ≈ 2.44/3.0"*.

### Root causes — two, independent

**1. The wrong scorer on 1,414 rows.** `debugbench` splits cpp 1438 / java 1401 / python 1414. The
cpp and java rows carry `scoring_method: substring` and score fine. The python rows were assigned
`code_execution` — presumably because Python is the executable one — but **no oracle was ever
attached**: `scoring_config` is `{"language","timeout"}` with no `test_code` and no `entry_point`.
Every one failed `_has_code_execution_oracle` and was dropped, on every run, while its siblings
carrying identical ground truth (the corrected source in `expected`) scored normally.

Retargeted the python rows to `substring`, matching their 2,839 siblings. Deliberately did NOT
fabricate test cases: no oracle ever existed, and inventing one would make the suite measure
something nobody specified.

**2. The needle was unreachable on 25 rows.** `instruction_precision` and `agentic` carry the
substring oracle in `scoring_config["substring"]` (`"P.S."`, `"send_email"`) and leave `expected`
empty. `debug_scorer._score_substring` only ever read `expected`. This is the documented
`expected=='' never scored` defect.

**Fixed the SCORER first, then the validator, deliberately in that order.** Making the validator
accept those rows without teaching the scorer to read the config would have converted 25 dropped
rows into 25 systematically WRONG ones. `_score_substring` fails closed on an empty needle, so the
exposure was 0% rather than 100% — wrong either way.

### Result

**1,452 → 14** invalid rows (0.018% of 79,480). Confirmed in the live run: it now drops 13.
Measured quality on the first post-fix run tracks ~48% correct against ~36% on the broken-scorer run.

The remaining 14 are genuinely broken data, not scorer bugs: `livecodebench` 11 (test_code is
comment-only, e.g. `"# assert __init__(/) == as a list of"`), `cruxeval` 1 (no ground truth
anywhere), `mode_advantage_hard` 1, and the pool's own `__pool_metadata__` header row.

## AutoPilot now ranks configurations by tasks/hour, and stopped halting on ordinary events

### The flip the operator asked for was not a flag

The Pareto panel's amber tripwire fired (`⚠ divergence criterion met — W3 flip decision
live`), which is the W3b-C contract working: legacy `median_request_tps` stayed the live
dominance vector while `task_rate`/`goodput` ran as display-only telemetry, with the flip
**armed on first observed divergence**. The operator threw it: *"can we fix this
immediately please. Autopilot should use tasks/hr."*

Three findings shaped the implementation, none of them a flag:

**1. The shadow 3-D vector could not become the live one.** Consumers index the objective
tuple *positionally* past axis 1 — `safety_gate.py:2303` refuses any entry with
`len(objectives) < 4` ("frontier representative missing objective tuple") and
`pareto_archive.py` reads `[2]`/`[3]`. Shipping `task_rate_3d_v1` would not have raised;
it would have **silently blocked every baseline promotion** behind a misleading message.
`tier_specs.objectives_from` is documented as "the single chokepoint", but a chokepoint on
*construction* is not one on *consumption*. So the 4-D shape was kept and only axis 1's
UNIT changed.

**2. The obvious rate metric was confounded.** `task_rate_qph_from` divides the
decision-partition question count by the FULL-batch wall clock:

| trial | n | wall | qph | t/s |
|---|---|---|---|---|
| 775 | 43 | 763 s | 202.9 | 51.5 |
| 778 | 38 | 802 s | 170.5 | 49.8 |

A **19% objective gap from a 3% speed difference** — the rest is `n` moving. It also
returns `0.0` for "unavailable" on **128 of 1,466** journal rows. Axis 1 therefore uses
`seq_task_rate_qph`, which counts the questions the wall clock actually covers and returns
`None`, never `0.0`.

**3. `dominates()` truncated silently.** It compared via `zip(a, b)`, so a 3-D point
against a 4-D one lined qph (hundreds) up against t/s (~50) and reliability against
`-cost`, returning a confident, meaningless answer. It now raises on a dimensionality
mismatch.

Live and verified on trial 1472:

```

objectives_live_v1  : [2.025, 59.49, -0.5, 0.8]    <- axis 1 = questions/hour
```

### Why AutoPilot kept stopping — the actual ratchet blocker

Not the `None`-action crash fixed earlier (`2ec74a83`); that held. This:

```
ERROR: Planner action blocked deterministically before dispatch: critique decision
       'revise' left final action unchanged
INFO:  AutoPilot shutting down (trial=1472)
```

A critic returning `revise` with confidence 0.94, whose substituted action equalled the
draft, **ended the entire run**. Every sibling breaker in the same `if/elif` chain —
critic-reject loop, consecutive meta, consecutive skip — substitutes a safe action and
halts only after a RUN. This one halted on its first hit, sitting directly beside
`planners_offline_no_deterministic_fallback`, which halts immediately for a genuinely
unrecoverable condition. A critic disagreeing with a planner is not that; it is the system
working.

The decision was **extracted** to `_planner_deterministic_block_decision` rather than
patched inline — the behaviour it replaced was a bare `break` a thousand lines into
`_run_loop_inner`, which is exactly why one disagreement could end a run unnoticed. Writing
the tests immediately found two ways the new guard **failed open**: a stored negative
counter (state is operator-editable JSON that survives restarts) counted `-3 → -2 → -1 …`
and never reached the limit, and a non-numeric value raised straight out of the trial loop.

### The eval instrument is now declared, pinned, and rotated

The sampler stratified by SUITE only (`per_suite = n // len(suites)`); difficulty tier was
never a sampling dimension. The realized mix was a byproduct — the real seed-42 n=50 draw
came out **T1:24 / T2:15 / T3:11**, T1-heavy — and it moved with `n` and with any edit to
the pool. Under a questions/hour objective that is load-bearing.

- **Declared mix (operator: equal thirds).** Verified against the real 79,479-row pool:
  n=50 → 17/17/16 exactly, n=100 → 34/33/33, 34 distinct suites still represented,
  deterministic. A starved tier is REPORTED, never backfilled from another — backfilling
  would return a draw that does not match the declared mix while still reporting the
  declared policy.
- **Rotation (operator: "the draw should be somewhat randomized").** Correct, but rotating
  PER TRIAL would have broken the ratchet: quality is a fraction-correct over n=50, so an
  independent draw each trial adds binomial error of `sqrt(0.25/50)` = 7.1% ≈ **0.21 on the
  0–3 scale** against a baseline near 1.5 — several times the effect sizes being detected.
  So it rotates on an EPOCH: fixed within a block (comparable), fresh between blocks.
  Measured overlap across blocks: **3/50, 0/50, 1/50**, with the mix 17/17/16 every time.
  Because n, mix and pool are constant, expected difficulty is unchanged across a rotation,
  so rotations do NOT force a re-baseline the way changing the MIX did.
- **Durable drift detection.** `_DATASET_SHA_BY_CORE_ID` was a module-level dict, so drift
  was only visible WITHIN one process. The drift that matters lands while the daemon is
  DOWN — that is precisely how this morning's debugbench retarget passed unnoticed. The
  ledger is now persisted, and the tier mix is compared too, because
  `dataset_content_sha256` deliberately does not hash `tier`.

### The episodic gate refused to start on a store that was fine

Root cause was the METRIC, not the data. `semantic_self_match` took a **mean over 8 rows**.
Measured: 59 of 60 rows self-matched at ~0.996 and exactly ONE scored 0.0212 —
`(7×0.996 + 0.021)/8 = 0.874` against a 0.90 floor, which is exactly the 0.8718 reported.
**One bad vector in 60,340 stopped the system.**

## AutoPilot native batching, resource cohorts, and staged region load (20:50 UTC)

Implemented the serving-process lease model requested by the operator:

- Region admission is now a crash-pruned cross-process **cohort**. Requests to the same
  `(role, instance)` may share its certified native slots; a different CPU process whose
  regions overlap cannot join until the cohort drains. This closes the gap that plain
  `flock(LOCK_SH)` could not express (same-process readers only).
- Both full CPU servers are certified at their declared native widths: frontdoor `:8070`
  and worker `:8072` each admit up to four eval requests. GPU aliases collapse onto their
  physical process and retain their independent two-slot lane.
- EvalTower now schedules per-resource cohorts with weighted capacity. Prompt size is
  converted to lane units from declared `n_ctx / slots / native_width` geometry, so short
  prompts batch while an input already near a slot's context limit consumes the lane.
- Native cohort waits inherit the request timeout instead of truncating the placement wait
  to 60 seconds. This was load-bearing for dynamically routed long-context work.
