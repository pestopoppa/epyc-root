## The eval scorer was discarding 1,452 questions every run

### Problem

The operator ruled that prior instrument eras are irrelevant and that the scorer itself was the
problem. The logs bore that out: every eval run dropped **1,452 rows** as unscoreable, and
`instrument_eras.yaml:known_dead_instrument_items` already recorded *"ALL T1 quality numbers have
effective n ≈ 35 of 43 and ceiling ≈ 2.44/3.0"*.

### Root causes — two, independent

**1. The wrong scorer on 1,414 rows.** `debugbench` splits cpp 1438 / java 1401 / python 1414. The
cpp and java rows carry `scoring_method: substring` and score fine. The python rows were assigned
`code_execution` — presumably because Python is the executable one — but **no oracle was ever
attached**: `scoring_config` is `{"language","timeout"}` with no `test_code` and no `entry_point`.
Every one failed `_has_code_execution_oracle` and was dropped, on every run, while its siblings
carrying identical ground truth (the corrected source in `expected`) scored normally.

Retargeted the python rows to `substring`, matching their 2,839 siblings. Deliberately did NOT
fabricate test cases: no oracle ever existed, and inventing one would make the suite measure
something nobody specified.

**2. The needle was unreachable on 25 rows.** `instruction_precision` and `agentic` carry the
substring oracle in `scoring_config["substring"]` (`"P.S."`, `"send_email"`) and leave `expected`
empty. `debug_scorer._score_substring` only ever read `expected`. This is the documented
`expected=='' never scored` defect.

**Fixed the SCORER first, then the validator, deliberately in that order.** Making the validator
accept those rows without teaching the scorer to read the config would have converted 25 dropped
rows into 25 systematically WRONG ones. `_score_substring` fails closed on an empty needle, so the
exposure was 0% rather than 100% — wrong either way.

### Result

**1,452 → 14** invalid rows (0.018% of 79,480). Confirmed in the live run: it now drops 13.
Measured quality on the first post-fix run tracks ~48% correct against ~36% on the broken-scorer run.

The remaining 14 are genuinely broken data, not scorer bugs: `livecodebench` 11 (test_code is
comment-only, e.g. `"# assert __init__(/) == as a list of"`), `cruxeval` 1 (no ground truth
anywhere), `mode_advantage_hard` 1, and the pool's own `__pool_metadata__` header row.

## AutoKernel: from 137k lines with no entrypoint to a runnable loop

**Problem.** AutoKernel had ~137,000 lines and 5,695 passing tests and could not be started.
`grep -rln '__main__\|argparse\|def main('` across every non-test module returned **nothing**. The
suite ran in 47 seconds because nothing touched hardware — every number in it was synthetic, which
the package's own README said outright: *"no benchmark has been taken, no calibration block has been
solved on real A/A material."*

**Root cause, and the operator named it.** Two of them, and the second reframed the work:

1. **Ordering.** `git log` is the evidence: the release plane — 17,782 lines to freeze a champion
   into production — was committed 2026-08-03; `execution/worktree.py`, without which no candidate
   can be compiled at all, landed 2026-08-04. We wrote the cutover ceremony for an artifact we had
   no way to create.
2. **Scar tissue with nowhere to go.** *"Issues tend to get patched like scar tissue; the refactoring
   expert integrates the sense of the patches into the core design."* A mining pass sharpened it:
   every lesson **was** hoisted correctly once, and the next site **copied** the helper instead of
   importing it, because `schemas.py` — the only module all 36 import — holds record shapes, not
   behaviour. The refusal is written down verbatim at `release/plan.py:393`: modules declined to
   "depend on another module's underscore surface". Correct instinct, no correct destination.

### What was measured

The first real A/A this project has ever taken (`data/autokernel_aa_20260804/`), four runs of
identical code under the ratified canonical recipe:

| run | pp512 t/s | tg128 t/s |
|---|---|---|
| A | 899.95 | 52.76 |
| B | 894.70 | 52.31 |
| C | 867.16 | 51.62 |
| D | 886.16 | 50.52 |

Between-run CV 1.62% / 1.88%. Decode declined **monotonically** — drift, not scatter — so an A/B
running candidate-then-anchor charges the second arm a systematic ~4% penalty that more repetitions
cannot remove. **Interleaved pairing is the minimum correct design, and this is the measurement that
proves it** rather than the argument that asserts it. Equally: 1.6–1.9% CV does *not* justify an
e-process, which is what `evaluator/statistics.py` had built.

Two runs were retracted within the hour: a parallel session brought up the orchestration stack
mid-probe (seven `llama-server`s, load 3.3 → 23.9, memory 54 → 306 GB) and the readings collapsed
26%. Reported as drift, that would have justified almost any amount of machinery. **We held no
claim; the co-tenant did nothing wrong.**

### Defects worth remembering, all one shape

A guard reporting **success when it could not actually check**:

- The e-process **could not be crossed at all**: threshold 10, ceiling 5.5687, and factors 1.08→3.0
  all returned the same e-value because the construction is sign-based. A +40% win and a +0.1% win
  were indistinguishable and neither could be banked. The fix's own authorization was then found to
  be **self-certifying** — `commitment.verify(rule)` compared its two arguments to each other, and
  three rounds of real benchmark time were spent on a held claim before the reducer refused.
- **"Alternating" was not alternating.** `OrderSchedule._base_order` hashes and takes the parity — a
  coin flip per block — so five blocks land all one way once in sixteen runs, which is a sequential
  A/B against a 4% drift.
- An unreadable or **vanished** ledger read as an **empty** one, so the next intake re-opened every
  hypothesis as new. `check_do_not_repeat` never compared the regime it was handed: 56/56
  contradicting cells, a 100% false-reject rate — the loop goes sterile while looking productive.
- **Four self-audits returned PASS on foreign source**, including the freeze gate's. Nineteen
  independent denylist definitions across ten modules; six of ten did not ban `importlib`.
  `evaluator/controls.py:2392` predicted the drift verbatim — *"a second copy of those sets would
  drift from the first, and the drift would be invisible: both would still return PASS"* — and nine
  modules then made a second copy.
- The dry run rendered **one** `env`, so it could not show that each arm loads its own `libggml`. A
  candidate linked against the anchor's libs measures the anchor and reports a clean, well-formed
  null with every gate passing.
