# 2026-07-02 — MI210 first-touch GPU inference + benchmarks

**Objective:** get basic benchmark metrics and a feel for running inference on the newly-installed AMD Instinct **MI210** (gfx90a, CDNA2, 64 GB HBM2e). Collect the best available Vulkan kernel AND test the native llama.cpp/ROCm(HIP) kernel; run gemma4-31B with the MTP head via speculative decoding. **Hard constraint this session: GPU-only, NO CPU inference of any kind.**

All measurements below are **first-pass OBSERVATIONS** (contended host — a live 28-process production CPU stack was running at ~106 load; operator-approved GO), not canonical decision-gating numbers per MEASUREMENT.md.

## Hardware / drivers
- MI210 confirmed (`43:00.0`, gfx90a, 64 GB). Passed into the devcontainer via `--device=/dev/kfd --device=/dev/dri --group-add=992`; **ROCm 6.2.0-66 bind-mounted at `/opt/rocm`** (host path `/opt/rocm-6.2.0`). `rocminfo`/`rocm-smi`/`hipcc` all functional.
- The GPU is idle even under the production stack — that stack is **CPU-only** (`.../llama.cpp/build/bin/llama-server`, `-t 48/96`), so GPU-resident decode does not contend with it (validated empirically — see below).

## Vulkan — architecturally IMPOSSIBLE on the MI210 (verified, do not re-attempt)
- Installed the full Vulkan userspace (libvulkan, mesa-vulkan-drivers/RADV 25.2.8, glslc/glslang). RADV loads but **enumerates ZERO devices for gfx90a** — it silently rejects CDNA2/Aldebaran; only `llvmpipe` (CPU) shows.
- **No Vulkan ICD from anyone — RADV, AMDVLK, amdgpu-pro — supports the compute-only Instinct MI200 family.** Kernel side is healthy; the gap is purely userspace drivers that don't exist for CDNA2. The only Vulkan-capable GPU in the box is a GT 1030 (2 GB, useless for 31B). **Use ROCm/HIP.**

## HIP/ROCm build (the working path)
- Isolated git worktree `/mnt/raid0/llm/llama.cpp-mi210-hip` (branch `mi210-hip-enable`) off `production-consolidated-v6`, to protect the shared production checkout from the codex agent's pathspec-less commits.
- **Build break #1 (fp8 / ROCm 6.2):** `ggml/src/ggml-cuda/vendors/hip.h` guards the OCP fp8 typedefs (`__hip_fp8_e4m3`) on `HIP_VERSION >= 60200000`, but ROCm 6.2 only defines the `_fnuz` fp8 types (OCP types landed in ROCm 6.3). Every TU failed. Fix = bump the guard to `>= 60300000` (fp8 unused for Q4_K_M/Q8_0). Committed `0ebf1b4d7`.
- **Build config:** `-DGGML_HIP=ON -DAMDGPU_TARGETS=gfx90a -DGGML_HIP_ROCWMMA_FATTN=ON -DGGML_HIP_MMQ_MFMA=ON -DLLAMA_CURL=OFF -DLLAMA_BUILD_UI=OFF`. (`LLAMA_BUILD_UI=OFF` did not skip the UI — it fetched a prebuilt bundle from HF, avoiding the fragile npm step.)
- **Runtime gotcha (important):** this fork uses `BUILD_SHARED_LIBS=ON` → the binaries are ~18 KB wrappers over `libggml*.so`. The container's inherited `LD_LIBRARY_PATH` starts with the **production CPU build** (`.../llama.cpp/build/bin`, no `libggml-hip.so`) → running our HIP binaries resolves the CPU `libggml` → **SIGSEGV**. **Always prepend `LD_LIBRARY_PATH=/mnt/raid0/llm/llama.cpp-mi210-hip/build-hip/bin:/opt/rocm/lib`.** With that, `llama-cli --list-devices` → `ROCm0: AMD Instinct MI210 (65520 MiB, 65416 MiB free)`.

|---|---|---|---:|---:|---:|---:|---:|

Decode variance was **±0.01 t/s under ~106 host load** → GPU-resident decode is fully insulated from the CPU stack (weights served from HBM, separate compute units). Model-load and prefill still touch the contended host, so those carry noise.

## gemma4-31B + MTP (NEXTN) speculative decoding — works GPU-only
- MTP is wired only in `llama-server` (the CLI/speculative example has an unfinished `// TODO: extend to support MTP`). Target + 514 MB NEXTN head both on ROCm0, `backend_sampling=1`.
- **Decode 43.25 t/s = 1.44× over plain** (30.01 → 43.25); **draft acceptance 59.7%** (163/273), **mean accept length 2.79** of n_max=3, per-position (0.758, 0.593, 0.440). Server healthy in ~10 s.
- The one per-step GPU→host→GPU hop is a ~tens-of-KB hidden-state memcpy (microseconds) — a PCIe shuttle, NOT CPU compute, so it satisfies the no-CPU-inference rule. gemma4 + NEXTN have **full HIP op coverage** (no missing kernels). Qwen3.6-27B's `qwen35` delta-net/ssm-conv path also ran clean on GPU (fork is a strict superset of the `dflash` tree's delta-net kernels).

## Kernel-headroom analysis
- **Q4_K is partly dequant-bound** on gfx90a: same-model Qwen3.6-27B reaches 766 GB/s (47% roofline) in Q8 vs only 537 GB/s (33%) in Q4_K. The Q4_K MMQ dequant costs ~14 pts of roofline.
- **Flash-attn does not help decode** (`-fa 0` 31.95 > `-fa 1` 30.14; FA helps prefill only) → the `GGML_HIP_ROCWMMA_FATTN` rebuild isn't worth it for decode.
- **Default MMQ beats forced cuBLAS/rocBLAS** for batch-1 decode (30.14 vs 29.62).
- Even best-case (Q8) tops out at ~47% roofline → the residual gap is llama.cpp's CDNA2 kernel maturity, not runtime knobs.

## Update 2 — vLLM head-to-head RESULT (completed 2026-07-02)

The verified image `rocm/vllm:rocm6.4.1_vllm_0.10.1_20250909` computes on gfx90a (torch matmul OK; `arch gfx90a:sramecc+:xnack-`; Triton attention backend) and supports Qwen3. Matched-precision **Qwen3-8B fp16** head-to-head (Goedel weights: HF loaded by vLLM, converted f16 GGUF for llama.cpp; both ~15.3 GB):

| Metric | llama.cpp-HIP | vLLM 0.10.1 |
|---|---:|---:|
| per-stream decode (batch-1) | **62.45 t/s** (62% roofline) | **~69 t/s** (69% roofline) |
| prefill pp512 | 2917 t/s | — |
| batched throughput (32 concurrent) | *(single-stream tested only)* | **1129 out tok/s** |

- **vLLM is ~11% faster per-stream** at fp16; its decisive advantage is **batched serving** (continuous batching → 1129 tok/s aggregate). llama.cpp can batch via `-np` but wasn't tested batched — so that row is not like-for-like.
- **KEY: the earlier ~47% (Q8) / 33% (Q4) roofline ceiling is a QUANTIZED MMQ-dequant artifact, NOT general CDNA2 kernel immaturity** — at fp16 (no dequant) llama.cpp-HIP reaches **62% of roofline**. The real tuning headroom is specifically in the quantized dequant kernels.
- **Not measured:** quantized-vs-quantized (vLLM AWQ/fp8 vs llama.cpp Q4/Q8) — that's where llama.cpp's gap was; needs vLLM quant weights. vLLM 0.10.1 predates our `gemma4`/`qwen35` archs, so the comparison used Qwen3-8B.
- gfx90a env for the image: `TORCH_BLAS_PREFER_HIPBLASLT=0`, `VLLM_USE_TRITON_FLASH_ATTN=1`, `VLLM_ROCM_USE_AITER=0`. Scripts: `vllm_verify2.sh`, `vllm_bench.sh`; converted GGUF `Goedel-Qwen3-8B-f16.gguf`.
