### 5. ThinkingCap MTP head — operator hypothesis confirmed at byte level

Operator hypothesis ("ThinkingCap uses the stock MTP drafter we already have") **confirmed**:
the entire 451 MB layer-64 block is **byte-identical** to our local
`Qwen3.6-27B-MTP-Q8_0.gguf` (single sha256), as are `token_embd`, `output.weight` (tied
shared head) and `output_norm`. A control tensor (`blk.32.ffn_gate`) genuinely differs, so
the offset arithmetic is sound. Differing set = exactly the **256 LoRA target modules**,
matching upstream `merge_verify_report.json` (r=64, α=128). The −1,184 B delta is **fully
metadata**, exact to the byte.

Consequences: MTP is **not** a ThinkingCap feature (hold constant across arms); it is a
genuine **co-trained-head vs modified-trunk mismatch**; the GGUF repo declares **no license**;
and our two local Q4_K_M artifacts are **not a clean A/B pair** (the MTP one is *smaller*
despite 15 extra tensors → different recipes → any Q4_K_M MTP-vs-non-MTP benchmark is
confounded).

**Method correction**: MTP presence must be read from **tensor count** (851 = no MTP,
866 = MTP) via a 24-byte ranged header read — *not* file-size deltas. ThinkingCap's Q4_K_M
is 722 MB **smaller** than our non-MTP Q4_K_M and still has MTP.

### 6. Production fix — GEPA reflective mutation was a guaranteed no-op

**Mechanism correction (this session's own error).** First reported as "LiteLLM routes to
api.openai.com with a bogus key". **Wrong** — litellm is never reached. `gepa_optimizer.py:192-194`
defined `propose_new_texts()` that unconditionally raised `NotImplementedError`, and GEPA
dispatches on **presence, not None-ness** (`reflective_mutation.py:66-67`); a bound method is
never `None`, so every reflection step raised **before any LM call**. An `api_base` fix alone
would have changed nothing.

Evidence: `logs/autopilot.resume700b.log:1210-1219` (trial 521, 2026-06-04) —
`GEPA optimization complete: 0.718 → 0.000 (-0.718) in 633s (50 evals)`. **633 s and 50 evals
burned per invocation for a guaranteed no-op**, since at least 4 June. Also corrected: only
**8 `gepa_optimize` trials have ever run** (one ever `keep`), and `gepa_ratio` is **absent
from live `autopilot_state.json`** (0.30 is a hardcoded fallback on the autonomous-fallback
path, not the primary dispatch).

Fix (3 parts): `propose_new_texts = None` class attr matching the protocol default (not
deleted — the class doesn't inherit the protocol, so a missing attribute would become an
`AttributeError`); reflection LM passed as a **callable carrying `api_base`** (GEPA's string
path calls litellm *without* it, so a bare model id could never reach a local server) plus
env-overridable endpoint; and full-budget seed-unchanged runs now log at **ERROR** and return
`None` instead of a fake completion.

Blacklist `gepa_optimize`/`frontdoor.md` **lifted** — removal condition genuinely met
(autopilot restarted 10:17, ~50 days after extractor fix `2cb40960`); verified via
`load_blacklist()` → 0 entries. Companion `prompt_mutation` freeze left in place.

Validation: dispatch + `api_base` proven via litellm intercept; `test_gepa_integration.py`
**11/11**. **Not yet exercised against a live model** — filed as AP-19b (supervised first run).

### 7. Production fix — cold-start stack-change gate (37 errors)

Surfaced while trying to validate §6. **Not registry drift** (both registries committed-clean).
On a cold host the guard resolves its launch view realized-fleet → env → **`full`**, while the
registry documents the restored `both` lineup ⇒ **37 wholesale errors** — and the CLI's
explicit `--numa-mode both` was **never consulted**. Same family as the 105-error class WP-13
fixed for live fleets.

Fix: `stack_commands.py::_run_stack_change_launch_gate` threads an explicit `--numa-mode`
into the gate subprocess env (precedence preserved: realized > CLI > env > default).
**37 errors → 1** on the identical cold dry-run; gate-wrapper tests **38/38**.

The residual 1 is **by design**: `_realized_compile_numa_mode` refuses on a dead fleet even
with env set (ESC-8 Fix 6 / kill-chain A4). A gate-green cold start is currently impossible
by construction — cold-start recipe + a design question for that trust boundary filed in the
ESC-8 handoff.
