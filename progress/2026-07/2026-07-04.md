## Dashboard live inference stream — root-caused + fixed (v6 /slots regression) + SSE multiplex

Operator report: opening a live inference stream tap in the AutoPilot dashboard no longer showed inference content in real time.

### Problem 1 — task-detail live stream dead since v6 cutover

- **Root cause**: `/dashboard/events/task/{id}` (`task_stream`) located the serving llama-server slot by substring-matching the task objective against the slot's `prompt` field and read generated tokens from the slot's `content` field. The **2026-06-26 v6 llama.cpp cutover** pulled in an upstream privacy change that **removed `prompt` and `content` from `/slots`**. Live-confirmed 2026-07-04: every port returns only `id, id_task, is_processing, n_ctx, n_prompt_tokens, n_prompt_tokens_processed, n_prompt_tokens_cache, params, next_token, speculative`. With `prompt` gone, `_find_slot_by_objective` never matched → stream found no slot → idle heartbeats → give-up; even a match would read empty `content`. Timing ("now/anymore") matches the cutover.
- **Backend was fine**: verified `raw_tap`, `structured_tap`, and per-token tap `chunk` events all stream live (all roles emit `chunk` except `architect_general`, which is safe-mode non-streaming). The break was isolated to the slot-matching path.
- **Fix**: re-pointed `task_stream` at the structured tap event stream (`inference_tap_events.jsonl` via `_find_structured_request_by_task_id`), which carries per-token `chunk` events keyed by `task_id` and is the concurrency-safe source the rest of the dashboard already trusts. First content SSE frame carries `reset:true` so the frontend clears the initial GET render (now sourced from the tap_section fallback) instead of doubling the prefix. `_find_slot_by_objective` / `_poll_all_slots` left in place (harmless; `task_detail` GET already falls back to structured tap — would resume if a future build restores slot prompt exposure).
- **Validated (data path, non-disruptive)**: `_find_structured_request_by_task_id("chat-e295ba69")` returned a live-growing response (511→627→720→783→847 chars over 2.4 s).

### Problem 2 — SSE connection exhaustion (flagged + fixed)

- **Root cause**: the dashboard opened **5 always-on `EventSource` streams** at startup (`stream`, `structured_tap`, `raw_tap`, `autopilot_log`, `planner_tap`). Browsers cap HTTP/1.1 at ~6 connections/host, so a single tab sat at the ceiling (opening a task detail = 6th) and a **second tab (10 needed) starved entirely**.
- **Fix**: added `/dashboard/events/multiplex` — one SSE connection fanning all 5 sources into named events (`event: snapshot|structured_tap|raw_tap|autopilot_log|planner_tap`) via a shared `asyncio.Queue` fan-in. Frontend routes named events to the existing handler bodies (extracted verbatim into `apply*Data()` functions shared by both transports). **Default-on with a `localStorage.sseMultiplex='0'` kill-switch** that instantly reverts to the legacy 5-connection path (standalone endpoints retained). Correctness: made the multiplex main loop the **sole** reader of `request.is_disconnected()` — producers terminate via task cancellation — to avoid concurrent ASGI receive-channel races.
- **Validated (throwaway port 8011/8012, non-disruptive)**: all 5 named events delivered on one connection (snapshot×7, structured_tap×13, raw_tap×24, autopilot_log/planner_tap initial); payload shapes match each handler; abrupt disconnect cancels all producers cleanly (no leaked-task warnings, no exceptions).
