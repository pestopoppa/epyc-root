## Autopilot dashboard: scannable planner-log trial boundaries

- **Problem**: the autopilot dashboard planner tap (`claude -p` / local
  planner stream) rendered as endless near-identical draft/critique blobs
  separated only by dim `====` rules, so an operator scrolling the panel could
  not spot where a new trial's planning begins.
- **Root cause**: the planner-tap renderer (`_stylePlannerLine` in
  `epyc-orchestrator/src/api/routes/dashboard.html`) styled the session-start
  line in the dimmest color in the panel, and its match regex targeted the
  stale `PLANNER session` string — the real log format is
  `PLANNER provider=<p> role=<role> start`, so no header ever stood out.
- **Backend change (committed `bb0451d2` "Mark planner tap trial boundaries")**:
  `plan_with_providers()` now writes one deterministic
  `>>>>>>>>>>>> TRIAL <n> <<<<<<<<<<<<` banner per live planning cycle via a new
  `_write_trial_planning_banner()` helper (guarded to no-op when `trial_id` is
  `None`, so unit tests do not pollute the shared
  `/mnt/raid0/llm/tmp/planner_tap.log`); `autopilot.py` passes the live
  `trial_counter` at the call site.
- **Renderer change (this session, uncommitted → committed below)**: the
  dashboard now (1) fixes the header regex to the real `provider=…role=…`
  format, (2) renders the live `>>> TRIAL n <<<` banner as a full-width,
  centered, high-contrast bar, and (3) promotes every `role=draft` header to a
  big `▶ NEW PLANNING · <timestamp>` banner so the planning-start boundary is
  visible **retroactively across all existing tap history** (no trial number
  required); `role=critique` stays a quiet sub-header so drafts remain the
  dominant anchor.
- **Why renderer, not file backfill**: historical tap entries carry no
  recoverable `trial_id` (the planner archive has timestamps but no trial id),

  autopilot (PID 131226) — rewriting it in place under a live writer risks
