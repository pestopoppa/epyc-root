### The embedder-outage path (found while closing M-17e)

Chasing "what if BGE is down when the gate runs" turned up an unfixed corruption path.
`use_fallback` defaults to **True** in `EmbeddingConfig` and `EmbedderPoolConfig`, and every live
site builds a bare `TaskEmbedder()`. So an embedder outage does not fail a write — it silently
stores a SHA-256 pseudo-vector. Measured over 5,000 real task texts:

| outcome | share | consequence |
|---|---|---|
| all-zero | **89.0%** | float32 `norm` overflows to `inf`; `norm > 0` is True for inf; `v/inf == 0` |
| contains NaN | 2.8% | permanently unretrievable — FAISS scores the row `-inf` |
| unit-normalised | 8.1% | well-formed, meaningless, passes every cheap check |

The blind spot was exact: the well-formed 8.1% pass sync and round-trip, so the only detector was
semantic self-match — which needs the very embedders whose absence produced them. **The condition
that causes the corruption is the condition that disables its detector.**

Audited all 58,322 live rows: **0 hash-fallback vectors**. The store is clean, because the reseed ran
with `use_fallback=False` and BGE has been up.

| Change | Repo | Effect |
|---|---|---|
| `is_degenerate_embedding` / `is_hash_fallback_embedding` | orchestrator | exact detection; the fallback is a pure function of the text |
| `EpisodicStore.store()` guard | orchestrator | raises `DegenerateEmbeddingError`; one chokepoint, not ~8 constructor sites |
| `degenerate_vectors` check | orchestrator | **needs no embedder** — detects 91.8% of fallback corruption in the exact condition that causes it |
| AutoPilot gate retry | orchestrator | 180 s embedder boot window, then fail closed |

Healthy startup costs 0.9 s; a structural failure blocks in 0.3 s without burning the window.

**Two defects in my own detector, caught by measuring instead of asserting.** A cosine test at 0.99
had a **45% false-positive rate** against random unit vectors — the overflowed reference is
unnormalised and dots high with anything — replaced with exact comparison, now **0 false positives
over 3,000 live BGE vectors**. And I first wrote that hash vectors are "maximally diverse and defeat
`vector_diversity`"; wrong, at 89% all-zero they collapse and that check would fire.

Store state: `ntotal=58322 id_map=58322 desync=0`, round-trip 500/500, diversity 57/57 (ratio 1.000),
degenerate 0/500, **semantic self-match 0.9943**. 23 new tests; episodic suite 173 passed.

## GPU shadow lane — P2-5a shed-trade measurement DESIGN (nothing run)

Designed the protocol for deciding whether D1 admission class 3 (shed batch) is worth building,
per the §3.4 finding that shedding is partially self-defeating. Design only: no inference, no region
claim, and the protocol it proposes is not ratified. Spec at
`epyc-inference-research/docs/design/p2-5a-shed-trade-measurement-spec.md` (`d5f5942f`).

Two decisions changed what actually gets measured. First, **the metric is `task_rate`, not t/s** —
my own §3.4 phrasing ("GPU throughput gained minus q3 CPU throughput lost") is convenient prose and
a bad metric, because the CPU side runs gemma4-26B-A4B and the GPU side a 27B dense, so their tokens
are not commensurable, and P-SPEED-OBJ already settled the axis as task_rate with t/s demoted to
host-health telemetry. Corrected in the spec rather than inherited. Second, **the net is measured
directly** as a paired whole-system comparison on one frozen corpus in one wall window; measuring
the two halves separately and subtracting inherits both CV≈9.1% noise terms and measures them under
conditions that never co-occur, which is the whole phenomenon.

Four arms — A0 CPU-only under stress, A1 lane resident but *idle*, A2 shed active, A3 GPU with CPU
quiesced. A1 is the control most likely to be skipped and the one that separates "shedding is bad"
from "the lane's mere presence is bad", which are different findings with different fixes. The shed
fraction is swept rather than assumed, since the residency tax is paid once while CPU displacement
grows with f, so the optimum may be interior and a single badly-chosen f would manufacture a false
negative.

The null result is pre-registered as informative: if the net falls below MDE, the verdict is "don't
build", not "needs more data". Writing that down before the run is what stops a null from being
re-litigated after someone has already built the feature. Likewise the measurement deliberately does
not require class 3 to exist — the split is harness-driven through the eval path — so a negative
result stays a decision instead of becoming a feature reversal.

(P-BENCH-2 is CPU aggregate, P-BENCH-3 batched slots, P-GPU-1 GPU throughput; none covers work moved

but cannot register it — MEASUREMENT.md is human-amendment-only — so until the operator ratifies,
any run yields observations regardless of execution quality. That is resolvable now, independent of

## C9 — spawn cap is now live concurrency, not a daily action count

`cmd_spawn` enforced `caps.max_spawns_per_day` by counting `spawn` rows in `adapter-ledger.jsonl`
for the current date. That is a rate limit on an ACTION, not a bound on live mains: killing or
closing a main never returned its slot, so on 2026-07-28 three spawn rows refused further spawns
at 3/3 while only two mains were actually alive — and it perversely penalised the lifecycle rule
that tells a session with nothing assignable to close itself.

**Fix.** `live_mains()` maps every roster row to the window that can carry it — its id, or the
window component of a tmux endpoint where the two differ (roster id `codex` lives in window
`codex-inference`, renamed by the operator to disambiguate it from `codex-bus-tests`) — and
intersects that with `tmux list-windows` against `tmux.live_session`. Tool windows (`htop`, `btop`,
`fish`) are not mains and do not count. A window-INDEX endpoint (`tmux:agent:3`) contributes no
name, so such a main counts only if a window also carries its id — a deliberate undercount in the
direction that refuses spawns, never one that invents capacity. Spawning a main that is already
live is refused too: one roster identity, one window.

**Fail-closed, deliberately.** tmux unreachable, the live session absent, or a roster with no ids
all return `None`, never an empty set. An empty set is the positive claim "no mains are live, all
slots free"; inferring it from a failed query is precisely the shape of C3, C6 and C8, which were
all fail-opens in this same file. There is now a test per branch.

**Key migration decision, stated explicitly.** `caps.max_spawns_per_day` is **refused, not read as
a fallback**. Its `6` authorised six spawn ACTIONS in a day; re-reading that same 6 as six
SIMULTANEOUS mains would grant concurrency nobody approved — more permissive than the behaviour it
replaces, i.e. a fail-open. The old key alone now exits `EX_MISCONFIG` naming the one-line config
edit. `caps.max_concurrent_mains: 4` set by operator decision (one slot above the then-steady
state of 3 live mains). The daily ledger count survives in `probe` as `spawns_today_history_only`
and gates nothing. `session_bus_coordinator.py` flag reporting follows the new key.

**Tests.** 10 new cases in `tests/test_tmux_adapter.py` (**40 passed**), including an end-to-end
disposable-session proof that spawning to the cap, closing a window, and spawning again succeeds —
the behaviour the old cap made impossible for the rest of the day. Plus 4 new cases in the
standalone `scripts/coordination/tests/test_tmux_adapter.py` (**37/37**).
