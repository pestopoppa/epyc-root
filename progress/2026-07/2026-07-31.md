### 1. The ngram result was retracted, and the retraction was propagated into the record

Yesterday's headline — *"`ngram-mod` composed with `draft-mtp` is 2.80× at depth"* — is **withdrawn**. It was a
harness artifact.

**Mechanism.** Every cell launched ONE server and sent the **same prompt** r times at
`temperature=0.3, seed=42`. Run 1 generates answer X; the server retains X in the slot KV; run 2 sends the
identical prompt, hits the prompt cache (`prompt eval = 4 tokens`), and `ngram-mod` — which drafts by matching
text **already present in context** — copies its own previous answer verbatim. Mean accepted draft length
`3.58 → 15.88`; acceptance → `1.000`.

**The control was in the data the whole time.** Sorting all 68 cell logs by `run2 ÷ run1`: *every* cell inflated
above 1.15× is an ngram arm, and *all 25* `draft-mtp`-only and `none` cells sit flat at 0.92–1.08×. `draft-mtp`
drafts from weights, so a warm context cannot help it — a free control nobody looked at.

```
Qwen3.6-27B Q8_0, GPU, 16.5k ctx     run1     run2   mean draft len   published
  draft-mtp   (control)             39.20    39.42    3.58 -> 3.58      39.31  sound
  ngram + draft-mtp                 39.61   105.21    3.58 -> 15.88     72.41  INFLATED
```

**Confirmatory re-run** (`/mnt/raid0/llm/tmp/ngramfix.sh` → `ngramfix_results.txt`), using **3 DISTINCT prompts
per rep** from disjoint corpus slices so no rep can copy a prior answer, plus a `draft-mtp` control in every
group:

| model · quant | depth | draft-mtp | + ngram | gain |
|---|---|---|---|---|
| Qwen3.6-35B-A3B Q8_0 (CPU full) | 8k | 26.20 | 25.71 | −1.9 % |
| Qwen3.6-35B-A3B Q8_0 (CPU full) | 16k | 22.59 | 22.26 | −1.5 % |
| Qwen3.6-27B Q8_0 (GPU) | 8k | 41.12 | 41.64 | +1.3 % |
| Qwen3.6-27B Q8_0 (GPU) | 16k | 36.71 | 35.15 | −4.2 % |

`ngram-mod` **alone** costs **23–31 %**. Verdict: **no role should enable it.**

**Caveat on my own detector:** 5 of 12 cells tripped the harness's `MONOTONE CLIMB` flag — but so did a
`draft-mtp` **control** cell (27B GPU d16k: 33.08 → 36.71 → 37.55), which cannot be contaminated by a drafter it
does not use. The flag catches ordinary warm-up. It means "inspect", not "void".

**Prompt screening was necessary but not sufficient.** These prompts were clean real text at 6–17 % repeated
5-grams (the earlier synthetic-filler failure was 99.7 %). The contamination came from the **generation**, not
the prompt.

### 7. A one-line upstream patch — NOT a kernel change

`qwentts.cpp/ggml/src/ggml-cuda/vendors/hip.h` guarded FP8 on `HIP_VERSION >= 60200000`, but the
OCP-format `__hip_fp8_e4m3` type only exists from **ROCm 6.3**. We run **ROCm 6.2.0-66**, which ships
only `__hip_fp8_e4m3_fnuz`. The header therefore included `hip_fp8.h` and then typedef'd a type that
does not exist:

```
error: unknown type name '__hip_fp8_e4m3'
```

Raised the guard to `60300000`. **Free for us: gfx90a has no native FP8 hardware**, so nothing is
lost — kernels gate on `FP8_AVAILABLE` and fall back.

**This is a third-party repo (`/mnt/raid0/llm/qwentts.cpp`, submodule `ggml`).** The frozen
production kernel `production-consolidated-v8` @ `67a433bf4` is **untouched**, and **no
experimental-kernel handoff is required** — the four-step experimental-kernel workflow in CLAUDE.md
governs *our* kernel tree, and this patch is not in it. Recording this explicitly because the
operator asked whether a kernel patch was needed: **no.**

### 10. Speculative decoding: what is and is not runtime-switchable — read from source

Answering an operator question from the frozen v8 source, **not** from a benchmark.

**`--spec-type` is LAUNCH-ONLY.** Which drafters are active is fixed at server start
(`common/arg.cpp:3935`). Autopilot cannot switch drafter per request.

**CORRECTION to the working assumption — the per-request draft-budget fields are COMPILED OUT.**
`tools/server/server-schema.cpp` does register `speculative.n_max` (208), `speculative.n_min` (212),
`speculative.p_min` (216), `speculative.type` (220) and the three `speculative.ngram_*` fields
(226/229/232) — **but the whole block sits inside `#if 0` at line 206, closed at line 234**, under
the upstream comment at line 205:

```
// TODO: to keep things simple, we disable speculative parameter adjustments for now
```

So on the production binary **there is no per-request speculative surface at all**: not `n_max`, not
`n_min`, not `p_min`. The `speculative.n_max` keys visible in `tools/server/README.md` (768-820,
917-967, 982-1032) are **`generation_settings` echoes of the launch defaults**, not accepted request
fields — which is exactly how the field was misread. A grep of `tools/server/*.cpp` confirms no other
per-request parsing path.

**Consequences:**
- Autopilot **cannot** dial the draft budget per call on v8, and **cannot** send `n_max: 0` to
  disable drafting for one request. Both would require a kernel change → a **new production
  version**, never a patch to the frozen tree.
- `n_max: 0` would in any case kill **both** arms together — ngram cannot be disabled selectively.
  Selective ngram would need **separate server instances**.
- The composed recipe's ~1.6 % cost is therefore paid on **every** drafted request, unconditionally,
  and the repetitive-context upside is its whole justification. With ngram now retracted (see §1),
  that justification is gone.

Filed as open tasks in [`speculative-decoding-mtp-refresh.md`](../../handoffs/active/speculative-decoding-mtp-refresh.md).
