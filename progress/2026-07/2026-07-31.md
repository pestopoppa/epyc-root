### 1. The ngram result was retracted, and the retraction was propagated into the record

Yesterday's headline — *"`ngram-mod` composed with `draft-mtp` is 2.80× at depth"* — is **withdrawn**. It was a
harness artifact.

**Mechanism.** Every cell launched ONE server and sent the **same prompt** r times at
`temperature=0.3, seed=42`. Run 1 generates answer X; the server retains X in the slot KV; run 2 sends the
identical prompt, hits the prompt cache (`prompt eval = 4 tokens`), and `ngram-mod` — which drafts by matching
text **already present in context** — copies its own previous answer verbatim. Mean accepted draft length
`3.58 → 15.88`; acceptance → `1.000`.

**The control was in the data the whole time.** Sorting all 68 cell logs by `run2 ÷ run1`: *every* cell inflated
above 1.15× is an ngram arm, and *all 25* `draft-mtp`-only and `none` cells sit flat at 0.92–1.08×. `draft-mtp`
drafts from weights, so a warm context cannot help it — a free control nobody looked at.

```
Qwen3.6-27B Q8_0, GPU, 16.5k ctx     run1     run2   mean draft len   published
  draft-mtp   (control)             39.20    39.42    3.58 -> 3.58      39.31  sound
  ngram + draft-mtp                 39.61   105.21    3.58 -> 15.88     72.41  INFLATED
```

**Confirmatory re-run** (`/mnt/raid0/llm/tmp/ngramfix.sh` → `ngramfix_results.txt`), using **3 DISTINCT prompts
per rep** from disjoint corpus slices so no rep can copy a prior answer, plus a `draft-mtp` control in every
group:

| model · quant | depth | draft-mtp | + ngram | gain |
|---|---|---|---|---|
| Qwen3.6-35B-A3B Q8_0 (CPU full) | 8k | 26.20 | 25.71 | −1.9 % |
| Qwen3.6-35B-A3B Q8_0 (CPU full) | 16k | 22.59 | 22.26 | −1.5 % |
| Qwen3.6-27B Q8_0 (GPU) | 8k | 41.12 | 41.64 | +1.3 % |
| Qwen3.6-27B Q8_0 (GPU) | 16k | 36.71 | 35.15 | −4.2 % |

`ngram-mod` **alone** costs **23–31 %**. Verdict: **no role should enable it.**

**Caveat on my own detector:** 5 of 12 cells tripped the harness's `MONOTONE CLIMB` flag — but so did a
`draft-mtp` **control** cell (27B GPU d16k: 33.08 → 36.71 → 37.55), which cannot be contaminated by a drafter it
does not use. The flag catches ordinary warm-up. It means "inspect", not "void".

**Prompt screening was necessary but not sufficient.** These prompts were clean real text at 6–17 % repeated
5-grams (the earlier synthetic-filler failure was 99.7 %). The contamination came from the **generation**, not
the prompt.

### 2. Vision models evaluated — the first real comparison in a long time

42 questions (OCRBench + ChartQA), all arms on the MI210, best quant present on disk.
Raw `/mnt/raid0/llm/tmp/vlquality_results.json`, harness `/mnt/raid0/llm/tmp/vlquality.py`.

| model · quant | strict | re-scored (true) | image tokens |

**MiniCPM-o is not a vision upgrade — it is a downgrade.** That kills the promotion case on vision grounds. The
prior evidence for it was n=10 with **one** discordant pair (McNemar p=1.0), and that single pair was itself a
scoring artifact: the incumbent answered `0.11 kWh` where the accepted answer was `0.11`. Corrected, the two
tied 7/10. Verified directly from
`artifacts/minicpm-o-phase1-v8-20260726/live-.../escalation-{baseline,candidate}-scored.json`.

**The scorer, not the models, had been driving our vision conclusions.** Two distinct artifact classes surfaced
today: comma/unit (`63,086` vs `63086`) and **LaTeX whitespace** (`\frac { 1 } { x + y }` vs `\frac{1}{x + y}`).
The first depressed the incumbent by 6 questions; the second depressed Qwen3-VL-8B by 2. Both required offline
re-scoring from saved responses.

**Saturation caveat that must travel with these numbers.** OCRBench + ChartQA is exactly the family where
Qwen3-VL was never claimed to improve — published deltas are DocVQA +0.4, ChartQA +2.3, AI2D +1.8, OCRBench
**+8** against the *independent* OpenVLM baseline of 888 (not the +32 the vendor card implies). Its real gains
are MathVision **+28.8**, MMMU-Pro **+17.6**, MMMU **+11.0**, OmniDocBench **−45 % edit distance**. So this
result is **not** evidence of a Qwen3-VL regression; it is evidence that this suite cannot separate them.

Operational findings:
- MiniCPM-o encodes images at **~750 tokens, fixed** — `--image-max-tokens` / `--image-min-tokens` are no-ops for
  it. Architectural (~64 tokens/slice, capped slices). Qwen2.5-VL spends 4103 on the same image.
- MiniCPM-o scores **0** without `enable_thinking=false` / `--reasoning off`: it emits `reasoning_content` and an
  **empty** `content`. Reproduced twice (1600 tokens of reasoning, no answer).
- `Qwen3-VL-2B-Instruct-GGUF/` is **empty** — and it is the only family member with independent third-party
  verification, which we therefore cannot use.
- Qwen3-VL HF benchmark tables are **JPEG images**, not text.

### 3. Speech stack mapped

**Whisper is deployed** — I initially reported it absent, which was wrong. `faster-whisper large-v3` (2.9 GB) and
`large-v3-turbo` (1.6 GB) live in `/mnt/raid0/llm/cache/huggingface/hub/`, launched by
`orchestrator_stack.py:2123 start_whisper()` on port 9000. Missed because they are **CTranslate2 in `cache/`**,
not GGML in `models/`.

**TTS is not wired.** There is no `start_tts` in `orchestrator_stack.py`. A complete voice stack already exists at
`epyc-inference-research/scripts/voice/` (`tts_server.py`, `validate_tts_e2e.py`, `create_tts_sidecar.py`,
`transcribe_batch.py`, `test_latency.py`) but is referenced **only from archived docs** — while
`multimodal-pipeline.md:324` still instructs a reader to build a FastAPI TTS wrapper from scratch.

**The C++ accelerator is unrecoverable.** `llama-tts-qwen3` exists only as a 2026-04-23 binary in a
`-preserved-<timestamp>` archive; it fails with `no backends are loaded`. Its **source is gone** — no `.cpp`
anywhere, no source dir, and branch `feature/qwen3-tts-support` contains none of it. Not rebuildable from disk.
Stock `llama-tts` is not a substitute: it misinterprets the weights as OuteTTS and emits unrelated tokens.

**The PyTorch path is viable and costs zero GPU VRAM.** `tts_server.py` runs Talker + CodePredictor + Decoder in
PyTorch at ~0.9× real-time on 48 CPU threads. Weights present (`hf/Qwen3-TTS-12Hz-0.6B-Base`, tokenizer and
CustomVoice in cache); `torch 2.6.0+cpu` and `transformers 5.5.1` present. Missing only `soundfile`, `fastapi`,
`uvicorn`, `librosa`, `scipy`.

**VRAM verdict:** MiniCPM-o omni stack **10.84 GB** vs dedicated Qwen3-TTS **1.14 GB** — a **9.70 GB** delta for
speech alone. Since MiniCPM-o also loses on vision, nothing justifies spending ~10 GB of contested MI210 on it.
