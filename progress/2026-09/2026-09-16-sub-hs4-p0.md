## What landed

### P0.1: `x_tool_mode="client"`

- **Request:** `/v1/chat/completions` forwards the caller's structured history to llama-server
  `/v1/chat/completions` unchanged. That history covers system and user turns, assistant
  `tool_calls`, and `tool` results with `tool_call_id` and `name`. The caller's `tools` and
  `tool_choice` go along with it.
- **Response:** the model's `tool_calls` come back with `finish_reason:"tool_calls"`:
  - non-streaming: `message.tool_calls`, with `content: null` on a tool-only turn;
  - streaming: one `tool_calls` delta per call (complete arguments, `index`, `id`), then the finish
    chunk.
  - Tool calls without an id get `call_<hex>`. Arguments given as a dict are serialised to a JSON
    string.
- **Default unchanged:** the REPL bridge stays the default, whether `x_tool_mode` is absent or
  `"repl"`. The golden fixture `tests/unit/fixtures/openai_compat_default_golden.json` was captured
  from the route **before** the change. It pins the `llm_call` arguments and the response bodies
  (JSON and SSE) for 5 cases: direct and REPL, streaming and non-streaming, with and without tools.
  A mutation check confirmed the fixture catches a change to the bridge text.
- **Plumbing, additive and inert without a payload:**
  - `LLMPrimitives.chat_completion_call()`, which raises on failure rather than returning an in-band
    `[ERROR]`.
  - `InferenceRequest.chat_payload`, a real dataclass field. It has to be one because the
    prefix-cache router's `dataclasses.replace` would drop a dynamic attribute.
  - `InferenceResult.tool_calls`.
  - `_call_caching_backend` makes batch-only calls when a payload is present, because tool calls
    arrive whole. It also skips the content cache for payloads.
  - `llama_server` sends any payload to `/v1/chat/completions`, even on a `/completion` backend. The
    role therefore needs a tool-capable `--jinja` template, as doc §4 says.
- **Refused in client mode:** image input returns 400. A malformed `tool_choice`, or one naming an
  undeclared tool, returns 422. The default mode keeps its permissive handling.

### Routing in client mode (decision)

- **Role resolution:** exactly the default path: `x_force_model` > `x_orchestrator_role` > model
  alias (`orchestrator`, `gpt-*` → frontdoor), then `normalize_ingress_role`. The code runs before
  the mode branch.
- **What applies:** the call goes through `_real_call`, so these all apply:
  - contention gate;
  - per-role semaphore;
  - admission control;
  - region locks;
  - circuit breaker;
  - same-tier model fallback (`model_fallback` flag);
  - depth override;
  - inference tap.
- **What does not apply:**
  - REPL turns;
  - escalation. `/v1` has none in either mode, and `x_max_escalation` stays metadata only. This is
    the existing P4 routing-parity gap and is unchanged here.
  - the role system-prompt suffix, persona and RAG injection (the client owns the conversation);
  - the content cache;
  - B2 history compression (P1 replaces it);
  - the `output_cap` truncation (8192 characters) in `_llm_call_impl`. In client mode, `max_tokens` is the only bound on output size.

### P0.2: typed keys

- **Validation:** 422 on any bad value.
  - `x_session_id` and `x_user_id` must match `^[A-Za-z0-9][A-Za-z0-9._:@+/=-]*$` and be 1–128
    characters.
  - `x_memory` takes `on` or `off`.
  - `x_tool_mode` takes `repl` or `client`.
- **Recording:** keys that are sent are echoed in `x_orchestrator_metadata.request_keys`, which
  follows the existing `x_show_routing` gate. They are also stamped on the inference-tap section
  metadata (`request_keys`), which is the `/v1` trace record. The `/chat` progress log was not used,
  because it feeds MemRL `q_reward`.
- **`x_memory="on"`** is recorded only, as `memory_injection:"not_implemented"`, until P2.
- **Existing `x_*` keys are unchanged.** `x_max_escalation` is metadata only.
  `x_orchestrator_role` and `x_force_model` pick the role. `x_disable_repl` picks the direct path;
  in client mode it is recorded and moot. `x_show_routing` gates the metadata. Unknown `x_*` keys
  are still ignored, because pydantic's `extra` setting is `ignore`.

### Session guard (coordinator request)

- New flag `v1_client_session_guard`, on by default in both test and production. Its spec line was
  added as `baseline`, and the spec re-renders byte-identical.
- It returns 422 for a `/v1` request with an **OpenCode user-agent** (substring `opencode`,
  case-insensitive) or `x_tool_mode="client"` and no `x_session_id`.
- Other clients are unaffected: tested with aider, the OpenAI SDK, httpx and an empty user-agent.
- Disable with `ORCHESTRATOR_V1_CLIENT_SESSION_GUARD=0`.
- **Behaviour change:** any existing OpenCode client pointed at `:8000` without the plugin now gets
  a 422.
