## Operator questions answered with evidence (R23-28, R23-29)

**"Should we use a different screening model in the appropriate quantization?"** Partly — but a
fully faithful cheap screen may be impossible. A screen must match on quant family, architecture
AND GEMM dimensions; the winning tile is selected by rocBLAS/Tensile *from the matrix dims*, which
derive from n_embd=5120, so any model small enough to be cheap dispatches different tiles. **The
property that makes a screen cheap destroys its fidelity for GEMM work.** A same-quant
same-architecture small model would faithfully screen dequant, SSM and attention families but not
tiling/occupancy. None exists on disk: the Qwen3.8 SSM-hybrid family has only the 27B, and
`Qwen3-1.7B-Q8_0` is a dense transformer that never touches `gated_delta_net`.

**"Could the screen-rung gains still be useful for a Q4_K target?"** Yes — and this **corrects my
earlier "worthless on production" framing, which was too strong.** Verified by reading the diffs:
`7d2ea88b` gates on `GGML_TYPE_Q4_K` and `732389d6` on `type == GGML_TYPE_Q4_K`; both are hard-gated
and **cannot execute on a Q8_0 model**. That is exactly why the champion measures
production-neutral (+0.337 pp, inside floor) — the code never fires. They are DORMANT, not harmful.
`db18f393` (fattn) has no quant gate and is the only one running on today's production model.
Caveat against over-correcting: the +5.097%/+13.930% were measured on a **1.5B** Q4_K; a large Q4_K
model has different GEMM dims, so the quant *path* transfers but the *magnitude* does not.

**"Should we have quantization-specific kernel paths?"** We already do — llama.cpp templates per
quant type and our keeps gate correctly, which is why a Q4_K-tuned champion sits harmlessly inert
under a Q8_0 workload. What is missing is *metadata*: a `quant_family`/`applies_to` field per keep
so the headline can be reported per target, a future Q4_K path inherits deliberately rather than by
archaeology, and the loop can be told which family to hunt.
