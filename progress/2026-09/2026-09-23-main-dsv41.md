## Max performance directive and the AutoKernel campaign (operator, 2026-09-23)

- **Preliminary canonical recipe for this model: `-t 48`** (decode > prefill). Prefill keeps 96 where
  a tool supports the split. Being codified in the research repo rather than left in prose.
- **Spec decode is part of the recipe, not an add-on** — *"I DO NOT CARE ABOUT BASELINE, ONLY MAX
  PERFORMANCE"*. This model's drafter is DSpark and **it is not in our artifact**: antirez's
  converter omits every `mtp.*` tensor. Official shards 44-46 (~8 GB) downloading; the tied
  `embed`/`head` come from the GGUF we already serve, so shards 2 and 43 (~21 GB) are NOT needed.
  The accept/verify loop does not exist even in DeepSeek's release — we write it.
- **Campaign shape**: planner = our live Qwen3.8-Flash-Next (:8074), critic = `gpt-6-sol high`,
  target = CPU decode on `experimental/deepseek41-port-20260923` at `-t 48`, measured
  **spec-dec-on once the drafter lands** so the loop never optimises the wrong surface.
  The operator confirms planner inference and measurement never run concurrently (serial loop), so
  the :8074 question is purely whether the loop's lifecycle can take that server down.
- **Where kernel effort should NOT go**: decode is flat 24->96 threads, so barrier/dispatch levers
  cannot pay here. The Engram gather is the first suspect (48 random rows/token, zero prefetch
  depth); the profiling surface being built must distinguish major from minor page faults, because
  "hitting disk" and "hitting page cache" have opposite fixes.

## Speculative decoding: wired, measured, profitable (INF-77 DS41-B13)

Serving class, -t 48 -tb 96, same server config throughout:

| arm | decode t/s |
|---|---|
| no drafter | 11.43 |
| greedy, serial verify | 7.18 |
| **greedy, batched verify** | **17.85 median; 18.79-22.08 on low-entropy** |

The serial path (forced for DSpark at temp <= 0) decodes each accepted token in its own
`llama_decode`, so it yields exactly 1 token per target decode and **can never exceed 1x** — a
drafter under it is worse than no drafter. Operator adopted batched greedy; recipe default is now
`greedy-batched` at block 2 (research `89e7f210`).

**Corrections I had to make to my own reporting, both caught before they hardened:**
1. I compared llama-bench tg128 (13.18) against a serving run (6.01). Different instrument classes;
   the comparison is refused, not caveated. The same-class control is 8.21-11.43.
2. I reported divergence as "confined to high-entropy prompts". The two low-entropy prompts had
   returned **1 token then EOS, empty content, in every arm** — they were instruction-phrased and
   this model ships no chat template, so they proved nothing and I read their silence as evidence.
   The re-run with continuation prompts: the arithmetic chain forks into a SYNONYM with every number
   preserved; the table and the counting sequence are identical over 160 tokens. Divergence tracks
   near-ties, not entropy class.
3. I quoted 22% of a 460.8 GB/s roofline. That is the sequential-stream figure; decode is a gather
   with dequant, and this host's measured gemv-pattern ceiling is 153-167 GB/s. We are at ~61% of
   the ceiling that applies, not 22% of one that does not.

## Targets (operator): gate 30 t/s, aim 45-50

30 is reachable by streaming alone (101 -> ~165 GB/s). 45-50 needs streaming plus a byte cut, and
the byte lever is the DENSE path: attention is 5.01 GiB/token against 4.56 GiB for the routed
experts, with 2.99 GiB in the output projections alone. "It's a MoE, so the experts dominate" is
false on this checkpoint.

## Residency (operator directive) — and a live defect on the champion

The engram table needs **no code**: under the canonical recipe (`--no-mmap` + interleave) it is
already fully resident at 25.0% per node; the lazy-tensor path cannot override `--no-mmap`.

But checking the sibling model found a live problem on the **planner/champion server** (PID
2021760): VMA A (68.34 GiB) is 100% resident and 100% locked at 25.0% per node, while **VMA B
(18.90 GiB) is 0% locked, 88% resident, with 2.27 GiB in swap** after an `mlock` failure at load
that never retried. That is almost certainly the repacked expert rows the iqk GEMM reads every
token. It needs a restart to fix (operator owns stack lifecycle), and until then any INF-70 arm
measured against it is comparing to a degraded baseline — a measurement-validity hazard, not just a
latency one.
