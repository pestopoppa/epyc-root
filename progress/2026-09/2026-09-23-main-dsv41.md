## Max performance directive and the AutoKernel campaign (operator, 2026-09-23)

- **Preliminary canonical recipe for this model: `-t 48`** (decode > prefill). Prefill keeps 96 where
  a tool supports the split. Being codified in the research repo rather than left in prose.
- **Spec decode is part of the recipe, not an add-on** — *"I DO NOT CARE ABOUT BASELINE, ONLY MAX
  PERFORMANCE"*. This model's drafter is DSpark and **it is not in our artifact**: antirez's
  converter omits every `mtp.*` tensor. Official shards 44-46 (~8 GB) downloading; the tied
  `embed`/`head` come from the GGUF we already serve, so shards 2 and 43 (~21 GB) are NOT needed.
  The accept/verify loop does not exist even in DeepSeek's release — we write it.
- **Campaign shape**: planner = our live Qwen3.8-Flash-Next (:8074), critic = `gpt-6-sol high`,
  target = CPU decode on `experimental/deepseek41-port-20260923` at `-t 48`, measured
  **spec-dec-on once the drafter lands** so the loop never optimises the wrong surface.
  The operator confirms planner inference and measurement never run concurrently (serial loop), so
  the :8074 question is purely whether the loop's lifecycle can take that server down.
- **Where kernel effort should NOT go**: decode is flat 24->96 threads, so barrier/dispatch levers
  cannot pay here. The Engram gather is the first suspect (48 random rows/token, zero prefetch
  depth); the profiling surface being built must distinguish major from minor page faults, because
  "hitting disk" and "hitting page cache" have opposite fixes.
