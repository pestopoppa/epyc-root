### CORRECTION — the pre-evict hazard is reclaim-then-load, not the constant (mtp-tip2)

My earlier filing ("is 40 GiB too low?") named the wrong variable. `mtp-tip2` looked at the evict logs and found the
real mechanism: two consecutive loads of the same model by the same launcher, both at `EVICT_GIB=40`, 33 s apart,
with **identical post-evict free profiles** (119/51/46/81 vs 118/50/46/81 GiB), produced **opposite** placements —
48.9% skew (23.03/23.03/11.77/34.28) vs perfect (23.02/23.03/23.03/23.03). The skewed run's evict had found **node 2
at 0 GiB free**, forced a 42 GiB membind alloc/release to reclaim it, and **loaded immediately**; the clean run's
evict did nothing because the previous run had already cleaned that node. **The node that required reclaiming is the
one that under-filled**, and its missing 11.26 GiB went entirely to node 3 (11.77 + 34.28 = 46.05 = 2 × 23.03).

**C7's merged launch path does exactly evict-then-load-at-once**, so the skew lands on precisely the launches the
setting exists to protect. A larger constant lowers the odds of a reclaim but does not remove the hazard. The agent's
primary recommendation — which I agree with and have filed over my own — is **verification, not evicting harder**:
production has no post-load placement check (C7 logs `[numa-placement]` but logging is not gating), so a skewed load
is served silently. Every INF-70 bench arm gates on in-window `numastat` at 15% deviation and refuses to run; the
launch path lacks that. Sub-tasks filed: add the gate; test a settle delay between reclaim and load (cheapest probe
of the mechanism); scale any constant with the per-node share rather than an absolute. Evidence strength stated
honestly by the agent: n=1 skew at 40, n=1 clean at 40, n>=4 clean at 60 — 60 was never observed to fail, not proven
sufficient.

## 2026-09-04 — BE-2 SOLVED: flash attention's "carrier 2" is not a bug, and the default is the fastest config

`be2-fa` named the mechanism from source and then measured the trade. **Recommendation: keep `--fa 1` with the
split path ON (the default) and accept the non-exactness — it is also the fastest configuration at every depth.**

**Mechanism.** `ops.cpp:9424-9426`: `use_split_kv_path` requires `neq1 == 1` (one query row) AND `nek1 >= 512`.
`llama-kv-cache.cpp:1270-1275`: **n_kv is padded to a multiple of 256**, so `nek1` is 256 for real n_kv 1–256 and
512 for 257–512 — the gate flips at exactly real n_kv 257, the measured bisect. **The "256 boundary" is the KV
padding quantum meeting the split path's 512 gate, not an FA block size.** Single-row decode splits KV across
threads into partials recombined by online-softmax rescale; any `neq1 > 1` batch takes one sequential pass with
rows split across threads. **Algebraically equal, numerically different — a 1-row decode and an n-row verify batch
cannot be bit-identical at depth by construction. No bug exists.** Provenance: upstream `9f682fb64` (2026-02-03,
#19209), a deliberate token-generation optimisation. "Repairing" it means giving it up.

**Proof**: prefix 254, `--fa 1`, carrier 1 already removed — default → `node_584 FLASH_ATTN_EXT [256,24,3]` row 2,
68,334,110 state bytes differ (reproduces batch-envelope exactly); **`GGML_FA_SPLIT_KV=0` → all 3 rows IDENTICAL,
0/248320 logits, 0 state bytes.** One boolean removes the whole carrier with FA still on.

**Speed decides it** (llama-bench 10221, t48):

| depth | `--fa 1` split ON | `SPLIT_KV=0` (exact) | `--fa 0` |
|---|---|---|---|
| tg32 @ d512 | **12.48** | 12.16 | 12.58 |
| tg32 @ d2048 | **12.01** | 11.78 | 11.85 |
| tg32 @ d4096 | **11.89** | 11.21 (−5.7%) | 11.19 (−5.9%) |
| pp512 @ d4096 | **188.12** | 180.39 (−4.1%) | 169.10 (−10.1%) |

Exactness costs ~5.7% decode / ~4% prefill at 4k; `-fa 0` costs the same decode and **2.5× more prefill**.
**`-fa off` is retired as a serving option**; `GGML_FA_SPLIT_KV=0` is kept as a diagnostic.

**⚠ Corollary — a real measurement hazard**: the split path's chunk size depends on `nth`, so **single-row decode at
n_kv > 256 is not thread-count invariant — changing `-t` changes the logits.** Any A/B varying thread count at depth
compares different numerics.

**My `LLAMA_ATTN_ROT_DISABLE` lead: FALSIFIED.** `attn_rot_k/v` require a quantised KV cache; our arms run f16, so
