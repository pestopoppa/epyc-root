# Window-2 findings 05b — MI210 single-GPU inference architecture (supplement to findings-02, §4B one level down)

**2026-07-03.** Companion to [findings-02](fable5-window2-findings-02-heterogeneous-gpu.md) (fleet placement) and the empirical campaign ([progress/2026-07/2026-07-03-mi210-qwen36-27b-speed-campaign.md](../../progress/2026-07/2026-07-03-mi210-qwen36-27b-speed-campaign.md)). Where findings-02 asked *which roles migrate*, this asks *what makes inference on one MI210 as fast as it can be* — the kernel/head/quant layer the bench sweep can't reach by itself. **Every throughput number here is an OBSERVATION** (no P-GPU-1; contended host, single runs) and gates nothing; the value is the architecture + the decisive experiment behind each claim. Substrate: gfx90a/CDNA2, 64 GB HBM2e (~1.64 TB/s), ROCm 6.2; HIP build `/mnt/raid0/llm/llama.cpp-mi210-hip/build-hip`; **kernel work lands in `llama.cpp-experimental`** (operator rule).

## 0. The frame is half-wrong — say it first

"Make `Qwen3.6-27B-MTP-Q8_0` fast" is the wrong *unit*. That 27B dense hybrid is **not a production role** — it's a clean single-GPU **test vehicle for the `qwen35` family**, and the family is what deploys: frontdoor = 35B-A3B `qwen35moe`, architect = 122B `qwen35moe` — both gated-delta-net (GDN) hybrids. So the only work worth doing on the 27B is the work that **transfers to those**. The profile (below) says exactly which does. Two distinct, transferable levers exist — and the biggest one is not a kernel rewrite, it's a one-line dispatch threshold.

**Bottom line up front (cheapest → highest transfer):**
1. **MMVQ→MMQ small-batch verify fix** — ~1 line, numerically safe, **~2× single-stream MTP** (33.6 → ~55–80 t/s obs-projected), transfers to *every* Q8 spec-dec on gfx90a (frontdoor + architect included). **Author first.**
2. **GDN-recurrence batched-MFMA kernel** — the aggregate/concurrent ceiling; bigger effort; transfers to all `qwen35`.
3. **Frontdoor residency (findings-02 Gate R)** — the placement bet the 27B work is *teaching*.
- **Head:** MTP now (in-hand, fused verify, gets ~2× from lever #1). **EAGLE-3 machinery already ships in v6** (cheapest upgrade if a trained head exists). **DFlash: hold** — v2-era, CPU-only, block-mode never worked; gated on a cheap offline τ that the GPU-only constraint currently blocks.
- **vLLM:** cannot load our archs on gfx90a (settled); closing the *fork's own* batched gap beats adopting vLLM.

## 1. Q1 — the kernel gap: which kernel first, and why

**Single-stream decode is pure bandwidth-bound Q8 weight-GEMV.** rocprof (B=1, `-fa 0`): `mul_mat_vec_q` = **77.8%**, whole GEMM/dequant bucket 84%; GDN/SSM = **2.0%**, attention 0.2% (`prof/b1/decode_b1.stats.csv`). So the raw batch-1 kernel headroom is small (Q8 = 47–52% roofline; the fp16 ceiling is 62% → ~+19% recoverable) and it is the hardest class to move (already BW-bound). **Q8 is the correct deployment quant** — fewer bytes than fp16 → faster in absolute t/s despite lower roofline-%. Q4_K is *not* a dead end but is the *inefficient* dequant (33% / 537 GB/s vs Q8's 47% / 766); reaching Q8's efficiency would give ~45 t/s (+55%) — a **quality-gated** side bet, decided by a Q4_K-vs-Q8 rocprof-counter check (VALU-busy vs mem-stall on `mul_mat_vec_q`) + an eval-parity run.

**The real single-stream lever is not a kernel rewrite — it's the verify dispatch.** MTP advances mean **2.99 tokens/round** yet yields only **+15.6%**, because the 4-token verify batch (`ne11=4`) dispatches to `mul_mat_vec_q` (per-column, **2.32 weight-reads/block**), not the batched `mul_mat_q` (one read). Cause: on CDNA2, Q8_0 hits `ggml_cuda_should_use_mmvq`'s `default: return ne11 <= MMVQ_MAX_BATCH_SIZE (=8)` (`ggml/src/ggml-cuda/mmvq.cu:320-322`, `mmvq.cuh:3`), and MMVQ is preferred over MMQ whenever eligible (`ggml-cuda.cu:2614` before `:2616`). Smoking gun: B=8 MMVQ = 14.8 ms/tok vs **B=12 MMQ = 8.5 ms/tok** (more tokens, less time). **Fix:** route small Q8 verify batches (2–8 cols) to MMQ — a CDNA2 `case GGML_TYPE_Q8_0: return ne11 <= 1;` or a dispatch reorder. Numerically safe (same result). **MEASURED (2026-07-03): the MMVQ→MMQ fix delivers +17.4% single-stream MTP (34.4→40.4 t/s), NOT the projected ~2×** — because `mul_mat_vec_q` already amortizes tile loads across the 4 columns in-register, so MMQ removes only ~15% redundant HBM traffic (not the full ~4× read reduction the ceiling assumed). One-line diff, 31 s build, coherent output + acceptance up (0.673→0.728), numerically-valid-not-bit-exact; validated in `llama.cpp-experimental` (branch `upstream-mtp-verify`, commit `de447119f`). §6 self-critique predicted exactly this partial outcome (MMQ tiles 16/32-wide → 4 cols waste 3/4 of a tile). Still a real, cheap, transferable win for GPU-resident Q8 spec-dec — MTP, EAGLE-3, and any DFlash on gfx90a — **operator-gated for prod promotion.** **This is the kernel to author first: cheapest, highest-ROI, and it compounds to every Q8 spec-dec on gfx90a — MTP, EAGLE-3, and any DFlash — plus the frontdoor/architect MTP verify.**

**The aggregate/concurrent bottleneck is the GDN recurrence.** rocprof (B=1→B=32): GEMM amortizes (84%→65%) while GDN balloons **2%→19.5%** (absolute ×39); the recurrent machinery (GDN + norm/gate/concat + state-gather) goes 7.5%→32%. The GDN state update is 128×128 per-head matmuls done in registers **without MFMA** (`gated_delta_net.cu:53-61,103,132`). At batch>1 those could be MFMA'd (CDNA2 has fp16/bf16/int8 MFMA) — the second kernel, bigger effort, for the concurrent regime; it transfers to all `qwen35`. Decisive pre-build check: rocprof hardware counters (VALU/occupancy) on `gated_delta_net_cuda` at B=32 to confirm it's occupancy/compute-bound (addressable) not already-saturated.

**Is the CDNA2 dequant ceiling architecturally addressable?** For *spec-dec* yes — the MMVQ fix is the big one. For *raw batch-1 dequant-GEMV*, mostly no (it's BW-bound; ~+19% to fp16-equivalent is the hard ceiling). For *aggregate*, yes via GDN-MFMA. So "author a dequant kernel" is the *wrong* first move; the dispatch fix + GDN kernel are the leverage.

## 2. Q2 — the spec-dec head: MTP wins; EAGLE-3 is the cheap upgrade; DFlash is held

- **MTP (incumbent, in-hand).** Embedded 1-layer full-attention NEXTN head (drafting never touches GDN; only verify does), fused GDN verify (already — `delta-net-base.cpp:527,564-567`; the "build a fused verify" idea was falsified by audit), snapshot-indexed O(1) rollback. Correct invocation is **`--spec-type draft-mtp` with NO `-md`** (the `-md <same file>` production recipe double-loads the model → ~0% gain — a live production bug for the CPU roles). +15.6% today, **~2× after the MMVQ fix.** **This is the deployment head.**
- **EAGLE-3 (already in v6).** The tap-target-hidden + conditioning machinery DFlash needs *already exists* as v6's EAGLE-3 path (`common/speculative.cpp:419-850`; `llama_set/get_embeddings_layer_inp`, `src/llama-ext.h:111-115`). It needs only a **trained EAGLE-3 head GGUF for `qwen35`** + relaxing the hard `target_layer_ids_n==3` assert (`:464-466`). **Cheapest capability upgrade if such a head exists** (open question — check HF for a qwen35/Qwen3.6 EAGLE-3 head); a tree draft could lift mean-accept above 2.99.
  - **MEASURED (2026-07-03) — EAGLE-3 no-go; MTP stays the head.** The `Ex0bit/PRISM-EAGLE3` head **loads and runs on our v6/HIP build and survived 900 tokens** — the upstream #24541 Part-2 >700-token crash does **not** reproduce on our fork (a genuine capability finding). But it is **slower than MTP: 25.0 t/s vs 33.6 t/s**, with acceptance mean **2.34 < MTP's 2.99** and a heavier 3-tap draft. So **MTP stays the head; EAGLE-3 is a viable-but-inferior fallback**, not the cheap upgrade this section had assumed.
- **DFlash (hold).** The `/mnt/raid0/llm/llama.cpp-dflash` worktree is **v2-era** (v6 is not an ancestor; 1585 commits behind), **CPU-only** (never ran on GPU), and its **block-diffusion mode has never worked** (acceptance 0.1–0.3%, τ≈0; the only healthy 27% is AR-mode on the *old* Qwen3-MoE pair). Its taps are hardcoded `{1,12,23,34,45}` and tap-capture was never wired into `qwen35.cpp` (→ zero taps on the real target). The GGUF is also missing `padding_token_id`/`unknown_token_id` (set pad=248044) and has an eos discrepancy (GGUF 248046 vs HF 248044) — the exact silent-block class to verify, not assume. **The graft is cheaper than feared** (it's "EAGLE-3 minus AR-decode plus block-mask-decode" — reuse v6's EAGLE-3 tap/encoder/verify), but the payoff is unproven.
  - **Decisive pre-port measurement (designed, deferred):** fix 3 stale constants in the existing CPU tool `llama-dflash-acceptance` (add qwen35 tap-capture ~12 lines; taps `{1,16,31,46,61}`; mask `248070` + pad override), rebuild CPU-only, score **block-τ = mean matching-prefix length** over 50–100 prompts vs the 27B's greedy continuation. **Go if τ ≥ 4.0** (paper target 6.49), **marginal 3.0–4.0, no-go τ ≲ 3.0** (MTP's 2.99 is already in hand, needs no 8.5 GB model and a cheaper verify). ~1–2 h patch + overnight CPU run. **Deferred** because it is CPU-heavy and the current directive is GPU-only + a parallel CPU session is live — which is itself an argument for MTP: DFlash's very go/no-go test is blocked by the substrate, while MTP already runs on the GPU today.
  - **Verdict: hold the port.** Design is understood (§ above); do not sink the port cost until (a) the MMVQ fix lands — if verify amortizes, MTP's ~2× raises the bar DFlash must clear — and (b) the offline τ clears ≥4 in a coordinated CPU window. Because short blocks are optimal in the BW-bound regime (n_max=3 best; 5/7 regressed), DFlash's 16-token block is a *headwind* unless its per-position acceptance is exceptional.

## 2b. CPU cross-check — the MMVQ fix is GPU-specific; the real CPU MTP win is a launch-config bug

The MMVQ→MMQ verify fix (§1–2, lever #1) was assumed to carry to the CPU-resident frontdoor/architect MTP verify. A CPU-side audit says **it does not** — and surfaces a different, larger CPU win:

- **CPU MTP verify already AMORTIZES the weight read — the GPU MMVQ non-amortization is CDNA2-specific; the fix does NOT transfer to CPU.** The production iqk path uses column-count-specialized kernels `funcs[0..7]` that are the *same* register-tiled GEMM for `nrc_y` 1–8, weight-block-outer / columns-inner (`iqk_gemm_legacy_quants.cpp:302-330` Q8_0; `iqk_gemm_kquants.cpp:392-413` Q4_K) → one weight read is reused across all N+1 verify columns. There is **no per-column vector kernel / no MMVQ-analog on the iqk path** — the only batch threshold (`iqk_mul_mat.cpp:238-332`) is a prefill dequant-GEMM switch at `nrc_y≥16/32/64`. The generic fallback also amortizes via 16×16 tiling (`ggml-cpu.c:1193-1242`). The one CPU gate `repack.cpp:4241-4251` (`nrows>3 ? gemm : gemv`) is **DEAD for production** because Q8_0/Q4_K bypass CPU_REPACK under `GGML_IQK` (`repack.cpp:4529-4551`).
- **The real CPU MTP win is a launch-config bug (not amortization).** `-md <same GGUF>` double-loads the model: `server-context.cpp:1172` enters `has_draft` whenever `-md` is set, `:1199` loads a second full copy, `:1207` `spec_mtp` only flips the context type without skipping the load; the zero-extra-load self-spec path (`:1220-1235`) is reached ONLY when `-md` is absent. Production frontdoor (:8070) + architect (:8083) launch `-md <same file>` → 2× resident weights + 2× DRAM pressure on BW-bound decode, defeating self-spec's memory benefit. **Fix: drop `-md` for Qwen NEXTN roles.** This is a production/orchestrator-config change owned by the CPU session, flagged here.

## 3. Q3 — the serving fabric: the fork stays sole substrate

vLLM **cannot** serve our archs on gfx90a — four independent blockers (arch needs post-0.16 nightly; the GDN Triton kernel won't compile on gfx90a, vLLM issue #44973; no native-fp8 on CDNA2; MTP-on-AMD WIP). Its +11%/+24% single/batched edge exists only on **stock models it can load** (Qwen3-8B). Is a second engine worth it? For our archs, no (it can't run them). For stock-model subagent fan-out, marginal — the fork already does ~910 t/s @32-way, and the MMVQ fix + GDN kernel raise the fork's *own* batched serving. **Single-user latency is the regime that counts for our production archs; closing the fork's batched gap (via lever #1 + #2) dominates adopting vLLM.** Keep vLLM only as a throughput *bar* on a shared arch, and mine its GDN algorithm (already done — the fused-recurrent-verify insight came from it).

## 4. Q4 — the reframe: the smallest bet that compounds

The compounding unit is **kernel + head + placement**, chosen so each transfers to the next card and the next `qwen35` model:
- **Kernel:** the **MMVQ→MMQ verify dispatch fix** (helps every Q8 spec-dec on gfx90a today; then the GDN-MFMA kernel for aggregate). Both transfer to frontdoor + architect + any future qwen35 + the next AMD card.
- **Head:** **MTP** — it's already baked into every `qwen35` GGUF and its verify is fused; the "upgrade" is EAGLE-3 (machinery in v6) before any new-head port.
- **Placement:** **frontdoor residency** (findings-02 Gate R). The 27B campaign is the *learning vehicle* that de-risks the kernels; the deployment bet is migrating the frontdoor (the hot interactive path + eval engine) onto the card.

The smallest thing that compounds is therefore **(MMVQ fix) × (MTP, kept) × (frontdoor residency)** — one ~1-line kernel change, zero new head, one migration — and it improves the 27B, the frontdoor, and the architect at once.

## 6. Self-critique — the weakest link

**Weakest: the ~55–80 t/s MMVQ ceiling is a projection, not a measurement.** It assumes MMQ realizes near-full weight-read amortization at only 4 columns — but MMQ tiles are 16/32-wide, so 4 cols wastes 3/4 of the tile; MMQ@4 could underperform MMVQ@4 and the real win might be half of projected (still large, but not 2×). The experimental build is measuring exactly this; if MMQ@4 loses, the fix becomes "tune the threshold" (maybe `<=2`, or a small custom 4-wide MMQ tile) rather than a clean one-liner — a bigger job. **Second weakest:** every number is an OBSERVATION on a contended, throttle-suspect host with no P-GPU-1 — the *ordering* is robust (MMVQ vs MMQ, GDN batch-scaling) but absolute t/s must be re-anchored under a ratified protocol before any of it gates a deploy. **Third:** the whole 27B analysis assumes clean transfer to the frontdoor (35B-A3B **MoE**) and architect (122B **MoE**) — but MoE decode reads only the *active* experts, a materially different GEMM shape/BW profile than the 27B dense; the MMVQ verify fix was listed here as an unverified "clean transfer" (arch-agnostic dispatch) — **the CPU cross-check (§2b) now comes back negative: the MMVQ non-amortization is CDNA2-specific and the fix does NOT transfer to the CPU-resident frontdoor/architect, which already amortize via iqk tiled GEMM** (the real CPU MTP win there is instead the `-md` double-load config bug, §2b). The GDN-MFMA and dequant conclusions still need one confirming profile on the actual MoE frontdoor before I'd bet the kernel-authoring budget on them. **What would most change this:** MMQ@4 measuring *slower* than MMVQ@4 (demotes lever #1 from one-liner to custom-kernel); or a qwen35 EAGLE-3 head existing (leapfrogs the DFlash question entirely).

## 7. GPU re-opens of CPU-era verdicts

Two verdicts reached on CPU/v2-era hardware deserve a GPU re-test now that the substrate has flipped. (Credit: operator flagged that we had already built tree-drafting.)

- **(a) Hybrid tree-drafting — GPU re-test warranted.** We already **BUILT** tree speculation ([../completed/tree-speculation-numa-drafting.md](../completed/tree-speculation-numa-drafting.md), 2026-03, DySpec dynamic trees) and measured it **NET-NEGATIVE on qwen35 hybrids**: −53% to −66% end-to-end, frozen-multipath acceptance −12–22 pp, and checkpoint/clone-cell −60% on 35B-A3B from copying **~450 MB recurrent state per round**. So it is guarded off (`!has_recurrent`) — **correctly, for CPU/v2.** BUT those were CPU/v2-era measurements: on GPU the recurrent state is only **149 MB** (rocprof) at **~1.6 TB/s**, so the per-path state-clone that killed Approach C on CPU is **~0.1 ms** on GPU. Phase-8 **Approach B (Delta-Net tree) was DEFERRED at ~40% viability, never killed.** → **GPU re-test warranted** — the state-clone term flips, though recurrent-*compute* scaling still argues caution.
- **(b) MTP/draft head on GPU + target on CPU — newly attractive.** The fork already has the plumbing (`-devd`/`-ngld`/`-otd` — draft on a separate device). This is newly more attractive because the CPU audit (§2b) proved **CPU verify amortizes the weight read**, so a GPU-hosted cheap draft + CPU target-verify **no longer eats findings-02's feared amortization penalty**; the only remaining cost is the per-step CPU↔GPU hidden-state PCIe shuttle. A future avenue for **target-on-CPU roles.**
