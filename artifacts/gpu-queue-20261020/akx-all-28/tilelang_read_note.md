## (a) The MFMA GEMM path

### a.1 How a `T.gemm` reaches MFMA, and what distinguishes gfx90a from gfx942/gfx950

- [F] ROCm `T.gemm` instruction pick: any CDNA target gets MFMA, any RDNA target WMMA. `src/rocm/op/gemm.cc:106` `SelectInst`, `:111` `if (TargetIsCDNA(target)) { return kROCmMFMA; }`.
- [F] "CDNA" means any `gfx9*` string: `src/rocm/target_utils.cc:22-31` (`return mcpu.find("gfx9") == 0;` with the comment `// if mcpu start with "gfx9", it is CDNA`). gfx90a, gfx942, gfx950 are all the same class here.
- [F] The ONLY sub-arch discriminators in the MFMA/GEMM stack are: (1) `TargetIsGfx950` (`src/rocm/target_utils.cc:44-52`), used at `tilelang/rocm/intrinsics/mfma_macro_generator.py:151` (8-bit k_dim) and `:222` (f16/bf16 k_pack remap) and `src/transform/pipeline_planning.cc:1155`; (2) `TargetRocmHasAsyncCopy` = gfx9x with number >= 94 (`target_utils.cc:54-65`); (3) FP8 FNUZ vs OCP variant (`src/tl_templates/hip/hip_fp8.h:14-24`, gfx940/941/942 = FNUZ). Nothing separates gfx90a from gfx942 for instruction choice.
- [F] gfx90a appears in the tree only as: a docs example string (`docs/get_started/targets.md:18`, `{"kind": "hip", "mcpu": "gfx90a"}`); macro lists in `src/tl_templates/hip/common.h:128-130` (SDOT4) and `src/tl_templates/hip/copy.h:20-22` (buffer-resource dword); and a docstring saying gfx950 tests are skipped on "non-gfx950 AMD targets (gfx90a, gfx942, RDNA)" (`testing/python/amd/test_tilelang_mxfp4_gfx950.py:3-5`).
- [F] CI: `README.md:124` "CI runs on a self-hosted gfx942 (MI300X) runner; gfx950 is not yet covered." There is no gfx90a CI statement anywhere. [I] gfx90a MFMA codegen is therefore untested upstream.
- [F] Tree assumes ROCm 7.x: `docs/get_started/Installation.md:45` (`whl/rocm7.0`), `docker/Dockerfile.rocm:1` (`rocm7.2_ubuntu22.04...`). [I] Compatibility with a ROCm 6.2 host was not checked.
- [F] Lowering path: `tilelang/rocm/op/gemm/gemm_mfma.py` (`GemmMFMA`, registered at `tilelang/rocm/op/gemm/__init__.py:17`) builds a `MatrixCoreIntrinEmitter` (`gemm_mfma.py:25-38` and `:79-93`) WITHOUT passing `mfma_shape`, so T.gemm always gets the default 16x16xK shape. Operand-scope variants SS/SR/RS/RR: `gemm_mfma.py:40-63` (layouts), `:124-157` (SS), `:158-188` (SR), `:189-215` (RS), `:216-234` (RR). Predicates `:238-248`.
- [F] Emission: the emitter calls `tvm_mfma(...)` (`mfma_macro_generator.py:495-509`), and the HIP codegen turns it into a plain builtin call: `src/rocm/codegen/codegen_hip.cc:1831` `std::string mfma_buildin = "__builtin_amdgcn_mfma_" + prefix;` with body `:1826-1830` `*c = builtin(*a, *b, *c, 0, 0, 0);`. Only "row" layouts are accepted (`:1797-1798`).
- [F] Wave size 64: `mfma_macro_generator.py:51` `WARP_SIZE = 64`; `src/rocm/op/gemm.cc` requires block >= one wavefront (`ICHECK_GE(block_size, warp_size)` in `ComputeWarpPartition`).

### a.3 k_pack

- [F] User API: `T.gemm(..., k_pack=...)` in the ROCm dialect, `tilelang/rocm/language/gemm_op.py:22` (`k_pack: int = 1`) and `:47-48` `if not (... k_pack in (1, 2)): raise ValueError("T.gemm k_pack must be an int equal to 1 or 2 ...")`. C++ re-check `src/op/gemm.cc:104-110` (`ICHECK(node->kPack_ == 1 || node->kPack_ == 2)`). Reader: `tilelang/tileop/gemm/gemm_base.py:140-141`.
- [F] Meaning: "k_pack represents the number of elements in a vectorized instruction" (`mfma_macro_generator.py:65-68`, points at the Triton kpack implementation). Mechanically: one wide per-lane load of `k_pack * local_size` elements (`T.vectorized(k_pack * local_size_a)` at `:407`/`:451`; local buffers sized `warp_rows * local_size_a * k_pack` at `gemm_mfma.py:133-134`), then `k_pack` back-to-back MFMAs along K (`for kp, i, j in T.grid(k_pack, warp_rows, warp_cols)` at `mfma_macro_generator.py:494`, A offset `(a_local_stride + (i*k_pack + kp)*local_size_a)` at `:505`).
- [F] Tile constraint: `gemm_mfma.py:117-120` asserts `block_K >= micro_size_k*k_pack` and `block_K % (micro_size_k*k_pack) == 0`.
- [F] CDNA examples use k_pack=2 for f16 (`examples/amd/example_amd_flash_attn_fwd.py:79`); RDNA WMMA restricted to k_pack=1 (`:70-72`).

### a.4 Fragment layouts (wave64, 16x16 base tile)

All in `tilelang/rocm/intrinsics/mfma_layout.py`; thread = lane 0..63.
- f16/bf16 (k=16), A: `thread_id_shared_access_64x4_to_16x16_layout_A` (`:41-44`): `i = thread_id % 16; j = (thread_id // 16) * 4 + local_id`. Forward map `:47-50`: `thread_id = i + 16*(j//4); local = j % 4`.

- k=64 (gfx950 i8): `:107-110`, `:119-122`. fp32 (k=4): `:7-26`. 32x32: `:131-183`.
- Index-map selection by (k_dim*k_pack, transposed, is_b): `mfma_macro_generator.py:238-293`; error text `:291` "k_dim must be 4 or 16 or 32 or 64 currently".

Reference decode being mapped (llama.cpp, read in `/mnt/raid0/llm/llama.cpp`, [X] w.r.t. the tilelang tree): IQ2_XXS `dequantize_row_iq2_xxs` `ggml/src/ggml-quants.c:2488-2512`: 32 bits read twice from `qs`, `db = d * (0.5f + (aux32[1] >> 28)) * 0.25f` (`:2501`), grid index = a byte (`iq2xxs_grid + aux8[l]`, `:2503`, 256 x uint64), 7-bit sign index `ksigns_iq2xs[(aux32[1] >> 7*l) & 127]` (`:2504`, a 128-entry uint8 table), per-bit sign via `kmask_iq2xs[j]` (`:2506`). [I] so blocks are only 2-byte aligned and a naive uint32/uint64 load at a block field is not aligned for odd block indices.

## (d) Verdict

**expressible-with-workaround (not shown by any shipped example).**

Every primitive an IQ2_XXS/IQ2_XS/IQ3_XXS/IQ3_S grid-lookup decode needs exists individually and the f16/bf16 MFMA path exists for gfx90a-class instructions, so a decode-to-f16/bf16-shared-tile then `T.gemm` kernel is expressible in principle (patterns: `cdna4:210-238`, `fine_grained:53-86`, scale indexing `cdna4:149-153`, bit-ops `quantization.py:310-343`, popcount `intrin_rule_hip.cc:124-137,263-265`, gather `nsa_fwd.py:79`). The tree contains no grid-decode example and no gfx90a-specific example or test, and the exact missing pieces are:

1. **No first-class constant/LDS-resident literal-table primitive.** The 256/512-entry uint64/uint32 grids (and the 128-entry sign table) must be (a) an extra global `T.Tensor` argument indexed with a computed value, (b) a staged shared-memory copy, or (c) hand-written HIP C++ injected through `T.import_source` / `T.Kernel(prelude=...)`. The only lookup table in the tree is a 16-entry `static const float` in function scope (`examples/dequantize_gemm/quantize/mxfp.py:141-153`), and it sits inside the gfx950-gated branch (`mxfp.py:215-226`) even though the C++ is portable.
2. **No gfx90a-valid int8 matrix-core path through `T.gemm`.** The emitter hard-selects `__builtin_amdgcn_mfma_i32_16x16x32_i8` for int8 on every gfx9 (`mfma_macro_generator.py:141-143,190-191`), an instruction that exists on gfx940+ [X]. On gfx90a the int8 routes are `T.dp4a` (sdot4, `common.h:128-143`; no HIP execution test in tree) or dequant to f16/bf16 then MFMA.
3. **Everything gfx90a is untested upstream** (CI is gfx942 only, `README.md:124`; no gfx90a test or example anywhere; pipelining stripped off-gfx950, `pipeline_planning.cc:1155`; tree targets ROCm 7.x, `Installation.md:45`, `Dockerfile.rocm:1`).
4. Alignment: IQ block sizes (66/74/98/110 B) force uint16/byte-granular reads or an offline repack ([I], from ggml-common.h static_asserts).

Not claimed: any performance expectation, any statement that these pieces compose without compiler errors (nothing was built or run), and anything about base-TVM lowering of AllocateConst/uint64 tables (`3rdparty/tvm` empty).
