## 2. `LLAMA_SPEC_EXACT=serial` — where it is implemented and what it changes

* Parse: `tools/server/server-context.cpp:76-96` (`spec_exact_mode_from_env`, read once at `:991`).
* Gate: `use_serial_speculative_verify()` `:3078-3104` returns true for `serial` whenever `sampling.temp <= 0` (any drafter, any `seq_rm` type). Default (env unset) is serial only for RS-rollback target + DSpark drafter (`:3094-3102`).
* Batch construction: `server_slot::handle_last_sampled_token(batch, serial)` (`:522-549`, called at `:3317`) puts ONLY the sampled token into the target batch; the drafts are not appended and `spec_i_batch` has one entry.
* Verification: `sample_and_accept_dspark_serial()` (`:3996-4049`, called at `:4302`) samples row 0, then for each draft token that matches the sample runs `llama_decode` on that one token (`serial_batch.init(1)`, `:4032`), feeding it to the drafter via `common_speculative_process`. It stops at the first mismatch.
* Consequences: every target forward is the n_tokens = 1 shape (the k=1 column of the route table, including the fused FFN, the 8-warp MMVQ and the VEC k=1 FA), so output is exact vs plain decode by construction; no rejected token is decoded, so no checkpoint (`:3288`) and no rollback; cost = up to (n_draft+1) sequential target decodes per round, no batching benefit. `rowexact`'s reference arm (`run_single`, n single-token decodes) is the library-level analogue.
