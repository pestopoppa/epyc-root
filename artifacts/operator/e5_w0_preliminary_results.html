Shape × concurrency — every row fully specified

How to read this table

Instances is how many llama-server processes are running. np/inst is the -np slot count given to each one. T = instances × np/inst is the total number of requests in flight across the whole machine — so 4 instances at np=1 and 1 instance at np=4 both sit at T=4, and only rows with equal T are comparable.

Per-stream is what a single request sees (the latency axis). Aggregate is the sum across all in-flight streams (the throughput axis). Highlighted rows are np=1, which tie back to the single-instance reference in §01.

All llama-server, canonical placement, cold, --no-mmap with per-node --membind on every fleet so each instance genuinely owns node-local weights. Reading it at equal T — one full machine wins everywhere

At T=4: gemma 114.45 (1×full, np4) against 58.88 (4×quarter, np1). The 80B 58.04 against 42.65. The 35B 79.73 against 52.90. At T=8: gemma 196.48 against 97.27; the 80B 72.53 against 66.62; the 35B 105.07 against 81.00. The quarter fleet closes as T rises — the 35B is within 1.5% by T=32 — but it never overtakes.

The np=1 rows tie this to §01 directly: one quarter serving one request does 15.14 tok/s on gemma, where the whole machine serving one request does 36.11. Splitting the machine costs single-request latency and, at every concurrency measured, aggregate throughput too.

Batching payoff tracks active parameters rather than total footprint: gemma's A4B scales 5.4× from np1 to np8, the 80B's A3B 3.1×, the 122B's A10B only 2.3× by np4.

04

Why a fleet needs --no-mmap

llama.cpp mmaps the GGUF, so its pages live in the shared page cache and are placed once — by whichever instance faults them first. Every later instance inherits that placement regardless of its own --membind, which is accepted and does nothing. Measured from /proc/<pid>/numa_maps, four quarters each pinned and bound to their own node:

Armq0q1q2q3Host RAMFleet aggregate
mmap (shared)25.6%25.6%24.2%26.9%30 GB40.91 tok/s
--no-mmap + --membind100%100%100%100%171 GB52.13 tok/s
Consequence

Under shared mmap the placement depends on instance start order, so fleet throughput is nondeterministic across reboots. --no-mmap alone is not sufficient — without per-instance --membind the private pages simply follow default first-touch; production has recorded --no-mmap quarters at 0.486 / 0.333 local for exactly that reason. Every fleet number in §03 was taken with both set, so those rows describe a correctly-configured fleet, not the current one.

05

Required configuration

Ordered so each step is independently verifiable. The stack is currently down, so these take effect at next cold start — no reload, no live disruption.

  • Placement. frontdoor and ingest_long_context onto taskset -c 0-95 + numactl --interleave=all. Recovers 2.16× and 1.85×. No RAM cost.
  • Weights. Any role running multiple instances against one GGUF needs no_mmap: True and per-instance --membind. Recovers +27% on fleet decode and removes the start-order nondeterminism. worker_general already has this and measures 1.00 locality on all five of its instances — it is the working reference.
  • Threads. Any half-machine instance running -t 96 is SMT-oversubscribed on 48 physical cores; -t 48 measures +13% per-stream and +8.5% aggregate at np=4.
  • Slot width. §03 gives the aggregate/latency trade per role. Nothing here mandates a particular -np — that is a serving-policy choice between throughput and per-request latency, and the table is the input to it.
