Two production roles are serving at about half speed, and it is a wiring regression — not a kernel or model problem.

frontdoor and ingest_long_context launch on cpusets that straddle two NUMA nodes with no memory policy. The canonical recipe that fixes this was established on 2026-04-26 and reverted on 2026-05-24 on the strength of a 1.7% warm-cache A/B. Everything below is the re-measurement.

Evidence 2

Why a warm-cache A/B could never have caught this

numactl --interleave binds at first touch only. Against a warm page cache it is a no-op — the pages are already placed, and the flag changes nothing. So an A/B run without drop_caches compares two configurations that are using the same physical page placement, and reports a difference of roughly zero. That is exactly the shape of the 1.7% result recorded in stack_numa.py that justified the 2026-05-24 revert.

The revert's own evidence, re-examined

The in-file comment reads "Config A: numactl --interleave=all + 96t → 26.60 t/s · Config B: NUMA_NODE0 + 96t → 27.06 t/s". That head-to-head is invalid twice over: it predates the 2026-04-24 NPS4 reboot, when 0-47,96-143 genuinely was a single NUMA node, and its source CSV records spec == "baseline". A 1.7% result overrode a documented 44% one.

Live topology, verified 2026-07-30 via numactl --hardware: node0 = 0-23,96-119 · node1 = 24-47,120-143 · node2 = 48-71,144-167 · node3 = 72-95,168-191. NUMA_NODE0 and NUMA_NODE1 are NPS2-era names; each now spans two nodes. Only the NUMA_Q* quarter constants are node-aligned.

Evidence 3

Shared mmap defeats per-instance --membind

llama.cpp mmaps the GGUF, so its pages live in the shared page cache and are placed once — by whichever instance faults them in first. Every later instance inherits that placement regardless of its own --membind. The flag is accepted and does nothing. Measured from /proc/<pid>/numa_maps, four quarter instances each pinned and bound to their own node:

Armq0q1q2q3Host RAMFleet decode
mmap (production default) 25.6%25.6%24.2%26.9% 30 GB40.91 tok/s
--no-mmap 100%100%100%100% 171 GB52.13 tok/s
Consequence · non-obvious

Under shared mmap, fleet placement depends on instance start order, so throughput is nondeterministic across reboots. Here four simultaneous loaders each grabbed ~25%. In the E5 W1 run a single straddling instance loaded first and put 100% of pages on node0, leaving the other three quarters entirely remote — worse than not splitting at all. That is why 14 nominally node-aligned E5 cells are confounded despite having correct cpusets.

--no-mmap alone is not sufficient; it must ship with per-instance --membind, or the private pages simply follow default first-touch. Production has recorded --no-mmap quarters at 0.486 / 0.333 local for exactly this reason.

This refutes the hypothesis I went in with

The expectation was that small-active models would favour quartering — fewer active parameters per token means less bandwidth per token, so more headroom to run four independent instances. gemma is the best -np scaler of the set (A4B, 5.4× from np1 to np8) and it is where the full machine wins hardest (+94% / +102%). The margin narrows at high T but the fleet never overtakes.

The gate the original campaign never had

np=1 on the corrected placement measures 38.72 tok/s, inside the independent AutoPilot production anchor (median_request_tps median 35.7, n=154, band 35–40). The original E5 grid sat at 7.8–16 and had no anchor check, so nothing flagged that every cell was running at roughly half the rate production actually achieves. P-BENCH-PLACEMENT-1 makes this check mandatory and voids any run that fails it.

Evidence 6

SMT oversubscription, and what the E5 record is worth

  • SMT. Half instances run -t 96 on 48 physical cores. Dropping to -t 48 gives +13% per-stream and +8.5% aggregate at np=4 (13.49 vs 11.91 tok/s). Quarters show the same sign, smaller (+2.4%).
  • The metric was a wall-clock rate. aggregate_predicted_tps was tokens / wall_seconds — including model load, prefill and idle. Renamed aggregate_wallclock_tps, with a true aggregate_decode_tps added from predicted_n/predicted_ms. Worth only ~5% median (22% worst) on its own — small next to the placement defect, and it must never again be conflated with a decode rate.
  • Rungs never saturated. Achieved concurrency against nominal was 100% at T=1 but 47% at T=32 — the fixed 43-prompt batch drains before it fills. Every high-T rung measured a partially-drained queue.
  • Disposition. Of 31 Stage-B cells, 4 are salvageable (gemma C1 np1/8/16/32 — full machine + interleave, weights verified 25%/node) and 27 must be re-run: 13 on straddling cpusets, 14 node-aligned but holding remote weights inherited through shared mmap. Recovered by offline replay of the persisted requests.jsonl — no re-measurement was needed to reach that verdict.
Retracted

“Four quarters is never the winning shape” as previously published here, and “production frontdoor decode is ~11–15 tok/s”. The first measured the defect rather than the shapes; the second came from long-context eval rows, not the model's rate. The wiki simultaneously asserted the opposite conclusion — “C3 quarters are aggregate-throughput-optimal for every model” — from the same defective grid. Both directions are withdrawn. What survives from the campaign: the 0.0% error rate on every cell, four harness fixes, and the protocol machinery.

The decision

What to change, and what it costs

Sequenced so each gate is independently verifiable. Nothing below has been applied — stack_numa.py currently carries explanatory comments only and is behaviourally unchanged.

Step 1 · placement

Rewire the two mis-wired roles to 0-95 + interleave=all

RAM: unchanged

Recovers 2.16× on frontdoor and 1.85× on ingest_long_context. Smallest change, largest single win, no new failure surface. Restores the canonical that was already in force before 2026-05-24.

Step 2 · weights

Set no_mmap: True + per-instance --membind on the quarter fleets

RAM: 239.8 → 561.0 GiB of ~1083 free

Recovers +27% on fleet decode and removes the start-order nondeterminism. Must ship with per-instance --membind or it does nothing. Note no_mmap is role-scoped in the current code with no per-instance analogue, so “quarters only” is not expressible without a small change.

Step 3 · threads

Drop half instances from -t 96 to -t 48

RAM: unchanged

Recovers +8.5% aggregate. Only relevant if any half-machine shape is retained after step 1.

Open question

Whether to keep the quarter fleets resident at all

would free ~4 copies per role

One full-machine instance wins at every rung measured, and needs one weight copy instead of five. The fleet's remaining justifications are failure isolation and letting different roles hold different nodes — neither is a throughput argument. This needs its own decision package; I have not pursued it.

Blockers

Things that must move before or with the fix

  • A test asserted the defect and forbade its fix — resolved. test_frontdoor_full_uses_numa_node0_not_full asserted both the straddling cpuset and that frontdoor carries no numactl_policy, so adding interleave=all would have failed CI. Replaced with test_straddling_cpusets_declare_a_numa_policy, which encodes the invariant that was missing and is xfail(strict=True) — it documents the live defect without breaking CI, and will fail the suite the moment the wiring is corrected, forcing the marker's removal rather than outliving the defect.
  • MEASUREMENT.md carries the retracted number as a ratified exemplar. Its claim-grammar section shows ✅ frontdoor decode 27.06 t/s [P-BENCH-2, n=5, 2026-04-26, attest a3f2] — that is the NUMA_NODE0-arm figure. It is illustrative grammar rather than a live assertion, but the exemplar is now retracted evidence. Needs your hand: the file is hook-enforced human-amendment-only, and a parallel session currently has an uncommitted rewrite of it, so I have deliberately not touched it.
