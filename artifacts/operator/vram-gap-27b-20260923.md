# SSU-F3 — the 27B's 38.61 GiB, buffer by buffer

**Date**: 2026-09-23 · **Subject**: `:8083` architect_general, PID 2021529 · **Mode**: read-only, live stack untouched
**Verdict**: the 4.90 GiB gap is **fully attributed**. It is not fragmentation, not transient peaks, and **not `-ub 8192`**.

---

## 1. Answer first

The declaration's capacity model has **two terms** — `vram_non_kv_gib` + attention KV. This process has **five**
allocations. Qwen3.8-27B is a **hybrid gated-delta-net / attention** model (`general.architecture = qwen35`, 48
recurrent layers + 16 full-attention layers + 1 MTP block) served with `--spec-type draft-mtp
--spec-draft-n-max 8`. That combination creates two GPU allocations the model has no term for.

| # | Buffer | GiB | Basis |
|---|---|---:|---|
| 1 | Model weights (`--no-mmap -ngl all`, incl. MTP block, shared by both contexts) | 27.0522 | measured (file size) |
| 2 | Target attention KV — 16 layers × 98304 cells × 2 streams × 2×1024 elem q8_0 | 6.3750 | source formula |
| 3 | **Target recurrent (GDN/SSM) state — 48 layers × 18 rows × (30720+786432) F32** | **2.6301** | source formula |
| 4 | **MTP draft context KV — 1 layer (blk.64) × 98304 × 2 streams × 2×1024 **F16**** | **0.7500** | source formula |
| 5 | Compute/graph buffers (×2 contexts) + HIP overhead | 1.8019 | **residual** (measured − 1..4) |
| | **Total** | **38.6093** | **measured: 38.6093** ✔ |

**Gap decomposition** (declared non-KV 27.33 vs measured non-KV 32.2343):

```
  2.6301  recurrent state cache          <- not represented in serving_shape
+ 0.7500  MTP draft context KV           <- not represented in serving_shape
+ 1.8019  compute buffers (two contexts) <- serving_shape budgets ~0.28 for ONE
- 0.2778  (27.33 declared exceeds the 27.0522 of actual weights)
= 4.9043  GiB   == the measured gap, exactly
```

Row 3 is the headline: **it is a linear function of `--spec-draft-n-max`**, at **0.2922 GiB per unit of draft
depth**. Nothing in the registry represents that, so MTP depth silently moves VRAM.

## 3. (b) Concluded by reading — with the five load-bearing sites verified verbatim

### 3.1 `-ub 8192` is silently clamped to 2048. It accounts for **zero** of the gap.

`src/llama-context.cpp` (read directly, verbatim):
```cpp
cparams.n_batch  = cparams.causal_attn ? std::min(cparams.n_ctx, params.n_batch) : params.n_batch;
cparams.n_ubatch = std::min(cparams.n_batch, params.n_ubatch == 0 ? params.n_batch : params.n_ubatch);
```
`-b` was not passed, so `params.n_batch` = the default **2048** (`common/common.h:455`). Therefore
`n_batch = min(196608, 2048) = 2048` and **`n_ubatch = min(2048, 8192) = 2048`**. No warning is emitted.

Three consequences:
1. **The process is already running at the canonical ubatch 2048** — by accident, not by declaration.
2. **Dropping `-ub` to 2048 would return zero VRAM.** This was the leading hypothesis; it is refuted.
3. `-ub 8192` comes from a **fleet-wide launcher default**, not the role: `launch_manifest.yaml:408`
   `default_ubatch_tokens: 8192` → `stack_manifest.py:546` → `stack_priors.py:2273` →
   `derived/stack_priors.yaml` → `orchestrator_stack.py:1426,1434`. The comment at `orchestrator_stack.py:1428`
   claims a frontdoor decode-throughput effect (12.66 → 25-27 t/s) that **this flag, as passed without `-b`,
   cannot have on any role**. That is a separate finding worth filing.

### 3.2 The MTP drafter IS resident in the same process, and its cost is inside the 38.61.

`--spec-type draft-mtp` with no `-md` creates a **second `llama_context` over the same `llama_model`**
(`common/speculative.cpp`, the `else if (spec_mtp)` branch: `llama_init_from_model(model_tgt, cparams)`).
So **no second weights buffer** — the MTP block's tensors ride in the one model buffer. But it does get:

- **Its own KV cache.** `src/llama-model.cpp:2342-2344` (verified verbatim):
  ```cpp
  if (mtp_on_hybrid_qwen35) {
      filter = [&](uint32_t il) { return il >= hparams.n_layer(); };
  }
  ```
  This routes the MTP context **out of** the hybrid wrapper into a plain `llama_kv_cache` covering **layer 64
  only** — and with **no recurrent state at all**. `n_ctx` is inherited at 196608 (nothing shrinks it).
  1 layer × 98304 cells × 2 streams × (1024+1024) × **2 B (F16)** = 805,306,368 B = **0.7500 GiB**.
- **F16, not q8_0.** `common/speculative.cpp` (verified verbatim): `result.cache_type_k = params_spec.cache_type_k;`
  — the *draft's* types, which default to `GGML_TYPE_F16`. `-ctk/-ctv` set `params.cache_type_k`, **not**
  `speculative.draft.cache_type_k`; the override is `-ctkd`/`-ctvd`, which is not passed. **Passing
  `-ctkd q8_0 -ctvd q8_0` would recover 0.3516 GiB for free.**
- **Its own compute buffer**, including its own 384 MiB KQ mask.
- `--device-draft ROCm0` is **inert** here — it is only read inside `if (has_draft)`, and `has_draft` is false
  without `-md`. Harmless, but it is not doing what its presence implies.

### 3.3 The largest un-modelled term: `--spec-draft-n-max 8` inflates the recurrent state cache ×9.

This is the one that costs 2.6 GiB, and it is entirely invisible from the argv.

`common/common.h` (verified verbatim) — for `DRAFT_MTP`, `need_n_rs_seq()` returns **`draft.n_max`**:
```cpp
uint32_t need_n_rs_seq() const {
    bool needs_rs_seq = std::any_of(types.begin(), types.end(), [&](auto t) {
        return t == COMMON_SPECULATIVE_TYPE_DRAFT_MTP || ... ; });
    return needs_rs_seq ? draft.n_max : 0u;
}
```
So the **target** context runs with `n_rs_seq = 8`. `src/llama-memory-recurrent.cpp:101` (verified verbatim):
```cpp
const uint32_t n_rows = mem_size * (1 + n_rs_seq);
```
with `mem_size = max(1, n_seq_max) = 2` (verified at the `llama_memory_recurrent(...)` call site) →
**`n_rows = 2 × 9 = 18`**. The hybrid wrapper passes `rs_size`/`n_seq_max`/`n_rs_seq` straight through
(`src/llama-memory-hybrid.cpp:59-61`).

Per row per layer, F32 (`gdn_recurrent_state_type()` is F32 unless `GGML_CUDA_GDN_STATE_BF16` is set —
it is **not** in `/proc/2021529/environ`, which carries only `GGML_IQK=1`):
- `n_embd_r = (d_conv-1)·(d_inner + 2·n_group·d_state) = 3 × (6144 + 4096) = 30720`
- `n_embd_s = d_state · d_inner = 128 × 6144 = 786432`
- → `(30720 + 786432) × 4 = 3,268,608 B`

**48 layers × 18 rows × 3,268,608 = 2,824,077,312 B = 2.6301 GiB.**

| `--spec-draft-n-max` | RS cache GiB | saving vs 8 |
|---:|---:|---:|
| 8 (live) | 2.6301 | — |
| 6 | 2.0457 | 0.5845 |
| 4 | 1.4612 | 1.1689 |
| 2 | 0.8767 | 1.7534 |
| 1 | 0.5845 | 2.0457 |
| (no MTP) | 0.2922 | 2.3379 |

This is **not waste** — it is the rollback snapshot ring that lets the recurrent state be rewound when a draft
is rejected. It is the *price* of MTP depth on a hybrid model. But it is priced at **0.2922 GiB per depth step**
and the registry does not know it exists.

### 3.4 `vram_non_kv_gib: 27.33` is wrong — and it describes the wrong model.

The model buffer does **not** exceed 27.33: weights are 27.0522 GiB (tensor data 27.0420), so 27.33 ≈
weights + ~0.28 GiB of graph buffer. As a *weights* figure it is roughly right. It is wrong in two ways:

1. **Wrong artifact.** Its provenance comment (master `model_registry.yaml:1418`) derives it from
   **PID 2019908 at `-c 16384` on 2026-08-02** — that was **Qwen3.6-27B-MTP-Q8_0**, not Qwen3.8. The artifact
   was swapped 2026-08-20 and the figure was never re-derived. (The stale log content at the head of
   `llama-server-8083.log` is from exactly that lineage.)
2. **Wrong shape of model.** It is a scalar in a two-term capacity model — `stack_manifest.py:1465` states it
   outright: *"each GPU role's VRAM is `vram_non_kv_gib + kv_gib` for its declared shape"*. For this role that
   is a two-term model applied to a five-term process.

The registry already contains a contradicting measurement it does not reconcile: `roles.qwen38_27b_q8_local.
production_throughput.vram_gib: 37.22`, measured at `-np 1 -c 32768` — i.e. **37.22 GiB at one sixth of the
current context**, which alone refutes "declaration implies 33.71".

There is also a **prior, unreconciled instance of this same defect** recorded in the master registry banner
(`model_registry.yaml:~1393`): a 3.71 GiB gap measured 2026-09-22 at `-np 2 -c 65536`. It is the same two
missing terms at a smaller context, and it scaled as feared.

### 3.5 Two collateral defects found

- **`kv_unified` is declared true and is false.** Master registry lines ~1325 and ~1398 assert *"KV IS UNIFIED
  ON THIS SERVER, so slots do not scale KV"*. The server reports `kv_unified = 'false'`. Total cells are the
  same either way (2 × 98304 = 196608), so the KV arithmetic is unaffected — but the declared fact is wrong and
  the claim built on it is now only accidentally true. (Non-unified is in fact the *better* setting here: it
  halves the KQ mask, 384 MiB/context instead of 768 MiB.)
- **`serving_shape` has only four keys** — `n_ctx`, `kv_quant`, `kv_kib_per_token_f16`, `vram_non_kv_gib`.
  There is no `batch`, `ubatch`, `np` or spec key anywhere in it, so the capacity model cannot see the two
  settings (`-np`, `--spec-draft-n-max`) that actually drive the missing 3.38 GiB.

## 4. Is `n_ctx 262144` affordable?

**Not as configured.** Free VRAM is **0.8603 GiB**; the move costs **2.6250 GiB** — short by **1.7267 GiB**.

| Term | at 196608 | at 262144 | Δ |
|---|---:|---:|---:|
| attention KV (16 layers, q8_0) | 6.3750 | 8.5000 | +2.1250 |
| MTP draft KV (1 layer, F16) | 0.7500 | 1.0000 | +0.2500 |
| KQ masks (2 contexts, F16, n_ubatch 2048) | 0.7500 | 1.0000 | +0.2500 |
| recurrent state (per-seq, not per-token) | 2.6301 | 2.6301 | 0 |
| **total Δ** | | | **+2.6250** |

**Note the trap**: two of those three growing terms (MTP draft KV, KQ mask) sit *inside* the "non-KV" bucket.
A corrected scalar `vram_non_kv_gib` would be right at 196608 and **under-predict 262144 by ~0.50 GiB**.

It becomes affordable only by spending the two levers this analysis exposed:

| Configuration | recovered | headroom after 262144 |
|---|---:|---:|
| as-is | 0 | **−1.727** (infeasible) |
| `-ctkd q8_0 -ctvd q8_0` | 0.469 | −1.258 |
| + `--spec-draft-n-max 4` | +1.169 | **−0.089** (too tight to commit) |
| + `--spec-draft-n-max 2` | +1.753 | **+0.495** |
| + `--spec-draft-n-max 1` | +2.046 | **+0.788** |

The draft-KV quantization lever (0.35–0.47 GiB) is close to free. The depth lever is **not**: measured draft
acceptance on the live log runs `mean len ≈ 3.0–4.6` (e.g. `0.84093 (3156/3753), mean len = 4.36`), so capping
depth at 2 would truncate accepted drafts that are actually landing. **This is a genuine
throughput-vs-context tradeoff and it is the operator's call**, not mine.

## 5. Recommended correction

The evidence **does** settle the immediate value, and I recommend it as measured, not guessed:

> **`vram_non_kv_gib: 27.33` → `32.23`** for `server_mode.architect_general` at its declared shape
> (`n_ctx 196608`, `slots 2`, `draft_max 8`).
> Derivation: measured 38.6093 (KFD) − attention KV 6.3750 (the registry's own corrected 34.0 KiB/token rate
> × 196608) = **32.2343**. Every term is measured or a source-exact formula.

**But shipping only that scalar would be a mistake**, and I want to be explicit about why: it is valid *only*
at `draft_max 8`, `slots 2`, `n_ctx 196608`. Change any one of them and it is silently wrong —
by 0.29 GiB per unit of draft depth, by ~1.3 GiB per added slot, and by ~0.5 GiB per 65536 of context.

The structural fix belongs in `stack_manifest.validate_serving_shape_capacity()`
(`epyc-orchestrator/scripts/server/stack_manifest.py:1465-1493`), beside `kv_layers()` /
`kv_kib_per_token_f16()` — three new terms, all of which this report gives closed forms for:

```yaml
serving_shape:
  n_ctx: 196608
  kv_quant: {k: q8_0, v: q8_0}
  kv_kib_per_token_f16: 64.0
  vram_weights_gib: 27.05              # artifact property; from the GGUF, never re-derived by hand
  rs_bytes_per_seq_per_step: 156893184 # 48 layers x (30720+786432) x 4  -> x n_seq_max x (1+draft_max)
  mtp_draft_kv_kib_per_token_f16: 4.0  # 1 layer x 4 kv-heads x (256+256) x 2 ; F16 unless -ctkd/-ctvd
  compute_gib: 1.80                    # two contexts at n_ubatch 2048, n_ctx_seq 98304
```

**Three fixes that are not judgement calls** and should go out with it:
1. `-ctkd q8_0 -ctvd q8_0` on this role — recovers 0.3516 GiB today for no behavioural change.
2. Drop `-ub 8192` from GPU roles, or pass `-b` to match. As passed it is inert, and the tuning claim at
   `orchestrator_stack.py:1428` cannot hold without `-b`.
3. Correct the `kv_unified` assertion in the master registry (lines ~1325, ~1398) — the server reports `false`.

## What changed against the subtraction

**The compute residual was understated by 0.277 GiB.** §1 derived 1.802 GiB by subtraction; the
kernel reports 1472.33 + 656.06 = 2128.39 MiB = 2.079 GiB. The difference is the DRAFT graph, which
subtraction folded into noise because it had no way to see a second `sched_reserve` block. This is
the general hazard, not a one-off: a residual computed as *everything I could not name* is a lower
bound on the things you did not know to look for.

## Two findings the log confirms independently

**1. The `full_attention_interval` correction is confirmed by the kernel's own words.** The line
reads `size = 6528.00 MiB ( 98304 cells, 16 layers, 2/2 seqs), K (q8_0): 3264.00 MiB, V (q8_0):
3264.00 MiB` — **16 layers on a 64-block model**, i.e. `full_attention_interval = 4`, exactly what
the corrected `kv_layers()` in `stack_manifest.py` computes (64 // 4). That fix was argued from the
GGUF metadata key; the server now states it directly, which is stronger evidence than the argument.
The 4.06x KV over-declaration was real and is now fixed at both ends.

**2. The MTP machinery is the whole of the remaining gap, and it scales with draft depth as
predicted.** `llama_memory_recurrent: size = 2693.25 MiB ( 2 cells, 64 layers, 2 seqs 8 rs_seq),
R (f32): 101.25 MiB, S (f32): 2592.00 MiB` — `8 rs_seq` is `--spec-draft-n-max 8`, and the target
recurrent cache is sized `n_seq_max x (1 + n_rs_seq)`. At 2693.25 MiB over 8 units that is ~0.329
GiB per unit of draft depth, against the 0.292 GiB/unit estimated earlier from `need_n_rs_seq()`.

So the still-open question from §3 is unchanged in shape but now has an exact price: dropping
`--spec-draft-n-max` from 8 to 4 returns roughly 1.3 GiB of VRAM. **What it costs in tokens/s at
the observed acceptance rates is still unmeasured**, and that is still the input the 262144-context
decision actually needs. It requires a bench the stack cannot give while serving.
