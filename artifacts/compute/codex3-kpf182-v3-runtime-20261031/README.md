# KPF-18.2 non-cohort CPU runtime control

The final private CPU build ran a pinned public Qwen3.5-0.8B Q8 model under the recorded q1 two-SMT / 300 s limit, one fresh server with tracing OFF and one with it ON. The actual synthetic source and two sibling HTTP requests completed in each arm; both runs forked source 0→1 at 302 and 1→2 at 310. All three paired response token arrays and content match. Both captured server PIDs were verified dead after rc0; the sampled combined server+supervisor peak was below 1.27 GB. Fresh private server implementation and libllama process maps and binary digests are retained. This is one non-cohort CPU engineering control, not a performance or full KPF verdict.

The ON log has two task/slot-bound native and custody events; OFF has none. The second child's per-request event reports target attention positions [0,310) and recurrent boundary 309 after the copy, while the first reports [0,302) and boundary 301. The implementation emitted SHA-256 of each selected nonempty target checkpoint blob; raw blob bytes were not retained for an independent digest replay. No speculative implementation was active; draft context and spec evidence are absent. Target/recurrent/draft hits, minimum, and restore success remain null, since metadata and call return do not prove the original task's component semantics. The source request with n_predict=0 yielded one token; that native behavior is retained, not silently normalized.

`audit-runtime.py` reopens and checks actual response pairing, receipt bindings, logs, event task/slot joins, own library maps and cleanup. Native-cell/custody/digest fixtures and explicit NDEBUG refusal passed; CPU full link and source catalog are pinned. This does not test MTP, DFlash, GPU, SWA, a hole in a live server, the original KPF cohort, held-out accuracy, or complete clause 2. The design remains private pending owner review and full-coverage semantics.
