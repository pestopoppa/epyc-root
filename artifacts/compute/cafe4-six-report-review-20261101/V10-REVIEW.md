## Semantics that line up, and limits

- Candidate builds a single explicit D-token batch with sequence 0 and consecutive positions (`:209–220`), saves the pre-batch first prediction (`:207`), then checks prediction row `j-1` for draft j and compares accepted row j to independently captured serial row `before+j+1` (`:223–239`). These offsets are coherent for this synthetic batch, conditional on successful matching prefix and valid output rows. v10 `include/llama.h:1035–1047` defines row ordering/`llama_get_logits_ith`; unlike candidate, the server nonserial path batches **sampled token plus D draft tokens** (`tools/server/server-context.cpp:500–529`) and handles the following sampled/bonus token as part of its accept/rollback bookkeeping (`:4155–4162`, `:4225–4234`). Thus this D-token same-model draft experiment is not exact server geometry and does not establish native MTP behavior.
- Let the first draft position be `start`, accepted drafts be `a`, and D be batch width. Candidate removes `[start+a-1, inf)` and re-decodes the retained boundary token (`:242–254`); for `a=0` that boundary is the previous output token, otherwise the last accepted draft. This intentionally discards **D-a+1** processed positions, not merely D-a. v10 recurrent `seq_rm` at `src/llama-memory-recurrent.cpp:192–200` sets `rollback=cell.pos-(p0-1)`, accepts only 1 through actual `n_rs_seq`, and returns false beyond it. v10 server itself counts rejected draft slots as `D+1-accepted.size()` and can use a checkpoint when above actual capacity (`server-context.cpp:4155–4162`); do not conflate that count with this harness's additional boundary replay. Candidate's `n_rs_seq >= D+1` and runtime `llama_n_rs_seq` check are conservative for the worst case, but the actual cut, processed tail and removal count must be logged and validated.
- `llama_memory_recurrent::init_batch` preserves trailing `1+n_rs_seq` tokens together (`src/llama-memory-recurrent.cpp:426–435`), whereas candidate `:135–137` only raises `n_batch`/`n_ubatch` to D, not D+1 (and actual effective values may be clamped to context; `src/llama-context.cpp:262–265`). This does not prove failure for every setup: defaults may happen to exceed the required size. Require explicit sufficient requested and actual `llama_n_batch` and `llama_n_ubatch`, plus context capacity, and report/refuse if unmet; do not infer snapshot correctness from parameters alone.
- v10 limits rollback-capable architectures explicitly (`src/llama-arch.cpp:1074–1084`) and clamps unsupported context requests to zero (`src/llama-context.cpp:103–108`). Candidate's runtime check catches an unsupported ring in verify mode, but the legacy branch has no equivalent. Hybrid memory tries recurrent removal first, then attention (`src/llama-memory-hybrid.cpp:143–149`); the stated no-mutation-on-failure in that source applies to recurrent refusal, and the harness should not reuse a context after any later failed operation without proving state.

## Fault-control and coverage finding

Candidate deliberately changes the token **fed to replay** (`:249–253`), observes changed full logits compared to the original reference (`:255–265`), and requires the specific `FAULT_DETECTED` marker. The marker is more informative than exit code alone, but it shows the oracle can detect an altered token input; the directly changed embedding/position can explain the difference without any corruption or mis-restoration of recurrent snapshot state. It is not a demonstrated state-specific fault witness. A separate controlled intervention must alter the rollback/recurrent state or restoration while holding replay token IDs and position fixed; pair it with an unmodified run in the same environment. Verify the injected fault actually reached the intended state and produce mismatch with the same full-logit oracle; inability to inject or a non-trigger is UNKNOWN, not negative evidence. Keep the input-token perturbation as a narrower comparator-sensitivity control if useful.

Only one forced mismatch location is generated (`:196–202`), and batch/serial numerical variation can cause an earlier rejection. The code does not force, enumerate or validate distinct partial-accept cut points. Require observed coverage of explicitly predeclared 0, intermediate and near-full cuts as appropriate (a full-accept path separately), plus actual rollback count and exact output lengths; do not count requested cuts as exercised. The fixed absolute `1e-5` comparison was borrowed from a v10 test of serial replay (`tests/test-recurrent-state-rollback.cpp:122–149`), not a validated cross-shape CPU/GPU equivalence threshold. Batched/serial difference yields UNKNOWN under the candidate, correctly not a rollback defect; calibrate by same-environment matched no-rollback controls, report full finite checks and thresholds.

## Undefined behavior and failure-path hardening

- `atoi` for `-n/-s/-r/-k` (`:77–84`) has undefined behavior for out-of-range numeric text; malformed values can be silently parsed. Signed expressions `stride+verify_batch` (`:90`) and `n_prompt+n_predict+64` (`:134–135`) can overflow; use bounded checked conversion and checked wider arithmetic before narrowing or allocation. `start+j`, vector/allocation sizes and int/size conversions need bounded checks too.
- `n_prompt = -llama_tokenize(...)` (`:112`) assumes the first call always returns a negative required length; INT_MIN negation overflows, unexpected positive/error/zero outcomes and the second tokenization return are unchecked, and unchecked `size_t` to API integer conversions can truncate. Validate both tokenization calls and actual counts before vector/batch use.
- `llama_batch_init` is checked only for top-level arrays; `verify.seq_id[j]` is dereferenced without per-row non-null check (`:210–217`). Check each allocated entry and free safely on failure. Unchecked `greedy` in the inherited non-verify rollback branch may pass -1 on missing logits (`:270–273`).
- Several early returns after context/model/backend creation do not free them (`:151–154`, `:169–172`, `:180–183`, `:219–221`, `:243–244`, and main `:310–314`); apply RAII/single cleanup, preserve original failure and verify actual owned-process drain. `llama_decode` fatal/abort may leave already-processed ubatches (`include/llama.h:984–995`); discard affected context on any nonzero return, do not continue from it.
- Candidate accepts all non-dash unknown arguments as prompt and silently ignores unrecognized dash options; reject unknown/missing options. Check model/vocab and prompt size, finite initial logits for greedy (currently NaN can silently select token 0), token ID range, actual context/snapshot getters, placement and loaded library identity.
