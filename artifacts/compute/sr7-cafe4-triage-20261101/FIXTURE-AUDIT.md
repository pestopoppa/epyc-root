## What the fixture checks

For D=1..16 and synthetic cut 0..D, `batch=[sampled]+proposed` models D+1 rows, and synthetic row j predicts draft j (`:26–38`). That matches the *shape* of v10's nonserial batch construction: sampled at the first position then D drafts, each requesting logits (`tools/server/server-context.cpp:500–529`). The serial speculative path intentionally does not add the D draft rows (`:516–529`), so this is not a model of every v10 mode. The 152 width/cut count is arithmetically correct. Reference state is independently replayed through a deterministic transition, but proposals are explicitly copied from `ref_tokens` (`:20–25`): this is a controlled synthetic input construction, not an independently generated drafter or MTP validation.

At accepted cut a, the fixture sets keep=a relative to the D+1-item batch, restores the state before that item and replays the boundary (`:39–48`). That discards D+1−a input positions. This is a coherent *extra boundary replay experiment*, not the literal v10 server rollback recipe. In v10, `n_rollback = D+1−accepted.size()` (`server-context.cpp:4155–4162`), where accepted includes the sampled replacement/bonus token; the server retains sampled plus accepted draft prefix in the prompt and removes from its next position (`:4225–4234`). For full acceptance the fixture removes and replays one boundary token while normal v10 full acceptance has zero rejected draft rollback. Report the fixture's and server's quantities separately; coverage of the artificial full-cut replay does not prove the server full-accept path or its bonus logits.

## Fault and resource limits

- `state_corruption` changes the abstract scalar state while keeping replay ID equal in the paired test (`:42–48,65–69`). This is a useful fixture-level discrimination, but the witness is constructed to expose state directly in every `scores()` element (`:6–9`), so no sensitivity or causal statement about a real recurrent tensor, snapshot slot, model logits, or GPU follows. It never reads/injects an `rs_idx` or checks bytes copied from a real backend.
- `skip_rollback` substitutes the last abstract batch state (`:42`) without preserving and checking real positional metadata or invoking any actual sequence removal. A native skipped-removal control must prove the selected fault reached the replay state while maintaining the intended replay token/position, or explicitly report failure/unknown; a setup failure or nonzero exit is not a detected state fault.
- The altered-input control changes the token and produces the same top-level `STATE_MISMATCH` string (`:45–52,72–76`); the only differentiation is the separate boolean and test context, not a state-specific classification by the comparator. An arbitrary unknown `fault` string silently takes the ordinary path (`:42–46`). Strict native/control schemas should reject unknown fault modes and retain event identity, actual mutation, and paired input equality; mismatches alone cannot identify cause.
- `snapshot_capacity < width+1` (`:16`) is a conservative blanket check for this fixture's deliberately extra boundary replay; actual v10 recurrent removal checks **the requested removal count** 1..`n_rs_seq` (`src/llama-memory-recurrent.cpp:192–200`). A just-sufficient nonzero cut may be supported with less than width+1. The fixture also lacks actual tail positions, context/ubatch bounds and `llama_n_rs_seq` clamp behavior (`src/llama-context.cpp:103–107,262–265`). Its hardcoded acceptance is not API validation.
- `target_rc`/`rm_ok` are passed-in booleans (`:13–17`); they test mapping to UNKNOWN, not native return-code semantics. In real v10 `llama_decode` errors/abort can leave processed ubatches (`include/llama.h:984–995`), and recurrent seq_rm may refuse out-of-range removal. Model actual positions, empty/no-op, partial failure, context disposal, and cleanup as separate cases, with real API receipts under keeper grants.
