# Asynchronous long-CPU qualification proposal

Status: **SOURCE-ONLY DESIGN / NOT INSTALLED / NOT A QUALIFICATION RECEIPT**. This is an integration proposal for the ws58 native-v3 owner session. It does not edit the v3 packet, keeper, qualifier, manifest schema, or live state. A two-core long qualifier must never occupy the keeper's synchronous scan path or falsely satisfy the current gate.

## Current integration surface

The reviewed router selects P0 `keeper_qual_gate.py` plus immutable v1 verifier by default, or the exact-ID native v3 gate/verifier via `qualifier-bundles.v1.json` (currently an empty map). The native gate exposes `qualify_pending(manifest, flags, region_lock, timeout, dry=False) -> (state, reason)`: it selects the R11 pair, locks `prep-locks/<physical-pair>.lock`, calls `q.issue(manifest, flags)`, synchronously invokes `qualify_launcher.py run ... --timeout N`, then calls `q.verify(manifest, flags, True)`. The q nonce is issued only from the live keeper descendant after its PID/argv certificate check; an unrelated supervisor must not call `q.issue`. The nonce store moves `issued` → `passed`, binds a single nonce per manifest ID, and requires a new ID after a failed attempt. The manifest loader and keeper currently restrict `qual_timeout_s` to 300 or 600. The existing `q.run` enters canonical v14, requires normal native proof plus active-cutoff evidence, and drains its captured process group. Preserve the router/allowlist, keeper-owned nonce issuance, receipt and verifier contracts; this proposal does not replace them.

## Proposed integration API

Keep `qualify_pending`'s tuple API for its caller; the P0 caller must recognize `qualifying-pending` as a nonterminal state and continue scanning later rows. After existing cheap validations and the disk gate, route only reviewed CPU long-qualification rows before the generic `q.verify` fast path to `async_qual_dispatcher.tick(manifest, flags, pair, deadline_s=7200)`. Return `('qualifying-pending', '<task id> owner=<pid>/<birth> pair=<pair>')` immediately while pending. On terminal success, the keeper calls existing `q.verify(manifest, flags, True)` before returning `('qualified', receipt_path)`. Failure remains refused with a durable reason and never changes the grant gate. Existing short CPU, GPU-quiet, and v1/v2 rows retain their current path until separately reviewed.

The dispatcher itself owns no nonce issuer: only the keeper process calls `q.issue`, after it acquires the pair flock and rechecks the actual `qual_pair`. It atomically creates a STARTING task record binding manifest digest, fixture digest, source-manifest digest, exact pair, task ID, and absolute deadline. It starts one owner supervisor with `Popen(start_new_session=True, pass_fds=(pair_lock_fd, start_gate_read_fd))`. The supervisor inherits the **same open flock description** so the physical-pair `prep-locks` lock remains held after the keeper tick returns. A one-byte start gate prevents supervisor work until the keeper has recorded its PID plus `/proc/<pid>/stat` birth ticks and group identity in the task record; EOF before the gate makes the supervisor exit before running the qualifier. After the keeper has acquired the pair lock and rechecked the pair, it issues the one-use nonce while still the certified keeper descendant, then passes it only through the transient supervisor argv/env; do not persist it in async state. If supervisor creation fails after nonce issue, fail this manifest ID permanently and require a fresh reviewed ID. The supervisor confirms its inherited pair-lock descriptor, waits for the start-gate byte, then runs existing `qualify_launcher.py run` with the remaining bounded deadline. The keeper never calls `wait`, `communicate`, or a blocking subprocess for this task; each scan performs one nonblocking state read and returns pending.

A task is eligible only when the immutable record matches its current manifest, fixture, source closure, and pair. One active supervisor per physical CPU pair is guaranteed by the long-lived pair flock; the per-task state lock plus atomic create/replace prevents two keeper ticks from launching duplicate supervisors. A second task on the same pair waits. Nonce issue occurs only after the keeper has acquired the resource lock; the supervisor must confirm that inherited lock is still held before it starts work. Existing `q.verify` remains the only path from pending to qualified.

## Deadline, restart, and failure rules

Use a hard 7,200-second wall deadline, starting when the owner acquires the pair lock. This is a resource bound, not a runtime prediction or rate claim. The qualifier gets the remaining wall seconds; no change to the predeclared statistical criterion, fixture, request count, or native proof requirements. The v3 source changes needed to accept a long CPU budget are a narrow, explicit CPU-only manifest/CLI policy update; GPU qualification remains under the current exclusive GPU claim and 300/600 cap until separately reviewed.

On every keeper tick, reconcile a pending owner by PID and birth identity, not PID alone. A verified missing or reused PID is distinct from unreadable/ambiguous `/proc` state; the latter refuses the receipt and is never treated as owner exit. If the owner is live and before deadline, return pending immediately. If the supervisor exits, read its digest-bound terminal record and require exit 0, successful `q.verify`, normal native first-request proof, active cutoff first-event marker, cutoff result `UNKNOWN`, actual STOP observation, `rc=75`, and complete child drain. If supervisor state is missing, corrupt, stale, digest-mismatched, or deadline-expired, refuse qualification. A reused PID is never signalled or treated as the replacement owner; it proves only that the captured owner identity is gone, after which terminal state and lock release still gate receipt acceptance. For a vanished owner with a still-matching process-group identity, the owner-scoped reaper may TERM then KILL only that captured group and must verify it drained; any mismatch/uncertain identity is a hard cleanup failure. Never issue a second nonce or retry under the same manifest ID after an owner-loss/timeout state; require a new manifest ID and fresh review. A restart resumes observation of the existing task record; it never launches another process just because the keeper restarted.

The supervisor owns a kernel subreaper boundary and is responsible for draining its qualifier/engine descendants on normal exit, timeout, signal, or exception. Its finally path writes terminal cleanup evidence only after verifying the captured process group is gone and releases the inherited pair flock last. The qualifier launcher waits behind a one-byte start gate until its active PID/birth/group record is durable. After `q.run` returns, it drains adopted children before checking the now-absent group leader; if descendants remain, the leader-absent reaper fails closed instead of inferring ownership from a potentially reused PGID. A keeper tick can call only the existing birth-checked group-drain primitive for a confirmed abandoned owner; cleanup failure records FAILED and keeps the hard gate closed.

## State and evidence contract

Proposed states: `STARTING` (atomic claim before nonce issue; a failed post-issue spawn makes the ID terminal and non-reusable), `PENDING` (supervisor PID/birth and pair flock confirmed), `TERMINAL_PASS` (all existing native verifier checks succeeded), and `TERMINAL_FAIL` (reason plus cleanup state). State records bind schema/version, task/manifest/fixture/source digests, chosen pair, created/deadline timestamps, supervisor PID/birth, qualifier group PID/birth, exit, terminal reason, receipt digest, and cleanup verification. They never store or authorize a free-form nonce. The canonical nonce store and predeclared receipt remain authoritative.

Only `TERMINAL_PASS` with a dead PID/birth owner and an available matching pair flock yields `qualified`. The final verifier call runs while holding that pair flock, preventing a new qualifier from racing the receipt check. The same async-aware `verify_ready` guard is used by keeper qualification, grant-time `classify` (the router check used by `grant_ok.sh`), booked-conflict evaluation, and worker-breaker release; no grant decision relies on bare `q.verify` for an async row. The generic early receipt fast path is bypassed for async rows. A receipt found without its terminal owner record is refused and requires a new manifest ID. The final `q.verify(manifest, flags, True)` remains mandatory. A result `UNKNOWN` from cutoff is required for the partial phase and is not itself a qualifier failure; it is the expected active cutoff observation. Any other partial/missing field is terminal failure. This preserves the hard gate without inventing a relaxed grading rule.

## Source-only verification

`dispatcher_model.py` is a no-process reference state machine with a backend interface for launch/observe/result/cleanup. `async_qual_dispatcher.py` and `async_qual_supervisor.py` are concrete unapplied integration sources; the accompanying patch adds CPU-only timeout validation, active qualifier-group publication, exact keeper routing, and pending-state continuation. `owned_supervisor_boundary.py` pins the original PID/birth and process group, holds the inherited pair-lock descriptor through the bounded child wait, and refuses every signal if the original identity changes or the leader disappears. It uses `waitid(WNOWAIT)` so the owner PID cannot be reaped and reused before group cleanup is verified. `test_dispatcher_model.py` covers start→pending, nonblocking poll, terminal receipt verification, malformed cutoff, deadline cleanup, restart observation, owner loss, same-ID digest drift, concurrent keeper tick races, mocked Popen/timeout/lock-FD boundaries, crash after nonce issue, start-gate ordering, and PID reuse. It exercises the actual proposed `qualify_pending` entry with an otherwise-valid receipt while the owner is live and while the pair lock is held; it also proves existing tasks retain their recorded pair when the preferred selector changes or returns no pair, abort an active owner when its recorded pair becomes unsafe, accept completed evidence after later unrelated use of that pair, exercises grant-time owner readability checks, and proves the final receipt check holds the pair flock. Tests use fake identities and mocked subprocesses; PID-reuse and missing-leader cases assert that no signal is sent. They do not issue a nonce, launch a process, touch a grant, or claim qualification.

Before any installation, the v3 owner must translate the proposal into its existing package and run its full source tests plus these race/failure cases. Keep the current `q.issue`, `q.verify`, allowlist routing, native first-request proof, cutoff event/STOP/UNKNOWN/rc75 evidence, and captured-group cleanup as mandatory gates. This design does not authorize installation or a live qualification.
